Concept dossier · AGT-2815

Model routing by assessed complexity

Analysis and an implementation plan become pipeline steps that declare a complexity assessment instead of three regular expressions guessing it from raw text. Token Economy owns the estimation prompts, the study behind them, and the versioned table of (model, thinking level) pairs per complexity class. Agent Studio consumes that table, requalifies between steps, and reports what was routed against what actually happened.

The pipeline has no analysis step and no plan step

Pre-steps in PipelineCatalogue.cs: pre-prompt-enrichment, pre-model-qualification, pre-orchestrator-prep, pre-loop-guard, pre-reissue-open-items, pre-ui-pipeline-routing, plus gates. The work itself is one step, core-agent-run. Everything else is a post-step: review, drift, post-analysis-* (the unrelated Quality Studio rule passes — Angular rules, C# rules, model review, visual quality, security, redundancy, consistency), gates, merge. Pipeline types are task, bug, feature, planning (PipelineTypes.cs); task types for routing are chore, feature, bug (TaskTypes.cs). pre-model-qualification runs before any agent turn exists, so the raw card text is the only signal it has — which is exactly why the regular expressions exist. There is no step between work order and implementation that could report a measured, checkable complexity.

Nothing measures whether a route was right

TaskTokenCall (backend/Shared/Models/TaskTelemetry.cs) records Model, DisplayModel, token counts, and cost per call — it has no thinking-level field. The effective thinking level is recorded separately, per run, on SessionEvent.ThinkingLevel (logs/session-events.jsonl), but no reader joins a session's thinking level back onto its token calls or onto the card's outcome. No record anywhere connects a routed (model, level) pair to what happened to the card: delivered, reissued, escalated, reviewed down. Token Economy owns the price catalogue and the benchmark matrix (ModelBenchmarkMatrix.FindCandidates, consumed read-only for “better candidate” suggestions), but nothing feeds the routing tier table from real outcomes; the tier scores themselves (15, 25, 49, 51, 70) are hand-set numbers in model-routing-policy.md, honestly labelled there as a hypothesis pending controlled comparison.

§3 Defining complexity: research this Dossier had to do, not assume

The operator asked directly whether there is research on recognising complexity for model choice, and whether an LLM can say something is complex. Three literatures bear on this, and none of them gives a ready answer for this product — each narrows the design instead of deciding it.

Routing and cascades: difficulty is predicted, not observed

Model routing and cascade research treats task difficulty as something a cheap classifier or a win-probability model estimates before dispatch, then sends hard-predicted items to a stronger model and the rest to a cheaper one. Recent survey work frames this as a spectrum from static binary-difficulty routers to learned win-prediction models that estimate the probability a strong model beats a weak one on a given query, and to decision-theoretic cascade analyses that ask when escalation is worth its cost at all. The common thread is that difficulty is always a prediction evaluated against an observed outcome (did the cheap model actually fail), never a ground truth read off the task text. That maps directly onto this product's gap: the three regular expressions are a difficulty predictor with no evaluation against outcomes at all.

LLM-as-judge: reliable only when calibration is checked, not assumed

The judge-reliability literature is consistent on one point: LLM self-assessment and LLM-as-judge verdicts are measurably overconfident by default, and calibration — the gap between stated confidence and empirical correctness — has to be measured with standard tools (Expected Calibration Error, Brier score) rather than assumed from a well-written prompt. Calibrated confidence is what lets a pipeline auto-accept high-confidence assessments and route low-confidence ones to a stronger tier or a human; uncalibrated confidence cannot be trusted for that split. This is a direct answer to “can an LLM say that something is complex”: yes, an LLM can emit a complexity judgement, but the judgement is only as trustworthy as its measured calibration against this product's own outcomes, and that measurement does not exist yet (§2).

Code-task difficulty prediction: features exist, task-specific calibration is required

Difficulty-prediction work specific to agentic coding benchmarks extends item-response-theory methods with dense features drawn from the task itself — problem statement, repository state, test patch, solution patch — to predict per-task success probability for a given model and scaffold, decomposing ability into a model component and a scaffold component. That is evidence that static, pre-execution features can predict coding-task outcome with more signal than keyword matching, but the predictor is fit and evaluated per benchmark; it is not evidence that a general-purpose complexity rubric transfers to this product's own card population without being fit and checked against it.

Honest reading. No literature answers “can an LLM classify this product's cards into complexity classes reliably enough to route on”. The literature instead specifies the check: build a labelled set from this product's own history, have the model emit a calibrated judgement, and measure agreement against the observed outcome before trusting the judgement for routing. §7 turns that into a concrete design using this product's own AGT-2243 historical benchmark (152 task records, 19 cohorts) as the starting labelled set.

The five dimensions sum to a 0–15 complexity score, reported alongside the per-dimension breakdown and a stated confidence (not folded into the score). This mirrors the existing weighted ladder in model-routing-policy.md in shape — scored criteria mapped through thresholds to a route — but every dimension is now something the analysis step can point at concrete evidence for, not a keyword match. The hard floors already in the policy (P0, fencing, lease authority, security, distributed concurrency, data loss) remain floors: a declared floor condition overrides the summed score exactly as it does today, because a rare catastrophic-risk signal must not be diluted by averaging it against four unrelated dimensions.

§4 Target workflow: four pipeline steps, complexity declared and checked

Analysis (new pre/early step)

Runs after pre-prompt-enrichment, before implementation. Reads the enriched card and produces analysis-report.json: the five-dimension breakdown from §3, a stated confidence, floor conditions triggered (if any), and the evidence excerpts that justify each dimension score (file paths, prior related cards, named unknowns) — not a bare number. Model qualification for the analysis step itself stays cheap (Luna/Mini-class), matching the existing bounded-decision role already used for aspect verdicts and route decisions in PipelineStepModelDefaults, because the analysis step's own job is bounded and structured, not open-ended implementation.

Implementation plan (new step)

Consumes the analysis report, produces the concrete plan, and may revise the complexity assessment with information the analysis step did not have (a plan can discover, for example, that a change touches a fifth subsystem). Model qualification runs again here against the (possibly revised) assessment, using Token Economy's pair table (§5) rather than the regular expressions. This is the point where “a cheap model may do the analysis, a strong pair the implementation” becomes concrete: the plan step is the last cheap gate before the expensive implementation route is committed.

Implementation (existing core-agent-run)

Unchanged mechanically. It now starts already qualified against a declared, evidenced complexity class instead of a keyword match, and its model/level choice is visible next to the analysis and plan assessments in the card's pipeline history.

Reported versus achieved (closes the loop)

On card close, write complexity-outcome.json: the complexity class and confidence reported at analysis, the class and route actually used at implementation (after any plan-stage requalification), and the observed outcome — rounds, reissues, review verdicts, tokens, wall-clock, and a derived flag for whether the pair looked too weak (reissued for a semantic reason), too strong (delivered first-pass with large cost margin versus the class median), or right-sized. This is the exact feedback the operator asked for: “what complexity was reported, and was it reached.” Token Economy ingests this record to recalibrate the pair table (§5); Agent Studio never edits the table from a single card.

§5 Alternatives

Three credible shapes for closing the regex gap, compared on how much they fix and what they cost.

Option A — Report only, keep the regular expressions

Add the outcome record from §4 without adding analysis or plan steps; keep ModelRoutingPolicyRegistry exactly as it is. Cheapest to ship. Does not touch the operator's core complaint (“the approach with regular expressions is nonsense”) and does not produce a declared, evidenced assessment — it only tells us, eventually, that the regexes keep being wrong, without giving analysis or plan a place to exist.

Option B — Analysis and plan as pipeline steps, Token Economy owns the pair table (recommended)

The workflow in §4. Complexity is declared with evidence at analysis, refined at plan, checked against outcome at close. Token Economy is the measuring authority for the (complexity class → model, level) table and the calibration study behind it; Agent Studio is the measuring authority for pipeline execution and the reported-vs-achieved record. Cost: two new pipeline steps to design, run, and keep fast; a new seam between Agent Studio and the Token Economy package for the pair table (mirroring the existing IModelEconomyAdvisor / ITokenPriceProvider replaceable-seam pattern already used for benchmark candidates and pricing).

Option C — Single external Token Economy call, no new pipeline steps

Replace the regex step with one call into a Token Economy complexity-estimation endpoint at intake, keeping the rest of the pipeline as-is. Fewer moving parts than Option B, but it does not give the operator's explicit ask — analysis and plan as pipeline steps with complexity showing in the analysis and becoming clearer in the plan — and it re-creates a single-point, single-signal estimate at exactly the moment (intake, before any agent turn) where the least information is available, the same structural problem the regexes have today.

§6 Recommendation

Recommended default: Option B

Add analysis and implementation-plan as pipeline steps that declare and refine the complexity assessment from §3, requalify the model against Token Economy's versioned pair table at the plan step, and write a reported-vs-achieved record at close. Token Economy owns the estimation prompts, the calibration study, and the pair table; Agent Studio owns step execution, the requalification call, and the feedback record. This is the only option that satisfies the operator's explicit workflow request and gives the calibration check from §3 something to measure.

Within Option B, do not run analysis and plan unconditionally for every chore-class card from day one: start with feature and bug pipeline types plus any card that trips a floor condition today, and treat chore as the deliberately narrow scope decision in §8. This keeps the two new steps from taxing the cheapest, most mechanical work while the calibration evidence is still being built. Ship the reported-vs-achieved record from the first slice regardless of scope, since it is required to validate every later decision in this Dossier.
