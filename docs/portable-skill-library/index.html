Recommendation

Extend the existing enrichment step into the managed skills delivery boundary. Resolve a small set of immutable skill packages, insert their complete instruction text into every applicable run, materialize their resources, and retain a receipt. Use the same receipt for review and for the library's usage record. Native CLI discovery remains a convenience for direct sessions.

The owner direction of 24 November is the product requirement: fitting knowledge reaches the agent through the prompt, across projects and CLIs, and its use is visible in both directions. Loading a skill proves delivery, not compliance or benefit. A weak skill can reduce quality. This proposal makes both the delivery and its consequences inspectable.

All behavior described below is proposed unless labelled as repository evidence. This delivery changes documentation only. No skill selection, product screen, release, or operator acceptance is implemented here.

Alternatives

A. Larger guide summaries

Raise the current 1,500-token limit and improve keyword matching. Cheapest migration, but scripts, skill identity, version pins and cross-project outcomes remain separate. Useful only as a short compatibility stage.

B. Native CLI skills

Install folders and let each CLI decide what to read. Efficient progressive disclosure, but discovery, precedence and observability differ. It cannot establish that every managed run received the required knowledge.

C. Managed prompt bundles

Recommended. Studio resolves versions, renders full bounded instructions and records transport receipts. The same bundle serves every CLI. Requires a resolver, a resource transfer contract and outcome joins.

D. Whole-library injection

Insert every skill into every prompt. Delivery is simple, but irrelevant procedures compete with the task and consume context. It also reproduces the content-depth failure described by the owner at larger scale.

A marketplace is outside this proposal. An installation can import a reviewed package from another installation or a private repository without delegating policy, updates or trust to a marketplace.

Format

A skill is a named, versioned unit of task-specific working knowledge with declared applicability, bounded instruction text, a responsible maintainer and evidence of its behavior. It explains how to perform work and what to check. A selected skill is an artefact, not an unversioned URL and not a permission grant.

KindExamplesBoundary
Area best practiceFrontend, backend, UX, tests, security, operationsTechnology-aware decisions and failure patterns. Security audit procedures do not activate merely because a file mentions credentials.
Task procedureIncident analysis, Dossier writing, release preparationInputs, stopping conditions, evidence and outputs for a bounded task.
Project knowledgeDomain invariants, API vocabulary, project verificationOnly for named projects or an explicit adoption, tied to repository revisions.
Role knowledgeDispatcher forecasts, guardian investigationRole charter and evidence method. Deterministic scheduling and transition authority remain in the decision library.

A rule is an individually identifiable requirement with authority, scope and a check. A style guide groups related conventions and rationale. A wiki page explains a subject and its history. A skill packages the actionable portion of these sources, cites their versions, and adds a procedure and examples. A plugin is an optional versioned container for one or more skills plus tool or connector declarations and assets. Installing it never creates credentials, tool grants or execution authority.

Package

frontend-best-practice/

  skill.json               # Studio schema, triggers, sources and delivery closure
  references/              # optional, task-specific supporting instruction modules
  scripts/                 # optional deterministic helpers

  tests/                   # routing cases, behavioral fixtures, script checks
  assets/                  # optional templates or output resources
  release.json             # generated hashes, licence, review and evaluation evidence

Only SKILL.md, skill.json and release metadata are required for a released Studio skill. Keep the portable frontmatter small: name, description and the existing sentinel where present. Put Studio-specific fields in the sidecar, avoiding a dependency on a CLI accepting custom YAML fields. A draft can consist of SKILL.md alone and is not eligible for automatic production delivery.

---
name: frontend-best-practice
description: Angular component and state changes with browser evidence.
---

# Frontend best practice
Use the project component and state contracts supplied with this skill.
Verify identity, loading, keyboard behavior and the changed user journey.

The sidecar declares schemaVersion, namespaced id, version, kind, owner, licence, compatible package/runtime versions, technologies, task kinds and modes, include/exclude path globs, roles, explicit labels, required dependencies, conflicts, replacement or extension relationships, source revision hashes, budget class, stable criteria ids with scope and authority, and a deliveryFiles list. Triggers use a validated expression schema with explicit allOf, anyOf and not semantics. Empty selectors match nothing; * is explicit. Dependencies form an acyclic graph.

Instruction closure

Whole skill in the prompt means the complete SKILL.md, including its metadata, plus every instructional reference declared in the released delivery closure. The compiler recursively resolves those references once, normalizes text to UTF-8 and LF, preserves instruction content, and records the resulting digest. No summary or truncation substitutes for selected instructions. A reference containing a requirement belongs in this closure. A long optional manual belongs in a separately selectable skill module.

Scripts, tests, example data and binary assets are shipped as files; their source is not automatically instructional context. A small instructional example can be declared in deliveryFiles and then counts in full. Every other reference is explicitly labelled supplementary and cannot hide an acceptance requirement. Network links are citations, never a way to defer loading required instructions.

Size

Target 800 to 1,800 tokens per skill closure; warn above 2,000 and reject a new general release above 2,500. Allow a reviewed procedure class up to 5,000 tokens for existing operations workflows. Store per-provider counts and tokenizer version; retain ceil(characters / 4) only as a clearly labelled fallback estimate. The current task-api entry alone is about 4,150 estimated tokens, so importing all existing skills under a universal 2,500-token cap would break compatibility.

Default added instruction budget: 6,000 tokens; hard limit: 8,000, and never more than 10% of the selected model's usable context after reserved task and output space. All numbers include delivery wrappers, policy projections and dependency text, excluding the skill catalogue, which is separately accounted. A reviewed project budget can lower these limits. A larger procedure is split by capability or explicitly budgeted; silently dropping a required tail is prohibited.

Library

Use three logical scopes with the same immutable package contract. Shipped defaults are bundled with the product, authored initially in .agents/skills/, and indexed by a release lock. Workspace packages are installation-owned state shared by its projects through the application API. Project additions live in that project's .agents/skills/. The exact workspace storage path belongs to the application filesystem contract, not to prompts or user scripts.

Resolve the project's explicit mapping, then its workspace activation, then the shipped baseline. Scope alone never shadows a skill with the same short name. An override explicitly names replaces: studio/frontend-best-practice, the compatible upstream version and a different qualified identity. A fork retains its upstream digest and review lineage. An extension uses extends; both the base and the additive instructions enter the closure and receipt. A replacement requires project maintainer adoption and cannot remove an independent mandatory policy dependency. Keep ownerRoleId (the role responsible for maintenance) distinct from roles (the invocations to which the skill applies). A dispatcher-owned skill can also support a concept run without becoming a dispatcher persona.

Examples: a workspace can share acme/backend-contracts@1.2.0 across three projects; one project can extend it with invoice invariants. A customer wanting a different visual convention forks the optional UX skill under its namespace. Studio's own mandatory UI rules apply to Studio UI projects through explicit project policy, not indiscriminately to every customer's application.

Versions

Use semantic versions for intended compatibility and SHA-256 of a canonical file manifest for exact identity. Changed bytes always produce a new artefact and digest, including an instruction typo. Patch means compatible clarification, minor adds compatible guidance, major changes triggers, required workflow or acceptance criteria. A version number is descriptive; the digest is the pin. Duplicate identity and version with different bytes is rejected.

Workspace and project activations name a channel or constraint; a reviewed lock resolves them to exact versions. Product upgrades introduce new shipped versions without rewriting local forks or active locks. New run attempts resolve against the active lock; retries and fix rounds retain the originating pin. An explicit re-resolution records old and new receipts and a reason. In-flight runs never change under them. Retain old bundles while any receipt references them, including archived cards.

Artefact lifecycle

  1. Draft: an author or a normal skill-creation card supplies scope, triggers, source revisions, content, owner and a specific expected improvement. AI-created packages stay drafts.
  2. Review: the domain maintainer checks correctness and scope; the quality maintainer checks budget, conflicts, exclusions, testability and permission boundaries. Script changes receive executable-code review.
  3. Test: validate package structure, path containment, dependency closure, source hashes, routing positives and negatives, deterministic script fixtures, and representative behavioral tasks with and without the candidate.
  4. Candidate: publish an immutable package and signed release manifest. Shadow selection establishes coverage; isolated comparisons test content. A candidate is never selected as the default merely because its description matches.
  5. Release: domain maintainer records evaluation and adopts a lock revision. Product releases ship tested baseline locks. Workspace forks release independently.
  6. Retirement: deprecate with a successor or explanation; stop new selection, retain historical bytes. Rollback changes the lock for future work, not historical evidence.

Wiki

Keep the cloned project wiki as the source for rationale, long domain knowledge and discoveries. The library links back to it. A published skill pins the source commit and section digest; a drift detector proposes a revision when that section changes. Guidance updates remain ordinary reviewed cards. The wiki can render a package and its usage projection, but cannot edit an immutable published version in place.

The Access-page pilot and the parallel “one look and feel” work own the future UI standard. Until those decisions are delivered, migrate the current hard rules as the baseline and identify pilot material as candidate. Their approved revision must update the UX package, project lock and visual review criteria together. Do not freeze an undecided pilot screenshot into every UI card.

Selection

Every model invocation passes through skill preparation, including a recorded empty or disabled result when nothing applies. Applicable declared requirements are automatic; manual skill requests add to that set within the same authority and budget rules. Keep pre-prompt-enrichment as the named pipeline step. It resolves the instruction bundle before local dispatch or remote admission, after model qualification. The service collects facts and persists a report; the selection function is deterministic and independently testable. It does not become a second scheduler or transition engine.

Facts

Use task mode and kind, explicit skill requests and exclusions, project and stack, declared work areas, acceptance criteria, forecast files and modules with confidence, role/persona version, CLI capability, model context size and budget. Consume the dispatcher concept's shared touch forecast by id, producer version, base SHA and confidence. It is a forecast, not a fact about changed files. If unavailable, use cited paths, a project module map and a fixed task-kind set. Do not require the dispatcher to be live before basic skills delivery can work.

Resolution

  1. Resolve the project lock, explicit requests, task-kind set and typed triggers. Record positive and negative evidence, including uncertainty. Validate scope, compatibility, sources, permissions needed by scripts, and installed tools.
  2. Expand required dependencies, flatten declared instruction references and deduplicate by exact identity and rule id. Same id with different content is a conflict. Shared dependencies count once in prompt bytes, with all selecting parents retained in the receipt.
  3. Resolve authority first: task instructions and repository guardrails, then applicable mandatory project policy, then required skills, then optional advice. A skill cannot override higher authority. Incompatible mandatory rules block bundle preparation with the conflicting ids and sources. Optional conflicts use the explicitly adopted replacement; otherwise omit the optional conflicting candidate with a reason.
  4. Reserve space for mandatory policy, explicit requests and role/task required skills. Rank optional skills by declared priority, forecast evidence/confidence, then stable id. Count the complete closure at each addition. There is no arbitrary two-skill limit.
  5. Emit every candidate decision: included, excluded-trigger, incompatible, superseded, duplicate, omitted-budget, source-missing or conflict, with a reason. Persist and verify the transport before launching.

If required text exceeds the hard or model budget, preparation reports a bounded skill-context-overflow failure for the existing pipeline recovery path; it does not start an unenriched run. The implementation must express any admission consequence through the existing decision boundary and AiOperatorDecisionGateway. The existing selector exception path fails open to the authored prompt; required-skill preparation deliberately strengthens that behavior. An optional miss can proceed with a visible warning and the available required set. Projects intentionally opting out must record disabled; an applicable mandatory policy cannot be turned into a silent opt-out.

After delivery, compare actual changed files with the forecast for selection diagnostics. A newly discovered area can trigger an explicit same-run bundle extension before work in that area; its full text, time and digest create a new receipt revision. The CLI can request this through the supported run-context seam or stop with a typed missing-context report. Ad-hoc reads remain labelled observations and cannot be counted as managed prompt delivery.

Examples

A .NET API regression with forecast backend/Features/Tasks/** gets backend best practice, regression guidance and project policy. A UI change with forecast Angular component/SCSS files gets frontend best practice, UX and visual standard, and UI evidence procedure, including the current hard-rule dependency. A concept card discussing frontend architecture gets the concept/evidence procedure and relevant project knowledge; it receives no implementation-only Angular instructions simply because its prose contains “UI”.

Distribution

The application compiler produces a canonical context-bundle.md, a machine-readable receipt and a content-addressed resource archive. Put resolved resources under a run-owned .studio/run-context/skills/<qualified-id>/<digest>/ directory inside the prepared worktree, outside native discovery folders. This is disposable runner context, not a new per-task workspace. The platform creates and excludes it from task diffs and preserves the immutable source archive with the receipt. Use logical paths in shared instruction text; bind absolute paths in the variable run-context section.

Check archive size, manifest digest, file hashes, executable flags and path containment before starting. Reject path traversal, symlinks outside the package, case-colliding files and unbounded archives. Proposed limits: 10 MiB expanded per skill, 40 MiB per run, excluding separately approved tool dependencies. Packages contain no credentials. Scripts run only when the task needs them and the existing execution policy permits them; importing a package executes nothing.

Prompt order

Target order: stable platform rules, stable project policy and resolved skill text, then variable role invocation, authored task, receipt-specific reasons, resource path bindings and evidence paths. Within the stable part use policy first, common task-kind skills next, specialist skills last, with explicit ranks and stable id ordering. Keep dates, task ids, selection reasons and absolute worktree paths out of the reusable skill prefix. Preserve the authored task verbatim and retain hashes for both the composed prompt and task.

The current enrichment renderer appends context after the authored task. Its audit seam can be reused immediately, but that placement prevents different cards from sharing the appended skill prefix across fresh calls. Reordering is an explicit transport slice with prompt-equivalence tests, not an assumed cache saving. CLI-added system text, tool schemas, session configuration and model switches can still change the effective prefix.

Visibility

Proposed card journey: open the card's Docs/context area, inspect “Skills delivered”, then choose an invocation: core, aspect review, fix or concept. Each entry shows qualified identity, version and digest, source scope, full text/resources, why it matched, required/optional status and tokens. Show budget omissions and conflicts next to inclusions. A separate native observation never carries a “delivered by Studio” label. This is a future surface specification, not a claim about the current UI.

Proposed reverse journey: open a skill's library detail, choose version or all versions, then inspect loads by project, task kind, invocation mode and date. Follow a row to its card and exact receipt. Default overview columns: owner, released version, scope, trigger summary, instruction tokens, unique cards, delivered invocations, acceptance numerator/denominator, relevant findings, rework, last release and evaluation status. Filter retired versions and local forks without merging their outcomes.

The library should be a shared workspace knowledge view with project filters, version comparison and source links. Card and library use the same ledger projection. Totals must equal visible child counts under the same filters; a page subtotal must not impersonate the workspace total. Empty means zero eligible records only when the dataset is complete; missing history is “unknown”. Metrics

Load count: distinct successful managed delivery invocations containing the skill. Card reach: distinct task keys with such delivery. Acceptance: accepted terminal cards divided by terminal eligible cards, with pending and censored cards shown separately. Relevant findings: findings with criterion or area attribution divided by completed applicable reviews. Rework: fix rounds per completed card, plus the share requiring any fix. Native observations and legacy summaries get separate denominators.

Observational outcomes are associations. Show model, task complexity, project, review regime and time window before comparing versions. A hard task is more likely to load more skills; raw acceptance rankings would punish the useful ones. Without reliable attribution show a finding as unattributed rather than blaming every skill on the card. Give workspace administrators export and retention controls; customer knowledge and card content stay private by default.

Quality

The owner's 24 November blind comparison reports that the version without the visual-design skill won because it had more content depth. Treat it as a concrete hypothesis about harm and a design for a repeatable comparison. The underlying briefs, outputs, prompts and scores were not supplied here, so this Dossier does not turn that observation into a measured effect size or a universal verdict on the skill.

Comparison

  1. Record the candidate version, intended improvement and harm hypothesis. Start with “visual procedure reduces decision or content coverage” as a regression case. Preserve mandatory policy in both arms.
  2. Build a stratified sample from actual task types: UI behavior, visual redesign, content-heavy Dossier, backend change and operational procedure. Freeze base revision, brief, acceptance criteria, model/effort, tools, token budget and reviewer version. Isolate outputs; neither arm reads the other's result.
  3. Randomize presence or version of the optional skill. Use at least 20 matched task pairs for an initial directional screen, with repeated seeds or runs where stochasticity is material. This is a screening target, not a statistical guarantee. Candidate runs cannot mutate live task state.
  4. Blind reviewers to skill, arm and model label. Score correctness and content coverage before visual coherence, accessibility and effort. Include independent task acceptance checks and the owner's pairwise choice. Report ties, failures and disagreements. A reviewer checking the candidate's own style rules cannot be the sole outcome judge.
  5. Report per-stratum effects with paired uncertainty intervals, costs and rework. “Inconclusive” stays inconclusive. Advance to a limited live rollout only when the target improves and no protected dimension materially declines.

Suggested rollout guardrails: no new critical correctness or permission failure, no loss of a required acceptance item, and no content-coverage drop greater than five percentage points in the pilot. These are proposed operating thresholds, not established product facts. A material harm finding pauses automatic selection of the candidate version; retain the previous released version. Optional skills may have a holdout cohort; mandatory hard rules are never withheld to make an experiment.

Review

Every delivered criterion has a stable id, scope and authority. The review aspect receives the exact original skill text plus an independent review procedure. Findings cite skill id/version/digest, criterion id, affected file or screenshot, and the evidence that fails it. Irrelevant criteria are marked not applicable with a reason. Advisory craft preferences cannot become blocking hard rules. Review must also report missing delivered guidance and any instruction that pushed the work away from the task.

For content-heavy documents, completeness of decisions, evidence and implementation scope is a protected dimension. For UI work, preserve actual content, tasks and states before appearance. A rule such as “use a diagram” is conditional on whether it explains the subject; a visual iteration does not authorize cutting required analysis.

Revision

Review and owner findings enter a feedback queue keyed to the exact package version and criterion. A domain maintainer triages instruction error, wrong selection, missing source knowledge, transport loss or agent noncompliance. Only the first three usually justify a skill edit. Produce a normal creation/revision card with a failing behavioral fixture, change, comparison and source updates. The role guardian can propose the card; its grants still control mutation. The released package keeps evidence and change rationale. No review agent silently edits the default skill while reviewing its own work.

Regular reporting should show harmful versions, inconclusive experiments, and unresolved feedback as readily as successes. Usage volume alone never promotes a skill. Retire general visual-design defaults for content-heavy concepts if controlled comparisons repeat the reported harm; keep useful capture procedures as a narrowly selected module.

Shipping

A product release contains a package catalogue, immutable bundles, compatibility metadata and a tested baseline lock. Workspace activation shares one version across projects; project-specific knowledge remains opt-in. Creation, review, release, adoption and retirement use normal artefact tasks, and installation-owned state is changed only through the application API. Runtime agents do not manage Git, worktrees or release publication.

Export a deterministic archive with skill identities and versions, file hashes, complete instruction closure, required dependency bundles, licence notices, source provenance and review/evaluation receipts. Tool declarations list capability requirements without endpoint secrets. A plugin manifest can group these packages with connector configuration templates and assets. Do not export credentials, private card bodies, usage history or project knowledge without an explicit export scope.

Import verifies manifest signatures or recorded local trust, hashes, size/path limits, dependencies, schema and tool compatibility, then shows an adoption preview. Unknown publishers remain inactive until an administrator adopts them. A dry run reports exact replacements and conflicts. Offline transfer works with the same archive. An import never auto-runs scripts, enables connectors or updates project locks.

Customers may create, fork, extend, select, disable optional packages, pin old versions and export their own knowledge. They may change project-specific policies through their authorised project governance. They cannot mutate a signed shipped version in place, rewrite prior receipts or bypass platform lifecycle and permission floors by adding a skill. Updates propose a three-way comparison between upstream, local fork and new release; adoption is explicit, with rollback to a retained lock.
