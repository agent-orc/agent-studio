Concept Dossier · AGT-3171 · 16 October 2026

Dynamic placement: work containers by load

One host agent admits eligible coding, review, gate and post work against one host budget. Each Linux work item can get a fresh bounded container; Windows keeps an isolated process executor. Claim authority and fenced publication remain with the Task Server.

Context

Robert asked on 16 October for coding slots, review containers and gates to move where load leaves room, with containers created for work. The current code already gives coding and review separate pulling daemons. It also contains a pulling gate daemon, but the batch gate defaults to the SSH bridge; the claimed path is opt in and rejects a configured remote Task Server because batch member IDs belong to the monolith. Thus “gates are pushed” accurately describes the default batch path, not every implemented path. The operator brief reports one coding runner and a review service on agent-runner-01, three long lived review containers on KORI, and kori-gate. That exact deployment count is operator supplied and is not derivable from source code. Source evidence separates the code facts.

Placement

Proposed. A host advertises role, OS and architecture, executor support, toolchain digest, provider account binding and tested repository access. A claim is eligible only when all hard requirements match, the host has a fresh budget version and a free grant, and the authority can atomically lease the item. Warm repository mirrors are a soft preference: an eligible warm host may claim within a short bounded preference window, after which a cold eligible host may take the item. Queue age prevents cache affinity from starving work. The response records the matched capabilities, grant, host, lease, fence and authority epoch. A stale or mismatched acknowledgement denies a new claim; existing work keeps its grant.

One supervised host agent owns role advertisements, admission and executor lifecycle on each machine. It multiplexes coding, review, gate and post claims while each claimed attempt retains its own state, heartbeat and fenced report. It is a new host component; today the code has role-specific daemons. Migration starts by adding a host inventory identity and a shadow admission view, then moves one role at a time. A role daemon stops taking new claims and drains its running attempts before the host agent enables that role. Its persisted attempt state is reconciled with authority before removal; an active attempt is never silently handed to a second executor.

Execution

Linux executor. Prefer a fresh rootless Podman or Docker container per work item behind one host agent. Pin signed role image digests for coding, review and gate workloads; build and publish through the existing release pipeline and retain the previous digest for rollback. Start as a non-root user with a read-only base filesystem, no host Docker socket, a writable attempt volume, CPU and memory limits no larger than the reserved host grant, and a process count limit. Mount versioned npm and NuGet caches and repository mirrors separately from the writable worktree. Caches are performance data: verify the exact fetched SHA and clear or quarantine corrupt entries. Never mount a host provider home or central secret into a work container. Persist logs and evidence before removing the container and its tmpfs secret mount. Reconcile orphaned containers by attempt ID and fence after a host restart.

The existing AGT-3019 allocator is the proposed admission core. Containers replace the per-worker cgroup as the Linux enforcement unit, but do not create a second capacity store. The host agent reserves half-core grants atomically across roles, applies CPU quota and memory floors at launch, and reports observed limits and throttling. The allocator's pending decision remains a dependency; its 6 October gate timings are a baseline, not evidence of container overhead. Measure p50 and p90 time from grant to first command, image pull, cache hit, cold repository materialization, CPU time and gate wall time against the current process executor. The canary may keep process execution if container start cost or tool compatibility fails its recorded threshold.

Windows executor. Keep process execution in a per-attempt worktree with an isolated process tree, Job Object limits and an ACL protected attempt credential directory. It advertises Windows toolchains and never claims Linux-only work. Docker is optional per the 12 September decision. Windows has no Linux tmpfs guarantee; the host adapter writes the shortest-lived files under an ACL protected encrypted volume and deletes them after use. This is a platform-specific exception to the Linux tmpfs requirement, visible in the credential inventory.

Gate conversion. Extend the existing gate claim protocol to every merge, promotion and batch verification gate. The gate subject carries exact SHA, policy digest, bundle digest and immutable bundle artifact locator. The host downloads the bundle from the Task Server, verifies size and checksum, then verifies HEAD before execution. Claim slots become host grant reservations backed by the same allocator; per-branch merge/rollback and ordered publication stay in the existing authority. During migration, SSH transport remains a compatibility mode only for work already dispatched or installations without an enrolled gate agent. The API-side GateSlotUsageTracker remains a compatibility projection until all gate paths report claimed occupancy; it does not become a second scheduler. Batch gate's current BatchGate:Execution=claimed cannot use a remote Task Server in its present form, so that identity boundary must be resolved before the bridge default can be retired.

Post work

Today. After a run moves into 4-auto-review, TaskTransitionService enqueues an AutoReviewPostProcessingRequest. AutoReviewPostProcessingQueue holds requests in an in-memory channel; its backend AutoReviewPostProcessingWorker limits concurrent cards and calls ReviewDecisionOrchestrator.ProcessCardAsync. The orchestrator classifies the card and runs the applicable review and decision steps. AutoReviewPostProcessingRecoveryService scans unfinished cards in the durable auto-review lane after restart and re-enqueues them. The lane and outcome records survive a restart, but queue entries do not. This is backend post-processing, not a host-agent claim today.

Claimable item. Materialize one durable post-work subject for each eligible card and lane entry, with project, card, source run, required review capabilities, input artifact references, policy digest and a stable idempotency key. The Task Server exposes post-work claim, renewal and fenced result operations through the same attempt authority and versioned host grant used by other roles. An eligible host agent claims when its post role and budget match, runs the bounded review workload in its Linux container or Windows process executor, and returns evidence and proposed outcome. The Task Server alone applies lifecycle transitions, reissue or human-review routing, delivery resume and publication after validating the current lease, fence and authority epoch. Deferred work returns to a durable eligible or waiting state with its reason and retry time; lease loss makes late reports inert.

Migration. First create subjects in shadow mode from the existing transition and backfill unfinished 4-auto-review cards, comparing eligibility and outcomes without a second executor. Then enable claimed post work for a bounded cohort: stop new in-memory queue admissions for that cohort, let active backend passes finish, reconcile their outcomes, and only then admit host claims. Keep the backend queue and recovery sweep for unconverted cards and rollback. On restart or rollback, reconcile each subject against lane state and recorded outcomes before re-enqueueing or reclaiming it; never run a backend pass and host attempt for the same card concurrently. Retire the queue path only after claimed attempts, deferrals, restart recovery and rollback show no duplicate decisions or missed cards.

Credentials

Proposed identity. Mint a short-lived work identity bound to host, role, task or subject, attempt ID, lease ID, fence and authority epoch. Renew only after a successful lease renewal; revoke and stop secret delivery on lease loss. The host agent receives a one-use exchange capability, obtains a role-scoped material set and writes it as mode-restricted files into a Linux tmpfs mount. The work container receives file paths, never secret values in environment variables or command arguments. Git reads through an isolated credential helper that reads the file only for the clone, fetch or approved write command. Logs, traces, artifacts and crash dumps redact or exclude the files. A teardown revokes tokens where the issuer supports revocation, deletes the mount and records a receipt. Expiry remains a backstop if immediate revocation fails.

Root secrets stay outside work containers. For a single-user installation, recommend one encrypted Task Server store protected by a local wrapping key and backed up with the installation recovery set; for a team or an installation with an existing vault, use an adapter to Vault, 1Password or Azure Key Vault. Store only root material and issuance metadata there. For reading roles, prefer checksummed server-supplied source and evidence bundles as the 16 October operator draft proposes; when a repository fetch is required, mint a read-only GitHub App installation token for that repository. Issue write permission only to the server-owned publication step. GitHub documents repository and permission narrowing, one-hour expiry and revocation. Reissue a token while its attempt lease remains valid; do not let an expired token silently turn a gate into an infrastructure failure. A server-side publication token never enters the work container.

Borrow the Kubernetes pattern of projected, rotating workload identity, not its Secret object as an implicit security boundary. Kubernetes recommends encryption at rest and least-privilege RBAC; Linux Secret volumes are memory backed, while Windows Secret data reaches node storage. The proposed broker must enforce these controls itself on non-Kubernetes hosts.

Provider accounts. The current dossier chooses host custody and native CLI refresh, and the setup guide warns that copied Codex credential files may share refresh-token lineage and lose validity after another login. Concurrent container safety for one Claude setup-token or one Codex login file is unproved. Before sharing either account, run two concurrent isolated containers through a refresh boundary and a third canary after refresh, with a redacted token-generation log and no copied operator login. If either provider invalidates peers, use one login holder per account that serializes refresh and lends attempt-scoped access where its terms and CLI allow; otherwise provision separate accounts or approved API keys per concurrent slot. Never copy a writable login file into multiple containers as an assumed solution. This decision is a rollout gate, not a request for a secret in this concept task.

Visibility

Planned for AGT-3169. The Environment view groups all active attempt containers and Windows process executors below one physical host. Each row shows role, project or subject, attempt ID and fence, image or process profile, admitted CPU and memory, cache state, start age, lease status, cleanup state and the reason a queued item cannot claim. The host row shows one grant total and per-role occupancy; a finished container leaves active occupancy but keeps its receipt in attempt history. A stale lease, failed cleanup or orphaned container is an acute finding rather than a permanent host row.

Planned for AGT-3170. Credential inventory shows a root credential or provider account as a protected binding and each attempt credential as a short-lived child: issuer, role, repository scope, host, attempt, expiry, refresh state, storage mode and revocation receipt. Values, token prefixes and file contents are never returned. The view distinguishes a shared provider account from the number of concurrent attempts using it and flags a failed concurrency proof. Both projections read the same attempt, grant and secret-issuance events, so a container cannot disappear from one view while its live credential appears healthy in the other.

Alternatives

A · Host pull and local executors

Each host claims only eligible work when its shared grant is free. It keeps the current attempt authority and supports Linux containers and Windows processes. A bounded warm-cache preference reduces cold starts without reserving a host forever.

B · Central placement scheduler

The Task Server chooses a host before a claim. It can optimize the whole fleet, but it must maintain live host capacity, reservation expiry and failure recovery in addition to current lease authority.

C · External scheduler

k3s, Nomad or a CI runner manages placement and executor lifecycle. This supplies mature primitives at the cost of an installation dependency and an adapter that must still enforce Task Server fences.

Recommendation

Adopt A in eight bounded slices

Keep host pull, make one agent per machine the local admission and executor owner, use AGT-3019 as the single host budget, and introduce fresh Linux containers after process-baseline measurement. Extend the existing claimed gate contract to all gate work and retire the SSH bridge after a fenced canary. Bind credentials to attempts through an issuer and a file mount. Keep Windows on a bounded process executor. Offer Kubernetes Jobs later when a team already runs a cluster.

Open decisions

Each block recommends a working option for implementation cards. The decision remains pending sight review and operator acceptance.

D1 · Placement authority

Options: A host pull with hard eligibility and bounded warm affinity; B central scheduler assignment. Recommend A. Reject B for the first delivery: it adds a second reservation path before host telemetry and grants are proven.

D2 · Host lifecycle

Options: A one agent per machine with role adapters and drain migration; B preserve role-pinned daemons and long lived containers. Recommend A. Reject B: separate role owners cannot spend one budget consistently without more coordination.

D3 · Executor

Options: A fresh Linux container per item plus Windows process executor; B process and cgroup on every host; C Kubernetes Job for every installation. Recommend A after the S3 measurement gate. Reject B as target: process limits alone do not supply a fresh filesystem and role image per item. Reject C as default: cluster operation is excessive for one machine. Retain B as a canary rollback.

D4 · Gate transport

Options: A extend claimable gates and pull checked bundles; B keep SSH push. Recommend A. Reject B as target: one configured SSH host and fixed slots prevent host choice. Resolve batch identity before switching the default.

D5 · Capacity source

Options: A adopt AGT-3019 one versioned half-core host allocator; B per-role container counts; C external scheduler quota. Recommend A as the working decision. Reject B and C as authority: either can admit a container without the shared host grant.

D6 · Scheduler product

Options: A local host agent now, optional Kubernetes Job adapter later; B k3s default; C Nomad default; D GitLab, Buildkite or GitHub Actions as the application scheduler. Recommend A. Reject B, C and D as defaults: their lifecycle and operations do not replace this product's attempt fence or publication contract.

D7 · Credential custody and provider concurrency

Options: A attempt identity, tmpfs files and brokered short-lived tokens with encrypted root store or external adapter; B mount a shared host login home; C inject credentials as environment variables. Recommend A. Reject B and C: shared refresh is unproved and environment values escape through process diagnostics. Select login holder, separate accounts or API keys only after the S5 concurrent refresh probe.

D8 · Visibility

Options: A show short-lived attempts as child rows of a physical host, with redacted credential bindings; B count each container as a host; C omit finished containers. Recommend A. Reject B and C: they obscure host budget and cleanup evidence. AGT-3169 and AGT-3170 should consume the same attempt and receipt records.
