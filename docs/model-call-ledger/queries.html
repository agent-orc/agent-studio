Model call ledger

Query workbook

Five fixed questions applied to every storage candidate.

All examples operate on de-duplicated response facts at one snapshot revision and authorized workspace/project scope. A time window is half-open, using the recorded request/response timestamp policy. usd holds fixed-scale integer USD units and is nullable. tokens is the disjoint total or null. Examples operate on responses. Run-level residuals are queried independently with their true granularity.

  1. Which projects cost the most per day or week?
  2. Which host and step incurred the most waiting and status usage?
  3. Which cards were most expensive, and which run causes account for that spend?
  4. How do model and level costs compare between periods A and B?
  5. By finding aspect, what did the resulting blocking/concern rounds cost and how many rounds were there?

SQL queries

For A SQLite/DuckDB and B PostgreSQL, create the scoped input from the indexed model_call relation and the selected price revision. For C JetStream, consume in bounded batches, upsert by call ID into a SQL projection and checkpoint only after commit. Its query results report the projected sequence. For E files, use the sealed manifest and DuckDB read_parquet below. The five statements are shared verbatim across those candidates: bind scope_calls to the corresponding input. Report intervals, project permissions and grouping keys are parameters built by the application, never raw user SQL.

-- A SQLite/DuckDB and B PostgreSQL: bind authorized filters and reporting buckets.
-- C: same source contract, from the checkpointed projection.
-- E: restrict to files in the selected authorized, committed manifest.
CREATE TEMP VIEW scope_calls AS
SELECT * FROM read_parquet(['sealed/project=p/day=2026-11-28/part-01.parquet'],
                           hive_partitioning = true);
-- Apply ACL and time to this view in production. Manifest admits only one
-- confirmed active revision per ID, or the view selects it by revision.

-- Q1. Substitute iso_week for local_day for the weekly view.
SELECT local_day, project, SUM(usd) AS priced_usd, COUNT(*) AS calls,
       COUNT(*) - COUNT(usd) AS unpriced
FROM scope_calls
GROUP BY local_day, project ORDER BY local_day, priced_usd DESC;

-- Q2. Split status checks and wait, with covered token volume.
SELECT host, step, kind, COUNT(*) AS calls, SUM(tokens) AS tokens,
       SUM(usd) AS priced_usd, COUNT(*) - COUNT(usd) AS unpriced
FROM scope_calls WHERE kind IN ('waiting', 'status')
GROUP BY host, step, kind ORDER BY tokens DESC;

-- Q3. The outer result explains each top card and reconciles to its subtotal.
WITH top_cards AS (
  SELECT project, task, SUM(usd) AS priced_usd
  FROM scope_calls WHERE task IS NOT NULL AND usd IS NOT NULL
  GROUP BY project, task ORDER BY priced_usd DESC, project, task LIMIT 10
)
SELECT c.project, c.task, c.cause, t.priced_usd AS card_subtotal,
       SUM(c.usd) AS cause_subtotal, COUNT(*) AS calls,
       COUNT(*) - COUNT(c.usd) AS unpriced
FROM scope_calls c JOIN top_cards t ON c.project=t.project AND c.task=t.task
GROUP BY c.project, c.task, c.cause, t.priced_usd
ORDER BY t.priced_usd DESC, c.project, c.task, cause_subtotal DESC;

-- Q4. period_calls assigns each response to each matching comparison period.
-- If A and B overlap, UNION ALL gives each period its own membership.
SELECT model, level,
       SUM(CASE WHEN period='A' THEN usd END) AS a_usd,
       SUM(CASE WHEN period='B' THEN usd END) AS b_usd,
       SUM(CASE WHEN period='B' THEN usd END) -
         SUM(CASE WHEN period='A' THEN usd END) AS delta_usd,
       SUM(CASE WHEN period='A' AND usd IS NULL THEN 1 ELSE 0 END) AS a_unpriced,
       SUM(CASE WHEN period='B' AND usd IS NULL THEN 1 ELSE 0 END) AS b_unpriced
FROM period_calls GROUP BY model, level ORDER BY delta_usd DESC;

-- Q5. attributed_aspect includes an explicit Shared/Unknown value.
SELECT attributed_aspect, cause, COUNT(DISTINCT run_id) AS linked_rounds,
       SUM(usd) AS priced_usd, COUNT(*) - COUNT(usd) AS unpriced,
       SUM(CASE WHEN run_id IS NULL THEN 1 ELSE 0 END) AS unlinked_calls
FROM scope_calls WHERE cause IN ('blocking_finding','concern')
GROUP BY attributed_aspect, cause ORDER BY priced_usd DESC;

Wide-column queries

Candidate D Cassandra uses one canonical table keyed by workspace and call ID, plus the following separately rebuildable tables. Reads below are CQL shaped for complete partition keys. Use a hash shard where one workspace/day is too large, keeping cardinality budgets and published revision/checkpoint metadata. The projection worker writes deterministic cells by revision from de-duplicated facts and publishes the completed revision after successful writes. Client merges use precise sums and nullable coverage. An arbitrary model/host/aspect combination outside these shapes still needs a new projection or SQL export. CQL queries

-- One read per authorized project/day/shard in the requested range.
-- Q1: merge by project/day, roll up seven calendar days for an ISO-week view.
SELECT priced_usd, priced_count, unpriced
FROM project_day WHERE ws=? AND project=? AND day=? AND shard=? AND rev=?;

-- Q2: merge host/step/kind across day/project/shard then rank.
SELECT host, step, kind, call_count, tokens, priced_usd, unpriced
FROM wait_by_step WHERE ws=? AND project=? AND day=? AND shard=? AND rev=?;

-- Q3: merge all task/cause cells over window, then rank spend and show causes.
-- A fixed-period ranking can be cached; daily top-10 alone loses candidates.
SELECT task, cause, priced_usd, priced_count, unpriced
FROM task_cost WHERE ws=? AND project=? AND day=? AND shard=? AND rev=?;

-- Q4: issue same read for the days in each period, merge model/level and diff.
SELECT model, level, priced_usd, priced_count, unpriced
FROM model_cost WHERE ws=? AND project=? AND day=? AND shard=? AND rev=?;

-- Q5: merge spend by aspect/cause and deduplicate round IDs across days.
SELECT aspect, cause, run_id, priced_usd, priced_count, unpriced
FROM finding_round_cost WHERE ws=? AND project=? AND day=? AND shard=? AND rev=?;

For Q5 an explicit unknown round key per unmatched call keeps costs while excluding those entries from the distinct round count. Single-call drill-down reads the canonical ID table and verifies authorization again.
