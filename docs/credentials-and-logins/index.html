Operations · Concept Dossier · AGT-2968

Credentials and logins

Host-owned credentials, evidence-based provider health, and renewals that leave a verified receipt.

Status Decision pendingPhase Decision readyAs of 26 September 2026

The operator direction is to make recurring host login work a managed product process. The recommendation is a metadata registry in the Task Server, secrets on their owning host, and a bounded renewal operation that the operator or an authorised agent can start. A browser step remains human work when the provider requires it.

This concept changes no credentials or product code. Its canonical path is docs/credentials-and-logins/index.html, following the card's single-directory delivery contract. Publication under docs/operations/credentials-and-logins/ and a documentation-index entry belong to later platform integration. Human sight review remains open.

Alternatives

Runbooks and manual tracking

Keep current sign-in tools and add an operator spreadsheet. Low implementation cost, but no source-aware expiry, automatic incident discrimination, or proof that every daemon adopted a replacement.

Central secret broker

Store and distribute every provider login centrally. This expands the compromise boundary and can copy refresh-token lineage between hosts. A broker cannot invent provider-supported renewal or remove browser consent.

Host custody and central process

Recommended. The Task Server records identity, evidence and operations; each host owns its provider and Git secrets. Existing login and restart adapters carry out typed steps. The cost is a small durable operation protocol and source-specific probes.

API credentials for all providers

A deliberate future deployment choice, subject to provider contracts and billing. It is not an automatic substitute for the subscriptions in use. Existing API-key configurations can be inventoried without changing the account or purchase model.

Recommendation

Keep credentials local to their consumer. Centralise metadata, lifecycle receipts and claim policy. Distinguish credential unavailable, provider incident, quota exhausted, and network failure before selecting the fleet reaction. Preserve an explicit indeterminate result when the evidence cannot decide.

The deployment-story Dossier, AGT-W63 (source AGT-2906) owns the one-box to distributed deployment ladder. The bus Dossier, AGT-W65 (source AGT-2905) owns authority, claims and replay. This proposal adds credential metadata and maintenance operations to that authority. It introduces neither a second task store nor a separate message broker.

Inventory

The registry is metadata, not a vault. Its key is installationId + hostId + credentialId; generation identifies each replacement. Provider, account alias, repository and role scope are separate fields. One host can have several accounts and principals. Coding and Review advertise their own adoption of a shared credential generation.

Registry design and initial observations provides typed fields, enumerations and secret-free seed records. Reported values are not live discovery. Unknown creation, expiry, owner identity and verification dates stay null with an explicit reason. File modification time is not creation time or successful verification.

Source authority

The resolver inspects effective daemon configuration and the CLI's selected authentication method without exposing values. For Claude, an active environment token must not inherit expiry from a native file. Conflicting provider variables require an explicit source check. For Codex, use the effective config home and native store, not an assumed global path. Record every alias and verify whether CLI atomic replacement changed its inode; hard-link count alone is not proof of refresh propagation.

Host advertisement

Extend provider-auth:<provider> with a versioned credentialHealth payload: credential ID and generation, consumer adoption, expiry semantics, last real verification, observation deadline, reason, retry time and runbook reference. Local secret locators stay on the host or in an authorised detail projection. Advertise Git, principal and transport health under their own capability families; a provider failure must not drain unrelated work.

The Task Server validates authenticated host ownership, monotonic generation and sequence, timestamps and a bounded TTL. Late observations cannot overwrite a renewed generation. Coalesce repeated Coding/Review observations of the same account into one incident while retaining per-consumer adoption. New fields require a protocol version; old producers remain visibly unverified. Old claim consumers receive a conservative legacy unavailable/limited projection with a typed reason. Roll out server admission support before enabling new producers.

Execution Hosts

Proposed product contract. Execution Hosts receives a flat credential list per host: provider/kind, scope, owner, source alias, last verified, expiry or “Unknown”, current reason and next action. Details disclose the last renewal receipt and adopted generations. “Renew”, “Verify” and “Rotate” start the same typed operations available to an authorised agent. An incident row says when the next check is due; it does not offer renewal as the default action.

This is a target interaction, not a claim about a rendered current surface. No product screenshot is presented as evidence here. I08 requires real light/dark captures of the implemented states, using the canonical full-bleed evidence figure and per-image provenance.

Probes

A local login-status answer proves a stored session is recognised; it does not prove a provider request will succeed. Combine source metadata, the existing cheap status command, bounded real-call evidence, provider status evidence and connectivity evidence. Preserve their independent timestamps and scopes.

Healthy and indeterminate complete the state space. A bare 401, malformed output, unavailable status feed or probe timeout enters indeterminate investigation, not forced expiry. After a failure, pause new affected claims while evidence is collected, retain last-good data with its age, and retry diagnostics at 30/60/120 seconds. At ten minutes unresolved, create one diagnostic operator item with “cause unconfirmed”, not a renewal demand. A routine probe timeout with no failed request can retain readiness only until its five-minute evidence deadline. No infinite last-good latch.

Decision order

  1. Resolve. Select the effective source and generation. Check host time and consumer adoption. A proved absent or revoked credential remains unavailable even during an incident; track both facts.
  2. Observe. Run claude auth status --text or codex login status in the same identity/environment as the consumer. Keep the existing bounded timeout, low priority and single-flight cache. Record process signals and intentional stops separately.
  3. Verify. Reuse a successful provider exchange from an authorised run in the last five minutes, tied to account, endpoint and generation. Otherwise make a minimal provider call with no repository access or tools, a 30-second bound and a configured spend ceiling. After renewal require a new call through the production launcher, including the clean-context credential path. A process merely being alive is not successful-request evidence.
  4. Correlate. On an auth-shaped failure, fetch the allowlisted official status feed from the control plane; require a relevant active component incident, retrieval time and a five-minute freshness limit. A green page is not proof of credential failure. If needed, ask an already enrolled independent host to run the identical canary locally. Never ship its credential to the failing host. No spare credential is a valid missing-evidence state.
  5. Decide. Match the normalised signature (provider, endpoint class, status, provider error code and scrubbed message template), not raw secrets or request IDs. A second host with the same refreshed lineage is not independent. Common proxy, CLI-version or request-configuration errors remain diagnostic uncertainty. Request entitlement/model refusals stay ProviderRejectedRequest, outside the four outage causes.
  6. Publish. Persist observation and policy revision before changing claim admission. One incident ID links capabilities, run evidence and recovery. Existing active leases continue under their authority; a failed in-flight request ends through existing outcome handling and awaits recovery without repeating completed side effects.

Normal real-call verification runs at most once per host/account per five minutes, using recent successful runs where possible. Incident checks elect one canary per affected service scope to prevent a fleet stampede. Status evidence alone cannot clear an outage: require two successful canaries at least 30 seconds apart, then resume gradually and verify each host's credential. An old signed-out latch is reconciled only for the matching generation.

26 September example

The operator reports Codex returning 401 Incorrect API key provided: [redacted] across runs on agent-runner-01, followed by ProviderUnauthorized and rejected claims. The reported decisive evidence was an OpenAI status incident, found after about forty minutes. No incident ID, timestamps or known-good comparison were supplied; this Dossier does not invent them.

Under this proposal the first 401 records an auth-shaped request failure with the host's ChatGPT source, then starts indeterminate investigation. A relevant active status incident moves service state to provider-incident; credential state retains its last verified value and age. Claims pause with the short canary cadence and no renewal item. If status evidence is unavailable and no independent credential exists, the outcome remains indeterminate. A demonstrated missing source still gets its own renewal item. Recovery requires real-call success, not another codex login status alone.

Renewal

A typed operation has operationId, actor, targetHost, credentialId, expectedGeneration, authorisedScope, deadline, idempotencyKey and a step journal. States are requested → preflight → awaiting-human → staged → verified → adopting → committed → retiring-old → complete; optional human and retirement steps may be skipped. failed, cancelled, rollback-pending and revocation-pending preserve the last safe boundary. A renewable host lease and generation comparison allow only one writer per credential.

The platform journals secret references and receipts, never token bytes. Commands and receipts travel over the authenticated host polling channel; no inbound runner listener. Keep the current SSH adapter during migration and use it as a separately authorised recovery route if a Runner principal is broken. Provider login sessions are bounded to 15 minutes. Browser URL/code are sensitive, temporary fields delivered only to the initiating authorised session; never ordinary logs, card text, bus history or screenshots.

  4. Platform: pause new affected claims, preserve existing workers, replace Coding through its lifecycle helper and use agent-runner-deploy restart-review. Busy Review remains adoption-pending until guarded drain completes. Do not force-kill detached workers. Retain the established recovery state and fences.
  5. Platform: verify each new daemon's effective generation and startup identity, then make a clean-context real call and publish a newer capability receipt. Rollback selects the previous still-valid generation if the new call or adoption fails. Browser OAuth issuance may invalidate earlier credentials; no seamless overlap is promised for provider-owned login lineage. If the old token is already invalid, preserve the staged operation and keep only that provider parked.

Codex

  1. Platform: resolve the host's native credential store and all clean-context consumers. Pause new Codex starts and let refresh-writing sessions drain, unless the installed CLI has a verified shared-store concurrency contract. An application mutex alone cannot control an already running CLI.
  2. Human: complete the host's codex login --device-auth browser step, when enabled for the account. If unavailable, use the documented host login with a protected callback tunnel. Do not copy the workstation refresh lineage.
  3. Platform: allow the CLI to write the selected host store. Check linked consumers after CLI atomic replacement and repair aliases while quiescent. Test that a refresh reaches later launches; do not overwrite a refreshed file with an older backup or start a second refresh writer to “repair” it.
  4. Platform: check login status, make a real call through the production clean-context launcher, refresh both daemon advertisements and resume claims. Restart only consumers that require it, using the same Coding/Review guards. Record host generation and renewed-by actor; access-token expiry alone does not schedule a human login.

The official OpenAI authentication guide supports device-code login and describes native credential storage. This Dossier chooses host-owned sessions as product policy because the reported fleet has already experienced copied refresh-lineage failures.

GitHub

Deploy keys: the host generates a new ed25519 private key in its protected store. The authorised GitHub adapter registers only the public key against the exact repository and records returned key ID, fingerprint and registration credential lineage. Prove read access with the intended SSH identity; prove write permission through the platform's permitted temporary-ref canary or a fenced publication receipt. A dry-run or ls-remote alone does not prove push permission. Switch new Git processes to the new key, let old operations finish, then remove the old public key. A failed registration leaves current access intact.

HTTPS tokens: a human issues a replacement if the issuer offers no delegated issuance API. The platform stages it in a protected helper, verifies each granted repository, switches the helper and tracks adoption before revocation. The existing plaintext ~/.git-credentials is an import source with restrictive permissions, not a registry export. Use credential-free remote URLs. The workstation OAuth credential used for registration remains on its owning controller; it must not become a runner-wide administrator token.

GitHub deploy keys have no intrinsic expiry and apply to one repository. The deploy-key API also documents that revoking an OAuth registration token can delete its deploy keys. Record this dependency before revocation; recreate and verify dependent keys under an approved independent issuer first. Overlap is guaranteed only when the issuer and repository policy permit two usable credentials. See GitHub's deploy-key constraints.

Task Server principals

The standalone server already has hashed credentials and a default five-minute overlap, capped at one hour. Extend the existing rotate API with a durable operation ID and adoption receipt. Issue a new generation, deliver it to the owning client file over the authenticated management channel, reload the consumer, and prove an authenticated request and the next active lease heartbeat. Retire the previous generation only when all named consumers acknowledge and its bounded grace permits it.

The current API starts the old credential's expiry clock when it issues the replacement. Preflight reachable consumers before invoking it. For a reliable zero-downtime process, I06 must stage issuance and explicitly begin retirement after adoption, with a maximum grace deadline; lost acknowledgements cannot extend validity indefinitely. If a client is offline, defer planned rotation. Compromise revocation overrides availability and may require re-enrolment via a separately authenticated administrator. Never rely exclusively on a credential being replaced to recover from its failure.

WireGuard and management access

Generate the new private key on its peer; distribute only the public key and intended route to the network controller. Verify independent SSH/console access first. Stage a second tunnel/address or another management route, update both ends, test handshake and an authenticated Task Server call, switch routing, then remove old peer trust. Do not assign overlapping AllowedIPs to parallel peers on one interface as an assumed seamless cutover. Without a secondary route, require an attended maintenance window and timed rollback. No provider renewal action can fix a failed tunnel.

For SSH management keys, add the replacement public key before switching the controller, verify a fresh connection with the pinned host identity, and remove the old key only afterward. Host-key changes require an independently verified fingerprint. These transport operations run through restricted host/network adapters, not general shell text from a task card.

Warnings and receipts

Evaluate deadlines hourly in UTC. At 14, 7 and 1 days remaining, emit one durable threshold event per credential generation, with owner, affected hosts and renewal action. A host returning after several thresholds gets one item at the highest urgency, with missed thresholds recorded. A successful replacement closes the prior generation's warnings. Expired credentials park claims immediately. Unknown expiry stays “Unknown”; request one metadata completion action rather than inventing a deadline.

Refreshable access-token deadlines trigger local refresh verification, not 14/7/1-day human alerts. No-expiry deploy keys, principals and WireGuard keys use a separately labelled policy rotation date. D5 recommends a configurable 90-day initial rotation interval for platform-controlled keys, subject to adoption and recovery capability. The product must never display that date as a provider-imposed expiry.
