Credentials and logins

Host-owned credentials, evidence-based admission and guided renewal as a managed product process.

Status Decision pendingPhase Decision readyAs of 26 September 2026

The operator direction is to turn repeated host login recovery into software-owned work. This Dossier defines inventory, diagnosis, renewal, rotation and recovery for one box and a fleet. Delivery is complete; human sight review and implementation promotion follow delivery. No host credential was read or changed in this concept run.

Alternatives

Runbooks and alerts

Keep secrets in their present locations and add reminders. This is inexpensive, but leaves source precedence, refresh ownership, rotation and incident diagnosis to individual operators.

Host custody and central metadata

Keep provider credentials on the host that uses them. Centralize typed metadata, evidence, workflows and admission decisions. Reuse native CLI refresh and the current capability protocol. This is the recommended first delivery.

Central secret service

Introduce a managed vault for all secrets immediately. This improves centralized access controls but adds bootstrap and availability dependencies, and does not by itself solve browser login, CLI refresh concurrency or incident classification. Keep a storage adapter boundary for later adoption.

Recommendation

Adopt host custody with a central credential registry and durable renewal operations. The Task Server owns metadata and claim policy. A host adapter owns secret installation and probes. Studio presents evidence and the smallest required human action. Native CLIs retain ownership of provider token refresh.

Use the single authority and host identities in deployment story, AGT-W63 (source AGT-2906). Follow Task Server bus, AGT-W65 (source AGT-2905): persist command intent and receipts through the Task Server, then let hosts pull bounded operations. An existing SSH administration adapter remains an explicit installation path; the engine gains no new direct daemon RPC. Bus messages carry operation IDs and secret references, never token values.

Inventory

The registry key is installationId / hostId / credentialId. Service bindings separately identify Coding, Review, engine, Studio edge and repository purpose. One credential may serve two units without being duplicated. Each secret generation has an opaque ID; public-key fingerprints are safe identifiers, while raw token hashes and token fragments are excluded from advertisements.

Capability advertisement

Extend the existing advertisement with credentialHealthVersion and summaries containing credential ID, generation, provider, effective source, outcome, confidence, evidence ID, observed time, last success, expiry knowledge and next probe. Preserve existing provider-auth:<cli> keys for Coding and Review. Host observations are sequenced by instance/generation; the server rejects stale generations and cannot let an old positive observation clear a newer failure.

Separate credentialHealth from serviceAvailability. The compatibility projection is ready only when both admit work, limited for quota and unavailable for other holds, with a typed reason. New UI consumers must never infer “sign in” from unavailable alone. Protocol negotiation prevents enabling these richer reasons against an old consumer that would issue the wrong alert.

Probes

Keep the bounded local CLI status probe. Add a minimal real authenticated request on enrolment, renewal, contradictory evidence and recovery, plus a proposed maximum healthy interval of 30 minutes when ordinary successful runs provide no equivalent evidence. Run it through the existing CLI invocation boundary in an empty protected directory, without tools or repository content, with a 30-second deadline and one in-flight request per host/provider. Budget the request and use configured model policy; no model downgrade or alternate billing credential is implicit.

Local status and file metadata alone do not establish service usability. Read only the effective source used by the daemon, identify shadowed sources, then combine local evidence, normalized real-call failures, network evidence and applicable provider-status evidence. Retain raw responses only in a redacted, bounded evidence record. Whitelist incident fields instead of storing arbitrary status-page HTML.

Uncertainty and recovery

healthy and indeterminate are control states around these four failure outcomes. A single 401, unsupported CLI status command or unreachable status feed cannot prove credential expiry. Hold new affected claims during contradictory evidence; retry at 60/120 seconds and at most every five minutes. After 15 minutes of inconclusive diagnosis, create one “diagnosis needed” item without a sign-in instruction. A confirmed incident continues without an action item even when it lasts longer.

Preserve the original successful-observation timestamp when a degraded probe runs. A proposed ten-minute last-good window handles transient probe failure; it cannot refresh itself indefinitely. Cold start with binary presence only is unverified and does not admit work. Ordinary authenticated successes count as evidence only for the same credential generation, endpoint and account. A reset or resolved status incident makes one isolated canary eligible; a successful canary plus a newer healthy advertisement resumes matching claims. A failed canary reopens the appropriate circuit without sacrificing another product card.

Independent evidence is checked in this order: missing effective source or explicit local revocation; trustworthy network/quota response; incident correlation for ambiguous unauthorized responses; confirmed credential failure. A provider incident can coexist with a missing local credential. Keep both facts and their scope; incident status never makes an absent token usable. “Known-good” means an independent credential with successful comparable use within ten minutes, not another host sharing the same token. Compare sanitized outcome codes and request shape, never secret bytes. The second host executes its own request; the credential never moves. No second account is created just for diagnosis.

Renewal

Every flow uses requested → preflight → awaiting-human (when needed) → staged → installed → verified → retired → complete, with explicit failed, cancelled and recovery-required states. A durable operation includes actor, credential ID, expected generation, idempotency key, deadline and safe evidence. A per-binding lock covers both units. Repeated commands return the same receipt; a stale generation cannot overwrite a newer secret.

R4 · GitHub HTTPS and provisioning tokens

Human: authorize OAuth or mint a scoped replacement token, including organization approval when required. Platform: use a credential-helper adapter or protected file, record issuer expiry and allowed repositories, stage the new generation, verify fetch and permitted push separately, switch future Git operations and revoke the old credential after proof. A token used to register keys remains on the administration endpoint and is never copied to the runner. Record issuance linkage because revoking a provisioning token may affect keys created through it; inspect the GitHub deploy-key lifecycle rules before revocation.

R5 · GitHub deploy keys

Platform with authorized repository administration: generate a new ed25519 key on the target host, store the private key locally at mode 0600, and register only its public key using a short-lived protected administration session. Otherwise the human repository administrator performs registration. Grant write only for a repository needing publication. Verify the exact origin using the new identity alone; a successful fetch cannot establish push permission. The managed Git layer performs a policy-approved temporary-ref push/delete proof or records write access as unverified. Switch the per-repository SSH identity, allow active transports to finish, then delete the old public key and private material.

GitHub deploy keys are per-repository and lack an issuer expiry; GitHub's deployment guide documents these properties. Use a proposed 90-day review/rotation due date, explicitly distinct from expiry. Multiple registered keys permit overlap where repository policy allows it. Failed registration or verification leaves the old key active.

R6 · Task Server principals

Platform: use the management API and existing principal rotation overlap, preserving principal identity, scopes and runner binding. Deliver the newly issued bearer once through the protected channel, stage it in the receiving secret file, hot-reload or safely roll the consumer, and prove authentication plus the required scoped operation. Keep the previous credential valid until all bindings acknowledge the new generation within the configured overlap. Completion requires old-generation rejection. If delivery fails, retain old use only until its existing deadline and enter recovery-required; never blindly call rotate again and shorten the rollback window. Emergency compromise uses immediate revocation and accepts interruption.

R7 · WireGuard peers

Platform with authorized gateway access: generate private key material at the peer, enroll the public key and explicit allowed IPs at the gateway, and exchange any preshared key over the existing protected channel. No browser is needed unless gateway administration requires one. Verify a handshake and an authenticated Task Server request. For continuous access, establish a separately addressed temporary peer/tunnel with nonoverlapping routes, test it, cut over, then remove the old peer. Never give two active peers conflicting allowed IPs. Without a second path, schedule a bounded maintenance window and a tested console rollback. WireGuard keys have a rotation due date, not an inferred OAuth-style expiry.

R8 · Provider API keys

Human or explicitly authorized issuer adapter: issue a replacement under the intended provider account and billing mode. Platform: stage through protected stdin or a store reference, select the mode explicitly, verify an actual request, switch and revoke the old key after all consumers acknowledge. Keep overlap only if the provider permits it. Do not exchange a ChatGPT login for an API key as a recovery shortcut.

R9 · Administration SSH keys

Administrator or authorized host adapter: generate the replacement at its custodian, add the public key while retaining the old key, verify a fresh connection with host-key pinning and only the new identity, switch the provisioner, then remove the old authorized key. Preserve a tested console recovery path. A changed server host key requires identity verification, not automatic trust.

Unit continuity

Before any restart, stop new affected admissions and read the active slot/fence ledger. Follow restart continuity and the drive-to-conclusion contract: detached workers, durable output and slot identity must survive; a replacement daemon reattaches only with PID/worktree and authoritative lease proof. Capture each installed unit's pre-restart identity, verify both services after reload, and wait for generation-matched advertisements. Busy Review work that cannot safely reattach drains before restart.

A daemon restart does not rewrite the environment of an already-running child. Let old-generation workers finish while their credential remains valid, or use the existing fenced recovery path if it has expired. Never kill worker process groups as a routine renewal action. If the installed unit configuration cannot prove reattachment safety, defer restart to drained idle rather than claiming zero downtime. Provider OAuth renewal can require a pause; controlled deploy-key/principal overlap is the zero-downtime target.

Warnings

Evaluate expiry and rotation due dates daily and when metadata changes. Emit deduplicated reminders at 14, 7 and 1 days, keyed by credential generation and threshold; update one operator item as urgency rises. If discovery happens inside the final day, emit only the most urgent applicable warning. Successful renewal clears prior-generation reminders. Unknown expiry displays “Expiry unknown”, with a verification/review due date; it never displays healthy merely because a date is absent. Automatic access-token refresh produces no 14-day login warning. Clock skew and stale observations are explicit evidence-quality failures.

Storage and transport

Use a HostSecretAdapter abstraction with native CLI store, restricted environment file, credential helper, file-backed Docker secret and optional external-vault implementations. The Task Server persists only metadata, authorization, operation state and its own hashed principal verifiers. It must never become a warehouse for runner OAuth tokens. Host encryption protects backups; filesystem permissions and service isolation control live access.
