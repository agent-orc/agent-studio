Concept Dossier · AGT-3459

Central model selection and fallback

One selection service for every consumer that picks a CLI, model or thinking level. It moves work to an equivalent model when a subscription quota is spent or a provider rejects a model, and it writes every switch to a selection log that the owner reads on the management page.

00 Situation

The owner set three goals on 3 November 2026. First, model selection happens in one central place in the code. Second, the system never stands still: a spent quota or a provider rejection leads to an equivalent model chosen from the Token Economy catalogue and explicit rules. Third, every such event is written to a log the owner can read on the management page.

Three incidents prompted the goals.

  • Manual switch, 2 and 3 November. Claude weekly usage reached 94 % before its reset, and Codex weekly usage reached 81 % with 22 hours left. The operator switched the review steps of 12 projects and 3 pipeline types by hand, in both directions: 72 PUT /api/projects/{p}/pipeline-step calls. New cards were pinned by hand ("3 of 4 cards on Codex").
  • Capacity block, 2 November 15:37 UTC. Codex reported "Selected model is at capacity". The event was handled as a quota limit: provider-auth:codex stayed limited and blocked every Codex claim for 60 minutes, and nothing fell back.
  • Unclear review coverage. Remote Review aspects and the grade are pinned per project step. It was unclear whether the existing fallback covers them on the review hosts. Section 01 answers this: it covers most aspects, but not deep review, immutable plans or tool commands.

Most of the pieces exist already. QuotaAdmissionService is the shared entry point for quota admission. CliQuotaFallbackService resolves a primary or fallback route per CLI model. ModelEquivalenceCatalog projects the Token Economy catalogue. ModelRoutingPolicyRegistry declares tiers and same-provider rejection siblings. The problem is not missing rules. Some consumers bypass these pieces, provider rejections other than quota have no cross-provider path, settings are scattered per project step, and the decisions are written to four places that the owner cannot read in one view.

Why capacity became a quota block

contracts/TaskServer.Contracts/ProviderAccessClassifier.cs has a dedicated ModelCapacity kind (:149), but the method checks the rate-limit signals first (:184) and capacity only afterwards (:203). If the run output contains both "Selected model is at capacity" and any rate-limit phrase, such as a retry line with "too many requests" or a 429, the result is RateLimited. That maps to QuotaExceeded (ExecutionOutcomeContracts.cs:274-282). Without a reset time, the runner marks the provider limited for UnknownLimitTtl = 60 minutes (runner/RunnerCapabilityProbe.cs:931). The verdict covers the whole provider, not only the rejected model. This explanation matches the observed 60-minute provider-auth:codex block. The raw run log of 2 November was not available to this run, so the first rejection card reproduces it before changing the order.

Even a correct ModelCapacity classification switches nothing. It retries the same session, then becomes a transient failure and returns the card to Ready on the same model (RemoteTaskRunner.cs:1863, TaskServerStore.cs:2272-2286).

Where decisions are recorded today

  • Per job: logs/timeline.jsonl events QuotaAdmissionDecision and QuotaFallbackActivated (QuotaAdmissionRecorder.cs:82-101,144-176), plus a chat note.
  • Per project: .orchestrator/orchestrator.jsonl, topic LoadDistribution.
  • Application log lines cli_quota_admission_decision and cli_quota_fallback_activated; workspace one-shots write only these.
  • Current state only: <job>/quota-fallback.json (QuotaFallbackMarker.cs), deleted when the fallback is cleared.
  • Per job: model-qualification.jsonl.

No workspace-wide selection log exists, and none of these files has retention. Provider rejections, deep-review exceptions and Task Server recoveries do not appear in any of them as selection events.

02 Alternatives

Option A: Close the gaps in place

Add quota admission to the merge resolver, deep review and the local provider-limit skip. Fix the classifier order. Add a cross-provider step to the rejection paths. Write a selection log from QuotaAdmissionRecorder.

Gains: smallest change; every card is a local fix. Costs: selection stays spread over about fifteen call sites and three rule copies (monolith, Task Server, runner). The next new consumer can bypass it again. Settings stay per project step, so the 72-PUT switch remains possible only through the global preference, which does not cover deep review or new-card pins.

Option B: One selection service over the existing rules

Add ModelSelectionService with a pure ModelSelectionPlanner in a shared contracts package. Every consumer sends a SelectionRequest and gets a SelectionResult with the route and the reason. The planner absorbs QuotaAdmissionPlanner, CliQuotaFallbackService.Resolve, the rejection siblings and the floor checks. Every non-trivial result goes to a selection ledger. Settings move to one workspace policy per consumer class, with project overrides.

Gains: one place for rules, tests and the log; an architecture test can forbid direct CLI starts. The Task Server and runner use the same planner through the contracts package. Costs: about eight cards; consumers migrate one by one, and two paths live side by side for a while.

Option C: Selection as an orchestration decision

Put the selection rules into the orchestration-decisions library as a typed decider. Hosts collect facts (quota, rejections, pins) and apply the returned route, as they do for lane transitions.

Gains: uses the existing decision boundary and its tests. Costs: model selection runs on every one-shot and chat turn, at a much higher rate than lane transitions. The decision gateway and its Monolith or Engine switch add latency and a dependency to calls such as title generation. Selection is not a lane transition, so it would stretch the library's contract.

03 Recommendation

Recommended default: Option B, starting with one switch for every consumer

Build one selection service over the rules that already exist. Keep its planner pure and put it in the shared contracts package, so the monolith, Task Server and runner decide the same way. The first card makes the 72-PUT switch unnecessary: one workspace action moves every consumer class away from a provider until its reset. The second and third cards make each switch visible in a selection log on the CLI Management page. Option C stays possible later, because the planner is a pure function with typed facts.

Target design

Request and result

SelectionRequest {
  consumer:      coding | review-aspect | review-deep | review-grade | concept-fit
                 | chat | one-shot:<kind> | merge-resolver | card-creation
  project, pipelineType, stepId?, taskKey?, attemptId?, round?
  pins:          { cliType?, model?, thinkingLevel?, mode: preference | hard }
  taskType, correctnessFloor?        // from qualification
  required:      { tools?, semanticReview?, imageInput?, longContext? }
  host:          { hostId?, acceptedModels[], cliVersions{} }   // remote only
  continuation:  { sessionCli?, sessionModel? }                 // same-session resume
}

SelectionResult {
  outcome:   primary | fallback | wait | throttle | refused
  route:     { cliType, model, thinkingLevel }
  primary:   { cliType, model, thinkingLevel }   // what would run without the rule
  rule:      pin | consumer-default | quota-cap | operator-switch | capacity
             | unauthorized | model-unavailable | floor | cost-guard | host-capability
  reason:    human sentence
  equivalence: { class, catalogueVersion, thinkingMapping }
  quota:     snapshot of the deciding window(s)
  retryAt?, returnToPrimaryAt?
  ledgerId?
}

The service is the only code allowed to call CliRouter.Get(...) for a model run. An architecture test in the style of TransitionDecisionBoundaryTests lists the allowed callers and fails on any new direct start. The Task Server and runner use the same planner from the contracts package and send their decisions to the ledger API.

Rules

The planner applies the rules in this order. The first rule that decides wins, and the result names it.

  1. Hard pin. A card or step pin with mode: hard runs as pinned or waits. It never switches.
  2. Continuation. A same-session resume keeps the session's CLI and model. A different provider cannot resume another provider's session.
  3. Model health. If the requested model is marked unavailable, the planner picks the equivalent (rule 6). Health is kept per model and host, with an expiry:
    • capacity: the model only, 15 minutes, or the provider's retry hint.
    • model-unavailable (model not found, not allowed on this plan): the model only, until the next CLI catalogue refresh.
    • unauthorized: the provider on that host, until a successful probe. Claims on that host switch provider; other hosts are unaffected.
    • rate-limited with a reset time: the provider and window, until the reset.
    The classifier checks the capacity signal before the rate-limit signals, so capacity no longer becomes a 60-minute provider block.
  4. Operator switch. "Conserve provider X until its reset" (today's CliFallbackPreferenceService) applies to every consumer class, including deep review, grade and card creation.
  5. Quota cap. A provider window at or above its cap (default 95 %, per provider and window, CliQuotaCapsService), or projected to cross it before reset, sends new work to the equivalent. The existing nearby-reset wait for cheap cards stays.
  6. Equivalence. The target is the cheapest selectable model of the same Token Economy capability class (light, balanced, frontier) on another provider, or the explicit providerFallbacks entry when one exists. Same-provider siblings (opus-5-5 → opus-5, gpt-6.1-sol → gpt-6-sol) come first for capacity and model-unavailable, because they keep the session format and the prompt contract. Thinking levels map to the same level when the target supports it, otherwise to the next higher supported level, and never lower. The consumer policy may list explicit fallbacks that win over the catalogue.
  7. Floor and capabilities. The target must meet the card's correctness floor (ModelRoutingPolicyRegistry.RouteMeetsFloor), the required capabilities and the host's accepted models and CLI versions. Review consumers (deep review, grade, code-quality aspect) accept only the same capability class; they never step down.
  8. Cost guard. A fallback whose price per MTok exceeds the primary by more than a factor set per consumer class (default 2.0) needs either an explicit policy entry or the operator switch. Otherwise the result is wait with rule cost-guard. Subscription CLIs are measured in quota rather than money, so the guard mainly protects API-key and pay-per-use routes.
  9. No equivalent. The result is wait with the earliest retryAt among the blocked routes. The card shows the reason; nothing fails.

Card pins

Today the planner ignores modelExplicit, so a quota fallback already overrides card pins. The recommendation makes that explicit. A pin is a preference by default: it wins over consumer defaults and qualification, and a switch away from it is logged with rule and reason. An operator who needs the exact model sets the pin as hard (new pinMode field, default preference). The card then waits rather than switches and shows why. The persistent re-pin after repeated rejections (ProviderRejectionContinuation) becomes a preference pin with an expiry instead of an overwrite of the operator's choice.

Running cards and their next rounds

  • A running process is never switched. Selection happens at launch, claim and continuation.
  • A same-session resume keeps its model (rule 2). After the bounded same-session capacity retries, the next attempt is a fresh attempt from salvage, and it goes through selection again.
  • Each new round (review rework, reissue, continuation, next review package) asks again. A card that ran round 1 on a fallback returns to its primary in round 2 when the primary is healthy again. Rework that depends on the earlier reviewer's wording keeps the review model if it is still healthy (consumer policy flag stickyWithinCard, default on for review consumers).
  • The ledger entry of the switch records returnToPrimaryAt. When the primary becomes healthy, a returned event closes the active fallback.

Hysteresis

The cap switches at 95 %. The return happens only after the window has reset, or after usage is at least 10 points below the cap with a minimum dwell of 30 minutes. A provider that sits at 94 to 96 % therefore switches once and does not flap. Model-health marks expire on their own timer and are renewed by the next rejection.

Storage. Daily JSONL files under <TaskRepository>/.runtime/model-selection/<yyyy-MM-dd>.jsonl, written by one writer in the monolith. This matches QuotaHistoryStore. The Task Server and runner post their events to POST /api/model-selection/events with a runner-scoped principal, and the post is retried with bounded backoff. Repeated identical waiting events for the same card collapse into one entry with a count. The active fallbacks are an in-memory projection rebuilt from the last 14 days at start. Retention: 90 days, then files are deleted. 90 days covers several weekly windows and is enough to compare quality across equivalents. A daily summary row (counts per provider, rule and consumer) is kept for 400 days.

API.

  • GET /api/model-selection/events?provider=&project=&consumer=&rule=&from=&to=&cursor=: newest first, paged.
  • GET /api/model-selection/active: open fallbacks and health marks, with their expected return.
  • GET /api/model-selection/effective?project=&pipelineType=: the route each consumer would get now, and why.
  • POST /api/model-selection/events: host ingestion, runner scope only.

Existing timeline events QuotaAdmissionDecision and QuotaFallbackActivated keep their type and gain a selectionEventId detail. The card timeline renders it as a link to the filtered view.

Management page view

The view is a new "Model selection" section in the CLI Management overlay (workspace-overlays.component.ts:132, the page the owner calls Verwaltung). It follows the admin flat-surface contract and uses existing table, badge and filter components. Status is shown by tint and badge, never by a coloured left bar.

  • Top strip: active fallbacks and health marks, grouped by provider, with the expected return and the number of affected cards. Each has an action "end now" (operator switch only) and "return to primary".
  • Filters: provider, project, consumer class, rule, period (24 hours, 7 days, 30 days, custom). The filters are kept in the URL, so a timeline link opens the view already filtered to its card and event.
  • Table: time, consumer, card or project, from and to, rule, reason. A row expands to show the quota snapshot and evidence.
  • Next to the table: the effective route per consumer class, from /effective.

Project overrides. ProjectSettings.ModelSelectionOverrides[consumerClass] holds an optional primary, fallbacks and pinMode, per pipeline type where needed. The pipeline-step settings keep their model fields for compatibility. A migration rewrites each step pin that equals the old global default to "inherit", and the rest become explicit overrides with a visible "overrides workspace" badge. The operator switch and health rules still apply to overrides, unless the override is hard. This is why the operator no longer needs 72 PUTs: a provider switch is one workspace action, and project overrides follow it unless they are hard pins.

Risks

  • Quality differences between equivalents. The review evaluation of 2 November found that the code-quality blocks raised by Opus were real defects. An equivalent of the same capability class is not an equal reviewer. Mitigation: review consumers accept only the same class (sameClassOnly). The reviewer model is stored with every verdict, so block rates can be compared per model. A review package that ran on a fallback can be marked for a second review on the primary when the primary returns (open decision 4).
  • Subscription terms for headless use. The fallbacks move headless, automated load from one subscription CLI to another. Provider terms on automated use and account sharing can change, and this Dossier does not assess them. Mitigation: the policy can only name CLIs and accounts already configured for headless use. The ledger shows the moved volume per provider, so the owner can check it against each plan.
  • Flapping near the cap. Snapshots are cached for up to 10 minutes, and forecasts move. Mitigation: the hysteresis rule, the minimum dwell, and the collapse of repeated waiting events. Suspicious snapshots count as blocked, as they do today, so a bad probe cannot cause a return.
  • Cost. Moving work to a pay-per-use or more expensive route can cost money that a subscription would not. Mitigation: the cost guard and the price fields in the ledger.
  • Both providers capped. With Claude at 94 % and Codex at 81 % in the same week, a full switch can push the second provider over its cap. Mitigation: the projected cap check also applies to the fallback target. The result is wait rather than overloading the target.
  • Two paths during migration. Until MS-6, some consumers decide outside the service. Mitigation: the boundary test's allow-list makes the remaining paths visible, and the ledger already records their decisions from MS-2 on.
