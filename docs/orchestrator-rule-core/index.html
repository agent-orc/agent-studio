Orchestrator rule core

A versioned, deterministic rule evaluation turns budget, progress, quality floors, and fleet pressure into one reviewable decision for each card. Consumption raises scrutiny continuously; it does not grant an LLM authority to change limits or execute actions.

Rule model

ORCH-3 owns a rule core with one pure evaluation boundary. It receives a frozen signal snapshot and a versioned policy bundle, and returns a typed decision receipt. Existing deciders remain the owners of their domain transitions. The core resolves shared pressure, admission, floors, and conflicts before dispatch through their existing APIs. It never mutates a task, starts a model, or reads a log in the pure function.

Rule record

id and immutable version; scope (workspace | project | delivery | card) and applicability; named signal inputs with freshness and missing-data behavior; one typed derivation; soft | hard | floor; predicate and parameters; admitted and forbidden action variants; required evidence kinds; autonomy class; owner and effective interval. A rule also names the loop-inventory id when it guards a re-entry. The existing inventory remains the only loop register.

Evaluation order is fixed: validate facts and authority, apply safety and correctness floors, enforce hard ceilings and loop breakers, evaluate soft rules, then choose the least costly admitted action that can satisfy the current objective. The receipt records every matching rule, including a losing one and why it lost. A missing required fact blocks the dependent automatic action and yields an explicit wait or human decision. Cost pressure cannot lower a model, evidence, security, exact-SHA, or human-only floor.

Workspace rules provide defaults. A project overlay may tighten a hard cap or raise a floor; it may relax a soft threshold only within the workspace's declared range. A card or delivery budget override uses AGT-W68's audited override and stays clamped by the host ceiling. No override can disable a loop breaker or change A3 authority. Pin the effective bundle version at admission; an in-flight run keeps that version, while a safety emergency rule can stop it with a separate, explicit decision receipt.

Signal set and normalization

Each signal records value, unit, source, observed time, coverage, and confidence in the measurement. Raw token counts are retained for audit; priced spend in cents comes from Token Economy at the rate version effective when the call was made. Unknown price is unknown, never zero. Slot occupancy counts wall-clock slot minutes, including tool waits; model latency remains a separate diagnostic. Quota is tied to its actual provider window, not added across incomparable buckets.

Route expectations use completed, comparable cards by task class, execution phase, CLI, model tier, thinking level, verification profile, and host class. Use the median expected cumulative spend at the same phase, not a global dollar average. The price-normalized and route-normalized terms keep an expensive approved model from being treated as an overrun merely because its tokens cost more. The absolute exposure term still makes a $400 card more consequential than a $2 card. All per-card pressure resets at accepted delivery or an audited new-scope decision; portfolio reservations do not reset with the card.

Measured coding budgets

Use the gate policy's principle, not its sample without filtering. For coding rounds, derive a starting budget from 1.25 × p90 of at least 20 comparable, cleanly completed rounds from the last 90 days, then clamp it to the RB-S2 project and host bounds. Require stable instrumentation and a recorded completion, result SHA, and slot duration. Exclude timeout-censored rounds, no-progress repeats, quota waits, host loss, and verification runs at anomalous host load from the estimator; keep them in risk analysis. Record cohort, sample count, window, percentile, margin, and clamp in the derivation sentence. With fewer than 20 comparable rounds, use the explicit RB-S2 card/project/host resolution; do not infer a ceiling from a handful of lucky completions. The RB-S5 120/150/180/240 minute choices remain operator override rungs, not the default estimator.

Consumption gradient

Pressure is a continuous, bounded diagnostic in [0,1], computed per delivery after every material event. Working default: P = clamp(0.35Rcost + 0.25Rslot + 0.15Rclock + 0.10Rround + 0.15A, 0, 1). The first four terms are capped usage fractions against the effective route expectation, forecast slot budget, current round budget, and RB-S1 exhaustion allowance. A = clamp(log(1 + spentUSD/20) / log(1 + 400/20), 0, 1) expresses absolute money at risk without letting a large price dominate the score. These weights and anchors are proposed first-version parameters, subject to dry-run calibration, not observed laws.

At $2, the absolute term is about 0.03; at $400 it is 1.00. With otherwise equal normalized usage, the $400 card has about 0.15 more pressure. If a strong model legitimately costs more, its route-matched expected cost raises the denominator of Rcost; the absolute term alone cannot trigger a stop. A new delivery starts a new pressure trajectory. Show both the dollar value and normalized terms in every decision so the number is not opaque.

Example: a sixth identical tool call is a warning at either spend level. At low pressure, the core can observe and wait for a changed result. At high pressure with no changed SHA or CPU progress, it requests an AGT-W68 checkpoint and may refuse a further automatic round. The log-silence and no-CPU window in RemoteReviewWorkspace is the precedent for a soft review before a hard command budget.

Pre-admission applies the same test before a slot is claimed: forecast the card's slot minutes and quota draw, reserve capacity, and compare with eligible Ready work under operator priority, deadline, age, and project fairness. Reserve the card's p90 incremental quota draw against the provider's remaining weekly window after active reservations; reserve forecast slot minutes against the fleet's staffed weekly coding minutes. Release a reservation on a fenced completion, cancellation, or expired claim, and reconcile it with actual use. A low-priority card with a poor measured completion chance may wait or enter a scope-cut decision when its projected slot use would displace higher-priority work. It is never silently judged "not worth doing". AGT-W56 owns complexity and the trusted model route; this core consumes that route and its floor. AGT-W70 owns integration gate slots; this core reads their reservations but governs coding admission only.

Spent money is a scrutiny signal, not a reason to finish a card merely to justify past expense. A continuation compares its forecast additional priced tokens, slot minutes, and chance of accepted delivery against the eligible queue. The receipt shows both cumulative exposure and marginal cost. At high exposure, the same weak progress evidence needs a stronger case for another round.

Action vocabulary

One typed verb is written to the receipt; an explicit variant names the existing dispatcher and target. An LLM may propose a verb, but the rule table selects it. The action union is observe | prepare | defer | continue | adapt | checkpoint | retry | halt | ask. Adapt covers a safe route change or a proposed scope cut. A scope cut changes acceptance only after an operator decision; while a run is live, the safe first action is a checkpoint. Halt includes a target and terminal reason so a force-failed process cannot be mistaken for an accepted task.

Autonomy classes from the Watcher remain authority limits: A0 observation, A1 reversible bounded acts, A2 prepared non-trivial intervention awaiting approval, A3 human-only. A rule cannot turn an A2 or A3 action into A1 because pressure is high. Every retry also spends its existing loop-inventory budget. An exhausted budget resolves to the existing owned terminal, including GaveUpToHuman where applicable.

Administration surface

ORCH-3 adds a workspace Rules page and a project Rules overlay page. The list shows rule id, scope, version, soft/hard/floor, effective source, last firing, last override, and affected cards. Opening a rule shows its typed signal fields and freshness, formula or measured derivation, threshold range, allowed action variants, floor, evidence requirements, and a plain-language example. A project row displays the inherited workspace value next to its override and the resulting effective value. Card budget overrides remain in the AGT-W68 card gate, linked to the rule that admitted them.

Save creates an immutable definition under .metadata/orchestrator-rules/<scope>/<version>.json through the application API. The stored revision includes actor, reason, UTC time, parent revision, normalized diff, dry-run digest, and activation time; decisions retain the version they used. An assistant may draft a schema-valid change, but never applies it. Compare, revert, and scheduled activation follow the pipeline editor's versioned-definition discipline.

The editor runs a read-only replay over the last 30 days or 100 eligible decisions, with matched cohort and a clearly marked missing-data count. It shows old versus proposed actions, extra model calls, projected cents and slot minutes, cards deferred, missed successful continuations, floor conflicts, and human reversals. The replay never claims a counterfactual result as observed: actual outcomes belong to the old action, while alternative outcome estimates carry uncertainty. A dangerous edit cannot activate if it weakens a hard loop breaker, host cap, A3 boundary, or quality floor, lacks a breaker test, or increases automatic spending beyond an approved range. A change that expands authority requires an operator review with reason and a shadow period. The first release may only edit bounded parameters and disable soft rules; new action kinds require code and tests.

History and correction

Each decision appends a receipt with rule ids and versions, matched predicates, input values and freshness, derived budget and provenance, pressure terms, candidate and chosen action, decider identity, model and calibrated confidence when used, evidence pack digest, dispatch result, and later outcome link. Daily rollups compare predicted completion, cost, and slot use with observed results by cohort. A threshold is suspect when false interventions, human reversals, wasted continuations, or missed completions exceed its declared target for a minimum cohort; the UI opens a proposed revision with cases, confidence interval, and replay. The service may refresh measured percentiles inside an approved formula and sample window. It may not silently change weights, thresholds, floors, action authority, or model eligibility.

Visibility contract

Every binding decision appears as one primary card statement above the pipeline: action, immediate blocker or next step, rule id and version, and actor. The timeline has a dedicated decision event linked to its precipitating signal and dispatch receipt. It always shows the signals actually read, their freshness, current budget and usage (cents, tokens, slot minutes, round count, quota window when relevant), derivation, pressure, chosen action, and a one-click evidence link. For an LLM classification it also names decidedByModel, provider, thinking level, calibrated confidence, and the deterministic decider that admitted the action. For mechanical decisions it says system rule, with no fabricated model.

The bus decision payload carries the same decision id, rule reference, model identity, confidence, reason, and evidence reference. Fix the current missing model field at the producer, not by joining a separate token event. The card header, banner, Result panel, and timeline project one canonical gate item and reason; they must not independently author competing red summaries. If the card needs a human decision, the specific blocker and controls appear in the primary statement, with the pipeline as supporting history. A dismissible symptom may be shown below it, but cannot replace the blocker.

Artefact boundary

A reusable orchestrator LLM step sees only a versioned DecisionEvidencePack, never a CLI session transcript or a path granting unrestricted log access. The deterministic producer joins run outcome, fenced attempt and tree SHA, token and slot ledger, rule snapshot, quota and capacity snapshots, progress receipts, prior decisions, and artifact descriptors. It may attach a redacted bounded log window when a named detector selects a specific interval. The pack is capped at 32 KiB of UTF-8 content and 8,000 estimated tokens; each log excerpt is at most 80 lines and 8 KiB, with at most two excerpts. On overflow it drops lower-priority excerpts, records omissions, and requires a narrower follow-up pack rather than reading the full file.

A bounded window carries source artifact id, attempt and fence, first and last line, byte-range checksum, selection reason, redaction version, and an authenticated drill-down reference such as task/AGT-3010/attempt/abc/log/cli-output?lines=3187-3230&sha256=.... The LLM sees the excerpt and opaque reference, not an open filesystem path. The UI opens the immutable source interval with access control and context lines. A raw stream is an unbounded sequential reader that can change under the consumer; it is forbidden at this boundary. The pack and model output are schema validated and stored beside the step input and output contracts.

Migration targets are the supervision-loop reader of cli-output.log and its line citations, the per-task session-log projection described in multichat-orchestrator.md when used as orchestrator context, and any StepKind.Orchestrator assembler that currently embeds an unrestricted cli-output tail, including abort review. Their deterministic source adapters may still read logs to select and redact windows; the LLM step cannot. RunTimeline may continue to serve an authorized human run view, but its output is not an unlimited prompt source. The Watcher already follows the bounded-pack pattern. This boundary reconciles the supervision concept with the telemetry layer's clusters and receipts rule.

Alternatives

A · Federate the eight policies

Add a common dashboard and leave decisions isolated. Smallest migration, but no rule can compare a card's spend with quota or another card's slot demand. Rejected for the cross-budget decision.

B · Versioned deterministic rule core

Adapt existing policies into typed rules, retain domain dispatchers, and use bounded LLM classification only for ambiguous evidence. Recommended. It gives one decision receipt without losing measured derivations or local hard guards.

C · LLM policy judge

Feed all signals to one model and let it choose actions and limits. Flexible in prose, but inconsistent on replay and incompatible with ADR-0032's pure-decider boundary. Rejected.

D · One universal score

Collapse cost, quality, quota, and liveness into a scalar stop threshold. Easy to graph, but a cheap signal could offset a correctness floor. Rejected. Pressure is a scrutiny input, not a substitute for typed hard rules.

Recommendation

Adopt B through ORCH-3

Start with a read-only decision receipt over RB-S1's ledger and the eight policy snapshots. Add the bounded artefact contract, then one shadow coding admission rule. Promote individual actions after replay, floor tests, and operator review. Use the pressure gradient to increase evidence and economic scrutiny, while existing hard ceilings and quality floors remain authoritative.
