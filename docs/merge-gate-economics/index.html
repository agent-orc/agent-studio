Concept dossier · AGT-2997

Merge gate economics

Every Agent Studio merge into develop runs the full backend suite for about 42 minutes, one merge at a time across all projects. This Dossier explains why neither existing reuse mechanism fired in the eight gates of 28/29 September 2026. It then proposes a rule set that keeps the gate honest but cheap, with modelled gate time, the guard against a wrong disjointness judgement, and implementation cards.

00 Summary

The gate did not fire its shortcuts for three structural reasons. None of them was an unlucky coincidence.

  1. Review reuse needs an unchanged develop tip and the delivery's own tree. The Remote Review tests the delivery commit on its own base, not merged onto the current tip. Reuse therefore applies only when develop has not moved since the delivery's base. In the eight gates, develop had moved by 5 to 10 merges each time.
  2. The per-SHA verdict cache is keyed by the new merge commit and lives on the Windows host only. The review on the runner host never writes to it, and every merge produces a SHA that has never been gated before.
  3. Test selection falls back to the full suite. No folder-to-test-project map is configured for this repository, so every code-touching merge runs all four test commands. Even with a map, the current rules would still run the full suite for seven of the eight merges, because each touched docs/ or more than one module.

The recommended rule set combines four changes, each defined in §04:

  • reuse the review verdict when develop moved only by path-disjoint merges;
  • make impact selection union mapped projects instead of falling back to the full suite;
  • run a nightly full suite on develop that opens a cause card and suspends disjoint reuse when red;
  • serialise gates per project instead of per machine.

On the eight logged merges this models to about 201 gate minutes instead of 348, a 42% cut, or 25 minutes per merge instead of 43.5. Across the stated input ranges the cut stays between 37% and 46%. Four merges would have been reused. The other four touched the same code files as develop and correctly keep a full or impact-selected run.

01 How the gate decides today

Three independent mechanisms can shorten a develop integration gate. Each has a precise firing condition, and each one failed in the logged case for a reason visible in the code.

Review reuse (AGT-2839)

IntegrationGateReusePolicy.Decide reuses the Remote Review verdict for tests and lint, while the compile step still runs. It requires every one of these conditions:

  • the review outcome is Pass with a passed build/test gate;
  • no conflict resolution and no mechanical replay;
  • the same integration branch;
  • the reviewed delivery is an ancestor of the merge result;
  • the pre-merge develop tip equals the tip the review captured before its commands;
  • the merge result tree equals the tested tree.

The tested tree is the tree of the delivery commit itself: the review checks out ExpectedResultSha and records HEAD^{tree}. Together the last two conditions mean reuse fires only when the delivery already contained the current develop tip, and nothing merged in between.

The log line reviewReuse=full ... reason=develop moved since the review: tip is c6673af8, the review verified d8f11a5f is condition five failing. Condition six would have failed as well: delivery 1a93b533 is based on 4e6de49c, from 16:18 the previous afternoon.

Per-SHA gate verdict cache

GateResultCache stores executed Ok, Warn and Fail verdicts under %LocalAppData%/agentstudio/gate-results/<project>/. The key is the exact tested commit SHA plus a profile digest. The digest covers:

  • gate id and pipeline definition version;
  • toolchain identity and profile fingerprint;
  • required test level and lane;
  • the changed-file list and the commands.

A hit needs the same commit SHA and the same digest. That is realistic only for:

  • a re-gate of the same merge commit, such as a restored environment-failure candidate or an AlreadyMerged recovery;
  • a repeated promotion of the same develop tip.

The cache never helps a first gate of a new merge, for three reasons:

  • Every develop merge is a new --no-ff commit.
  • Its changed-path list is computed against the new pre-merge tip, so the digest differs too.
  • The runner-host review never writes to this cache: no code under runner/ or task-server/ references it, and the toolchain identity is host-specific.

Test selection

PreDevelopBuildGate asks for work-package whenever the merge touches .NET or frontend/. DeterministicTestScope then falls back to the full suite in each of these cases:

  • the folder-to-test-project map is missing;
  • a changed path is unmapped;
  • a mapped row lists no test project;
  • the change spans more than one module.

This repository configures no map, so the logged test-level=full; selected=4 is the documented fallback: all four commands from .agent-studio/project.yml. Selection granularity is a whole test command. The class-slice planner exists but the gate does not use it, so a one-line backend change and a 60-file change cost the same 7,700 tests.

What full-suite=not-run; omitted=3 means

In the develop code, CompleteAudit counts a test command as omitted only when the sequential command loop never reached it. The loop stops at the first blocking failure or timeout; a green flaky re-run lets it continue. With the full plan (build, then backend, runner, task-server and frontend tests), omitted=3 means the gate ended at backend.Tests. Runner, task-server and frontend tests never ran.

A green run records full-suite=map-fallback-and-run instead. Either the logged gate was red or out of budget at the backend step, or the Windows host runs an older build with different audit semantics. The verdict header of those logs decides which; see Open decisions, Q0.

Gate slots

Two locks serialise the gates, and both span every project:

  • MergeIntoDevelopRunner is a singleton that holds one SemaphoreSlim(1,1) around merge, gate and rollback for all projects.
  • Inside it, BuildTestGateRunner takes a process semaphore plus the machine-wide file lock agentstudio-build-test-gate.lock.

The Task Server's remote gate claim also admits one live gate attempt per host. No setting raises any of these limits. A Quality Studio or Token Economy merge that arrives during an Agent Studio gate therefore waits for it.

03 Alternatives

Four independent axes. Each option is judged on what it saves on the eight logged merges and on what it can let through.

Axis A: when the review verdict may stand in for the gate

A1 · Exact tip only (today)

Reuse only when develop has not moved since the delivery's base. It is safe by construction. It fired for none of the eight merges and cannot fire on a busy night.

A2 · Path-disjoint movement (recommended)

Reuse when develop moved only through gate-green merges whose gate-relevant paths are disjoint from the delivery's, and neither side touched a global input. The gate still compiles the merge result and runs the repo-contract slice. It fires for 4 of 8 merges. It can miss a semantic interaction through unchanged code, and the nightly guard covers that residual.

A3 · Project-reach disjoint

As A2, but also runs every test command that both sides can reach through the project graph. The residual risk is lower, but backend.Tests references runner/ and contracts/, so the command runs in 3 of the 4 reuse cases and the saving on those four merges falls from about 136 to about 53 minutes.

A4 · Rebase before review

Refresh every delivery onto the current tip before review, so that A1 fires. Develop moves about hourly, so the refresh would have to happen minutes before the gate. That moves the cost into re-reviews rather than removing it.

Axis B: which tests a non-reused gate runs

B1 · Full suite (effective today)

All four commands on every code-touching merge, because no map is configured.

B2 · Generated project map with union (recommended)

Derive the folder-to-test-command map from the .csproj ProjectReference graph and frontend/, instead of maintaining it by hand. Declare gate-inert rows that select nothing and do not count as a module. Take the union of mapped commands across modules instead of falling back. Keep the full fallback for global inputs, unmapped paths and a stale map. Add the missing test projects as map-only commands. This saves little on this night, 3 to 5 minutes on three merges, because backend.Tests is reachable from most paths. It makes the gate complete for setup/ and similar paths.

B3 · Coverage-derived class map

Record per-test coverage in the nightly full run and select backend test classes that cover the changed files. This is the only lever that shrinks backend.Tests itself. It needs a measured miss rate before it may gate. Deferred.

B4 · Model-based selection

Rejected on 25 July 2026 and recorded in AGT-W59 §5. It spends tokens to save CPU. Not reopened here.

Axis C: when the full suite runs anyway

C1 · Promotion only (today)

The operator-run promotion gate is the only full solution-wide run. Nothing watches develop between promotions.

C2 · Nightly on develop, plus a reuse budget (recommended)

One scheduled full run per day on the exact develop tip, using the promotion gate command set. When red, it opens a cause card listing the merges since the last green run, and suspends disjoint reuse for the project. Separately, a reuse budget forces a full gate after 6 consecutive reused merges or 24 hours without a green full run.

C3 · Every Nth gate full

Simple, but it charges the full cost to an arbitrary delivery inside the merge queue, and it attributes a red result to that delivery even when an earlier one caused it.

Axis D: how many gates run at once

D1 · One slot for every project (today)

Consistent, but a 42-minute Agent Studio gate blocks Quality Studio and Token Economy merges.

D2 · Per-branch serialisation, host capacity 2 (recommended)

Merge, gate and rollback stay serialised per (project, integration branch), which is the real consistency boundary. The machine lock becomes a counting semaphore with a configured host capacity, starting at 2. Queue wait across projects disappears. Two concurrent suites contend for CPU, which the metrics card must show before the capacity rises.

D3 · Separate gate host

The measured scale-out step already chosen in AGT-W59 D2. It composes with D2 and is not needed before the D2 measurement exists.

04 Recommendation

Recommended default

Adopt A2 + B2 + C2 + D2, in this order:

  1. metrics first;
  2. the repo-contract slice and the inert-path declaration;
  3. the nightly guard;
  4. disjoint reuse;
  5. impact union;
  6. per-branch slots.

The guard ships before the reuse widening, so that no merge is admitted on a disjointness judgement without a scheduled full run behind it.

Rule set

R1 Disjoint reuse. Keep every existing AGT-2839 condition except the tip and tree equality. Replace those two with the following conditions:

  1. Let base be the merge base of the reviewed delivery and the pre-merge tip. Every first-parent commit in base..tip is a platform merge with a green develop gate receipt, or a commit that itself passed a gate.
  2. The delivery's changes (base..delivery) and develop's changes (base..tip) share no gate-relevant file.
  3. Neither side touches a global input: Directory.Build.*, Directory.Packages.props, global.json, NuGet.config, .nvmrc, .agent-studio/**, testsupport/**, tools/**.
  4. The review's command set covered the gate's full command set, proven by a matching verify-plan digest.
  5. The project's reuse budget is not exhausted, and reuse is not suspended by a red nightly run.

The gate then runs compile plus the repo-contract slice on the merge result and records reviewReuse=disjoint with the base, the develop range and the checked path counts.

R2 Gate-inert and repo-contract paths. The repository declares gate-inert paths in .agent-studio/project.yml: docs/** except docs/app/**, .github/**, deploy/**, and root-level *.md. It also declares the repo-contract slice: test classes that read real repository files through a repo-root helper, tagged Category=RepoContract, which are about 359 of 6,319 backend test methods. An architecture test fails when a test locates the repository root without that tag. That keeps the inert list honest.

R3 Impact union. Generate the folder map from the ProjectReference graph at gate time and pin it by digest. Treat gate-inert rows as selecting nothing. Union mapped commands across modules instead of falling back. Always add the repo-contract slice when a non-inert, non-code path changed. Keep the full fallback for global inputs, unmapped paths and a stale map. Add setup.Tests, operations-server.Tests, orchestrator-engine.Tests and retention.Tests as commands that run only when mapped.

R4 Scheduled full suite and reuse budget.

  • Run the promotion command set once a day on the exact develop tip.
  • After 6 consecutive rung-2 merges, or 24 hours without a green full run on develop, the next gate takes rung 4.
  • A red nightly run opens one deduplicated cause card and sets disjointReuseSuspended until the next green full run.

R5 Per-branch slots. Replace the singleton merge lock with a lock keyed by (project, integration branch). Replace the machine-wide gate lock with a counting semaphore sized by Gates:HostCapacity, default 2. Keep rollback and push serialisation per branch.

Queue effect. The eight gates occupied the single slot for 348 of the 518 minutes between 20:22 and 05:00, a utilisation of 0.67. A deterministic-service queue model gives a mean wait of about 44 minutes for the next arriving merge of any project. At 25.1 minutes per gate, utilisation falls to 0.39 and the modelled wait to about 8 minutes. With per-branch slots (R5), a Quality Studio or Token Economy merge no longer waits for Agent Studio gates at all. It waits only for its own project's queue and pays the CPU contention of a second concurrent suite.

Relation to AGT-W59. The operator decided on 25 September that the full suite runs once as the final batch gate (D1) and that host scale-out is measured (D2). The batch gate is not built. This rule set governs per-merge gates until it exists, and it stays valid inside it:

  • disjoint reuse is per-member evidence;
  • the nightly run is the scheduled full evidence;
  • host capacity 2 is a measured step on one host, not a second host.

The AGT-W59 per-SHA cache card proposes keying by tree SHA. On these merges that would not have helped either, because every merge result has a new tree.

The Ops panel defines its metrics exactly:

  • Gate minutes per merge: the receipt durationMs of the final develop gate per integrated task, excluding queue wait. Median and p90 over 7 and 30 days, per project and for all projects.
  • Reuse rate: merges on rung 1 or 2 divided by all gated merges, split into exact and disjoint.
  • Queue wait: GateQueueWaitMs plus the time spent waiting for the merge lock.
  • Full-suite share: gates on rung 4 divided by all gates.
  • Guard state: the result and SHA of the last nightly run, and whether reuse is suspended.
