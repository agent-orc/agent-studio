Concept · Runner

Run budget per card

A single host-wide 90-minute run timeout ended AGT-2955 four times on 28 and 29 September. The salvage kept every line of work each time, but the next round kept nothing else: not the session, not the verification it had already done, not the diagnosis it was in the middle of. This Dossier analyses those rounds and proposes a per-card run budget with a soft checkpoint, a same-session continuation from the salvage, and an operator decision at the third exhaustion.

01 Situation

Every coding round on the remote runner gets the same wall-clock limit, RUNNER_RUN_TIMEOUT_SECONDS. The code default is 3600; the production host sets 5400 in /etc/agent-runner/runner.env. The limit is read once per host in runner/RunnerOptions.cs and handed to every worker by DurableAgentProcess. There is no card-level or project-level value. The only per-run override that exists today is the 300-second ceiling of a mechanical same-session resume.

When the limit is hit, the runner kills the CLI, commits the worktree as wip(runner): salvage before teardown - outcome Unknown, pushes it as agent-studio/salvage/<runner>/<card>/<run>/fence-<n>/<sha>, and reports a non-terminal outcome. AGT-2861 added one automatic continuation round per delivery generation (RunTimeoutSalvageContinuationPolicy.MaxAutomaticContinuationRounds = 1). That round:

  • starts on the integration branch, not on the salvage. The prompt tells the agent to fetch the salvage ref and rebase it itself (RunContinuationCause.Timeout leaves StartsFromSalvage false);
  • pins a clean CLI context. The code comment says a salvaged worktree "leaves no resumable session behind";
  • appends a ## STEER note to prompt.md, so the prompt grows with every round.

A second timeout in the same generation escalates to 5e-escalated, and the reason names the salvage. An operator requeue then starts a fresh round with the same 90 minutes. The agent is never told that it has a limit. None of the five AGT-2955 transcripts mentions the time left.

Findings

  1. Files always survived. Every salvage patch shows up again with the same git patch-id in every later chain: fence 1 in four later chains, fence 3 in three, fence 4 in two, fence 6's commit in one. The only thing missing later is fence 6's temporary debug spec and instrumentation: fence 7 re-applied the e2e spec change alone.
  2. Continuing was the agent's job and depended on its prompt. Every round started on the integration branch. Each agent found the salvage by searching refs and SHAs quoted in its prompt, then used git cherry-pick (fence 6), a rebase (fence 4) or git merge --ff-only (fence 8). It worked all three times, but nothing in the platform checked it.
  3. The session never survived. There were five sessions and none resumed an earlier one. Each re-read a prompt of 24,660 to 51,036 characters made of appended session notes, review reports and STEER blocks. All the transcripts were still on the host, so the claim that a salvaged run "leaves no resumable session behind" did not hold here.
  4. Verification did not survive, and it used up the budget. Fences 7 and 8 spent 84 of 86 and 84 of 90 minutes rebuilding and rerunning suites that had already passed on the same tree. .agent-studio/project.yml declares 24 minutes for the backend suite alone; at load 27 to 39 on 12 cores it took longer. Both rounds found the same CLAUDE_CONFIG_DIR test failure on their own. Neither reached the evidence specs.
  5. In-flight diagnosis did not survive. Fence 6 was killed while it was instrumenting a 46,420-request storm. The next prompt called the failure "infrastructure", and fence 7 never picked up the storm again.
  6. Bounded continuation worked when it ran. The one AGT-2861 round (fence 4) delivered in 29 minutes. The AGT-2861 case log also records continuations of AGT-2858 and AGT-2859 that delivered in 44 to 62 minutes.
  7. The escalate-and-requeue loop has no brake. Once the one continuation was spent, two operator redeliveries each bought another 90 minutes at the same budget and got the same result. Together they used 176 minutes of coding slot, and the product diff did not change.

In total, the five rounds with transcripts used 380 minutes of coding slot and 608,168 output tokens. The two redeliveries account for 176 of those minutes and 49,283 of those tokens, and they produced no product change.

03 Alternatives

Each option is checked against the four failures above: lost session, lost verification, lost diagnosis, and a requeue loop with no brake.

A. Raise the host timeout

Set RUNNER_RUN_TIMEOUT_SECONDS to 9000 (150 min) for every run. It is one line of config. It would probably have let fence 3 and fence 6 finish. But every stuck or looping run would also hold a coding slot for 150 minutes. The agent still gets no warning, the salvage still arrives without a checkpoint, and a requeue still starts from zero. This option changes when the problem appears; it does not remove it.

B. Per-card budget only

Resolve the limit from card, project and operator settings and pass it in the run spec. Heavy cards such as frontend work with e2e evidence get 150 minutes; everything else keeps 90. This is cheap and targeted, but a round that runs out still loses its session, its verification state and its diagnosis, and the escalation loop is unchanged.

C. Budget, checkpoint and same-session continuation

Option B plus three mechanisms. First, a soft limit at which the runner interrupts the CLI and resumes the same session for a bounded checkpoint turn. Second, a continuation round whose worktree is prepared on the salvage and which resumes the captured session when the continuation ledger allows it. Third, a per-delivery allowance of three budget exhaustions: automatic continuations need measurable progress, and the third exhaustion becomes an operator decision. This addresses all four failures. It needs the same-session resume gate lifted for this path, so it depends on the parity scenario the runner code defers to T2/T3.

D. Take full-suite verification out of the round

Tell the agent to run targeted tests only and leave the declared routine suites to the platform gate, which already caches verdicts by exact tree SHA. This would have saved most of fences 7 and 8 and costs no runner work. It does nothing for fence 3 or fence 6, where the time went into real test-first work, and it does not stop the requeue loop.

04 Recommendation

Recommended default: option C, with D's verification rule as part of the checkpoint contract

A round should end with a checkpoint rather than a kill. The next round should start on the salvage in the same session. The platform, not the agent, should decide from measured progress whether another automatic round is worth its slot. The AGT-2955 evidence shows that the lost work is not files but context and verification, and only option C preserves both.

Budget model

  • Run budget. This is the wall-clock limit of one round. It is resolved in this order: an operator override on the card (audited, with a scope of "next round" or "this delivery"), then the card's runBudgetMinutes, then the project's default, then the host's RUNNER_RUN_TIMEOUT_SECONDS. The result is clamped to a host ceiling, RUNNER_RUN_BUDGET_MAX_SECONDS (default 14400). It travels in RunSpecDto and reaches DurableAgentProcess through the timeoutSeconds parameter it already has. The runner logs the effective budget and its source.
  • Soft limit. At 0.8 of the budget, and never later than 10 minutes before the hard limit, the runner interrupts the CLI and resumes the same session with a fixed checkpoint prompt. The checkpoint turn is capped at 10 minutes. In it, the agent stops new work and writes results/checkpoint.md: what is done, what is verified (command, result, and the tree SHA it ran on), the diagnosis in progress, and the next step. The runner types the round BudgetCheckpoint and salvages. If the CLI cannot resume, the prompt carries the deadline from the start and the hard limit salvages as it does today; the round is then typed BudgetExhausted.
  • Continuation. The worktree is prepared on the salvage commit through ContinuationBaseStore, as worker-loss rounds already are, so the agent no longer cherry-picks. The session resumes when the continuation ledger admits it: same provider, worktree path, clean-context identity and captured session present, and total tokens under the ceiling. Otherwise the round starts clean, with the original card prompt plus checkpoint.md as the handoff instead of the stack of STEER notes.
  • Verification rule. A continuation round reruns only commands whose inputs changed since the tree SHA recorded in the checkpoint, plus targeted tests for what it touches. The declared routine suites are left to the platform gate, whose verdict cache is keyed by exact tree SHA.
  • Progress. A round made progress if its salvage tree differs from its start tree, or if its checkpoint records a passing verification on a tree that had not been verified before. Fence 8 (same commit, no new verification) had none.

Operator decision at the third exhaustion

Budget exhaustions (BudgetCheckpoint or BudgetExhausted) are counted per card per delivery. The counter resets only when a delivery is accepted, or when an operator decision changes the budget or the scope. A plain requeue does not reset it, and neither does the night-shift infrastructure redelivery. Automation that redelivers after infrastructure failures must skip cards escalated for budget.

The card escalates to 5e-escalated with a typed gate item run-budget-decision in three cases: at the third exhaustion, after an automatic round with no progress, or after a checkpoint turn that wrote no checkpoint. The gate offers three actions:

  1. Raise the budget: 120, 150, 180 or 240 minutes, for the next round or for the rest of the delivery. The allowance grows by one round.
  2. Cut smaller: deliver the verified partial state named in the checkpoint as this card's scope, and create follow-up cards from its remaining steps through the Task API.
  3. Stop: park or archive the card. The salvage ref and SHA stay in the reason.

Retrying with an unchanged budget stays possible through /continue, but it needs a reason, is recorded as budget-retry-unchanged, and counts as an exhaustion. The gate also shows a rule-based suggestion with its numbers. If at least 60 % of the last round was spent in build and test commands, it suggests raise. If the diff keeps growing and the checkpoint lists more than three remaining steps, it suggests cut. After two rounds without progress, it suggests stop and re-plan.

What the card shows

The section belongs on the card detail, next to the run history. It shows the budget per round and where that value comes from; the exhaustions used out of the allowance; the total minutes in this delivery; one row per round with trigger, minutes, typed outcome, progress (diff size and newly verified commands) and a copyable salvage SHA; and one next-step line. The next step reads "Automatic continuation 2 of 3 queued, same session", "Operator decision required", or "Within budget".

Expected effect on AGT-2955 (inferred)

With these rules, fence 3 would have written a checkpoint at 72 minutes, including the pending build. Fence 4 would have resumed that session; it took 29 minutes even without the session. Fence 6's checkpoint would have recorded the storm diagnosis, and its continuation would have resumed that diagnosis instead of re-verifying. A continuation with no progress would have gone to the operator after at most one wasted round instead of two, together with the verification-share evidence that supports raising the budget.
