01 · Language policy

Public repository artifacts are English

Use English for every artifact that becomes part of a public repository or its public operating history.

Required: code identifiers and user-facing strings, source comments, documentation, Wiki pages, prompts, test names and messages, commit messages, branch slugs, issue text, and pull request text are English.
  • Keep quoted user input or fixture data in its original language only when the language itself is relevant to the test or behavior.
  • Translate existing non-English material when the task makes that material canonical or substantially revises it.
  • Prefer plain, direct language. Define project-specific terms at first use.

Public tone

Website copy, organization profiles, and public documentation use factual, neutral English.

  • Use claims that can be verified, such as Every run leaves evidence.
  • Do not use marketing adjectives, metaphors, or honest as a product adjective.
  • Do not describe a feature as the mechanism and do not position the product by contrasting it with chat.
  • State an open-source license as a fact. Do not present open source as a value claim.
  • Describe pipeline capability as Custom pipelines with multiple review steps. This wording does not assume prior pipeline knowledge.
  • Use the plural category statement Management layers on top of coding work.
02 · Diagram style

Apply the Agent Host Protocol diagram specification

Architecture diagrams use grids and whitespace, flat bordered boxes, thin SVG wires, and three defined semantic colors. Blue represents authority or the control plane. Teal represents execution. Coral is reserved for numbers and small labels.

  • Build self-contained, theme-aware HTML with no external fonts or runtime dependencies.
  • Keep labels as selectable HTML and use SVG only for connection lines.
  • Support reduced motion, responsive overflow, and both light and dark themes.

03 · Test conventions

Separate machine-dependent tests

Tests that depend on machine timing, host load, real child processes, real ports or sockets, live services, live workspaces, or performance thresholds must carry the xUnit trait [Trait("Category", "MachineBound")]. Put the trait on the class when every test in the class is machine-bound; otherwise put it on each affected method.

Do not use the trait to hide a fixable test. Prefer fake time, deterministic synchronization, temporary isolated resources, and mocked boundaries. Apply MachineBound only when the test intentionally exercises a real machine-dependent boundary.

Process- and timing-dependent Runner tests that remain useful in exact-subject Remote Review also carry [Trait("Category", "ReviewFlaky")]. This second trait does not replace MachineBound. A failing Review command is compared with the integration baseline and repeated in a fresh worktree without restored dependencies before it may charge a card. A clean repeat that passes is an environment result; a product failure requires a green baseline, a reproduced fingerprint, and evidence that the fingerprint is specific to the card. The quarantine policy remains an open delivery-chain decision.

The canonical routine .NET test command excludes MachineBound tests:

dotnet test --filter Category!=MachineBound

Run machine-bound tests separately in an appropriate environment when the change affects them, and report both commands and outcomes.

04 · Commits and branches

Follow the commit and branch naming rules

Commit messages are English and follow Conventional Commits. Describe the task intent and the delivered behavior, not a mechanical file list. Keep subjects concise and use a body when rationale or verification matters.

task/<slug>

Platform-owned branch for isolated task work. The slug is the normalized stable task key, for example task/agt-2237.

agent-studio/{results,salvage}/...

Remote result and salvage refs, namespaced by run attempt, fencing token, and immutable result SHA. Lease-loss salvage uses the quarantine namespace.

Ownership: the platform creates, commits, pushes, integrates, and cleans up managed task branches. Run agents must not create or switch branches, commit, amend, push, merge, rebase, or mutate remotes unless the individual task explicitly grants that authority.
05 · Evidence expectations

Store review evidence with the task

Put durable review artifacts under the task job folder's results/ directory. Evidence must let a reviewer connect the requirement, the implementation, and the verification without reconstructing the run.

All changes

Report changed files and the exact verification commands with outcomes. Store reports, logs needed for review, and generated artifacts in results/.

UI changes

Add relevant Playwright coverage and screenshots. Verify both themes and responsive states when affected. Persist review captures under results/.

  • Label task-evidence screenshot provenance in the filename with --real or --mocked. Use --composite for an explicitly documented composite. Documentation and marketing captures from the committed deterministic workspace use --pinned.
  • Prefer real-backend screenshots for UI acceptance. Mocked screenshots are valid when labeled and appropriate to the claim.
  • Ensure every linked image exists. Do not cite a path that was not preserved.
  • Documentation-only changes need link and diff verification, not a product build or Playwright run.
