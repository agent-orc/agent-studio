Recommendation

Make Task Server authority the only steering boundary. The engine reads bounded task and attempt facts and writes versioned intent. The server validates intent, selects eligible work, grants fenced authority and records the outcome. A daemon polls for work; it never owns the card's lane or acceptance decision.

Use many instances of one runner-host implementation. Coding and review are capability and slot configurations. A workstation is a runner host with local repository, Windows-toolchain and preview capabilities. Quality is shared pipeline library work. No separate Workstation Agent or Quality Host Agent belongs in this target picture.

The Operations Server proposed by W49 remains a host-operation backchannel: installation, health, bounded probes and lifecycle operations with Task Server permits. It must not create a second task queue, mint attempt authority or bypass claim admission. Daemon execution and task delivery stay on the Task Server bus.

These are logical daemon registrations, not one process per slot. The engine should address capability requirements and project access, such as a Linux toolchain plus repository permission, rather than a hostname. Adding a host registers an authenticated identity, capabilities, capacity and project grants; it does not rewrite tasks. Removal drains new admission, lets valid leases finish, then revokes registration. Abrupt loss expires authority and creates a bounded recovery decision. Existing project-to-runner assignment means class routing is still a proposed change (D11), not a current fleet guarantee.

Steering loop

  1. Observe. The target engine reads task revisions, dependencies, current attempt, prior settlement, host eligibility and unresolved incidents. Current external engine handlers only consume their claimed orchestration payload. Expand that read contract before claiming that the engine “looks at everything”. [EH] [E]
  2. Decide. Write lane intent, next-run model/prompt revision, dependency hold, explicit park, continue round or review request through the Task Server. The server accepts/rejects with a reason and current revision. That unified command receipt is proposed in D5/D6; today these operations use separate mutation endpoints. [TM] [TF] [F]
  3. Admit. A daemon registers and advertises capabilities; polls default to 5 seconds, with bounded connectivity backoff. Coding admission checks fresh CLI/provider capability, assignment, project access, free slots, load and project concurrency; preflight may require another poll before acquisition.   4. Execute. Claim returns fenced identity and execution specification. The runner persists local recovery state, prepares its worktree and invokes the CLI or review library plan. Pipeline control today

This section reconstructs the production path as of 11 October 2026. It answers four questions: which unit a runner receives, who orders the steps inside and between units, where review runs and what it reads, and who requests rework. Statements are observed in code at develop 691c812ae unless they say live (protocol answer, runner journal) or inferred.

Unit of work

A runner receives one attempt of one task. The claim returns the task key, a lease with lease id, attempt id, fence, authority epoch and expiry, and the run specification. The fence counter is kept per task and only increases. The worktree path is keyed by task (worktrees/<taskKey>), but its lifetime is the attempt: it is created at claim and removed after the result push is verified. [L] [A] [GW]

Order inside an attempt

The order is fixed in the runner: admission check, worktree on the authoritative base, project preparation from .agent-studio/project.yml, prompt, detached worker that runs the CLI through CodingAgentRunner, result commit with the fenced result ref and salvage ref, artifact upload, completion. The server sends no pipeline definition, and no gate runs on the coding host. [RT] [W]

Decisions between units

The monolith decides inside the request that reports the previous unit. The completion handler settles the run, moves the card to Auto Review and creates the review subject with a server-built plan. The report handler settles the verdict, applies the round budget and the follow-up policy, and then either opens a finding round, integrates and moves to Human Review, moves a failed delivery gate to Human Review, or schedules a review infrastructure retry. Background services complete the rest: the settlement reconciler every 30 seconds, the integration workers, and the operator sweeps that turn a ProductFailure in Human Review into a fix round. The Orchestrator Engine takes no part. [C] [RP] [FUP] [RB] [OSW] [MODE]

Review

Review is a separate claim by the review daemon, with its own lease and fence, against an immutable subject: repository, exact result SHA, source attempt, requirement and policy hashes, and a plan sealed at completion. The worker clones fresh, fetches the result ref and checks out the SHA detached; it checks the SHA before the commands, before each step and in its final proof, and the report handler checks it again. The coding worktree is never read. Agent aspects run read-only; tool commands compare against the merge base. Any review-capable registration may claim; today agent-runner-01 holds both roles. [EX] [V] [PLAN]

Rework

Since the Stable update of 10 October 2026, a blocking verdict on a card in Auto Review moves it to Ready in the same report request and appends the findings to prompt.md. Before that release, and still for a failed delivery gate, the card goes to Human Review and the operator sweep or an operator continue opens the fix round. In every path the next attempt is a new claim with the next fence. [RP] [OSW]

Provider comparison metadata contract (AGT-2972)

GET /api/v1/runners/{runnerId}/provider-comparison is a runner-scoped, read-only Task Server projection for an ambiguous provider probe. A principal with the required scopes but the wrong kind or runner ID receives 403. This endpoint does not command another host to run a probe or transfer a credential. It compares already advertised metadata from active hosts and active credential-registry records.

The path runnerId identifies the affected runner. A missing generation or unsupported shape/signature produces empty evidence.
200 response{"credentialIdentity": string|null, "comparison": object|null}. Provider fleet canary contract (AGT-2973)

The standalone Task Server owns credential-health admission and retry state. A runner negotiates credential-health-v2 before sending credentialHealthVersion: 2 and separate credentialHealth, serviceAvailability and healthOutcome fields. The provider-auth:<cli> keys and old schema remain stable. A runner principal bound to the route calls POST /api/v1/runners/{runnerId}/provider-canary/{provider}?instanceId=... before a real request. The response is {"allowed": boolean, "nextRetryAt": timestamp|null, "reason": "no-hold"|"cohort-held"|"canary-in-flight"|"canary"}. An allowed no-hold response permits the initial and normal budgeted real checks; canary forces a recovery check. The Task Server stores one owner and deadline for the affected service and binding circuits in the same SQLite authority that gates Coding and Review claims. Repeating the permit from its owner is idempotent. A failed or expired permit never authorizes a card as a canary; a fresh real success and later advertisement clear only matching held evidence. GET /api/v1/management/provider-health-items is management scoped and returns generation-keyed renewal or diagnosis items without secret values. This endpoint records operation intent and evidence only; host secrets and CLI execution remain with AGT-W63 custody and the runner host.

GET /api/v1/management/provider-renewals/{operationId} returns the current receipt and promotes a timed-out operation to cancelled before preflight or recovery-required after preflight.

POST /api/v1/management/provider-renewals/{operationId}/steps accepts allowlisted metadata steps in order: requested, preflight, awaiting-human, staged, installed, verified, retired, complete. Failure after preflight becomes recovery-required; it cannot be silently cancelled or retried as a new login. Verification needs a generation different from the expected one, the selected effective source, fresh real-request success and distinct Coding and Review runner observations of that same generation. Recovery of the old generation needs both units and a real request before cancellation. An installed operation whose deadline passes becomes recovery-required, but a later verified new generation may still advance through retired and complete; the deadline prevents new issuance, not recovery proof. Receipt fields and evidence references reject secrets, browser codes, raw shell commands and arbitrary payloads. Task Server never executes a provider login or receives credential values; the selected host owns local capture, protected installation, rollback, rebinding and unit lifecycle.

The invariant across these transitions is that an unverified local unit cannot produce success; a root-only rollback copy remains when a prior credential existed. A recovery failure stops affected units and preserves any copy and the recovery-required receipt. The host lifecycle is specified in the AGT-W63 renewal contract.

The Claude and Codex sign-in status routes accept an optional validated sshTarget for resumed polling after Studio restart; the sign-in dialogs send it on every poll, and a missing or invalid target leaves the receipt untouched instead of guessing the host ID. While the central receipt is installed or recovery-required, the host receipt finalizer runs under the original binding lock. A pending local unit leaves central proof pending; a host rollback yields recovery-required; only local verified state permits the separate two-unit real-request proof. This does not put an SSH command, token, or rollback path in Task Server metadata.

Credential runbook journal contract (AGT-2979, AGT-W65)

Task Server executes the versioned catalogue in runbooks.json, embedded at build time. Every platform step must be an allowlisted adapter opcode; an unknown step, an untyped predicate field or operator, an extra property, a receipt contract other than the ten listed fields, or a retirement without a later verification step rejects the catalogue. No route accepts or runs a command text. All routes require the existing management scope.
