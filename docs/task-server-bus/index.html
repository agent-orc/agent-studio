Task Server bus

The orchestrator writes intent to the Task Server. Runner hosts claim admitted work, execute it, and return fenced facts. The server settles authority and makes the next decision possible.

This companion makes the operator direction of 25 September explicit. It complements AGT-W49, Operations Server backchannel and AGT-W57, Delivery chain. AGT-W49 D1 to D4 and their existing decision receipt are preserved in their original files. New decisions start at D5.

Scope of the bus. A durable coordination contract over task state, attempts, leases, immutable result references, settlements and receipts. HTTP is the transport; polling and claims are consumption. This is not a claim that every event already belongs to one replayable broker. The existing AgentMessageBusStore is an observability stream within this larger contract.

Code baseline: local develop and task HEAD both resolved to 50b767f014386fc0b4c00d1bb9db8c554be72d0f. No remote fetch or deployment equivalence is asserted. Runtime journal evidence comes from the installed runner and is separately dated. The only repository additions are in this directory; reciprocal AGT-W49/AGT-W57 links and the documentation index row are publication work in I8, because this task explicitly forbids edits to existing documents elsewhere.

Alternatives

A. Task Server coordination

Persist intent and results beside task authority. Daemons pull work through fenced claims. Recover by reading accepted facts and replaying unfinished effects. Recommended: it extends the existing claim and attempt contracts.

B. Direct daemon control

The engine sends start, stop and review RPCs to selected hosts. Fast acknowledgement is possible, but an engine restart needs another durable command store and daemon reconciliation. This perpetuates the local/remote split.

C. Separate broker

Publish work to an external queue and replicate task transitions into it. Useful only if measured scale requires it. It introduces a second delivery boundary and a transactional outbox requirement without removing Task Server fencing.

Recommendation

Adopt A as the target contract. The engine proposes changes; the Task Server validates and commits them; a host discovers them on its next admitted poll. The engine never calls a daemon to start a card, launch review, or resume a CLI. Host maintenance may still use the Operations Server from AGT-W49, but it cannot mint execution authority or overwrite task outcomes.

Keep one authority per fact. Task intent belongs to Task Server mutations; attempt identity, fence and epoch belong to attempt authority; runtime observations originate at the owning host; integration belongs to platform pipeline steps. A timeline entry is evidence of an action, not permission to execute it.

Fleet

Proposed starting profile, not a measured deployment inventory: 2 or more general Linux hosts, each with one coding service identity and one review service identity; 0 to N specialist Windows hosts, with at least one when Windows-only work is admitted; 0 to N operator workstations, each an ordinary optional host. A review-only machine is allowed without becoming a new agent species. Begin with 2 coding and 2 review slots per general host, 1 coding and 1 review slot per Windows host, and 1 coding plus 0 review slots per interactive workstation. These are configurable ceilings, subject to measurement and load admission, not a throughput promise. The current runner defaults to 2 per role; role identities, roots and credentials are deliberately separate. S01 S02

The engine addresses a requirement set such as coding-executor, provider authentication, repository access and toolchains. Review adds review-executor, baseline comparison, dependency preparation, and any visual or failure-domain constraint. Do not invent a current hostClass field: class selection is proposed in D10. Production coding currently filters by project-assigned runner identity before capability admission. S03 S04

Adding a host means provisioning a scoped principal, registering a stable runner ID plus fresh instance ID, advertising capabilities and capacity, then joining the eligible pool. Removing one means drain admission, finish or explicitly reconcile its attempts, expire its capability freshness and revoke credentials. Neither operation rewrites task ownership; existing leases stay with their exact owner until reconciled. Project execution stays sequential by default. Extra hosts do not override project maxParallelism or isolated-worktree admission.

Steering

Lane moves, model and thinking-level edits, prompt changes, release gates and follow-ups are writes through Task Server APIs. Model routing must follow the model-routing policy; quota cannot lower its correctness floors. Edits affect the next admitted execution spec. They do not mutate an already executing CLI. A park is a lane decision, a dependency hold is a derived admission condition, and a stop is an attempt-specific directive. These must remain distinct.

The implemented remote path polls every 5 seconds by default, advertises capabilities every minute, and renews coding leases every 30 seconds. Transport failures back off linearly to six poll intervals, bounded at 60 seconds; with the default poll this is 5 to 30 seconds, plus request time. Coding requests a 900-second TTL, but the production authority clamps to 30–600 seconds. Always use the issued expiry. Claims also enforce available slots, host capacity, quota and capability checks; the review daemon adds load admission, default threshold 1.5 load per effective core. None is an exact scheduling latency guarantee. S05 S06 S07 S08 S09

Protocol boundaries

The production coding route is /api/runner/claim. The standalone v1 route is POST /api/v1/runners/{runnerId}/claims; its lease renew/release, completion, events and artifacts are under /api/v1/runs/{runId}/.... The runner client negotiates this choice. Production review already mounts v1 review routes. Mixing the standalone SQLite guarantees with the production JSON compatibility facade would overstate today’s bus.

S76 S77 S78 The standalone restart path marks active runs and leases process-unknown and blocks replacement without positive reconciliation. The production authority instead retains exact attempt leases across epoch rotation. These are different recovery policies to converge deliberately, not two interchangeable descriptions.

Engine implementation

The standalone orchestrator-engine/ already speaks only to the Task Server: it claims ReviewDecision, Council, PostProcessing, GateDispatch and CompletionJudge stages, reads PayloadJson/prior stage results, and posts a fenced action/output. Default poll is 2 seconds and lease request 120 seconds. S121 S122

That is narrower than the requested supervision loop. PostProcessingLoop currently returns a status marker; GateDispatchLoop evaluates gate statuses already in the payload. It does not launch a pipeline command on a host. The client exposes claim, stage completion and release, without a renewal call or a general task-intent API. Production prep/review services still own richer behavior in the backend. D5/I10 define the migration, rather than claiming the standalone engine already watches every bus fact. S123 S124 S125

Standalone review also persists the full report JSON/hash in a transaction and rejects replay with changed payload. Production SettleReview persists a narrower summary. Preserve the stronger semantics when converging the two, instead of weakening the standalone store. S126

Open decisions

Inherited decisions

The original AGT-W49 blocks retain IDs d1-architecture, d2-standard-deployment, d3-agt-2736 and d4-orchestrator-sessions. Its 25 September receipt selects new Operations Server, one-box Docker, expand AGT-2736, and Task Server session ownership; D3 also contains the operator’s uncertainty. This companion neither reopens nor silently changes those selections. Original receipt. Only D5–D13 below are new choices. Checked defaults are recommendations, not submitted decisions.

D5. Steering boundary

Current remote continuation is persisted and polled; local continuation/start still dispatches directly through TaskRunnerService to ProjectRunner. OrchestratorPrepHostedService also changes server state in-process. This is valid colocated implementation but not yet a separately deployable bus-only engine.

Bus consequence: I10, using I1 receipts; preserve mode guards and queued-versus-started responses.

D6. Intent ownership

Model edits, prompt append, pending intent and Ready promotion span several writes. Host slots, task mirrors and authority records describe different stages without one durable command identity. Duplicated delivery is safe only where an explicit replay key exists.

Bus consequence: I1 defines the command transaction and conflict response. Host slots remain disposable recovery journals, never task authority.

D7. Stop persistence

RemoteRunStopRequestStore is a ConcurrentDictionary. Restart between operator stop and renewal loses the request; lease renewal looks up by task key and returns the stored attempt ID without an explicit equality check at that call site.

Bus consequence: I2; do not use a park or a model edit as implicit cancellation.

D8. Review handoff

SettleReview persists terminal summary. The full ReviewReportRequest is held by an in-memory projection Channel; duplicate reports return without projection. The endpoint awaits integration; the delivery sidecar is atomic per write but best-effort and Advance is not cross-process compare-and-swap.

Bus consequence: I3 and I4; crash-window tests must cover settlement before sidecar and ACK before projection. Do not claim global exactly-once delivery.

D9. Outage authority

The journal shows a stop after its recorded stop-before time; the production heartbeat checks the deadline after a failed HTTP request. Standalone boot marks process-unknown, while production epoch rotation lets exact old leases drain.

Bus consequence: I5; state the intended parity between compatibility and standalone recovery. A new fence fences writes, not proof that an old process is dead.

D10. Runner-host fleet

Operator lean: the target requires many runner-host agents. Today production coding is assignment-aware; capabilities and capacity do not yet constitute a general project host-class selector.

Bus consequence: I6; default project concurrency remains one. A temporary host pin may narrow a pool without creating a new execution role.

D11. Workstation identity

Operator lean: remove the separate Workstation Agent. The workstation is a runner host on the operator’s machine, with local repository, Windows-tooling and preview-URL capabilities.

Bus consequence: I6 and I8; remove the separate role from target diagrams while preserving the AGT-W49 Operations Server boundary.

D12. Quality execution

Operator lean: quality work belongs in the shared pipeline library. Current RemoteReviewPlanBuilder already composes gates and aspects into ReviewPlanDto; review has separate daemon identity, credentials, workspace and slot budget.

Bus consequence: I9 and I6; credentials, failure-domain constraints and capability admission remain mandatory. No unbounded fan-out or new workflow engine.

D13. Feedback receipts

Timeline, task-card projection, OrchestratorLog and AgentMessageBusStore are separate readers and writers. Best-effort mirrors can disappear; a held prep decision can intentionally emit no row. The operator lacks a guaranteed causal chain for every request.

Bus consequence: I7; rendered claims require pinned screenshots, full-bleed figures and both themes for status/hierarchy findings.
