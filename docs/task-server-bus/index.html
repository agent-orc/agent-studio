Task Server bus

The engine decides. The Task Server persists and fences. Runner hosts claim work and return evidence through the same authority.

This sibling extends AGT-W49, Operations Server backchannel and complements AGT-W57, Delivery chain. It changes no runtime contract. W49 D1 to D4 remain in their original Dossier with their recorded receipt. D5 to D13 below are recommendations for the operator's next sight review, not approvals.

Alternatives

ModelConsequence
Task Server as durable work busDesired state, claims and outcomes share one authority. Workers pull. Restart recovery uses records and immutable result identities. Recommended.

The existing AgentMessageBusStore is an observation stream. It is not the work-claim queue. A bus in this Dossier means the Task Server's authenticated state and claim APIs plus durable records, not a new universal JSONL topic. [BR] [A] [DB]

Recommendation

Make Task Server authority the only steering boundary. The engine reads bounded task and attempt facts and writes versioned intent. The server validates intent, selects eligible work, grants fenced authority and records the outcome. A daemon polls for work; it never owns the card's lane or acceptance decision.

Use many instances of one runner-host implementation. Coding and review are capability and slot configurations. A workstation is a runner host with local repository, Windows-toolchain and preview capabilities. Quality is shared pipeline library work. No separate Workstation Agent or Quality Host Agent belongs in this target picture.

The Operations Server proposed by W49 remains a host-operation backchannel: installation, health, bounded probes and lifecycle operations with Task Server permits. It must not create a second task queue, mint attempt authority or bypass claim admission. Daemon execution and task delivery stay on the Task Server bus.

General LinuxAt least two independent hosts for continued service during drain; grow to N according to admitted queue demand. Each host has one coding registration and, where enabled, one review registration with separate instance identity and slot budget.
Windows toolingZero if no task requires Windows; at least two if Windows work requires host-loss continuity. A single licensed or local-only host remains an explicit single point of execution.

Quality roleZero dedicated Quality Host Agents. Review capability may be enabled on any eligible host, with its own slot ceiling and resource envelope.

These are logical daemon registrations, not one process per slot. The engine should address capability requirements and project access, such as a Linux toolchain plus repository permission, rather than a hostname. Adding a host registers an authenticated identity, capabilities, capacity and project grants; it does not rewrite tasks. Removal drains new admission, lets valid leases finish, then revokes registration. Abrupt loss expires authority and creates a bounded recovery decision. Existing project-to-runner assignment means class routing is still a proposed change (D11), not a current fleet guarantee.

Steering loop

  1. Observe. The target engine reads task revisions, dependencies, current attempt, prior settlement, host eligibility and unresolved incidents. Current external engine handlers only consume their claimed orchestration payload. Expand that read contract before claiming that the engine “looks at everything”. [EH] [E]
  2. Decide. Write lane intent, next-run model/prompt revision, dependency hold, explicit park, continue round or review request through the Task Server. The server accepts/rejects with a reason and current revision. That unified command receipt is proposed in D5/D6; today these operations use separate mutation endpoints. [TM] [TF] [F]
  3. Admit. A daemon registers and advertises capabilities; polls default to 5 seconds, with bounded connectivity backoff. Coding admission checks fresh CLI/provider capability, assignment, project access, free slots, load and project concurrency; preflight may require another poll before acquisition. Review has its own slot admission and required plan capabilities. No guarantee that a task starts within one poll interval. [O] [L] [D] [RD] [VR]
  4. Execute. Claim returns fenced identity and execution specification. The runner persists local recovery state, prepares its worktree and invokes the CLI or review library plan. Requested coding TTL defaults to 900 seconds and heartbeat to 30 seconds. This file-backed authority clamps the TTL to 30 through 600 seconds; the returned expiry controls execution. Execution authority ends at the server-issued boundary. [W] [O] [HB] [EX] [A]
  5. Return. Heartbeats renew, logs/artifacts carry evidence, and terminal outcomes carry immutable result identity. The server settles, integrates and transitions. The engine observes those facts on a later turn and writes the next decision. Replays reuse delivery identity, not the code-generation action itself. [C] [RP] [I] [OUT]

Coding delivery

  1. Task mutation and transition persist 2-ready plus the authored task specification. [TM] [TS] [T]
  2. The daemon calls POST /api/runner/claim. Assignment, dependencies, access, fresh capabilities, capacity and preflight can refuse it without moving the task. [D] [L]
  3. Authority acquires the run, the server moves to 3-in-progress, and returns the lease and RunSpecDto. Claim replay can repair the move; acquisition and filesystem lane movement are not one transaction. [A] [L] [W]
  4. Heartbeat renewal and fenced log ingestion continue while the runner owns authority. [HB] [LG]
  5. The runner platform commits/pushes the immutable result ref and records manifest identity. A failed push is not durable delivery. [RT]
  6. POST /api/runner/completion validates envelope/authority and settles the run. Successful coding delivery moves through 4-auto-review and creates a review attempt. Stopped, blocked, missing-envelope and infrastructure outcomes follow other branches. [C] [A]
  7. The review daemon claims the immutable subject, not a mutable branch name. [V] [RD] [EX]
  8. The report endpoint settles the tested SHA and applies the delivery gate. Pass alone is not proof that the code is integrated; the gate also handles an attributed integration-branch defect. [RP] [I]
  9. RemoteDeliverySettlementStore records IntegrationPending, the coordinator runs integration, then advances IntegrationSettled. The resume service re-enters only for the matching current generation. [S] [I] [MERGE] [GATE] [R]
  10. The normal continuation moves to 5-human-review; the acceptance rail can later complete the card. Integration errors stay explicit. This figure stops at integrated plus handoff, not at a fabricated human approval. [R] [RP]

Review attempt

  1. CreateReviewAttemptRequest names source run, repository, expected result SHA and policy/requirements hashes. [C] [AT]
  2. Registration supplies runner/host/instance; capability advertisement and review slots govern review-claims. [V] [VR] [RD]
  3. A claim returns ReviewAttemptDto and isolated resource namespace/ports. No slot means no work lease. [V] [AT] [LIFE]
  4. RemoteReviewExecutor materializes the exact subject and executes the supplied plan. A review command carries step/aspect, execution kind and provenance; the target shared-library contract formalizes version/digest (D13). [EX] [RP] [PLAN]
  5. The executor renews with attempt, executor, instance, lease, fence and epoch. A narrowly validated /reclaim can re-fence the same detached worker after handoff; it is not carte blanche to replay expired reports. [EX] [V]
  6. Worker output produces command exit/timing data, environment attribution, verdict citations and artifact hashes. [EX] [RP]
  7. TryValidateReportLease plus SettleReview reject wrong authority or subject; the endpoint normalizes review verdicts before settlement. [RP] [A]
  8. The same settled delivery key returns Duplicate without rerunning integration or evidence projection. That prevents duplicate side effects but exposes a crash gap if the first projection was never durably queued (D8). [RP] [Q]
  9. ReviewInfra may schedule a bounded delayed successor; pass/gate outcomes continue delivery. The evidence worker writes the report files separately, and AutoReviewDeliveryResumeService resumes matching settlement checkpoints. [RP] [Q] [R]
  10. /cleanup records the executor cleanup result under its authority. A missing cleanup receipt remains diagnosable; it does not mint a new review verdict. [V] [EX]

Target review-step bus message: request identity = task + source run + review subject + expected SHA + requirements/policy hashes + library step id/version/digest + required capabilities. Claim adds attempt/lease/fence/epoch/host/instance, slot and resource namespace. Report adds actual SHA, command evidence, cited verdict, hashes and stable delivery key. Cleanup closes resource ownership. Existing DTOs already cover most identities; the universal versioned library-step envelope and shared registration are the D13 extension, not current wire fields.

Operator continue round

  2. RecordUserFollowUpAsync appends the authored note; extend mode adds prompt history. Remote admission queues pending-intent.json, then promotes to Ready. These are multiple writes; latest-wins may replace an earlier pending note. [F] [PI]
  3. The endpoint responds 202 for queued remote work. It does not start a local CLI merely to acknowledge the user. [TR] [F]

  5. Renewal carries the directive back. A stop directive differs from lease loss: the holder retains authority to salvage and complete. [HB]
  6. The runner reaps its worker, salvages and completes with Stopped. The completion handler routes a follow-up round and preserves the continuation base. [RT] [C]
  7. Subsequent claim admission still checks the lease and project slot, so moving a lane alone cannot authorize an overlapping run. [L] [A]

Outage and replay

Worked incident: 24/25 September 2026 tunnel outage. The operator supplied the incident and its heartbeat-loss, expiry, quarantine and restarted-run sequence. The checkout contains no dated incident packet that proves exact times, affected task keys, host counts or loss duration. The following is a code-checked reconstruction of those phases, not measured incident telemetry. Earlier tunnel analysis in Runner link supplies architectural context only.

  1. LeaseHeartbeat marks authority uncertain on transient network errors. The absence of an acknowledgement is not yet proof of takeover. [HB]
  2. It stops at the last known expiry minus the uncertainty margin if the route stays unavailable. With default 30-second heartbeat, this boundary is one renewal interval before expiry; use the actual lease grant, not an assumed outage duration. Definitive denial may stop sooner. [HB] [O]
  3. RemoteTaskRunner preserves coding work in a generation-specific quarantine ref after lease loss; a failed quarantine push retains local worktree evidence. Review recovery uses its persisted slot/worker evidence, not a coding result branch. [RT] [EX]
  4. Authority rejects expired/stale writes. Server claim/recovery can reconcile interrupted progress, but moving the card does not make the old worker's output deliverable. [A] [L]
  5. After route restoration, re-registration advertises capabilities and positively present attempts. The current ReAdoptRunnerAttempts implementation can reopen an expired lease if its state is still Leased and task, executor, host, lease id, fence, epoch and lease-instance identity match. Expiry alone is recoverable here. A terminal, superseded or replaced generation fails adoption. This is a new server confirmation, not autonomous offline renewal. [V] [ADOPT] [CLIENT]
  6. Daemon restart/poll reconciliation reads persisted slots and finalization state. A durable worker can be adopted only within the authority rules. Review reclaim is explicit and re-fenced. [D] [RD] [EX] [CF]
  7. Replay accepted delivery payloads with their existing idempotency keys, after authority reconciliation. A report already settled returns Duplicate. A generation that the runner has already rejected and quarantined must not be presented as a fresh success without an explicit recovery path. Distinguish that local disposition from an expired lease that the server can still re-adopt. [OUT] [CF] [RP] [HB]
  8. Recoverable tasks restart through a new admitted claim, new attempt and fence. Quarantine can supply an explicitly chosen recovery base, not an automatic merge. This is the operator-reported “restart of the runs”, not proof that the old CLI continued. [L] [C] [RT]
  9. If review was already settled before the outage, recover its matching delivery sidecar with AutoReviewDeliveryResumeService instead of paying for another review. D9 adds a repeatable drill and a correlated recovery receipt. [R] [S]

Incident evidence still needed for a measured replay: tunnel/service logs with UTC bounds, last granted expiry per attempt, old/new attempt and fence identities, quarantine ref/SHA and push status, rejected writes, daemon restart/adoption records and final lane/integration receipts. I5 creates a deterministic outage drill; it must label synthetic timings as drill data and must not backfill invented historical facts.
