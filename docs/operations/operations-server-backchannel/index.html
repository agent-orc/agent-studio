Operations Server backchannel beside the Task Server

A decision boundary for operations used by several frontend products and host fleets. The Task Server remains the durable task authority; the proposed Operations Server brokers executable capabilities without becoming another task store or a browser session host.

Key statements

Observed: no current process is both safely reachable from other containers or the LAN and able to serve the full Studio route surface.

  • The route migration changed the size of the problem, not its shape. AGT-2755 to AGT-2758 delivered all 268 Task Server-classified target handlers. The remaining architectural mismatch concerns executable operations, browser security, and deployment boundaries.
  • Task truth and executable operations need different authority. Tasks, runs, reviews, workspace identity, orchestration state, leases, and lane transitions stay in the Task Server. File, Git, CLI, launcher, dossier, and host-control work belongs behind a separate operations boundary and executes on a declared host.
  • The Connector remains valid. Its exact loopback Host and Origin checks, CSRF session, allowlisted routes, denial paths, credential injection, and atomic upstream selection remain the correct local-browser edge. It should not be relaxed into a general LAN service.
  • The recommended target adds one runtime role. A new Operations Server is a browser-independent service. Frontend backends and Operations Agents authenticate as scoped principals. Browsers never receive its bearer credentials and never send cookies directly to it.
  • Deployment changes wiring only. Workstation, one-box Docker, and distributed WireGuard profiles use the same logical components and contracts.

01 Current system

The repository contains several valid process shapes at once. They are profile-dependent and should not be read as one production chain. The local monolith is still the broad compatibility backend. The distributed preview adds independent Task Server and Engine services. The Connector is the approved local edge for the remote Task Server topology. The current studio-bff is network-addressable inside Compose but only fronts /api/v1 and /hubs.

02 Ownership boundary

The split is not based on whether a route sounds operational. It is based on authority and side effects. Durable product truth stays with the Task Server. A command that touches a host, checkout, toolchain, process, local secret, or OS integration belongs to the Operations Server and executes through a declared Operations Agent.

Orchestration sessions stay in the Task Server

A session is durable product state and can lead to task decisions. Moving it to the Operations Server would create a second orchestration truth. The executable model call may be dispatched through the Operations Server, but context, budget, actor, accepted response, and resulting transition remain Task Server records.

Two services are justified by failure containment. A stopped Operations Server prevents new executable operations but does not make cards, history, or accepted results unreadable. A compromised Operations Agent cannot mint a run permit or move a lane. The Task Server can be backed up and restored without carrying host toolchains and workstation secrets; the Operations Server can scale and roll with the fleet without becoming the system of record.

03 Target system

The Operations Server is a central API and coordination service, not a remote desktop backend. It publishes a versioned operation catalogue, accepts authorized commands, selects an eligible Operations Agent, tracks a bounded attempt, and returns typed events and artifacts. It has no Angular application, no recovery UI, no browser cookie authentication, and no implicit access to a project filesystem.

04 LAN and security

The LAN problem disappears when browser security and service authentication stop being the same boundary. A browser talks only to its selected frontend edge. The edge validates Origin, Host, session and CSRF, then calls the two central services with audience-bound, server-side credentials. The Operations Server accepts principals and permits, not browser cookies.

Connector inheritance

Connector decisionTarget treatment
Explicit route ownershipKeep. Extend the inventory with an owning service, operation definition, allowed edge, and required principal scope. No broad local or remote fallback.
Exact denial pathsKeep. Unknown routes, unclassified operations, browser Authorization headers, foreign cookies, stale protocol versions, untrusted forwarded headers, and mismatched origins fail before dispatch.
Session-bound CSRFKeep at browser edges. The Operations Server itself has no browser session and therefore no CSRF cookie contract.
Credential injectionKeep and split. The edge holds independent Task Server and Operations Server audiences. A Runner or operations credential never authorizes a Studio route.
Atomic upstream generationKeep per service. Task Server and Operations Server may switch or fail independently. A partially sent mutation is never retried against another authority.
Public-demo profileKeep separate. A public demo edge receives no Operations Server credential and exposes no executable operation. Read-only sample projections are not a mode of the production Operations Server.
Fixed loopback authority and OriginKeep for the Connector. LAN and Compose use a different browser edge profile with explicit HTTPS origins; they do not loosen the decided local Connector profile.

Required denials

  • A direct browser request or cookie presented to the Operations Server returns unauthenticated; the service does not opt into credentialed CORS.
  • A valid Studio edge principal without the requested operation scope returns forbidden.
  • A valid Operations Agent credential cannot read arbitrary task data, move a card, issue a lease, or call another agent's control route.
  • A task-linked command without a current permit, or with a stale task fence, is rejected before agent selection.
  • An operation outside the agent's declared roots or capability version is rejected before execution.
  • The public-demo profile has no credential capable of submitting an executable operation.

The existing Phase B gates remain prerequisites for network exposure: scoped principals, protocol negotiation, route classification, negative authorization tests, exact listener and firewall evidence, frozen migration inventory, backup and restore proof, sole-writer proof, detached-Studio rehearsal, and fallback. An Operations Server adds equivalent agent-enrollment, permit, Origin-edge, and denial-path gates; it does not waive the Task Server gates.

07 Recommendation

Alternative D with a staged start

Create a distinct Operations Server and an outbound Operations Agent protocol. Keep the Task Server as the durable authority and keep orchestration sessions there. Retain the Connector as the loopback Studio edge and first workstation-agent adapter. Use studio-bff as the browser edge for one-box and LAN deployments, not as the home of native operations.

This recommendation deliberately changes the current three-component target architecture. The existing document says shared contracts are not a fourth runtime product. A separately deployable Operations Server would be a fourth runtime component, so approval requires an ADR and a coordinated update to the target architecture. It must not be introduced through an incidental Connector configuration change.

The recommendation preserves the P0 to P3 investment. Durable task, host, operations and insight projections stay in the Task Server. Only executable commands and host capability state move behind the new boundary. Existing legacy paths can remain compatibility aliases at the edge while ownership changes behind them.

Failure contract

FailureRequired behavior
Frontend closesTask Server, Engine, Operations Server and agents continue. Another authorized client sees the same durable state.
Operations Server unavailableNo new executable operation is admitted. Existing agents stop at their lease boundary, preserve bounded evidence, and replay idempotently. Task and review history stays readable.
Task Server unavailableOperations Server accepts no new task-linked work and cannot mint substitute authority. Standalone host maintenance requires an explicitly separate break-glass scope and audit path.
Operations Agent unavailableThe attempt becomes unreachable or timed out. Reassignment requires fence advancement and positive no-overlap evidence when the operation can mutate state.
Edge unavailableBrowser access stops; backend services and agent work continue. No bearer has been stored in the browser.
