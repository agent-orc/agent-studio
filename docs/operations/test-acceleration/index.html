Key statements

  • One review verification on the Linux runner takes about 131 minutes. Tests are 88 % of that, and the backend suite (OrchestratorApi.Tests, about 8,980 tests) alone is 68 %, 85 to 93 minutes.
  • The median backend test takes 0 to 1 ms. About 4 % of the tests carry 97 % of the test time. Almost all of them are HTTP endpoint tests that boot a full host.
  • The same trivial test took 6 s in one run and 54 s in another. Six backend suites ran at the same time on 12 cores (load 28 to 42). Contention dominates the tail, and the flag that was meant to limit parallelism (-p:ParallelizeTestCollections=false) has no effect on xUnit v2.
  • A failing test triggers a rerun of the whole 85 to 93 minute suite.
  • Playwright runs 499 spec files on one worker, with 365 fixed sleeps (about 5 minutes in total). Spec runs compile the backend (dotnet run) and the frontend (ng serve) first.
  • No timing data is persisted anywhere. Measuring comes first, in both tracks and in the new Quality Studio aspect (QS-123).
  • Target: review verification from 131 to 20 minutes or less, backend suite under 15 minutes even under contention, compile-free Playwright starts, details in §6.

§3Slow tests as a signal of slow code

Status 2026-10-11: Hypotheses with partial evidence; B5 measures.

A test that boots the application and makes one request should take tens of milliseconds. The slowest endpoint tests take 40 to 58 seconds under load and still several seconds without it. Part of that is contention, but each boot also runs the production startup path: hosted services, index warm-ups, scans of the task workspace, Git state indexing. Everything that makes a test host slow also makes deploys, restarts and the developer loop slow.

Related production evidence from the same day: the board card list took 94 s because a duplicate card id made every Git state index run fail (fixed by data; AGT-3042), and it still took 12 to 18 s afterwards because it serialises 7 MB for 235 cards behind a single-slot read gate (AGT-3043). The Git facts architecture is handled in its own Dossier (AGT-3044).

What the backend track measures and fixes on the code side

  • Startup budget: time from host build to first request served, production and test profile, broken down by hosted service. Hosted services that are not needed for a request become lazy, or can be switched off in a test profile without weakening what the test checks.
  • Request budgets: endpoint latency measured in the existing task-operation-timing log (budget 30 ms today, often exceeded by 100× and more). Slow endpoint tests point at the endpoint; fix the endpoint.
  • Process spawns: Git and CLI spawns on request paths are a known cost on Windows (70 to 100 ms each plus antivirus scan). Zero spawns on request paths is the rule.
  • Profiling: dotnet-trace / dotnet-counters on the slowest test classes, uncontended, to separate test setup cost from product cost.

§4Frontend: Playwright, Vitest and test strategy

Status 2026-10-11: Diagnosed statically, not measured. Levers in the frontend track (AGT-3050).

Playwright today

  • frontend/playwright.config.ts:44-46: workers: 1, fullyParallel: false, retries: 0. 499 spec files with about 1,317 tests run strictly one after another. Largest folders: task-detail 111, board 97, project 66, chat 28, layout 26, system 24.
  • No webServer, no globalSetup. The devBackend fixture (frontend/e2e/fixtures/dev-backend.ts, used by 60 specs) starts the backend via dev-lifecycle.sh → api.sh → dotnet run (source build, start timeout 420 s). The frontend is ng serve, a JIT development build, started by hand by agents.
  • waitForTimeout 365 times, about 297 s of fixed sleeping. 991 page.goto, 129 page.reload.
  • trace and video are recorded for every test (retain-on-failure).
  • Perf measurement loops sit in functional specs, for example e2e/system/crash-recovery-prompt.spec.ts:55-78 (warm-up plus 100 samples).
  • The suite frontend-e2e is marked machine-bound with an expected 900 s in .agent-studio/project.yml; gates do not select specs by changed files.
  • A static server for prebuilt bundles already exists in the devspace root: serve-prebuilt-frontend.mjs (serves dist, proxies /api and /hubs). It is not available inside the repository.

Angular unit tests today

  • Vitest via @angular/build:unit-test (angular.json:116-125), 162 spec files, about 75,700 lines.
  • Gate command test:ci = ng test frontend --watch=false --progress=false --coverage; build target frontend:build:development, so every run compiles the app plus specs and computes coverage. About 6 minutes.
  • ng test was red because of a disabledReason type error; if that is still the case, the suite gives no signal at all.

Better test strategy

The frontend has 1,317 browser tests and 162 unit spec files. Much of what the browser tests check is UI logic (a badge appears, a panel opens, a field validates) that does not need a real browser, a real backend and a full app load. The strategy shift:

  • Move UI-logic checks down to component tests (Vitest with Angular Testing Library or TestBed, services mocked). A spec that only asserts rendered state after a mocked API call is a component test.
  • Mocked-API Playwright project with contract fixtures (page.route, already used in 287 places): no backend start, safe to run with parallel workers.
  • Real-backend flows stay in Playwright, run on prebuilt servers and isolated workspaces, sharded.
  • Selection by changed area: map frontend/src/app/<area> to e2e/<area> and to component specs at review time; full run on a schedule (decision D1).
  • Signals of slow frontend code: specs that need long waits often wait for slow rendering or change detection. Where a wait hides a slow component (large lists without virtualisation, missing OnPush, heavy computed state), fix the component.

§7Decisions

D1 · Selection by changed files at review time (P5, F9) — decided 2026-10-11

Robert decided to put batch verification live now ("Das Konzept jetzt umsetzen und direkt deployen"). Per card, the review runs the model review, the build and the tests selected for the changed files and areas; the full suites run once per batch on the combined candidate and before every release. Implementation: AGT-3052 (backend, look-ahead planner, LLM batch advisor) and AGT-3053 (UI and settings). Until it is deployed, deliveries are integrated through an operator fast path that imitates it: independent model review per card, affected tests on the merge result with develop, one merge per card.

Rollout of batch verification on Agent Studio (after AGT-3052 is deployed)

  1. Quiet window: no promotion gate running, Dev checkout clean and without index.lock (the batch publication fast-forwards the checkout that holds develop).
  2. List the review attempts of the cards in 4-auto-review: pending ones are replanned by the settings PUT; leased ones keep their full-suite plans and integrate per card; the five attempts stopped on 2026-10-11 (workers killed) are re-created so they get the cheaper per-card plan.
  3. PUT /api/projects/Agent%20Studio/batch-gate with enabled: true, scope: code, planner: look-ahead, minimumSize: 2, maximumSize: 4, overlap: separate, reviewTestLevel: work-package, gateTimeoutMinutes: 150, advisor.mode: advise.
  4. Watch /state, /report and the board panel for the first two batches: published SHA equals the verified remote SHA, every member carries a batch integration record, red batches halve to the culprit.
  5. Record real batch pass rates in the report; they replace the D10 proxies (per-card gate green 57.9 %, four-card proxy 32.4 %). Raise maximumSize towards 6 and switch the advisor to enforce only when the pass rate supports it.
  6. Rollback: enabled: false or scope: documentation; the running batch is abandoned and members fall back to the per-task gate on the same immutable SHA.

Until then the review plane runs with three parallel reviews instead of six (Stable AutoReviewQueueAdaptiveParallelism, baseline 3, no raise), because six concurrent full suites on 12 cores slowed each other down (§1, quiet-host reference points). The planner and advisor move into the Orchestrator Engine with the engine programme (AGT-3055 after AGT-3059, decision D14).

D2 · Production bundle for end-to-end tests (F2) — decided 2026-10-11

The operator follows the recommendation: a dedicated e2e build configuration only where specs rely on development helpers, otherwise the production bundle. The frontend track (AGT-3050) checks the specs and applies the rule.

Option A: e2e runs against the production build (what users get, fastest to serve; development-only helpers are unavailable). Option B: a dedicated e2e build configuration (production optimisation plus test hooks). Recommendation: B if specs rely on development helpers, otherwise A.

§10Reporting protocol

  • Each track reports after every applied lever, not only at the end of its run.
  • A lever counts as done only with a measured before → after and its source (log or report path, host, number of concurrent suites at that time). Without a measurement it stays part.
  • The backend track writes only <section id="backend-track">, the frontend track only <section id="frontend-track">. Neither edits §1 to §7, the other track's section or workbench.json. Both tracks run in parallel; this keeps their commits free of conflicts.
  • New ideas go into the track's findings list with an ID suggestion (B11, F13, …). The operator moves accepted ideas into §5.
  • A run that cannot finish its scope leaves the remaining levers open with a note and the next step.
