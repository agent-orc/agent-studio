# Commit / Push Doctrine

## Headline

**The platform owns the commit boundary. Models execute work; the platform records it.** Every coding agent that runs under Agent Software Studio produces a working tree, never a commit. The runner decides when work is "done enough to record", composes the commit message, stamps the resulting SHA onto the job, and (where configured) pushes. The CLI never speaks for itself in git history. That separation is the difference between a workbench and a hopeful prompt.

## Why

- **One state machine, one author of git history.** Letting the CLI commit splits authority over the same tree between the CLI's internal heuristics and the runner's lifecycle policy. Two writers, one branch: drift is guaranteed.
- **The commit must align with the lifecycle transition.** A commit only makes sense at `3-progress -> 4-auto-review`, when the runner has *also* decided this run reached review. A CLI committing mid-run, on its own clock, breaks that alignment.
- **The recorded SHA must be the one stamped on the job.** `JobInfo.Commit` (Sha, message, file list, timestamp) is the durable evidence the detail view, the run timeline, and the per-run change set all read. If the CLI commits and the runner later commits an empty diff, the stamp lands on the wrong SHA.
- **Workers never own branches.** Coding tasks run in platform-owned `task/<id>` worktrees; only the platform creates, pushes, integrates, and cleans them up. A CLI that "tidies up" by branching, switching, or amending breaks the assumption every other layer was written against.
- **Auditability for the user.** A deterministic candidate gate records the exact manifest and decision before staging. Codex `gpt-5.4-mini` then provides additive semantic review and the commit message through `prompts/runtime/commit-message.md`.
- **Clean separation for marketing and onboarding.** "Models do work, the platform records work" is one sentence a new user can repeat back. Anything more nuanced is a leaky abstraction.

## How it works

The commit and push flow today lives in `TaskTransitionService.MoveAsync` ([backend/Services/Tasks/TaskTransitionService.cs](../../../backend/Services/Tasks/TaskTransitionService.cs)):

1. The runner finishes a CLI execution. `RunCompletionPolicy.ShouldMoveToReview(execution.Status)` ([backend/Services/Runner/RunCompletionPolicy.cs](../../../backend/Services/Runner/RunCompletionPolicy.cs)) returns `true` only when the status is `completed`.
2. `ProjectRunner.OnCliFinished` (see [backend/Services/Runner/ProjectRunner.cs](../../../backend/Services/Runner/ProjectRunner.cs) around the `RunCompletionPolicy.ShouldMoveToReview` call) invokes `_transitions.MoveAsync(jobId, TaskStates.AutoReview, ...)`.
3. Inside `TaskTransitionService.MoveAsync`, the auto-commit guard fires only when **all three** are true: the job is leaving `3-progress`, entering `4-auto-review`, and the project's `ProjectSettings.AutoCommit` flag is on.
4. `GitService.AutoCommitAsync` ([backend/Services/GitService.cs](../../../backend/Services/GitService.cs)) runs:
   - `git status --porcelain` -> if clean, returns "nothing to commit" (soft skip, no error).
   - The commit candidate gate enumerates every dirty path and exact content hash before staging, runs the built-in scanner plus any configured Quality Studio/Gitleaks adapter, and persists `results/commit-candidate-gate.json`.
   - High-confidence secret or private-key findings block. Root scratch and unrelated paths are recorded and excluded. Other suspicious artifacts pause unless the operation carries explicit operator review.
   - Coding-run add-all semantics are allowed only after the platform verifies the linked worktree and expected `task/<id>` branch. Direct develop, legacy, and unknown paths require explicit task-owned pathspecs.
   - `GenerateCommitMessageAsync` runs Codex `gpt-5.4-mini` against the candidate manifest, diff summary, task intent, and scoped diff. `COMMIT_REVIEW: SUSPICIOUS` pauses the commit; model output never overrides a deterministic block.
   - Falls back to `chore: snapshot for review (<N> files changed)` if the LLM hiccups.
   - The platform stages only the inspected manifest paths, verifies staged blob IDs against the manifest, and commits with the same explicit path list. A concurrent file cannot ride along.
   - The commit body records task ID, runner ID, and gate decision provenance.
5. The folder is moved to `4-auto-review` and the resulting SHA, message, file list, and timestamp are stamped onto `JobInfo.Commit` / `JobInfo.Commits` via `_mutations.SetJobCommitOnFolder`. The detail pane and run-timeline endpoints read this stamp.
6. Per-project `AutoCommit` is a boolean setting ([backend/Services/ProjectSettingsService.cs](../../../backend/Services/ProjectSettingsService.cs), `PUT /api/projects/{name}/auto-commit`) so a user who would rather stage commits manually can keep the rest of the lifecycle automatic.
7. Per-project `AutoPushStrategy` controls when stamped commits are pushed:
   - `never`: the operator pushes manually.
   - `on-completed`: push only after a job reaches `6-completed`, meaning it has passed review.
   - `always-immediate` (default): push immediately after auto-commit and again on completed as an idempotent backstop. Remote durability is the default; review findings produce follow-up commits instead of leaving history on one machine.
8. Completed pushes use `GitService.PushShaAsync`, which runs `git push origin <sha>:refs/heads/<targetBranch>`. The sequential completed-job path uses `main`; the parallel worktree path passes `task/<id>` before integration so the task branch is durable on `origin`. It first checks whether the SHA is already an ancestor of the remote branch, skips if so, and relies on normal git fast-forward rules. It never force-pushes. When both `develop` and `main` exist, the direct `main` path fails closed unless the candidate is the exact tip already published on `develop`; raw task and delivery SHAs must go through the ordered develop-then-main integration path.
9. The completed push runs off the request path. The move to `6-completed` enqueues a snapshot on `CompletedPushQueue` (instant, non-blocking) and returns; `CompletedPushWorker` drains the queue and performs the `git fetch` + `git push` on a background thread. The push was previously awaited inline, so a "move to complete" took 2-3 s on the network round-trip; the SHA is immutable, so the deferred push is always still correct.
10. `CompletedPushBackstopHostedService` sweeps `6-completed` every 15 minutes and retries completed-job SHAs that are not on the remote. This covers missed transition triggers, backend restarts, and anything still queued when the worker shut down.
11. Workspace evidence commits follow the same durability rule. `WorkspaceArtifactCommitService` enqueues every successful artifact commit on `WorkspaceArtifactPushQueue`; `WorkspaceArtifactPushWorker` pushes `HEAD` to `origin/main` off the run path and retries transient failures with bounded exponential backoff. A 30-second timeout promotes later attempts to the 600-second catch-up budget, pushes are single-flight per repository, and a spent budget raises `workspace-repository-push-failed` with the ahead count. `WorkspaceArtifacts:AutoPushEnabled` defaults to true. The full path classification, maintenance values, hourly tracked sweep, and recovery procedure live in [the workspace repository lifecycle](../workspace-repository-lifecycle.md).
12. Backend-owned mutations of tracked project files use `ManagedRepositoryMutationService`. It holds a per-repository gate across the write and exact-path commit, refuses a target path that was already dirty, restores the declared paths to `HEAD` when the commit fails, and queues the full commit SHA plus its checked-out branch on `WorkspaceArtifactPushQueue`. This is the non-task counterpart to the runner commit boundary for discovery keys, lifecycle receipts, content-metadata companions, and similar service writes.
13. A platform-owned commit is not considered remotely durable until verification reports no commits ahead. Final workspace, task, and integration push failures emit the typed `managed-repo-push-failed` operator-feed event with repository, branch, status, and error context; later commits and backstop workers retry pending history.
14. Project Overview renders the managed `main`, `develop`, and `task/*` tracking branches from the git inventory. `ahead == 0` is the pushed state; a positive ahead count is shown as unpushed, with a subdued warning above 50 commits.

The commit-message template is editable in [prompts/runtime/commit-message.md](../../../prompts/runtime/commit-message.md) and is the single source of voice for every commit the platform produces, regardless of which CLI did the work.

## Branch boundary

Coding tasks use an isolated, task-owned worktree on `task/<id>` even in the primary sequential slot. The platform commits there, pushes the task branch with retry, then serializes integration into the configured work branch. A failed task-branch push is visible as the Warn `task-branch-unpushed` outcome issue; branch cleanup runs only after integration.

Interactive operator edits may still exist directly on `develop`. Read-only tasks, legacy repositories, and unknown recovery paths may also lack a task worktree. Those paths never receive an implicit add-all commit: the platform must capture and supply the exact reviewed pathspecs, including for an operator-confirmed crash-recovery item, or leave the changes dirty for attribution. A file that appears after the pending recovery manifest was shown remains dirty and cannot join that snapshot.

The boundary is the same in both modes: worker CLIs do not create branches, switch branches, merge, commit, or push. The platform owns those operations. PR-shaped review remains a future integration strategy; the current implemented path is direct merge plus visible conflict or unpushed-branch outcomes.

## What models / CLIs should leave to the platform

Worker prompts use a calm ownership rule: please do not commit or push yourself; the platform commits after review. If a worker still creates a normal linear commit, that is recoverable bookkeeping drift. The runner shows an Info finding and folds the commit back into the platform commit where safe. If cleanup cannot be proven safe, the pipeline continues with a visible `worker advanced HEAD - needs cleanup` hint.

Read-only inspection such as `git status`, `git diff`, and `git log` remains fine. The hard safety boundary is narrower:

- Never push to a protected branch.
- Never rewrite history that existed before the current run.
- Never use destructive operations that discard uncommitted or foreign work.

Runtime prompt scope and `AgentGitCommandGuard` still prevent routine mutation by default. The post-run backstop in `ProjectRunner.OnCliFinishedAsync` compares the actual worker-directory HEAD before and after the process. A linear advance produces `[worker-head-advanced]` with Info severity. `GitService.FoldWorkerCommitsIntoPlatformCommit` performs a guarded `reset --soft` only when current HEAD still matches the observed worker tip and the run-start SHA is its ancestor. The file changes then flow through the normal platform commit. Only a verified protected remote change with worker push evidence, or proof that the original local branch ref no longer contains the run-start SHA, produces High `[agent-git-violation]` and stops for human review. A non-linear end HEAD by itself may only be a branch switch and remains an Info finding.

## What the orchestrator does

The orchestrator (the per-project supervisory Claude session that wraps a project's pipeline; see [ADR-0017](../../system/architecture/decisions/adr-archive.md#adr-0017---supervisor-as-advisory-layer-above-the-deterministic-orchestrator-2026-05-04)) is a **supervisor over the runner, not a second author of git history**. Its role with respect to commits and pushes:

- **Supervise**, do not commit. The orchestrator may *check* whether the runner committed, whether the working tree was clean, whether the SHA stamped on the job exists - and it may emit a `STEER` follow-up that asks the runner to retry or asks the worker CLI to re-run if the commit step skipped due to a fixable cause. It must not run `git commit` itself.
- **Supervise**, do not push. The orchestrator may verify that the local SHA reached the remote and surface a typed advisory if it did not. The push call itself is the runner's.
- **Speak through typed messages.** Per ADR-0002, the orchestrator's voice in the activity log is `OrchestratorChatLog` ([backend/Services/Runner/OrchestratorChatLog.cs](../../../backend/Services/Runner/OrchestratorChatLog.cs)) entries (`decision`, `reissue`, `heuristic`, `giveup`). A commit-supervision verdict is one of those; it is not a side-channel git invocation.

Why not let the orchestrator commit when the runner skipped? Because the runner skipping is data: either the working tree was clean, or AutoCommit was off, or the run did not reach review. Each of those has a deliberate meaning. An LLM "fixing" the skip by committing anyway would launder a state-machine signal into a silent write, which is the failure mode ADR-0002 was written to prevent.

## Future / known gaps

The doctrine above describes today's commit and completed-push path. Remaining gaps are persisted per-job push evidence and higher-level push supervision.

- **Worker-run commit/push ownership is now explicit.** [prompts/runtime/runner-fresh-start.md](../../../prompts/runtime/runner-fresh-start.md), `runner-resume-interrupted.md`, `runner-resume-restart.md`, and `runner-recovery-continuation.md` ask the worker to leave commits and pushes to the platform, while explaining that an accidental commit is shown and cleaned up rather than punished. `TaskRunnerPromptTests.AllRunnerTemplates_UseCalmPlatformCommitOwnership` locks this in.
- **Worker-run git mutation blocking now exists for CLI subprocesses.** `AgentGitCommandGuard` injects a worker-only git wrapper into Claude, Codex, Antigravity/Gemini, and Copilot runs. The wrapper blocks commit/push and other history-mutating verbs by default, while platform-owned `GitService` calls and manual/operator actions keep using the normal environment.
- **Worker-run commit detection remains as a backstop.** `ProjectRunner.OnCliFinishedAsync` treats a linear run-window HEAD advance as an Info finding and attempts guarded cleanup. Only verified protected-branch push damage or a rewrite of pre-existing history is an `agent-git-violation`.
- **No end-to-end regression test for the `JobInfo.Commit` stamp via `MoveAsync`.** `TaskCommitBindingTests` pins the lower-level `JobMutationService.AppendJobCommitOnFolder` path, and `AutoPushStrategyTests` reads a pre-stamped SHA off `JobInfo.Commit`, but no spec drives `TaskTransitionService.MoveAsync(3-progress -> 4-auto-review)` against a faked `GitService` and asserts the resulting `JobInfo.Commit.Sha` matches what `AutoCommitAsync` returned. The stamping wire is therefore exercised only transitively.
- **Completed-branch push outcome is not persisted beside `JobInfo.Commit` yet.** `GitService.PushShaAsync` returns a typed `GitPushResult` (`pushed` / `already-remote` / `remote-rejected` / `failed`), and `CompletedPushBackstopHostedService` logs the count of pushed commits, but the sequential completed-job path does not stamp a `push` block next to `commit`. This is separate from Slice B task-branch durability: failed `task/<id>` pushes are already persisted through `[task-branch-unpushed]` orchestrator chat and surfaced as a Warn outcome issue.
