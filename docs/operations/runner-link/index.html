Concept dossier · Agent Studio

Runner link as part of the application

The connection between the control plane and the remote runner host is today an operations script next to the product. This dossier makes it a supervised component: owned by a service, probed functionally, healed automatically, visible and operable in Studio, and finally retired together with the reverse tunnel.

Key statements

State 06.09.: The tunnel has no owner inside the application. Studio neither observes it nor can it restart it, and a dead link is reported to the operator as a provider sign-in problem. Six outages since 01.08. share this shape.

  • The link is only useful while the Task Server process runs. Therefore the Task Server process should own it: a hosted LinkSupervisor spawns and supervises the SSH forward, probes it functionally through the runner heartbeat, and exposes state and a reconnect action. No scheduled task, no second supervisor.
  • Honesty first. A stale runner snapshot means "runner unreachable since", never "waiting for sign-in". This part is already in flight as AGT-2711 and is re-scoped onto the supervisor's state.
  • The tunnel is interim by design. The remote Task Server (Phase B of remote-task-server-local-studio.md) removes it: runner and Studio become ordinary outbound clients over WireGuard, and a sleeping laptop no longer stops the fleet.
  • Immediate measure applied 06.09.: keeper task enabled and started, battery and logon settings corrected. This restores service; it does not change ownership.

§1The link today

The Task Server runs inside the Windows Studio backend on 127.0.0.1:5031. It is not reachable from the network on purpose. The remote runner host agent-runner-01 reaches it only through an SSH reverse forward that the Windows machine initiates: ssh -R 15031:127.0.0.1:5031 agent-runner. On the host, both runner units poll http://127.0.0.1:15031.

§1.1 What Studio sees when the link is down

The capability snapshot from GET /api/v1/management/remote-hosts is empty or stale. providerAuthWaitReason in the frontend treats every non-OK badge alike and renders "Waiting for Codex sign-in on agent-runner-01" on each Ready card. The tooltip promises a retry "after a fresh provider probe", which cannot happen because no probe reaches Studio. On 06.09. the operator therefore looked for a sign-in problem; the host was logged in the whole time.

§1.2 What exists but is not wired

  • Repository-owned keeper and watchdog under deploy/windows/agent-runner-tunnel/: functional probe through the host, zombie-listener cleanup, two-probe recovery, alarm log. The watchdog is not registered because registration needs an elevated shell; the live keeper is the older copy under C:\Users\rmisc\ops\.
  • Runner-side health check in agent-host: it reports "could not reach the task server" honestly and exits with code 4, so systemd restarts it. The report never reaches an operator surface because the channel that would carry it is the one that is down.
  • Provider-auth probes and capability snapshots (60 s cadence) that could carry a link timestamp but today only carry provider state.

The common denominator

Every recovery path lives outside the application, and every operator-facing symptom is a side effect somewhere else: a provider wait reason, a stale snapshot, an empty host list. The product has no fact "link to agent-runner-01 is down since 02.09. 18:53" and therefore cannot show, alert, or act on it.

R1 to R6 are reachable with the tunnel kept. R7 is not: as long as the Task Server lives on the laptop, a sleeping laptop is a stopped fleet by definition. R7 is the argument for the second stage.

§5Recommendation: two stages

Stage 1, now: LinkSupervisor in the Task Server process (Option B)

The Task Server owns the forward it needs. It starts ssh -R as a child, judges health by the runner heartbeat, cleans the host listener, reconnects with backoff, and exposes one link resource per runner with state, timestamps, last error, and a reconnect action. The scheduled task is disabled once the supervisor has held the link for a week. AGT-2711 (honest wait reason, link health in Execution Hosts, reconnect) is re-scoped to read this resource instead of probing the scheduler.

Stage 2, on approval: retire the tunnel with the remote Task Server (Option D)

With task-server-01 on WireGuard, the runner reaches the control plane directly and the Studio connector is an outbound client. The LinkSupervisor's resource becomes the connector's "Task Server connection" state; the SSH forward remains an emergency administration path only. Nothing from Stage 1 is thrown away: state model, UI, wait reasons, and notifications stay.

§6LinkSupervisor design

§6.1 Configuration

One entry per runner link in the Task Server configuration, next to the registered runner identity, for example:

"RunnerLinks": [
  { "runnerId": "agent-runner-01", "kind": "ssh-reverse",
    "sshTarget": "agent-runner", "remotePort": 15031, "localPort": 5031,
    "extraForwards": [ "5031:127.0.0.1:5031", "4011:localhost:4011" ],
    "heartbeatTimeoutSeconds": 90, "backoffSeconds": [5, 10, 30, 60, 120] } ]

The SSH alias and key stay in the service account's ~/.ssh. The supervisor never reads key material; it only passes the alias to ssh. On Linux hosts the same component can run an ssh -L or an autossh-equivalent for Option B of the persistent-connection runbook.

§6.2 State machine

§6.3 Probes and recovery

  • Heartbeat probe. The Task Server already receives runner heartbeats and capability snapshots. The supervisor subscribes to them: a snapshot younger than heartbeatTimeoutSeconds means Up. No extra SSH round trip in the healthy case.
  • Route probe on doubt. When the heartbeat is late, one bounded ssh agent-runner curl --max-time 5 http://127.0.0.1:15031/healthz distinguishes a dead route from a stopped runner service. The verdict goes into the link resource as lastProbe.
  • Recovery. Terminate the child, ask the host to free the listener (the keeper's proven non-sudo ss and kill sequence), wait for the port to clear, start ssh -R with ExitOnForwardFailure=yes, verbose stderr captured to a bounded per-link log. Backoff follows the configured ladder and resets on the first heartbeat.
  • Process ownership. The child is created with a job object on Windows so it dies with the Task Server; on Linux it runs in the service's cgroup. Nothing survives the parent.
  • Sleep and resume. A resume is a late heartbeat, nothing special. The first probe after wake fails fast on the dead socket and the ladder starts at 5 seconds.

§6.5 Migration from the scheduled task

  1. Ship the supervisor disabled by default; enable it for agent-runner-01 in stable.
  2. The supervisor adopts an existing matching forward once (same rule the repository keeper uses) so the link does not flap during the switch.
  3. After seven days without a manual intervention, disable AgentRunner-TunnelKeeper and record the date in the persistent-connection runbook. Keep the deploy assets as the documented emergency path.
