AGT-2906 · Deployment journey

Deployment story

One complete installation, then more runner hosts, then an independent control plane.

Status DecidedPhase Decision readyAs of 27 September 2026

A complete system

AGT-2736's option C is a compatible transitional step, not the complete target.

Start with one box on the operator's workstation. The administrator installs the services; the operator signs in, registers a repository and submits a small task. Completion means that task passes its required review, reaches the canonical Git remote and survives a backup and restore rehearsal.

  1. Install one box: Task Server, orchestrator engine, Studio web edge and one runner-host agent, using one release and installation identity.
  2. Connect the project: register its repository; give the runner Git access, provider authentication, verified capabilities and a finite concurrency budget.
  3. Prove the result: follow coding, review and publication; restore the workspace into a separate empty installation and compare the evidence.
  4. Add runner hosts: enrol each against the same Task Server, with its own identity, capabilities and budget.
  5. Relocate authority: move Task Server and engine to an always-on box through the gated migration. The workstation becomes one runner among many; Studio only observes and submits requests.

Today: building blocks exist, but this complete guided journey is not yet verified. AGT-2736 supplies the transitional Compose baseline; AGT-2738 owns the installer. Remote delivery and recovery still have gates. The details below identify every stop.

The operator owns tasks and results. The administrator owns installation, identity, connectivity, capacity and recovery. One person can perform both roles.

Shapes

The ladder changes placement and capacity. It keeps one Task Server authority, one bus contract, one family of runner-host agents and one workspace identity. A slot admits one concurrent attempt. A lease is time-bounded permission; a fence rejects writes from an obsolete owner. The bus is the persisted task, attempt, lease, review and result state plus its events. It is not an additional message-broker installation. The engine writes steering facts there; coding and review daemons claim permitted work there and report through fenced, replayable APIs.

The workstation has no separate agent product. Review aspects, gates and verification are steps from the shared pipeline library. Today's coding and review daemons may remain separate service processes with separate budgets on one host; that does not create a Quality Host Agent. These terms follow AGT-W65 (AGT-2905) and the operator's 25 September direction. AGT-W49's three host boxes are reconciled in its deployment section as placements and role examples from this one runner-host family.

Shape 1: one-box workstation. Advertise only probed coding/review executors, platform/toolchain, Git fetch/push, repository access, disk, provider authentication and Task Server connectivity. Local repositories, preview URLs or Windows tools are optional capability requirements, not implicit workstation privileges. A Linux container on Windows advertises its actual Linux execution platform. The operator gains a short installation path and local control; sleep, disk loss or reboot still takes the whole installation offline. Co-location also shares resource and security failure domains.

Shape 2: one box plus N remote hosts. The original box keeps every Shape 1 role; new hosts add execution only. Each host advertises its own freshness, tools, repository proof and coding/review budget. The box does not advertise remote capacity as its own. More hosts add toolchains, isolation and capacity across projects; they do not automatically permit parallel tasks inside one project. The operator gains compute headroom and loses some locality, adding network and credential administration. If authority remains on a sleeping workstation, remote work still loses its bus.

Shape 3: remote authority. Task Server, engine, private TLS edge and backup service share the remote control-plane box. Studio's edge is local or independently hosted; it holds service credentials server-side. Execution lives on eligible runner hosts, including the workstation. The control-plane box advertises service health, not coding capacity, unless an administrator deliberately enrols a runner there. Keeping project execution off that box is the recommendation. The operator gains independence from Studio and workstation uptime, while taking on VPN, DNS, certificate, off-host backup and server recovery duties. This is neither high availability nor an automatic failover promise.

AGT-W18 makes remote integration an explicit boundary: candidate construction, verification, canonical-ref publication and recovery run remotely under Task Server authority. Moving only the Task Server leaves workstation-dependent post-processing. AGT-W57 supplies delivery and recovery constraints; successful execution alone cannot stand in for an integrated, remotely durable result.

Recovery set

Exists: the standalone Task Server's POST /api/v1/management/backups creates and checks a SQLite snapshot. POST /api/v1/management/restore accepts {"backupId":"…","verifyOnly":true}. A replacing restore requires resolved attempts and Maintenance, retains a safety copy and remains in Maintenance afterwards. The restore contract owns these steps.

Exists: the legacy file-tree workspace has retention backup-full, verify-full and restore-full. The set includes a workspace bundle, untracked evidence, referenced cold payloads, inventory hashes and a final complete.json. Restore requires an empty destination. These tools and the SQLite backup are different store paths, not interchangeable commands.

  1. Inventory. Declare which store is authoritative, all cold payload locations, repository origins, externally stored artifacts, service configuration and credential custody. Include pending host outboxes and salvage obligations.
  2. Capture. Use the store-aware backup tool, preserve referenced cold data, retain a protected installation manifest and separately encrypted recoverable secrets. Principal hashes in a database do not reconstruct the clients' cleartext credentials.
  3. Copy and verify. Keep a verified copy off the authority machine. A named volume on the same disk is not off-host recovery. Record timestamp, digest, warnings and expected identities.
  4. Restore in isolation. Start an empty rehearsal target in Maintenance with no admitted runners. Restore the matching version and full data set, validate inventory and sampled evidence, and verify repository refs independently.
  5. Resume once. Close the old writer, reconcile attempts and advance authority as required by the restore contract. Re-enrol or restore credentials deliberately. Reconnect one host, reject stale replay, then run a canary and reopen admission.

Exists, I07 (AGT-2948): the agent-studio.recovery-manifest/v1 manifest and the task-server recovery capture, copy, verify, restore, fence-hosts, reenrol and resume workflow, with an empty-target drill; see installation-recovery.md. Missing: installer ownership of this workflow (I02/I06) and a Task Server capture of a legacy file-tree workspace set, which migrates first. Workspaces must be backed up through product services; this concept never instructs an agent to edit managed project or metadata folders directly.
