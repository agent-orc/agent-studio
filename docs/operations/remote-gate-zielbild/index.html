Concept Dossier · Remote gates

Replace the SSH bridge with a first-class remote gate step

Decision target for Robert's sight review: preserve the 2:11 remote path, but move ownership, scheduling, evidence, timeout, and recovery into the Tranche 0 control-plane contract. This page compares the three realistic shapes and recommends one bounded protocol addition.

Decision in one paragraph

Choose claimable gate steps, with capabilities inside the claim

Recommendation: add a dedicated, narrowly scoped gate-step claim to the Task Server protocol. The Task Server persists immutable gate subjects, attempts, leases, fences, state transitions, and reports. The Orchestrator Engine dispatches the gate stage but owns no durable gate state. An Agent Host with matching gate and toolchain capabilities claims the attempt, materializes the exact subject, executes the typed plan, and reports a fenced result.

Do not make “host capability” a stand-alone execution model: capability is an eligibility predicate, not a work item. Reuse the Review Plane's exact-subject and isolation implementation, but do not hide deterministic gates inside the review lifecycle. This preserves clear gate identity and matches the Tranche 0 actor split.

In the target, “local fallback” means another registered Agent Host that is eligible to claim the same immutable gate attempt. It never means silently returning to an in-process build on the Task Server or Studio backend. If no eligible executor remains after the infrastructure retry budget, the central state is GateInfra, not a fabricated product failure.

§1 · Evidence

The current bridge is fast, but out of band

The existing remote-gate cleanup Dossier correctly defines the ordering constraint: replacement first, teardown second. Code inspection on 2026-07-26 confirms that the replacement does not exist.

SubjectThe backend supplies a full SHA. The host scans $HOME/runner-work/*/repo, fetches, then verifies the materialized HEAD.
TimeoutQueue, infrastructure, and command budgets exist, but ownership stays inside one backend call and SSH process.
FallbackQueue, discovery, worktree, and exception paths return null and activate the local gate. Once command execution starts, a nonzero SSH process becomes a remote verdict; only typed infrastructure results enter the caller's retry loop.
VisibilityRemoteGateActivityStore is process-local, starts late, has hard-coded capacity, and is lost on restart.

The backend currently guesses host work. It derives an SSH alias from the configured execution runner, strips an instance suffix, and correlates the alias with a process-local activity dictionary. That is useful display telemetry, but it is not authority. A backend restart erases active entries, and discovery/materialization time is not represented centrally. The transport boundary also leaks into verdict classification: after the remote command loop starts, an SSH exit can be recorded as the gate result instead of selecting the local fallback.

§2 · Target requirements

What the replacement must make true

R1 · identity

One immutable subject

Repository identity, expected result SHA, durable ref or source bundle, plan digest, and pipeline-definition version are fixed before dispatch.

R2 · authority

One fenced attempt owner

Every execution has a lease, fence, idempotency key, and explicit attempt number. A late report cannot overwrite a newer attempt.

R3 · materialization

No directory guessing

The claim names the repository and durable source. The executor fetches that source, verifies the SHA, then creates a disposable workspace.

R4 · outcomes

Product and infrastructure stay separate

Test failures are product outcomes. Missing source, tool failure, timeout, lost lease, and cleanup failure are typed infrastructure outcomes.

R5 · visibility

State is central and replayable

Queue, claim, host, materialization, command, cleanup, retry, and terminal facts are Task Server data, not backend inference.

R6 · bounded scope

No general workflow engine

The protocol accepts catalogued deterministic gate/post-step plans with bounded commands, evidence, time, and resources. It does not accept arbitrary fan-out.

§3 · Alternatives

Three credible shapes

A · Claimable remote gate steps

A first-class GateSubject/GateAttempt lifecycle in the Task Server protocol, claimed by an eligible Agent Host.

recommended
Subject SHAEngine creates an immutable subject from repository ID, expected SHA, verified result ref or source bundle, policy hash, and typed plan. Host fetches the declared source, verifies SHA and HEAD, then opens a disposable workspace.
Timeout and fallbackServer queue deadline plus lease TTL; host-side command and cleanup deadlines. Infrastructure outcome schedules a new fenced attempt on another eligible host. Product failure is terminal. A registered local Agent Host may be fallback.
Central stateTask Server stores queued, claimed, materializing, running, reporting, cleaning, retrying, and terminal events with host, lease, fence, evidence digest, and timestamps.
Tranche 0 fitExact fit: Task Server owns durable gate truth, Engine owns dispatch/decision, Agent Host executes. Existing GateDispatch becomes real orchestration instead of inspecting prefilled payload status.

B · Run gates in the Review Plane

Represent build/test gates as commands or aspects inside the existing ReviewSubject/ReviewAttempt contract.

credible, coupled
Subject SHAAlready strong: ReviewSubject carries repository identity, expected Result SHA, result ref or source-bundle identity, policy hash, and plan. Review Executor verifies the exact snapshot.
Timeout and fallbackExisting review lease, renew, fenced report, cleanup, and infrastructure retry are reusable. Fallback remains another Review Executor; the server checkout is not used.
Central stateReviewAttempt is durable and visible, but an individual gate is only a command/aspect inside one review report unless the contract grows gate-level state.
Tranche 0 fitAuthority is central, but deterministic gate lifecycle becomes coupled to review identity, review capacity, same/different-host policy, and review outcome semantics. Gates outside Auto Review fit poorly.

C · Gate-capable host with central dispatch

The host advertises executor:gate and toolchain capabilities; a central component chooses it.

incomplete alone
Subject SHAA dispatch envelope still has to name repository, exact SHA, durable source, and plan. Without a claim object, direct calls recreate the SSH bridge with a different transport.
Timeout and fallbackCentral dispatch can choose another capable host, but needs a durable attempt, deadline, lease, fence, and idempotent report to do so safely.
Central stateCapability health says what a host may do, not what work it owns now. It cannot by itself represent queue position, attempt state, subject, evidence, or terminal outcome.
Tranche 0 fitUseful as admission and placement inside option A. As a complete architecture it leaves gate ownership ambiguous; once made safe, it converges on claimable steps.

§5 · Recommendation

A bounded GateAttempt contract, not a new host orchestrator

The old AGT-2229 label suggested a separate “orchestrator instance” on the remote host. The target actor model no longer needs that actor. The Agent Host already owns host-side execution; the Orchestrator Engine already owns gate dispatch; the Task Server already owns durable truth. Adding another orchestrator would duplicate responsibility and complicate recovery.

Adopt together

  • Claim kind: gate-step, separate from coding RunAttempt and ReviewAttempt, but using their lease/fence/idempotency conventions.
  • Capability admission: executor:gate plus repository, Git fetch, disk, and required toolchain capabilities. Capability health can drain only affected gate claims.
  • Implementation reuse: extract or share Review Workspace materialization, containment namespace, command evidence, environment proof, and cleanup primitives.
  • Bounded catalog: start with post-build-test-gate. Permit additional deterministic tool/post-steps only through a versioned plan schema and catalogue, not arbitrary workflow fan-out.

Keep separate

  • ReviewAttempt remains the semantic/visual review lifecycle.
  • GateAttempt remains deterministic verification with its own product and infrastructure taxonomy.
  • Engine stages decide what should run; hosts never decide pipeline outcomes.
  • Task Server persists facts; it never checks out a repository or launches a build.

§6 · Proposed contract

Central state machine

  • queued
  • claimed
  • materializing
  • running
  • reporting
  • cleaning
  • passed
  • product-failed
  • infra-retry
  • infra-failed
  • timed-out
  • cancelled

Studio derives queue age, active host, attempt count, phase, deadline, outcome, and evidence availability from these durable facts. The current “GATE count” becomes the sum of visible claimed/running/cleaning attempts for that host, rather than a hard-coded process-local capacity snapshot.

Materialization sequence

  1. The Engine resolves the authoritative result SHA and creates the immutable GateSubject through the Task API.
  2. The Task Server admits a claim only when the host has fresh matching capabilities and an available gate slot.
  3. The Agent Host fetches the declared result ref. If unavailable, it may fetch the declared source bundle whose digest is pinned by the subject. It never scans unrelated host repositories by glob.
  4. The host verifies repository identity and object type, creates a fence-specific disposable workspace, checks HEAD == expectedSha, and records tree/dirty proof.
  5. The host executes the frozen plan under per-command and overall deadlines, records bounded evidence, cleans the workspace, and submits a fenced report.
  6. The Task Server validates the report. The Engine consumes the terminal outcome and applies pipeline policy.

Timeout and fallback policy

Queue

No executor before deadline

Remain centrally queued until the dispatch deadline. Then classify NoEligibleGateExecutor. Do not launch on the Task Server checkout.

Lease

Heartbeat or host lost

Expire the attempt, raise the fence, and retry the same immutable subject on an eligible host after positive no-overlap/containment evidence.

Command

Build/test deadline

Kill the process tree inside the attempt namespace. Classify timeout as infrastructure unless the command contract explicitly defines a product timeout.

Product

Tests fail normally

Report ProductFailure. Do not try another host merely to seek a green result; pipeline reissue policy handles the finding.

Fallback

Preferred host unavailable

Retry another capable host. A workstation is eligible only when it runs a registered Agent Host gate executor with the same contract.

Budget spent

No trustworthy result

Terminalize as GateInfra with all attempts visible. Escalation or pause follows policy; never relabel it as a task-quality failure.

§7 · Follow-up chain

Move the gates, prove parity, then remove the bridge

Implementation-card acceptance source

  • Task Server persists GateSubject, GateAttempt, GateLease, events, report, cleanup, and typed retry/outcome state across restarts.
  • Agent Host claims only with fresh gate/repository/toolchain capabilities and materializes the declared exact SHA without directory scanning.
  • Orchestrator Engine dispatches and consumes the gate through the public Task API; it owns no durable attempt state.
  • Product failure, queue timeout, execution timeout, lost lease, missing snapshot, tool failure, and cleanup failure have distinct tested classifications.
  • Stale-fence reports and cleanup messages are rejected; an infrastructure retry preserves the immutable subject and raises the fence.
  • Studio reads queue, active host/phase, retry history, tested SHA, and terminal evidence from Task Server facts. The backend no longer guesses remote gate load.
  • The migrated build/test gate meets or improves the current remote throughput envelope and never runs in the Task Server checkout.
  • A bounded canary proves remote pass, product failure, host loss, Task Server restart, Engine restart, no eligible host, and cleanup failure before the bridge is disabled.

AGT-2262 teardown entry condition

Only after the new path is the default and the canary/restart matrix is green: remove RemoteSshHost, ResolveRemoteGateSshHost, the complete SSH bridge region in BuildTestGateRunner, its process-local remote gate semaphore and scripts, RemoteGateActivityStore, and the backend alias-based gate-count projection. Remove obsolete SSH/config documentation in the same teardown. The local in-process compatibility path is removed or explicitly retained by a separate decision; it must not survive accidentally as a silent target fallback.
