Alternatives

Gate-only offload

Preserve the original W18 boundary: host verification, Studio merge and push. Smaller migration, but local checkout, publication authority and restart coupling remain. This is an intermediate stage only under the operator direction.

Remote integration attempt

Separate IntegrationAttempt owns a candidate and publication transaction, consuming Review and Gate receipts. Clear authority and restart reconciliation at the cost of a new claim contract. Recommended.

Expanded gate attempt

One GateAttempt means gate, merge and push. Fewer top-level kinds, but standalone verification, Windows execution and publication privileges become different modes of the same object. Viable only with explicit phase/permission separation; not the recommended default.

Each D1-D14 row below names the alternative, recommendation and consequences. These are bounded product contracts, not an invitation to add a workflow engine or agent-managed Git.

Recommendation

Make the remote plane own candidate construction, verification, ref publication and recovery. Task Server stores the authority; the integration executor performs the Git work under it. Studio is an observer and request client.

Authority composition

The fence/lease/epoch contract supplies the vocabulary, not automatic Git enforcement. Each write carries attempt ID, lease ID, owner/instance, fence, the attempt's own authority epoch and operation-scoped idempotency key. Epoch rotation soft-drains live attempts; it does not invalidate an older still-current attempt merely because the global epoch increased. Takeover invalidates the previous holder and increments the durable fence.

The project ref-mutation lease is a separate authority from a GateLease or ReviewLease. The Batch Gate coordinator lease owns manifest membership and construction. Acquisition order is coordinator/attempt authority first, project ref-mutation lease second, with release in reverse order; no holder waits for a coordinator while holding the publication lease. Acquire publication authority only for final base/generation revalidation and publish/reconcile, not for a long suite. A moved base discards publication eligibility and rebuilds remotely.

One common publisher enforces a non-force expected-old-to-exact-new update, with all enabled writers routed through it. Protected canonical refs and attempt-scoped publication credentials or a fenced Git receive gateway must prevent an expired executor from pushing outside the Task Server. A fence checked only on an HTTP report is insufficient. The publication boundary must validate the current grant and expected ref at the ref transaction; a check-then-unrestricted-Git-push design is rejected. If the Git host cannot enforce that contract, cutover waits for an exclusive publication gateway.

Operator merge, release-commit and promotion requests use the same authority queue. The already remote promotion train becomes a client of this authority, not another independent lease owner. It retains its pinned candidate and atomic main/tag update. Batch and train may prepare concurrently but may not publish concurrently. Studio cannot create a release commit directly on main/develop. Unmanaged external writers require branch protection or an explicit audited emergency authority transfer.

Integration contract

Proposed immutable IntegrationSubject: project/repository identity, target ref, expected base SHA, result ref/SHA, run and delivery generation, review identity, ordered parents, candidate SHA/tree, policy/plan/profile digest and optional batch membership digest. An attempt records host, owner, lease/fence/epoch, verification receipts, publication intent, command evidence, retry counts and cleanup. A changed base or result produces a new subject; retries cannot silently change one.

queued → claimed → materialising → candidate-ready
       → verifying (or verified receipt reuse) → ready-to-publish
       → publishing → reconciling → integrated

Before publication: conflict | product-failed | infra-retry
                    infra-failed | timed-out | cancelled | superseded
After ambiguous publication: reconciliation-required (blocks another writer)
Cleanup: separate durable obligation, including after integrated

Claim/renew/report validation is server-owned. No host with an expired lease starts another command or publication. Infrastructure retry is bounded, uses a higher fence after containment, and preserves subject identity. Product failure is not retried for green. A cleanup failure retains evidence and a cleanup obligation without turning a known published result back into failure. Stop before publication cancels; stop during an ambiguous push waits for reconciliation and cannot promise that nothing landed.

Publication recovery

  1. Persist an intent before any push: attempt/fence/epoch, operation key, expected old SHA, exact new candidate SHA, gate receipt digests and complete target-ref set. The host journals delivery before sending; the server durably records it.
  2. Revalidate current generations, receipts, policy, ref tip and publication lease. The canonical update only fast-forwards to the exact tested candidate. Never create an untested merge commit after verification.
  3. After push, query authoritative Git refs and persist the publication receipt before reporting completion. Duplicate identical reports return the stored result; the same key with a different digest is a conflict.
  4. If push succeeded but acknowledgement/report was lost, the new holder reconciles the old intent before new publication. Exact candidate at the remote ref proves success; if a later approved tip descends from it, verify the candidate's ancestry and the publication chain. For atomic main/tag publication verify both refs and the tag object. A ref still at expected old allows a re-authorised retry of that exact intent; a diverged or partially updated ref set requires an authority incident. Never blindly merge again or force-reset the remote branch.
  5. A published candidate is not rolled back by local reset. Subsequent defect correction is a new reviewed revert/fix through the same integration contract. Before publication a red gate simply abandons the disposable candidate; develop/main never moved.

Verification identity

AGT-2839's current tip/tree checks remain necessary but are not the entire target receipt. Require repository and integration-ref identity, exact pre-tip, current delivery/run/review generation, delivery containment and attribution, candidate SHA and ordered parents, tested tree, clean-before/after proof, passed mandatory commands and matching policy/toolchain/environment digests. A waived, partial, resumed-without-proof or baseline-defect-adjusted review cannot masquerade as a complete green gate; explicit policy must account for every required command. Required platform checks remain separate.

The adopted materialisation constructs the final merge object before Review and retains that immutable object through publication. The integration executor then validates/fetches it and publishes by fast-forward; “merge and push” does not mean generating a fresh untested commit after the review. If only tree equivalence is available, conservatively perform remote verification, including commit-sensitive build inputs. If the integration tip moves, construct a new candidate, invalidate reuse and re-verify on the host. New semantic conflict resolution or changed delivery requires new review; mechanical moved-base verification follows the approved review policy.

Windows coverage

Adopted D10 selects an independent Windows host with a blocking Windows-sensitive suite on the same candidate, with explicit OS and toolchain in the receipt. Include path/case and separator assumptions, drive/temp semantics, file sharing/locking, process/shell behavior and Windows installer/setup contracts. These are plausible defect classes covered by platform-sensitive tests, not a claim that each named incident had every cause. Unknown dependency impact selects the conservative Windows suite.

Scheduled verification is a lower-cost fallback proposal only if the operator explicitly accepts defects reaching develop: it would catch these classes at the next scheduled run plus execution time, record the exact failing develop SHA, raise a branch defect and gate release. Promotion-only Windows runs delay the same defects until release, increase diagnosis distance and can stop the train. Neither alternative protects each card before integration. The adopted Windows host costs provisioning, license where applicable, patching, caches, reserved slots and extra latency; measure these rather than quoting an invented price. It may be a VM, but it must not depend on the operator workstation.

Conflict recovery

Use the existing merge and attribution invariants remotely. Abort conflicting temporary Git operations cleanly; preserve base/result/candidate SHAs, conflicting paths, operation kind, host, attempt/fence, typed failure and recovery count. AGT-2875 should consume that durable conflict record. Do not report gate timeout as merge conflict.

The Engine requests a recovery RunAttempt through the Task Server, bounded to one automatic round per operator epoch under adopted D11. This changes the current two-round, delivery-chain-scoped attribution policy and therefore needs explicit migration and tests. The coding agent resolves content in the delivery worktree; platform steps own Git. New result evidence returns to Review. Repeated conflict escalates visibly, not to an unbounded loop. Co-location and prompt publication shorten transfer and queue delay, but do not remove the 45-90 minute review window or stop develop advancing. Immutable candidate checks remain mandatory; Batch Gate can reduce repeated reconstruction later.

Observer contract

Studio shows queued/active/terminal attempts, phase and host, lease ownership, conflict paths, verified candidate, canonical remote refs, policy and receipts, retries and cleanup obligations from Task Server projections. These are proposed data requirements, not claims about the current UI. Actions carry authenticated operator identity, request key and expected generation; server responses and durable events drive the displayed result. Acceptance remains distinct from integration and does not bypass a red gate.

No lease renewal, candidate retention, review handoff, conflict recovery, publication credential, evidence upload, retry, release or reconciliation may require Studio to remain running. Loss of the remote Task Server still pauses new authority-dependent mutations safely. AGT-2737 must move authority off the workstation; merely connecting a host executor to the sleeping local backend fails the target.

Rollout

  1. Decision and inventory. Apply adopted D1-D14, including Windows policy, Git enforcement boundary and N=20. Audit AGT-2262 residuals and all canonical writers. Preserve the W59 history. Implementation cards may be created from the adopted record; this concept performs no product implementation.
  2. Remote authority prerequisite. AGT-2736's Docker-deployable Studio choice is not a prerequisite for protocol/shadow work, but any observer route that relies on its unresolved connector choice must be resolved or explicitly scoped before full workstation-off acceptance.
  3. Protocol and executor. Deliver D1-D6 gate substrate and D7-D9 integration authority, candidate and reconciliation. Add Windows verification and move enabled operator/release/promotion publishers under one authority. Batch Gate is not required for the first project, but its coordinator must delegate publication to this same contract whenever enabled.
  4. Shadow canary. One project, N=20 consecutive comparable cards. Local integration is the only canonical writer. Host permissions allow only refs/heads/agent-studio/integration-shadow/<project>/<attempt>. Pin identical pre-tip, delivery, policy and environment requirements for both paths. Record tree, ordered parents/attribution, command coverage, verdict/classification and intended remote SHA. Commit timestamps can change SHA; compare tree and parent semantics, record the difference, and never describe a different SHA as exact-object reuse. A moved base makes a pair incomparable and it does not count toward N. Every unexplained discrepancy stops the canary.
  5. Failure matrix and performance. Inject pass, product red, Windows-only red, no eligible host, moved base, mechanical conflict, semantic recovery, duplicate/conflicting report, lease expiry, stale writer, host loss, Task Server/Engine restart, push success with lost report, cleanup failure and stop during push. Require zero unauthorised ref writes and complete evidence for every terminal result. Compare queue and execution time separately against matched local runs; acceptance is no p95 regression in end-to-end latency, with lower workstation load. Twenty cards alone cannot establish tail reliability.
  6. Authority cutover. Drain local integration and queued pushes. Reconcile ambiguous intents, freeze new local mutations, record remote refs, revoke local canonical-ref credentials, transfer authority durably, then enable one remote canary project. Confirm by attempted stale-writer rejection. Run for 12 hours with Studio shut down, including review, conflict recovery and publication; expand only after evidence review.
  7. Fallback. Before transfer, disable shadow freely. After transfer prefer pause or another remote host. Emergency rollback to the old Studio is a time-bounded, explicit operator migration rollback: drain/contain remote publishers, reconcile Git and intent state, revoke their grants, advance authority fencing and transfer credentials before re-enabling the old path. Never run both; no remote history reset. This temporarily suspends observer-only operation and must be recorded.
  8. Retirement. After default-on parity and rollback rehearsal, delete the local BuildTestGateRunner integration execution path, local merge/push routing, %TEMP% gate workspace lifecycle and workstation-derived integration budgets. Do not blindly delete shared verification planners, receipts or promotion policy. Complete only actual remaining AGT-2262 SSH cleanup; keep historical evidence. Remove stale local configuration/docs in the implementation scope, then publish the staged extracted page.
