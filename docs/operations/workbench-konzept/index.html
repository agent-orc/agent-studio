Dossiers: Name, Patterns, and Becoming an App

The operator considers the working pattern almost ideal: analysis matures into decisions, and decisions into tasks. The points of friction are the name, the navigation integration, and the static nature. This document organizes the current state and presents the decisions. In doing so, it demonstrates the proposed article style itself.

01Thesis

The Dossier is the preliminary stage of a task. Analysis, comparison, and decisions happen here; cards are created only afterward. Its location in the Wiki (versioned, linkable, and readable without Studio) is correct and remains unchanged. What is missing is the app layer above it: recording decisions (coming with AGT-2520), maintaining status, showing the resulting tasks live, and keeping content current.

Practice confirms the pattern: on 8 and 9 August alone, four decision Dossiers were created (navigation, task header, badge contrast, and protocol condensation), each with a prepared backlog card. The flow analysis → decision → card works, but every step is currently manual.

02Current state (plainly)

  • Discovery: a folder containing workbench.json anywhere below docs/ in the project repository; schema v1 (id, title, summary, entrypoint, status, phase, updatedAt, sourceTaskKeys, relatedTaskKeys).
  • Lifecycle: status active | decision-pending | decided | archived; phase shaping | testing | decision-ready (other values ⇒ invalid). The list shows only active/decision-pending; everything else appears under History.
  • Decision: previously a sight-review form; it is being replaced by inline decisions in the document (AGT-2520: checkboxes + free text, with "Prepare feature card" prefilled).
  • Known friction: awkward navigation integration, with the active Dossier not highlighted (AGT-2509); the archive button writes to the wrong visibility field (AGT-2375 context); relatedTaskKeys are inert strings without live state; content is a snapshot that silently becomes stale.

06More app: status, task tracking, continuity

  1. Live task block (host-rendered): above the document, the viewer renders relatedTaskKeys as a live row containing key, lane, integration state, and a direct link. No content is duplicated in the HTML; the document remains statically readable while Studio provides the app layer. This is the least expensive first step with the greatest effect.
  2. Maintain status: decision states from AGT-2520 (selected/open, by whom, when) appear in the same header block; "decided" becomes derived instead of manually maintained.
  3. Continuous updates: two clearly separated mechanisms: (a) the host renders live data (card states, counts) fresh on every opening, never stale. (b) Content updates (new findings, completed sections) remain an explicit write: a small "Refresh" action creates a prefilled update card (an agent updates the document against reality). Documents do not silently rewrite themselves.
  4. Interactivity: AGT-2520 is the foundation (checkboxes + free text). On top of it: variant images as switchable comparisons (ui-heavy), and collapsible evidence blocks (concept-heavy). Everything is progressive enhancement; without Studio, it remains a readable article.

07Navigation integration, project level, real time

Current navigation, 01.11.2026: The operator selected one flat Dossiers row directly below Wiki. It has no disclosure or Dossier children, opens the project overview, and keeps the live waiting-decision count. The navigation-child design recorded in the original proposal below is historical.

Today: one subitem per project, without highlighting or state (AGT-2509 fixes highlighting + expansion). Beyond that, each list entry will carry a pattern icon, status dot, and, for decision-pending, the number of open decisions ("Navigation consistency · 4 open"). This turns the navigation from a storage location into a work list.

Project level: dedicated list page

In addition to the central page (section 08), each project gets its Dossier list as a dedicated page, with the same sorting and list-based decision-making as the central page, but filtered by project. The navigation children under "Dossiers" remain as shortcuts; the page is the working surface. (Analogous to Board vs. card links.)

Real time instead of reload: SignalR

Evidence from current practice: four new Dossiers were immediately listed through the API but remained invisible in the navigation tree until the operator reloaded. The tree does not poll and receives no push updates. Because the system is intended to support multiple users, Dossier events belong on the existing SignalR route (Studio already operates hubs under /hubs): created, updated, decisionRecorded, statusChanged. Consumers: the navigation tree (children + count), project list, central page, and open viewer (other users' decisions appear live, with decision-maker attribution from AGT-2520). This uses no new transport concept, but the same mechanism that keeps Board lanes current.

08Relationship to Epics, and the central page

Epics and Dossiers are siblings: both group work above the individual card. The difference is the state of aggregation. An Epic groups decided work (cards that already exist), while a Dossier groups the entire lifecycle: emerging work (decisions from which cards are created) AND its tracking through documented completion (operator correction, 9 August). To some extent, it is therefore the operator's backlog: what is here is serious, but has not yet been sliced.

This leads directly to the requirement for a central page analogous to the Epics page: all Dossiers from all projects in one place, under the new name, sorted by need for action. Decision-pending items with a count of open decisions come first, then active items by most recent activity, followed by History. This page supports decisions, not just reading: inline decision points (AGT-2520) are accessible directly from the overview, ideally in an expandable card without changing pages. The operator can see at a glance where they are needed.

The complete lifecycle: documentation at the end

The crucial addition: a Dossier that was not discarded does not end with the decision. It tracks the resulting cards through completion (line by line in the slice plan) and then moves into its final state: documentation. The decision document becomes the record of current reality, covering what was built, why, and with what evidence. The current status value decided is conceived too early for this; the lifecycle needs a documented stage (alternatively, archived retains its dual role but the list distinguishes "discarded" from "completed and documented"). Discarded Dossiers remain visible as discarded history, which is also knowledge.

09Keys and references

Dossiers currently have only the folder slug (workbench-konzept), which is unwieldy to cite and unusable as a card reference. They receive a key modeled after card keys:

  • Schema: project-scoped with a W prefix, for example AGT-W4 (alternative considered for the decision: global sequence WB-17). The W disambiguates it from task keys, and the project scope sorts as usual.
  • Assignment: automatic on first discovery without a key. The backend takes the next number from a project sequence (analogous to NextTaskKeySeq) and writes it atomically to workbench.json (the Decision Service write path). The slug remains the folder identity; the key survives renames.
  • Presentation: subtle, with a small monospace chip in the viewer header, lists, and navigation tooltip; clicking copies the key (the same pattern as commit SHAs).
  • Cards reference by key: cards that emerge from a Dossier or relate to it carry the key, either in a dedicated reference field (references.workbenches) or as an extension to the relatedTo vocabulary (the validator resolves both namespaces; the W prefix makes it unambiguous). Task detail displays the Dossier chip as a link.
  • The elegant consequence: the Dossier's live task block (section 06) no longer requires manual maintenance. It becomes derivable from all cards that reference the key. relatedTaskKeys is demoted to a legacy-data bridge.
