Kernaussagen

  • Der Bestand ist klein, die Historie ist das Problem. Der Arbeitsbaum hält 7,6 GB für 2.264 Tasks. Die Git-Historie der letzten elf Tage hält 28,7 GB, davon 27,3 GB in 5.416 Versionen von cli-output.log. Einzelne Tasks tragen 1,1 bis 1,8 GB Historie durch wiederholte Zwischenstände desselben Logs.
  • Vier Datenklassen, ein Regelmodell. Autorität (nie archivieren), Evidenz (mit dem Task archivieren), schwere Arbeitsdaten (nach Größe und Alter archivieren), Laufzeitdaten (nie ins Repository, nach Alter löschen).

§2Drei Ursachen

Ursache 1: Das lebende Log wird bei jedem Zwischenstand committet

Der Evidenz-Committer (WorkspaceEvidenceBatcher, Debounce 15 s, harte Grenze 60 s) und die Run-Grenzen (WorkspaceArtifactCommitService) nehmen cli-output.log in jeden Commit auf, solange der Run läuft. Ein Run von zwei Stunden erzeugt so 100 und mehr Versionen einer wachsenden und rotierenden 10-MiB-Datei. Zeitstempel in jeder Zeile lassen Git-Deltas schlecht greifen. Ergebnis: 1,1 bis 1,8 GB Historie je langem QS-Task, 2,6 GB je Tag insgesamt.

Ursache 2: Keine Alters- und Größenregel für abgeschlossene Tasks

1.828 archivierte Tasks halten 6,8 GB heiß, obwohl sie niemand mehr liest. results/ mit 2,2 GB liegt nur auf Platte, aber ebenfalls ohne Regel. Der Task-Server der Zielarchitektur kennt bisher nur eine Frist für entfernte Git-Refs (ResultRefGc, 30 Tage) und löscht nie eine Zeile oder ein BLOB.

Ursache 3: Laufzeitdaten im oder neben dem Repository ohne Rotation

.metadata/attempt-authority.json mit 118 MB plus Sicherungskopien und Tagesarchive (352 MB untracked), logs/bus/ getrackt aber seit 19.07. nicht committet, 134.000 lose Git-Objekte ohne gc.auto. Das ist keine Aufbewahrungsfrage, sondern fehlende Rotation; es gehört trotzdem in dieselbe Regelmaschine, weil der Operator eine Stelle für alle Fristen braucht.

§3Datenklassen

Der Klassifizierer ist Code in der gemeinsamen retention/-Bibliothek und wird von beiden Speichern benutzt (Dateibaum heute, SQLite nach dem Cutover). Die Pfadmuster sind die des heutigen Dateibaums; im SQLite-Store trägt jede Artefaktzeile die Klasse als Spalte.

§5Kaltes Archiv

Ablage

  • Pfad: ARCHIVE_PATH/<projekt>/<task-key>/<archivedAt>/ mit manifest.json und payload.zip. Standard für das heutige Workspace-Repository: das Geschwisterverzeichnis C:\Projects\agent-taskboard-archive, nie innerhalb des Git-Repositories. Standard für den Task-Server im Container: /var/lib/agent-orchestrator/archive als eigenes Volume.
  • Manifest: Task-Key, Id, Projekt, Lane und Terminal-Zeit, angewandte Regel-Ids, Richtlinien-Version, Dateien mit relativem Pfad, Größe und SHA-256, Gesamtgröße, Kompression, Ziel und dessen Prüfsummen, Zeit und Akteur.
  • Stub im heißen Store: Dateibaum: archive-manifest.json neben task.json; SQLite: Spalten archive_state und archived_at am Task, Artefaktzeilen behalten Hash und Größe, verlieren nur den Inhalt.
  • Restore: liest die Nutzlast, prüft jede SHA-256, schreibt zurück, setzt restoredAt; niemals verändert ein Archiv- oder Restore-Lauf Klasse A.
  • Zweites Ziel: S3-kompatibel (Hetzner Object Storage, MinIO in CI); lokal zuerst schreiben, dann kopieren und verifizieren; Löschung des lokalen Exemplars ist konfigurierbar. Wöchentliche Stichprobe der Hashes gegen das Ziel. Details: below.
  • Archiv-Lebensdauer: standardmäßig unbegrenzt; eine Löschfrist in Jahren ist möglich, verlangt eine zweistufige Bestätigung und hinterlässt das Manifest als Grabstein.

S3-compatible target (R4)

The policy's archiveStorage block (ArchiveStoragePolicy in retention/RetentionPolicy.cs) makes the second target explicit instead of implying it from other fields: archiveTarget is local or s3 (default local); copyToSecondary is only valid with a local primary target and writes the local object first, then uploads it to S3 and verifies the SHA-256 there before the run counts as complete; deleteLocalAfterVerification requires copyToSecondary and removes the local object once the S3 copy verifies; deleteArchivedAfterYears (1 to 100, default unset/never) drives stage 3 in place of the per-rule deletion cutoff from §4 once set. Both targets implement the same contract (PutAsync/OpenReadAsync/VerifyAsync/DeleteAsync, exposed as LocalDirectoryTarget and S3Target in retention/ArchiveTargets.cs), so the planner, restore, and the integrity check below never special-case which target holds a payload. Every archive stage records one object reference per uploaded file — target name, object key, ETag, SHA-256, size, and the target's own server-side checksum when the target returns one — in ArchiveManifest.Objects, addressed by key <project>/<task-key>/<archivedAt>/<file> under an optional bucket prefix. Credentials live in a protected JSON file (accessKey/secretKey) referenced by path, never in the policy or a manifest.

Weekly integrity check: the same scheduler that runs the daily sweep (§6) also samples up to 25 manifests (TaskServer:RetentionIntegritySampleCount) every Sunday (TaskServer:RetentionIntegrityDayOfWeek): it re-verifies every recorded object against its target, and for anything that verifies, re-hashes every ZIP entry against the manifest. The run lands in archive_runs with mode=integrity; a discrepancy appends a retention.integrity-discrepancy audit record and publishes a Studio feed event instead of only failing silently. POST /api/v1/management/retention/integrity/check runs the same sample on demand with an optional {"sampleCount": N} body; GET /api/v1/management/retention/target returns the active policy and non-secret target configuration status (used by the Admin card in §8).

Archive retention and tombstones: deleting a payload keeps its manifest with a tombstone state and an audit record; stage 3 still requires confirmColdDelete: true on the apply request. Deletion is refused with archive-referenced-by-backup while any retained full backup set still references the payload (see below), so a set never silently loses a payload it depends on.

Full backups follow the same target: once an S3 target is configured, creating a full backup set (§12) uploads it under <prefix>/full/<backup-id>/ after the local complete.json exists, uploading complete.json itself last; listing reports a remoteState computed from the remote inventory.json/complete.json pair and the set hash. The 7 daily / 4 weekly / 12 monthly thinning rule from §12 deletes both the local and the remote copy of every set outside the kept union.

§6Schnittstelle des Task-Servers

Der Task-Server ist Eigentümer von Richtlinie, Läufen und Archiv. Das Muster ist dasselbe wie bei RuntimeCapacitySettingsService: eigene Tabelle, versionsgeprüftes Update, Audit-Zeile je Änderung, RequireWritable-Gate.

POST /api/v1/management/retention/planTrockenlauf: Report mit Zählungen und Bytes je Regel und Projekt, gespeichert als Lauf im Modus planmanagement

  • Tabellen: retention_policies (Scope, JSON, Version, Zeit, Akteur), archive_runs (Auslöser, Modus, Richtlinien-Version, Zählungen, Bytes, Report), archive_manifests (Task, Manifest, Nutzlast, Hash, Zustand).
  • Zeitplan: ein Hosted Service mit PeriodicTimer wie ResultRefGcHostedService; Ereignis retention.run.completed für den Feed; Fehler stoppen nie den Server.
  • Artefakt-Lesen: archivierter Inhalt liefert 409 artifact-archived mit Manifest-Referenz statt eines leeren Bodys.
  • CLI: TaskServer retention plan|apply|restore --workspace <pfad> | --store <STORE_PATH>, dieselben Reports als JSON; damit sind Migration, Notfall und Skripte ohne UI bedient.
  • Bis zum Cutover: OrchestratorApi hostet dieselbe Engine mit dem Dateibaum-Adapter unter /api/workspaces/{id}/retention/* und /api/projects/{name}/retention-policy; die Richtlinie liegt in .metadata/retention-policy.json im selben JSON-Vertrag. Der Connector (AGT-2734) leitet nach dem Cutover auf die Task-Server-Routen; die UI kennt nur eine Routenfamilie.

Eine Seite „Aufbewahrung" in den Workspace-Einstellungen nach der Admin-Design-Richtlinie: flache Abschnitte, ein Raster je Tabelle, jede Tatsache genau einmal, beide Themes.

  • Regeltabelle je Klasse mit Standardwert-Badge („Platform default") bis zur ersten Änderung; Projekt-Overrides auf dem Projekt-Einstellungspanel mit „Workspace default" oder Override und einem Klick zum Zurücksetzen.
  • Vorschau als Trockenlauf: eine Zeile mit Tasks, Bytes archivieren, Bytes löschen, Dauer; darunter eine sortierbare Tabelle der betroffenen Tasks. Ausführen ist eine zweite, ausdrückliche Aktion und zeigt danach denselben Report.
  • Verlauf der Läufe mit einer Disclosure-Zeile für den vollen Report; Zeitplan und nächster Lauf als eine ruhige Zeile.
  • Archivierter Task: Hinweis in voller Breite („Archiviert am …, 41 MB kalt", eine Aktion „Wiederherstellen"), Files-Tab zeigt Manifest-Einträge gedämpft statt fehlschlagender Requests; die Archiv-Lane trägt eine leise „kalt"-Markierung; Suche und Dossiers lösen weiterhin auf den Stub auf.
  • Cold archive card (R4 extension, English strings): a "Cold archive" card on the Task Server settings surface reads GET /retention/target and shows the active target, whether the S3 copy is configured and reachable, whether the local copy is retained or deleted after verification, and payload expiry in years or "Never". A "Review expired payload deletion" action previews the stage 3 plan and opens a confirmation dialog that requires typing DELETE ARCHIVED PAYLOADS before the confirmed apply is sent; the dialog states that deletion is blocked while a retained full backup still references a payload (see §5, "Archive retention and tombstones").

§12Nachtrag 06.09.: Verdünnung in Altersstufen und Vollsicherung

Stand 06.09. 23:00: Roberts Ergänzung nach der ersten Fassung: große Blobs mit dem Alter verdünnen und dabei auf den Inhalt schauen, nicht nur auf die Größe; Sicherungen der vollen Daten als Feature, zuerst im Dateisystem, dann extern sicherbar, auch als Grundlage für Auswertungen. Beides ist in R1, R2 und R4 eingearbeitet (Nachtrag in den Karten-Prompts).

Verdünnung in Altersstufen (Klasse C)

Die Regel „nach 30 Tagen kalt" aus §4 wird zu einer Leiter. Jede Stufe ist eine Regel mit eigener Frist in der Richtlinie; die Standardwerte stehen in der Tabelle. Der Übergang zwischen Stufen ist idempotent und im Manifest protokolliert.

StufeStandardfrist ab TerminalHeißer StoreKaltes Archiv
0 voll0 bis 30 TageAlle Dateien vollständig (Deckelung 10 MiB je Log gilt weiter)nichts
1 verdünnt30 bis 180 TageJe schwerer Datei ein Auszug (siehe unten) als kleines Evidenzartefakt der Klasse B; die Originale verlassen den heißen StoreOriginale vollständig, Manifest mit Hashes
2 Stub180 Tage bis 2 JahreStub aus task.json, status.md, Auszügen und ManifestzeigerGanzer Task (B und C)

Auszug heißt inhaltsbezogen: Der Verdünner liest die Datei und behält, was später gefragt wird. Für cli-output.log: Kopf (erste 200 Zeilen), Schluss (letzte 500 Zeilen), jedes Fehlerfenster (50 Zeilen um error, exception, failed, nicht-null Exit), Zeitmarken und Dauer, Zähler für Tool-Aufrufe, Test-Läufe, Commits und Token-Zeilen, sowie eine Liste der ausgeführten Kommandos. Für Review-Stdout-Logs: das Urteil und die Findings-Zeilen. Für results/: die Dateiliste mit Größen und Hashes, Reports und Markdown vollständig, Traces und Bilder nur als Eintrag. Strukturierte JSONL-Dateien (Session-Events, Timeline) bleiben vollständig, sie sind klein. Der Auszug ist ein Markdown-Artefakt mit festen Überschriften, damit Suche und Dossiers darauf zugreifen können; Auszüge älterer Aufzeichnungen werden bei einer Regeländerung nicht neu erzeugt, dafür lässt sich jeder Task wiederherstellen.

Vollsicherung als Feature

  • Sicherungssatz: BACKUP_PATH/full/<zeitstempel>/ mit der SQLite-Sicherung (nach dem Cutover) oder dem Dateibaum-Bundle (heute: git bundle des Workspace-Repositories plus ungetrackte Evidenz), allen Manifesten und allen kalten Nutzlasten, die der Sicherungsstand referenziert, und einer inventory.json mit Zählungen und einer SHA-256 über den Satz. Ein Satz ist vollständig: aus ihm allein lässt sich der gesamte Stand auf einer leeren Maschine wiederherstellen, geprüft durch den Inventar-Hash.
  • Zeitplan und Aufbewahrung: täglich nach dem Archivlauf; Sätze werden nach Alter verdünnt (7 Tagessätze, 4 Wochensätze, 12 Monatssätze als Standard); die Verdünnung der Sätze ist eine eigene Regel in derselben Richtlinie.
  • Extern sicherbar: das Verzeichnis ist so gebaut, dass ein externes Werkzeug (rsync, restic, Objektspeicher-Sync) es unverändert kopieren kann; unveränderliche Dateinamen, keine offenen Handles nach Abschluss, Abschlussmarker complete.json zuletzt geschrieben. R4 fügt die S3-Kopie hinzu.
  • Wiederherstellung: Management-Route POST /api/v1/management/backups/full/{id}/restore im Maintenance-Modus, mit Verifikation und Rollback wie die bestehende SQLite-Wiederherstellung; CLI TaskServer backup full|restore-full|verify-full.
  • Auswertungsbasis: jeder Sicherungssatz enthält zusätzlich einen Auswertungsexport: normalisierte JSONL-Dateien (Tasks mit Lanes und Zeiten, Runs mit Modell, Dauer und Tokens, Reviews mit Urteil, Integrationen, Kosten je Projekt), so dass Analysen über die ganze Historie ohne den Task-Server laufen (DuckDB, Notebooks, Reports). Das Schema ist versioniert und in docs/operations/setup/task-server.md dokumentiert.
  • Admin-UI: die Seite „Aufbewahrung" bekommt einen Abschnitt „Sicherungen" mit Sätzen (Zeit, Größe, Inventar-Hash, Verifikationsstand), „Jetzt sichern", „Prüfen" und „Wiederherstellen" (letzteres nur im Maintenance-Modus).

Zuordnung: Verdünnung und Auszug in R1 (Engine) und R2 (SQLite-Adapter); Sicherungssatz und Auswertungsexport in R2; Sätze-Verdünnung, externe Kopie und S3 in R4; UI-Abschnitt in R3.
