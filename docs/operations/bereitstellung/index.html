Programm-Dossier · Agent Orchestrator

Bereitstellung nach Octopus-Muster

Die Teile von Octopus Deploy weitgehend vollständig in der Plattform abbilden: Umgebungen, Lebenszyklen, Releases, Deploy-Prozesse, Variablen, Runbooks, Mandanten, Dashboard. Pipelines sind dabei Bürger erster Klasse, und jede Karte weiß, in welchen Umgebungen sie läuft.

Stand 16.10.2026 Anlass Operator-Vorgaben 16.10.2026 abends Baut auf Integrierte Plattform §6 bis §9, Anwendungs-Lebenszyklus §12 und §13, AGT-W51 D8 Recherche offizielle Octopus-Dokumentation, abgerufen am 16.10.2026 (Quellen am Ende)
Kernaussage. Octopus trennt das, was gebaut wurde (Release), von dem Weg, den es nimmt (Lebenszyklus), und von dem, was dabei passiert (Prozess, Variablen). Genau diese Trennung übernehmen wir. Dazu kommt, was Octopus von außen anbinden muss: Die Karten sind bei uns selbst die Work-Items. Pipeline und Prozess stehen ganz im Repo, auch die Verweise auf Geheimnisse. Externe Secret-Speicher sind echte Adapter und keine Prozess-Schritte. Das bestehende Panel „Deployment“ wird durch einen eigenen Bereich „Deploy“ je Projekt ersetzt. Deploy ist keine eigene Software: Es ist ein Bereich der einen Anwendung, mit derselben Anmeldung, denselben Karten und demselben Zustand (Operator, 16.10.2026). Erstes Projekt ist die Website, mit Staging remote und Production.

§1Anlass und Vorgaben

Operator-Vorgaben vom 16.10.2026, sinngemäß und in der Reihenfolge, in der sie kamen:

  1. Hosting kann Docker sein, ist aber vor allem ein Prozessschritt in der Pipeline.
  2. Pipelines werden über YAML konfiguriert und sind im Werkzeug sichtbar, als Bürger erster Klasse. Jede Karte weiß, in welchen Umgebungen sie schon deployt ist. Also CI/CD, aber besser integriertes Deployment, nach dem Vorbild Octopus Deploy.
  3. Bei der Oberfläche sollen wir uns an Octopus bedienen. Die Entwicklung kann schon starten. Jedes Projekt bekommt eine Umgebungs- und eine Pipeline-Ansicht, aber neu gedacht.
  4. Projekte, für die das relevant ist, werden gleich angebunden, zuerst die Website. Staging ist dann nicht mehr lokal, sondern remote. Zwei Stufen reichen vorerst: Staging und Production. Kompliziertere Szenarien kommen später.
  5. Auch das Secret-Management von Octopus ansehen.
  6. Die Octopus-Teile weitgehend vollständig abbilden.
  7. Das bestehende Deployment im Admin-Bereich ist dort nur eines von vielen Panels und muss überarbeitet werden.

§3Oberfläche

Neu gedacht gegenüber Octopus: Auf jeder Ansicht sind die Karten das Bindeglied. Ein Klick auf eine Karte zeigt ihren Weg durch die Umgebungen. Der Chat neben der Ansicht kennt Release, Umgebung und Log: „Warum ist Staging rot?“ bekommt eine Antwort mit Logauszug und Karten.

§4Karten und Umgebungen

  • Auf jeder Karte stehen Abzeichen je Umgebung: wann, welches Release, mit welchem Status. Auch der Fall „noch nicht in Production“ ist sichtbar.
  • Im Board filtert man nach Umgebung, z. B. „in Staging, nicht in Production“.
  • Karten seit dem letzten Deploy: Jede Umgebung zeigt, welche Karten mit dem nächsten Deploy dazukommen. Das ersetzt das „Deployment changes“ von Octopus und braucht keinen Issue-Tracker.
  • Release-Notizen entstehen aus den Karten, in Produktsprache, für Staging als Vorschau.
  • Ein Rückweg markiert die Karten des zurückgenommenen Releases. Ein Fehler in Production wird eine Karte mit Release und den Karten des letzten Deploys.

§5Geheimnisse nach dem Octopus-Vergleich

Octopus speichert sensitive Variablen verschlüsselt in der Datenbank (AES-256 ab 2024.4). Sie sind nur schreibbar, auch per API nicht auslesbar. Der Haupt-Schlüssel entsteht bei der Installation und ist mit Windows DPAPI geschützt. Masking in Logs ist „best effort“, und Octopus nennt sich selbst ausdrücklich keinen zweiseitigen Schlüsseltresor. Externe Speicher (Vault, Azure Key Vault, AWS und GCP Secret Manager, 1Password, Bitwarden) gibt es nur als Community-Schritte. Laut Dokumentation kommt an die Werte, wer den Prozess bearbeiten darf. Bei Config as Code bleiben sensitive Werte in der Datenbank und sind auf jedem Branch gleich.

§7Erste Projekte

  1. Agent Studio Website (WEB): Staging aus develop, remote auf der Web-VM unter agent-orchestrator.dev/_staging/studio/; Production aus main wie heute. Vorbereitet durch WEB-35 und AOW-15. Später läuft das unter einer Staging-Subdomain, sobald der DNS-Eintrag steht.
  2. Weitere Websites auf derselben Web-VM: Agent Orchestrator, Quality Studio, Voice Lint, Runner, Chat. Gleiches Muster, eine Zeile je Site in sites.json.
  3. MemoWikis als erste Anwendung mit Datenbank und vielen Geheimnissen (Integrierte Plattform §12).
  4. Agent Orchestrator selbst: develop → Stable als eigenes Projekt im eigenen System. Damit läuft der Deploy, den der Operator heute per Skript fährt, über dieselben Releases und Freigaben.
