§1What this document is

Agent Studio orchestrates coding agents: cards run through code, automatic review, batch verification and integration. The North star is the single entry point to that target picture. It answers "what are we building and what has already been decided" in one page, and then hands the reader to the Dossier that owns each part.

Since 11 October 2026 this page states the finished target picture: the decided outcomes, consolidated. Arguments, alternatives and evidence stay in the owning Dossiers and are linked from the decision register in §6. When a decision changes, its Dossier changes first and this page follows in the same edit.

Five rules

One authority: the Task Server. One decider: the Orchestrator Engine; nothing decides in the monolith once the programme in §8 is through. One execution path: claims on runner hosts. Host operations apart: the Operations Server never touches task state. Replaceable UIs: closing every Studio window stops nothing.

Who decides: two operators and two kinds of steps

The Orchestrator Engine is a runtime, not an actor. Two operators and two kinds of steps make the decisions and do the work; the engine runs the AI Operator and the decision steps. Proposed on 11 October 2026 in answer to the operator's question; confirm or change it in AGT-W73 O1.

LevelWhat it isExamplesRuns in
Human OperatorA person. Sets goals and rules, decides Dossiers, approves proposals, accepts deliveries in Human Review, takes human-only actions.Dossier decisions, releases, priorities, approvals of proposed actionsAny Studio UI
AI OperatorA standing role with its own sessions and context. Watches the whole system, steers, heals, proposes improvements and talks with the human. Acts on its own within autonomy classes A0 and A1, prepares A2 as a proposal, never takes A3.Capacity and quota pacing, priorities across cards, rescue of stuck cards, gate triage, outage handling, improvement proposals, orchestrator chatOrchestrator Engine: periodic, event-triggered and chat occurrences
Decision stepA pipeline element. Answers one bounded question for one card or one plan from frozen grounds, chooses one typed action, writes a receipt and ends. No memory beyond its grounds, no view of other cards, no initiative.Next step after a review, fix round or escalation at budget end, composition of a batch waveOrchestrator Engine
Execution stepWork that produces evidence. A model may run inside it, but it never chooses the next step.Coding agent, review aspects, builds and tests, batch suiteRunner hosts

Escalation runs one way: a decision step asks the AI Operator; the AI Operator asks the human. Both operators act only through Task Server intents with the same floors and audit, so for every action the autonomy class allows, the human and the AI Operator are interchangeable. A step that looks like operator work is still a step: it answers a question it was given. The AI Operator is the instance that notices what no step was asked. Today that role is played largely by operating Claude sessions in the devspace (night shift, sweeps, triage); AGT-3011 moved the first sweeps into the product, and the programme in §8 moves the role into the engine. Host operations it needs, such as restarting a stuck daemon, go through the Operations Server like a human's.

§5Guardrails in force

  • One durable authority. Tasks, runs, reviews, leases and lane transitions live in the Task Server; an operations credential never authorizes a task mutation. Owner: AGT-W49.
  • One decider. Transition decisions, planners and advisors run in the Orchestrator Engine and act through intents; the monolith keeps no decision once the programme is through. Owner: AGT-W65 D14.
  • Claimable work stays on runner hosts. Model calls, builds, tests, review and batch suites run inside claimed units; the Operations Server runs only host operations. Owner: AGT-W65 D16.
  • Isolation applies to the run, not to the sources. One stable checkout per project, one leased worktree per run, prepared by a script that travels with the commit. Owner: AGT-W51.
  • Git ownership belongs to the platform. Pre and post steps commit, push and manage worktrees; one fenced publication lease guards every canonical push. Owner: ADR-0052, AGT-W59 D4.
  • Review before integration, Human Review after it. Model review and cheap checks per round, full suite once per batch. Owner: AGT-W59 D1, AGT-W57 D5.
  • The browser never holds a service bearer. Owner: AGT-W49.
  • No fallback authority. When the Task Server is down nothing claims or decides; when the engine is down transitions wait visibly. Owner: AGT-W49, AGT-W65.

§10History: what this Dossier absorbed

Four Dossiers are recorded as superseded by AGT-W14 and leave the current list. Their durable content is the sentence or two below, plus the decision that replaced them. Nothing else survived: their plans were written against a topology and a card set that no longer exist. Per the operator's archiving rule of 13 September 2026, a Dossier superseded by a theme Dossier needs no separate artefact, because its content lives in the theme Dossier.

AGT-W6, execution model: container default 2026-08-11

Proposed the direction change from host direct operation with full access to container isolated local execution as the default, with local or mixed operation as a deliberate opt out in host administration. It carried the layer map, the change list per project, and six worked decisions E1 to E6, including spawn path convergence and gate isolation.

What survives: isolation is the default and the host direct path is gone; spawn paths converge on one execution path. What does not: the container is no longer the mechanism that delivers isolation, and an installer no longer preselects it.

Replaced by AGT-W51, operator decision of 12 September 2026: isolation per run by executor profile, sandbox process by default, container optional.

AGT-W8, installer story: guided steps, Linux all Docker and Windows 2026-08-18

Designed the guided setup of a fresh machine with every component as a container, once for Linux and once for Windows: the component matrix container against host, per step failure modes and remedies, the state of Compose and secrets, and a test protocol template. Its core finding was that the evidence chain ended at an empty Studio board, with agent hosts in containers, provider authentication, and a dummy card completion proof all missing.

What survives: the finding that setup must be proven end to end by a card that actually completes, and the per step failure and remedy shape. What does not: the all Docker premise for both operating systems, and the three planned validation runs, which were never executed as cards.

Replaced by AGT-W51 for the execution premise, which keeps two native pieces per operating system, an outer installer and a host management process, and requires that onboarding does not become harder; and by AGT-W49 step 5 for the installer itself, which exposes the workstation, one box, and distributed profiles once the contracts are stable.

AGT-W22, implementation plan towards the target picture 2026-08-11

The detailed card level plan from the state of 27 July in four phases: P0 heal the pipeline, P1 container default, P2 distributed platform, P3 replace the SSH tunnel. It held the guardrails, spawn path convergence, bundling by overlap, and verification in the same container.

What survives: the guardrails, restated in §4, and the rule that architecture changes ship as coordinated batches while features ship as single cards. What does not: all four phases as a plan. P0 and P1 completed, P2's card chain is closed, and P3's premise changed when the direct WireGuard path replaced tunnel replacement as the goal.

Replaced by AGT-W49 §08, whose ordered programme of six steps is the current delivery plan, and AGT-W51 stages M1 to M7 for the execution half.

AGT-W25, target picture: components, protocols, cut, build, deploy 2026-08-11

Distilled from the night incident of 27 July. Its core finding was that three of five blockers were protocol drift between runner and backend, and that the integration branch did not build. It described the components and their contracts and answered four steering questions on cut, build, and deployment, with five open decisions E1 to E5.

What survives: the diagnosis that one versioned protocol plane plus a build gate before integration is the load bearing requirement, paired runner and backend releases, and the cut policy that feature equals card while architecture equals coordinated change. What does not: the component inventory itself, which the route migration and the operations boundary have since redrawn.

Replaced by AGT-W49 for components, contracts, and deployment, which records the current process shapes and the 366 route inventory; the gate and validation half is being consolidated by AGT-W55 into the Gates Dossier.

The previous version of this Dossier, dated 28 July 2026, is superseded by this rewrite. Its situation table, its four phase list, and its map of ten deep documents were the three parts that had aged; the entry point role is what carried over.

§12Recommendation

Since 11 October 2026: outcomes here, arguments in the Dossiers

The operator asked for a finished target picture. This page therefore states the decided outcomes of every Dossier that shapes the target, with the decision register as the link back. The September recommendation below still governs the arguments: they are never copied here.

September recommendation: A, map with history and links only

The North star keeps the arc, the guardrails, and the history of what it absorbed, and links every live decision instead of summarising it. This is what the operator's answer to D1 of AGT-W55 asks for: sixteen Dossiers with W14 rewritten as the single entry point, and W49 and W51 kept as separate current Dossiers rather than folded in.

Two consequences follow, and this rewrite applies both. First, the four absorbed Dossiers are recorded as superseded by AGT-W14 in their descriptors, and their status is set so that they leave the current list. Second, no separate archive artefact is written for them, because the operator's D2 note states that a Dossier superseded by a theme Dossier needs no artefact: its content lives in the theme Dossier, and artefacts are only for historical Dossiers whose knowledge has no home.

The maintenance rule that keeps this document from ageing the way its predecessor did: when a decision changes, only the linked Dossier is edited. This page changes when a Dossier joins or leaves the current list, or when a new decision replaces one of the two in §3. A dated situation report never becomes part of the arc.
