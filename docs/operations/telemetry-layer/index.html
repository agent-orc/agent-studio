Organization-wide telemetry layer

A local-first event layer for every organization application, with durable files at the edge, Agent Studio as the operations hub, and policy-bounded conversion of repeated signals into visible, reviewable work.

Recommendation

Adopt the hybrid architecture: every app writes a local append-only JSONL buffer, a collector normalizes and deduplicates those records, and Agent Studio receives a fast local HTTP notification when reachable. Agent Studio persists derived observations on the existing Agent Message Bus and fans them out through the existing SignalR channel.

  • Raw facts remain file-first and app-local. Offline use never loses events, and Agent Studio downtime never blocks an app.
  • The bus remains an observability spine, not a workflow engine. A policy service consumes observations and asks the orchestrator to act through existing application APIs.
  • Start with Coding Agent Chat. Pilot one category, chat.message-send.failed, from the local workbench through clustering to one idempotent healing card in Backlog.
  • No cloud dependency and no implicit export. Event files, fingerprints, bus messages, analysis, and cards stay on the operator's machine unless an existing, explicit repository or task delivery workflow publishes a reviewed artifact.

§1Scope and evidence basis

This dossier covers a shared telemetry contract for Agent Studio, Quality Studio, Coding Agent Chat, Coding Agent Runner, Token Economy and its website, the Agent Studio website, voice-lint, and later onboarded organization applications. The architecture is product-independent: app adapters own domain semantics, while Agent Studio owns cross-app operations.

Inventory boundary

The dated Project Map currently inventories Agent Studio, Coding Agent Runner, Coding Agent Chat, Token Economy, and the Agent Studio website. Quality Studio and voice-lint are not present in that capture. Their rollout therefore begins with a stable appId, repository registration, and local event-root declaration. This dossier does not invent file names inside repositories that were not available in the current checkout.

The proposal extends two existing contracts without merging them:

  • Product Runtime Observability records what a built app did. Its current stream is read-only and has no lane or task authority.
  • Agent Message Bus records who observed, decided, advised, or intervened. A message never performs the action it describes.

The new layer is the bridge between these contracts: raw product events are normalized and clustered; a derived bus observation points back to the raw evidence; a separate orchestrator policy decides whether to observe, ask, prepare a card, or invoke an already-approved recovery recipe.

§3Event model and privacy

The shared unit is an OrgTelemetryEvent/v1. It is a small immutable envelope produced directly by a logging adapter or derived from the existing ProductRuntimeEvent. This is a future schema, not an in-place edit in this concept card. The existing runtime schema has additionalProperties: false, so organization fields must be added through an explicit schema decision rather than smuggled into payload.

Structured logging is the seam

Adapters attach to the logging system each app already uses: ILogger in .NET, a small typed logger in TypeScript, and equivalent native adapters elsewhere. An event is emitted only when the record has a stable eventName and structured dimensions, or when a narrowly configured adapter maps a known legacy template. Free-form text scanning is a migration aid, not the target contract.

Level is not policy

An Error does not automatically create a task, and an Info usage event is not automatically harmless. Event name, category, privacy class, fingerprint, distinct correlations, cooldown, open-card state, and recipe authority are evaluated together. Logging configuration controls volume; policy controls action.

Privacy posture

  • Local first, export never by default. No telemetry collector requires a cloud account, vendor endpoint, OpenTelemetry backend, or internet connection.
  • Never collect secrets. Authentication headers, cookies, access tokens, credentials, private keys, environment secrets, and raw authorization failures are rejected or redacted before append.
  • Never collect content by default. Chat messages, prompts, transcripts, audio, document bodies, source file contents, clipboard contents, and Quality Studio input artifacts stay out of the shared event payload.
  • Reduce identity. Human actors use rotating app-local pseudonyms unless a task already has an authenticated principal that is required for an audit record.
  • Bound paths and stacks. Prefer project-relative route or component ids. Absolute home paths and full stacks remain in local evidence; the bus carries a redacted summary and a reference.
  • Reviewed publication only. A task result may cite selected telemetry evidence through existing artifact review. That is a separate explicit delivery action, not telemetry export.

Retention recommendation: raw edge buffers rotate daily and retain 30 days by default; Trace and Debug retain 3 days when enabled; derived bus observations and action receipts follow the workspace's task and Activity retention. The collector checkpoints files by app id, file identity, byte offset, and last event id. Retention never deletes an unacknowledged tail.

Hybrid write contract

  1. The app redacts and atomically appends the event to its configured local daily JSONL file.
  2. The app optionally sends a tiny loopback wake-up containing appId, file identity, offset, and event id. It does not resend private payload by default.
  3. The collector validates the event, advances a durable checkpoint only after acceptance, and computes a stable fingerprint. File watching and polling recover missed wake-ups.
  4. Agent Studio persists a telemetry intake receipt, then emits one derived observation or error bus message with raw evidence references.
  5. The existing busMessageAdded SignalR fan-out updates Activity. A reconnect replays from durable bus files, not from transient SignalR memory.

Security boundary: loopback intake is disabled or token-authenticated by default, binds only to the configured local interface, enforces registered app roots, rejects path traversal and unknown app ids, caps line and request size, and never permits a producer to choose a task lane or action.

§5Orchestrator consumption: event to action

The orchestrator does not read every raw line. A deterministic cluster service produces a TelemetrySignal with policy version, source app, fingerprint, window, distinct correlation count, sample evidence refs, privacy summary, and any linked open card. The orchestrator then chooses from a bounded action vocabulary.

PatternInitial ruleOrchestrator behaviorAuthority and breaker
Repeated usage friction Same fingerprint at least 5 times across 3 distinct correlations or local sessions in 7 days. Write an Activity observation and prepare a feature card with counts, affected flow, evidence refs, privacy-safe reproduction hints, and a proposed acceptance signal. Default is needs decision. No queueing. One open card per (appId, fingerprint, policyVersion).

Guardian and visual-QA integration

AGT-W15 / AGT-2557 already defines the Global Orchestrator Watcher as an intelligent exception layer above mechanical guarantees. This telemetry layer supplies its missing cross-product trigger substrate. The Watcher consumes clusters and receipts, not unbounded raw streams. Observe-only signals stay cheap; ambiguous diagnosis follows the Watcher's strong-analysis floor and decision surface.

AGT-2654 is the first implemented guardian consumer: deterministic capture, a bounded multimodal verdict, one restart-safe defect steer, and proof-preserving escalation. Its shape becomes the reference for telemetry-triggered action: durable evidence first, pure policy next, bounded action through an existing authority, then a receipt visible to the operator.

Card contract

A telemetry-created or prepared card includes sourceAppId, telemetryFingerprint, policyVersion, time window, occurrence and distinct-correlation counts, first and last seen, app version range, redacted summary, evidence references, privacy classification, linked Activity message id, and the dedupe key. It never copies raw chat, prompt, audio, source, or Quality Studio analysis content into the prompt.

§6Agent Studio as the operations hub

The observed convergence should be explicit product architecture: Agent Studio is the organization management layer for software delivery and operations. It is where CI/CD state, telemetry, alarms, and orchestration become one inspectable operating picture across products. This is consistent with the repository's positioning language: management layers on top of coding work.

Agent Studio owns

  • App registry, stable ids, collector configuration, and local trust.
  • Cross-app normalization, redaction enforcement, checkpoints, dedupe, clustering, and retention visibility.
  • Derived Agent Message Bus observations and Activity projection.
  • Guardian and orchestrator policy, decision packets, task creation through the Task API, action receipts, and audit links.
  • CI/CD convergence: promotion train status, GitHub Actions hygiene, delivery alarms, deployment evidence, and cross-project health.

Each product keeps

  • Domain event names, semantic dimensions, logging calls, local raw evidence, and product-specific retention overrides.
  • Quality Studio's analysis engine, scoring, rule packs, and report meaning.
  • Coding Agent Chat's conversation state and message content.
  • Token Economy's pricing and token-accounting logic.
  • voice-lint's audio and linguistic analysis; websites' audience analytics decisions and consent surfaces.

Agent Studio does not become a runtime dependency for using an app, a warehouse for private product data, or a replacement for product-owned debugging. It hosts the management and action layer. Apps continue to run when Studio is stopped, and their domain cores remain independently testable and releasable.

§7Pilot and rollout slices

Recommended pilot: Coding Agent Chat, not Quality Studio. The current Project Map already proves the library, local workbench, website, and Agent Studio package relationship. A chat pilot also tests attribution for a reusable library embedded in more than one host. Quality Studio should follow after its own app identity and event root are confirmed, avoiding a first slice that accidentally centralizes its analysis core.

Pilot acceptance story

When the Coding Agent Chat workbench records three chat.message-send.failed events with the same normalized failure fingerprint across two distinct correlations inside 30 minutes, the app remains usable and the events survive Agent Studio being offline. On reconnect, the collector replays them once, Agent Studio shows one clustered Problem in Activity, and the orchestrator creates exactly one Backlog healing card with evidence references and an idempotency receipt. No message content leaves the chat app and no task is queued.

Rollout order after the pilot

  1. Quality Studio: onboard stable identity and instrument analysis-run lifecycle plus one failure category. Keep reports and scoring in QS; Agent Studio receives status and references only.
  2. Agent Studio and Coding Agent Runner: adapt existing GitProcessTelemetry, pipeline health, runner diagnostics, and visual-QA receipts. Prefer adapters over duplicate logging calls.
  3. Token Economy and its website: connect durable token-ledger health, pricing drift, and one website delivery or runtime error category. Do not interpret token spend as user value.
  4. Agent Studio website: add consent-appropriate operational events for local preview and deployment verification; exclude audience tracking unless separately approved.
  5. voice-lint: onboard last because audio and linguistic payloads require the strictest content-exclusion proof. Emit processing status, duration, rule ids, and error codes, never audio or transcript text.
  6. Remaining apps: require stable app identity, event registry, privacy review, an offline test, and one named owner before enabling collector discovery.

Rollout controls

  • Feature switches exist per app, event category, bus projection, card preparation, and card creation.
  • Default action mode is observe; the pilot alone may enable idempotent Backlog healing-card creation after fixture acceptance.
  • Collector health is itself a local operational signal: lag, invalid rows, rejected secret fields, checkpoint age, and disk pressure. It cannot recursively create unlimited telemetry about itself.
  • Every policy has a window, threshold, distinct-correlation minimum, cooldown, duplicate-card lookup, maximum actions per day, and versioned receipt.

§8Decision request

Requested operator decisions

  1. Architecture: approve hybrid file-first buffering plus best-effort local push, with no cloud dependency.
  2. Truth boundaries: approve raw app JSONL as event truth, Agent Message Bus observations as cluster truth, and orchestrator receipts as action truth.
  3. Positioning: approve Agent Studio as the operations and management hub for CI/CD, telemetry, alarms, and orchestration across organization products.
  4. Authority: keep the bus inert; let only the orchestrator act through existing APIs and approved guardian recipes.
  5. Pilot: approve Coding Agent Chat and chat.message-send.failed, ending in one idempotent Backlog healing card.
  6. Privacy: approve local-only defaults and the never-collect content list in §3.
  7. Rollout: approve the order Chat, Quality Studio, Agent Studio and Runner, Token Economy and websites, voice-lint, then remaining apps.

Recommended answer: approve all seven decisions. The design builds on the repository's existing file-first runtime stream, Agent Message Bus, SignalR projection, alarm policies, and guardian receipts. It adds the missing cross-app collection and action loop while keeping raw product data local and preserving existing state-machine authority.

Explicit non-goals

  • No cloud telemetry vendor, central SaaS account, data lake, or mandatory OpenTelemetry deployment.
  • No automatic feature implementation, task queueing, Git mutation, or lane movement from an event or bus message.
  • No replacement of runner journals, review evidence, task records, CI receipts, or product-owned analysis cores.
  • No full-text capture of user activity, conversations, prompts, code, audio, or documents.
  • No single global log level that turns all application logs into events.

Related contracts and evidence: Product Runtime Observability, log capture, Agent Message Bus, Global Orchestrator Watcher (AGT-W15), visual QA and steered retry, develop-to-main promotion, and Project Map.
