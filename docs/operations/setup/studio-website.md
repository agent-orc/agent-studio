# Studio website

The operator owns the host, DNS, TLS, backups, and access to it. Studio users need only the HTTPS URL and a password. The monolith, static frontend, and Caddy edge run in one Compose stack. The release workflow publishes `agent-studio-api` and `agent-studio-web` images with matching `v<version>` tags. Application lifecycle D15 selected option B: Studio runs on `agent-runner-01` with repository-managed resource containment.

## Install

1. Point the hostname at the VM. Allow inbound TCP 80 and 443. Install Docker Compose, Git, and OpenSSL on the VM. Use an operator account with Docker access. Clone or extract the matching release's `deploy/compose/monolith-networked` directory.
2. Run `bash setup.sh <version> <hostname> /srv/agent-studio-website`. The script initializes the workspace repository, creates data directories, and prints a random installer owner code. Keep that code private until the first owner account is created. The script writes `.env` with mode 0600; keep it out of backups shared with users.
3. A public hostname uses Caddy's automatic ACME certificate. For a private hostname, set `STUDIO_CADDYFILE=./Caddyfile.private`; install the Caddy internal root certificate from `caddy-data/caddy/pki/authorities/local/root.crt` on every browser machine. For a hostname behind a Cloudflare-proxied DNS record, run setup with `--cloudflare` (see [Cloudflare mode](#cloudflare-mode)).
4. If the release packages are private, authenticate the VM to GHCR with `docker login ghcr.io`. In this directory run `docker compose pull && docker compose up -d`. Open `https://<hostname>`. On the first visit enter the printed installer owner code, owner name, and password. Later visits use the URL and password. The first remote visitor cannot claim the owner without the code. The code ceases to authorize bootstrap once an owner exists.

The API and frontend have no published ports. Caddy is the only public listener. `AllowedHosts` is the configured hostname. The frontend and edge containers have fixed addresses `172.30.83.3` and `172.30.83.2`. The API trusts forwarded addresses only from these two proxies, and the frontend trusts only the edge. The edge passes its resolved client address through `X-Forwarded-For`, so the installer-code rule, login throttling, and API logs see the visitor address. Do not connect untrusted containers to the Compose network. For a different subnet, change both proxy addresses in `Security__TrustedProxyAddresses` and the frontend Caddyfile. The Update Service is not part of this stack and Studio does not poll port 5039 on HTTPS unless explicitly configured.

Every response carries a Content-Security-Policy with `frame-ancestors 'self'`, `X-Frame-Options: SAMEORIGIN` where the response is not sandboxed, `Cross-Origin-Opener-Policy: same-origin`, a minimal `Permissions-Policy`, and HSTS with `includeSubDomains`. The frontend Caddy sets them for the static shell, the API for its own routes, and every edge mode forces HSTS. Only the shell policy allows inline script. API documents such as agent-written HTML and wiki SVG are sandboxed without script; the URL preview proxy, task result HTML, and `/recovery` keep their own policies. API and hub responses carry `Cache-Control: no-store`, including authenticated responses. Session and CSRF cookies are host-only `__Host-` cookies, `Secure` and `SameSite=Strict`; the session cookie is also `HttpOnly`. A browser change must carry a matching `Origin` or `Sec-Fetch-Site: same-origin` in addition to its CSRF token. A WebSocket or `/hubs/*` request with a session cookie is refused when its `Origin` or `Sec-Fetch-Site` shows another site. Scripts that use a session cookie with curl must send `-H "Origin: https://<hostname>"`. See [Security overview](../security/overview.md).

## Cloudflare mode

Use this mode when the hostname is a proxied (orange-cloud) Cloudflare DNS record. Create an **A record only**, no AAAA record: the Compose network is IPv4-only, and Docker's userland proxy would rewrite every IPv6 peer to the gateway address `172.30.83.1`, which is outside Cloudflare's ranges. Set SSL/TLS mode to **Full (strict)**. Caddy obtains its own publicly trusted ACME certificate for the hostname through the proxied record (HTTP-01 on port 80), so keep ports 80 and 443 proxied to the VM. If the first issuance fails under Full (strict), use **Full** until `docker compose logs edge` shows the certificate, then switch to Full (strict).

- New installation: `bash setup.sh --cloudflare <version> <hostname> /srv/agent-studio-website`. This writes `STUDIO_CADDYFILE=./Caddyfile.cloudflare` and `STUDIO_CLOUDFLARE_ALLOW_DIRECT=false` to `.env`.
- Existing installation: set those two lines in `.env`, then run `docker compose up -d`.

The edge treats only peers in `cloudflare-ips.caddy` as proxies and takes the client address from their `CF-Connecting-IP` header. A request from another address receives HTTP 403 unless `STUDIO_CLOUDFLARE_ALLOW_DIRECT=true` (or setup uses `--allow-direct-origin`). A direct peer is then its own client address; its `CF-Connecting-IP` is ignored. An IP in Cloudflare's published ranges does not prove traffic came through this zone. AGT-3298 owns Authenticated Origin Pulls and host firewall enforcement; its controls plug in at the edge TLS listener and the host ingress path. Until then, restrict origin ingress operationally before exposing the hostname.

Add a Cloudflare Cache Rule with **Bypass cache** for URI paths matching `/api/*` and `/hubs/*` as a second layer to the origin's `Cache-Control: no-store` policy. Keep Rocket Loader, Email Address Obfuscation, and Pseudo IPv4 disabled for this zone; the Studio shell policy, origin client-IP checks, and IPv4-only origin network depend on Cloudflare forwarding these requests unchanged.

`cloudflare-ips.caddy` is a versioned copy of Cloudflare's published ranges (`https://www.cloudflare.com/ips-v4` and `ips-v6`). Refresh it with `bash update-cloudflare-ips.sh`, then `docker compose restart edge`. The script updates the public edge's peer matcher with the same ranges, fetches over HTTPS only, accepts only CIDR lists with prefixes of at least IPv4 /12 and IPv6 /24, and with `--check` writes nothing and exits 1 when either range list differs. Run the check regularly, for example monthly from cron; a missing new Cloudflare range makes the edge refuse traffic that Cloudflare sends from it.

## Login protection behind Cloudflare

Before proxying `robert.omgai.dev` through Cloudflare, add a WAF rate limiting rule:

| Setting | Value |
|---|---|
| Match expression | `(http.host eq "robert.omgai.dev" and http.request.method eq "POST" and http.request.uri.path eq "/api/auth/login")` |
| Counting characteristic | IP source address |
| Threshold | 20 requests per 1 minute |
| Action | Block for 1 minute |

Count all login requests, including successful ones. This rule reduces work before requests reach the API. A shared public IP can hit the edge limit together, so review Cloudflare's rate limiting events after cutover and adjust the threshold if legitimate users are affected. AGT-3298 owns the host firewall restriction; a direct request to the origin bypasses this edge rule until that control is deployed. The current source ranges are published at [Cloudflare IP ranges](https://www.cloudflare.com/ips/). Refresh both the versioned trust list and the public edge's peer matcher with `update-cloudflare-ips.sh`. Caddy accepts forwarded visitor IPs only from those ranges, reduces the forwarded chain to the verified client IP, and the frontend and API trust only their named proxy peers.

The API also keeps independent failure budgets per client and per username. A client is one IPv4 address or one IPv6 `/64`. Defaults are 10 client failures and 20 username failures in 15 minutes. The client is denied for 15 minutes after its budget is exhausted. When the username budget is exhausted, a client without a successful login to that account in the last 24 hours waits 2 seconds before another password check; a recently successful client can continue immediately. This avoids a stranger locking out every client of a known account. A new legitimate client may need one short retry during an attack, while a distributed attack can still spend hashes across client addresses. At most one password hash per client and a core-sized number of hashes overall run concurrently. The limits are set with `Security__LoginThrottle__ClientMaxFailures`, `UsernameMaxFailures`, `WindowMinutes`, `ClientLockoutMinutes`, `UsernameDelaySeconds`, `RecentSuccessMinutes`, and `MaxConcurrentHashes` on the API container. Keep the Cloudflare rule active even when these limits are tuned.

Login state expires on the injected clock and has separate caps for client attempts, username attempts, recent successes, and per-client delays. Each cap defaults to 8192 entries and can be set with `Security__LoginThrottle__MaxTrackedClients`, `MaxTrackedUsernames`, `MaxRecentSuccesses`, and `MaxDelayEntries` (1 to 65536). Expired entries are removed before capacity is reused. A full failure-budget table keeps its active entries. When either exact-key table is full, unknown and known usernames both use fixed-size overflow failure counters: each failed attempt checks one password at the same cost and returns the same 401, and an exhausted budget returns the same 429 without a password check, so a full table does not reveal whether an account exists. Each of the 1024 overflow client slots allows `ClientMaxFailures` password checks per `ClientLockoutMinutes`, which bounds the hash work of clients beyond the table. An overflow client that exhausts its failure budget cannot check another password until `ClientLockoutMinutes` elapses, even when the short retry delay or failure window has passed. A new client with no failures can still sign in when the exact table is full, provided its overflow bucket is clear. An exhausted username overflow budget allows one password check per client after the short delay; its failure count is shared across clients, but its retry slots are per client. Hash collisions can make an unrelated client wait for a shared lockout or delay; they cannot clear a failure budget. A full recent-success table replaces its oldest entry, so that client may face a short delay during an ongoing username attack. A full delay table uses fixed-size shared delay slots so new clients can retry after the short delay; collisions can add a wait. Usernames longer than 64 characters fail without a username entry and still count against the client budget.

This stack starts an empty workspace. Add projects, runner credentials, and CLI authentication through their normal owner/operator flows before running jobs. An existing installation needs a planned workspace and project-checkout migration; [move-studio-to-server.md](./move-studio-to-server.md) performs it with a rehearsal before the agreed outage, then verify runner access and job execution.

## Backup and restore

Stop the stack with `docker compose stop` before copying `/srv/agent-studio-website/workspace`, `projects`, `home`, `caddy-data`, and `caddy-config`. The workspace includes `.security/access-state.json`, so protect the backup as credential material. Keep `.env` with the backup in a separate restricted location. Restore those directories and `.env` onto a replacement VM, retain ownership of workspace, projects, and home by UID 10001, point DNS at it, and run `docker compose up -d`. Test sign-in before retiring the old VM.

## Update and stop

For an update, back up first, change `STUDIO_VERSION` in `.env` to a published release version, then run `docker compose pull && docker compose up -d`. Check `docker compose ps`, `https://<hostname>/api/auth/status`, sign-in, and the board. To roll back, restore the backup and previous `STUDIO_VERSION`, then run `docker compose up -d`. To stop without removing data, run `docker compose stop`. `docker compose down` removes containers and the network but leaves the bind-mounted data directories.

## Studio on a runner host

On a runner host, install the cgroup v2 slices before starting the website or the [orchestrator engine](../../../deploy/compose/monolith-engine/compose.yaml). The host needs systemd, Docker with its systemd cgroup driver, and at least 2 GiB RAM. From the repository checkout, run `sudo bash deploy/runner-host/apply-containment.sh`. Re-run it after a host resize or repository update; `--remove` removes the installed units, drop-ins, and derived slice properties. The script prints effective before and after properties and the required restarts. It does not restart live jobs or containers.

The script gives `studio.slice` CPU and IO weight 1000 and a memory protection floor. It gives `agent-work.slice` CPU and IO weight 25 and an aggregate CPU quota, memory reclaim threshold, and hard memory limit. It calculates the work quota as all but two logical cores, with one core minimum. Studio gets up to 10 GiB of protected memory on a large host; on a smaller host the floor is a quarter of MemTotal. The work slice has the remaining memory as its hard limit and a reclaim threshold at 90% of that limit. On a 12-core, 62-GiB host these are a 1000% work CPU quota, 10-GiB Studio MemoryLow, about 46.8-GiB work MemoryHigh, and 52-GiB work MemoryMax. CPU weight favors Studio under contention; Studio has no CPU cap. MemoryLow protects memory Studio actually uses under pressure and does not allocate 10 GiB in advance.

After applying, drain coding and review work, then restart `agent-runner.service` and replace `agent-runner-review.service` through `agent-runner-deploy restart-review`. The managed Review unit refuses a direct `systemctl restart`. Their `Slice=` drop-ins move the services into `agent-work.slice`; existing delegated `worker-*` cgroups stay in their old location until those workers exit. Do not interrupt active jobs just to move them. Check placement with `systemctl show -p Slice -p ControlGroup agent-runner.service agent-runner-review.service` and inspect `/sys/fs/cgroup/agent-work.slice/`. Existing per-worker CPU and process envelopes continue to apply inside the aggregate work slice.

In `deploy/compose/monolith-networked`, use both Compose files for every website lifecycle command:

```sh
docker compose -f compose.yaml -f compose.runner-host.yaml pull
docker compose -f compose.yaml -f compose.runner-host.yaml up -d --force-recreate
docker compose -f compose.yaml -f compose.runner-host.yaml ps
```

The override places `api`, `frontend`, and `edge` under `studio.slice` through Docker's systemd cgroup driver. The API has a 1-GiB reservation and 4-GiB limit. The engine Compose file already places `orchestrator-engine` under the same slice; recreate that container after the slice is installed. Check live placement with `docker inspect --format '{{.HostConfig.CgroupParent}}' <container>` and `systemctl show studio.slice agent-work.slice -p CPUWeight -p IOWeight -p CPUQuotaPerSecUSec -p MemoryLow -p MemoryHigh -p MemoryMax`. Keep the override in update, rollback, stop, and restore commands so a recreated website container stays in the slice. After `--remove`, restart the runner services and recreate the containers to leave their current slices.
