# Studio website

The operator owns the host, DNS, TLS, backups, and access to it. At Stage 0 the owner must pass an identity-aware access layer with a second factor before reaching any Studio path, then sign in to Studio. The monolith, static frontend, and Caddy edge run in one Compose stack. The release workflow publishes `agent-studio-api` and `agent-studio-web` images with matching `v<version>` tags. Application lifecycle D15 selected option B: Studio runs on the designated runner host with repository-managed resource containment.

## Stage 0 access and image prerequisites

Configure an identity-aware access provider for the entire hostname, including `/`, `/api`, `/hubs`, `/healthz`, and sign-in. Its policy must require the owner identity and a phishing-resistant or time-based second factor for each new access session. Configure an HTTPS authorization origin whose `/verify` endpoint returns 2xx only for a current MFA-backed session and 401 or a provider login redirect otherwise. It must validate its own signed session, not client-supplied identity headers. Set `STUDIO_ACCESS_AUTH_URL` to that HTTPS origin and `STUDIO_ACCESS_MFA_ENFORCED=true` only after checking the provider policy and testing an unauthenticated request. The public Caddyfiles call `/verify` before serving any site path. Origin-pull mTLS and the Docker firewall continue to restrict who can connect to the origin. Keep this access provider on a separate hostname so its login flow cannot loop through the Studio edge. The private Caddyfile is reserved for isolated LAN, VPN, or loopback recovery and is not a public alternative to this policy. Studio also requires a registered authenticator or passkey for Owner and Admin sign-in and step-up. The access provider remains required at Stage 0.

Pin all five images by immutable digest. Resolve the published API, web, Operations Server, and Operations Agent `v<version>` manifest digests and the chosen Caddy manifest digest with `docker buildx imagetools inspect <image:tag>`; copy each `Digest: sha256:...` value without the `sha256:` prefix into `STUDIO_API_DIGEST`, `STUDIO_WEB_DIGEST`, `STUDIO_OPERATIONS_SERVER_DIGEST`, `STUDIO_OPERATIONS_AGENT_DIGEST`, and `STUDIO_EDGE_DIGEST` in the environment before `setup.sh`. Keep the exact values in the installed `.env`, update them with each release, and run `check-edge-config.sh` before deployment. The script refuses missing or malformed digests. Install Python 3.12 or newer, OpenSSL, and OpenSSH `ssh-keygen` on the host for setup, baseline, backup, restore, and monitoring scripts.

The non-root installer uses the pinned Caddy image for a one-shot ownership handoff before Compose starts. The image digest must resolve to a published Caddy image, not merely match the 64-character digest format. The website smoke pulls `caddy:2-alpine`, resolves its real registry digest, and uses that same digest for setup and the edge container. It checks that both Caddy containers start as UID 10001 with read-only roots and writable `/data`, `/config`, and `/tmp`. The private edge skips installation of its local root into the container's read-only system trust store. Trust the private root on browser machines as described below.

## Install

The public stack also starts the Operations Server and a local outbound
Operations Agent. Before `setup.sh`, set `STUDIO_OPERATIONS_SERVER_DIGEST` and
`STUDIO_OPERATIONS_AGENT_DIGEST` to the published release digests alongside
the API, web, and edge digests. `setup.sh` creates the Studio-held OpenSSH CA
outside the data directory at `STUDIO_HOST_CA_DIR` (default
`deploy/compose/monolith-networked/keys/host-ca`) and prepares an owner-only
certificate receipt directory in the API data volume. Back up the CA private
key separately from the data backup. The Operations Server's port is bound
to loopback; remote host agents need a private authenticated tunnel and their
own scoped Operations Server principal. See the
[operator host migration](operator-agent.md#host-access-migration-sm-6).

1. Point the hostname at the VM. Allow inbound TCP 80 and 443. Install Docker Compose, Git, OpenSSL, Python 3, and iptables on the VM. Use an operator account with Docker access. Clone or extract the matching release's `deploy/compose/monolith-networked` directory. Configure the access provider and digest variables above first.
2. Run `bash setup.sh [--cloudflare | --private] <version> <hostname> /srv/agent-studio-website`, selecting the mode described in step 3. The script initializes the workspace repository with `.security/` ignored (the API also keeps that folder out of every commit), creates data directories, and prints a random installer owner code. Keep that code private until the first owner account is created. The script writes `.env` with mode 0600; keep it out of backups shared with users. It also creates the secret store key at `keys/secrets.kek` in the stack directory (mode 600, owned by UID 10001) and records it as `STUDIO_SECRETS_KEY_FILE`; Compose mounts it read-only into the API as `Secrets__KeyFile`. Set `STUDIO_SECRETS_KEY_FILE` to an absolute path before setup to place the key elsewhere, outside the data directory. Copy the key to a safe place separate from the data backups (see [Backup and restore](#backup-and-restore)).
3. For a Cloudflare-proxied hostname, run setup with `--cloudflare` and configure [Cloudflare zone-level Authenticated Origin Pulls](https://developers.cloudflare.com/ssl/origin-configuration/authenticated-origin-pull/set-up/zone-level/) with a leaf client certificate issued by an account-specific private CA. Upload that leaf certificate and its private key to Cloudflare, enable zone-level Authenticated Origin Pulls, and place exactly one issuing CA certificate at `$STUDIO_DATA_DIR/origin-pull/ca.pem` with mode 644 so the edge can read it. Do not use the shared global origin-pull certificate: it also authenticates other Cloudflare customers. Caddy requires and verifies this client certificate. Use Cloudflare Full (strict) mode. For a private LAN or VPN installation, run setup with `--private`. This writes `STUDIO_CADDYFILE=./Caddyfile.private`, `STUDIO_PUBLIC_CLOUDFLARE_EDGE=false`, and `STUDIO_RESTART_POLICY=unless-stopped` to `.env` so Docker restarts the stack after reboot. For an existing private install, set those three values in `.env` and recreate the containers. Trust the internal Caddy root at `$STUDIO_DATA_DIR/caddy-data/caddy/pki/authorities/local/root.crt` on each browser machine. Private clients can then sign in; the API still logs a private login address and reports `/healthz` unhealthy so operators can inspect the proxy chain. The container healthcheck uses the local `/healthz/container` probe and remains healthy during this warning.
4. For a public or Cloudflare edge, run `bash check-edge-config.sh <matching-release-stack-directory>` and install the Docker firewall described below. The baseline portion checks the containers in every mode; the origin-pull checks apply to public modes. Set `STUDIO_PUBLIC_CLOUDFLARE_EDGE` explicitly to exactly `true` or `false` in `.env`; Compose refuses to render without it, and the API rejects invalid values at startup. Public installs keep `STUDIO_RESTART_POLICY=on-failure` so the firewall boot unit starts first. If the release packages are private, authenticate the VM to GHCR with `docker login ghcr.io`. In this directory run `docker compose pull && docker compose up -d`. Verify a request without the access session is refused, then complete the provider second factor and open `https://<hostname>`. On the first visit enter the printed installer owner code, owner name, and password. Later visits use the URL, password, and a registered second factor for Owner or Admin accounts. The first owner receives a limited setup session until an authenticator or passkey is registered. Store the one-use recovery codes outside the browser. The first remote visitor cannot claim the owner without the code. The code ceases to authorize bootstrap once an owner exists.

In Settings > Access, the Owner verifies a second factor before revoking a user's sessions. Each verification permits one revocation action within five minutes. A user can revoke their own sessions from the Sessions control.

The API and frontend have no published ports. Caddy is the only public listener. `AllowedHosts` is the configured hostname. The frontend and edge containers have fixed addresses `172.30.83.3` and `172.30.83.2`. The API trusts forwarded addresses only from these two proxies, and the frontend trusts only the edge. The edge passes its resolved client address through `X-Forwarded-For`, so the installer-code rule, login throttling, and API logs see the visitor address. Do not connect untrusted containers to the Compose network. For a different subnet, change both proxy addresses in `Security__TrustedProxyAddresses` and the frontend Caddyfile. The Update Service is not part of this stack and Studio does not poll port 5039 on HTTPS unless explicitly configured.

Every container runs as UID 10001 with a read-only root file system, drops all Linux capabilities, uses `no-new-privileges`, and has explicit writable mounts for state and scratch paths. The edge binds its ports through an unprivileged-port sysctl. Release images are selected by digest. The API retains its process and memory limits; `STUDIO_API_MEMORY_LIMIT` defaults to `20g`. Its local state is mounted at `/data/home/.local/share`.

Every response carries a Content-Security-Policy with `frame-ancestors 'self'`, `X-Frame-Options: SAMEORIGIN` where the response is not sandboxed, `Cross-Origin-Opener-Policy: same-origin`, a minimal `Permissions-Policy`, and HSTS with `includeSubDomains`. The frontend Caddy sets them for the static shell, the API for its own routes, and every edge mode forces HSTS. Only the shell policy allows inline script. API documents such as agent-written HTML and wiki SVG are sandboxed without script; the URL preview proxy, task result HTML, and `/recovery` keep their own policies. API and hub responses carry `Cache-Control: no-store`, including authenticated responses. Session and CSRF cookies are host-only `__Host-` cookies, `Secure` and `SameSite=Strict`; the session cookie is also `HttpOnly`. A browser change must carry a matching `Origin` or `Sec-Fetch-Site: same-origin` in addition to its CSRF token. A WebSocket or `/hubs/*` request with a session cookie is refused when its `Origin` or `Sec-Fetch-Site` shows another site. Scripts that use a session cookie with curl must send `-H "Origin: https://<hostname>"`. See [Security overview](../security/overview.md).

## Quality Studio profile

Quality Studio is optional. Set `QUALITY_DOMAIN` to a sibling hostname (setup defaults to `quality-<Studio hostname>`), create its Cloudflare A record and enable the same account-specific Authenticated Origin Pulls rules as Studio. Set `QUALITY_STUDIO_IMAGE` to the deployed Quality Studio image, `QUALITY_REPOSITORY_ROOT` to the runner's canonical checkout root on the host, and `QUALITY_SERVICE_TOKEN_SHA256` to the SHA-256 of a Quality Studio registrar client token. Keep the token itself only in Studio's secret provider at `secret://workspace/quality-studio/api-token`, entered by an Owner under Settings › Integrations › Quality Studio. The service client defaults to `agent-studio` and can be changed with `QUALITY_SERVICE_CLIENT_ID` and the matching Studio connection field. Configure Studio's internal base URL as `http://quality-studio:8080` and public URL as `https://<QUALITY_DOMAIN>`.

Before starting the profile, create its writable mounts for the container's UID 10001:

```sh
sudo install -d -m 755 /srv/agent-studio/quality
sudo install -d -o 10001 -g 10001 -m 700 /srv/agent-studio/quality/data /srv/agent-studio/quality/registry
```

Start with `docker compose --profile quality up -d`. The profile adds a container at `172.30.83.5` on the existing bridge and mounts `QUALITY_REPOSITORY_ROOT` read-only at the same path. Its data and registry live under `/srv/agent-studio/quality`. Only Caddy publishes a host port. The profile sets Quality Studio's federation issuer, audience, public key URL and Studio public URL from `STUDIO_DOMAIN`. The container sets Git `safe.directory` for repositories below that root so it can read checkouts owned by the runner UID. Without the profile, `docker compose up -d` starts the Studio services alone. The Owner saves the connection to generate Studio's Ed25519 signing key in the secret provider, then maps each project to a Quality Studio repository ID in the Deck Quality Studio panel. Repository registration remains an Owner action until automatic registration ships.

## Cloudflare mode

Use this mode when the hostname is a proxied (orange-cloud) Cloudflare DNS record. Create an **A record only**, no AAAA record: the Compose network is IPv4-only, and Docker's userland proxy would rewrite every IPv6 peer to the gateway address `172.30.83.1`, which is outside Cloudflare's ranges. Set SSL/TLS mode to **Full (strict)**. Caddy obtains its own publicly trusted ACME certificate for the hostname through the proxied record (HTTP-01 on port 80), so keep ports 80 and 443 proxied to the VM. If the first issuance fails under Full (strict), use **Full** until `docker compose logs edge` shows the certificate, then switch to Full (strict).

- New installation: `bash setup.sh --cloudflare <version> <hostname> /srv/agent-studio-website`. This writes `STUDIO_CADDYFILE=./Caddyfile.cloudflare` and `STUDIO_CLOUDFLARE_ALLOW_DIRECT=false` and `STUDIO_PUBLIC_CLOUDFLARE_EDGE=true` to `.env`.
- Existing installation: set those three lines in `.env`, then run `docker compose up -d`.

Both public edge Caddyfiles treat only peers in `cloudflare-ips.caddy` as proxies and take their client address from `CF-Connecting-IP`; they never trust a forwarded client address supplied in `X-Forwarded-For`. The Cloudflare mode refuses another peer with HTTP 403 unless `STUDIO_CLOUDFLARE_ALLOW_DIRECT=true` (or setup uses `--allow-direct-origin`). A direct peer is then its own client address; its `CF-Connecting-IP` is ignored. An IP in Cloudflare's published ranges does not prove traffic came through this zone. Both public edge Caddyfiles require the account-specific Authenticated Origin Pulls certificate, and the Docker firewall restricts origin traffic to Cloudflare source ranges. The preflight rejects CA bundles and certificates whose subject or issuer identifies Cloudflare as the organization.

Add a Cloudflare Cache Rule with **Bypass cache** for URI paths matching `/api/*` and `/hubs/*` as a second layer to the origin's `Cache-Control: no-store` policy. Keep Rocket Loader, Email Address Obfuscation, and Pseudo IPv4 disabled for this zone; the Studio shell policy, origin client-IP checks, and IPv4-only origin network depend on Cloudflare forwarding these requests unchanged.

The account-specific origin-pull **leaf certificate** has the validity dates issued with it; Cloudflare presents it only until its `notAfter` date. Cloudflare's [zone-level setup example](https://developers.cloudflare.com/ssl/origin-configuration/authenticated-origin-pull/set-up/zone-level/) issues a 730-day leaf, but use the actual uploaded certificate's `notAfter` date as the rotation deadline. Keep a public-certificate-only copy at `$STUDIO_DATA_DIR/origin-pull/leaf.pem` for monitoring, without storing the private key on the Studio host. `check-edge-config.sh` warns when the leaf expires within 30 days or is missing for monitoring. Enable Cloudflare's zone-level AOP expiry notifications as well; they alert at 30 and 14 days. Run `openssl x509 -in "$STUDIO_DATA_DIR/origin-pull/leaf.pem" -noout -dates` during routine checks. Before expiry, issue a replacement leaf from the same account-specific CA, upload its certificate and key to Cloudflare, replace the monitoring copy at `leaf.pem`, verify traffic through the zone, and remove the old leaf there. If rotating the CA, install the new CA at `ca.pem` during a coordinated edge restart and verify the new leaf. A leaf past expiry makes the public edge unavailable even if DNS and the server certificate are healthy.

### Owner recovery when Cloudflare access is unavailable

`STUDIO_CLOUDFLARE_ALLOW_DIRECT=true` alone cannot restore browser access: the public Caddy listener still requires Cloudflare's client certificate. With SSH and Docker access to the host, temporarily set `STUDIO_PUBLIC_CLOUDFLARE_EDGE=false` in `.env` and run `docker compose up -d --no-deps --force-recreate api`. This lets the API accept the tunnel's private address while the public edge still requires its client certificate and the host firewall still restricts origin ingress. Use Docker Engine 28.3.3 or newer for this loopback-published listener; older releases had localhost port exposure issues. Then run a separate private Caddy listener bound to host loopback. From the installed stack directory, find the frontend network with `docker inspect "$(docker compose ps -q frontend)" --format '{{range $name, $_ := .NetworkSettings.Networks}}{{println $name}}{{end}}'` and use that network in this command:

```sh
docker volume create studio-owner-recovery-data
docker run -d --rm --name studio-owner-recovery \
  --network <frontend-network> -p 127.0.0.1:8443:443 \
  -e STUDIO_DOMAIN=<hostname> \
  -v "$PWD/Caddyfile.private:/etc/caddy/Caddyfile:ro" \
  -v studio-owner-recovery-data:/data caddy:2-alpine
for attempt in $(seq 1 30); do
  docker cp studio-owner-recovery:/data/caddy/pki/authorities/local/root.crt ./owner-recovery-root.crt && break
  sleep 1
done
test -s ./owner-recovery-root.crt
```

Copy `owner-recovery-root.crt` to the Owner workstation through SSH. Open `ssh -N -L 8443:127.0.0.1:8443 <host-IP-or-SSH-alias>` and temporarily map `<hostname>` to `127.0.0.1` in its hosts file. Trust `owner-recovery-root.crt` only for this recovery session, then open `https://<hostname>:8443` and sign in with the existing Owner account. The hostname must match `STUDIO_DOMAIN`; the tunnel and listener are both loopback bound. After restoring the public edge, set `STUDIO_PUBLIC_CLOUDFLARE_EDGE=true` again and run `docker compose up -d --no-deps --force-recreate api`. Verify a Cloudflare sign-in and `/healthz`, then remove the hosts entry and temporary CA trust, stop the listener with `docker rm -f studio-owner-recovery`, and remove the recovery volume with `docker volume rm studio-owner-recovery-data` and copied certificate.

`cloudflare-ips.caddy` is a versioned copy of Cloudflare's published ranges (`https://www.cloudflare.com/ips-v4` and `ips-v6`). Refresh it with `bash update-cloudflare-ips.sh`, then `docker compose restart edge`. The script updates the public edge's peer matcher with the same ranges, fetches over HTTPS only, accepts only CIDR lists with prefixes of at least IPv4 /12 and IPv6 /24, and with `--check` writes nothing and exits 1 when either range list differs. Run the check regularly, for example monthly from cron; a missing new Cloudflare range makes the edge refuse traffic that Cloudflare sends from it.

## Login protection behind Cloudflare

Before proxying `<hostname>` through Cloudflare, add a WAF rate limiting rule:

| Setting | Value |
|---|---|
| Match expression | `(http.host eq "<hostname>" and http.request.method eq "POST" and http.request.uri.path eq "/api/auth/login")` |
| Counting characteristic | IP source address |
| Threshold | 20 requests per 1 minute |
| Action | Block for 1 minute |

Count all login requests, including successful ones. This rule reduces work before requests reach the API. A shared public IP can hit the edge limit together, so review Cloudflare's rate limiting events after cutover and adjust the threshold if legitimate users are affected. Keep the origin restricted to Cloudflare source IP ranges in Docker's `DOCKER-USER` chain; ufw INPUT alone does not filter Docker-published ports. The current source ranges are published at [Cloudflare IP ranges](https://www.cloudflare.com/ips/). Refresh both the versioned trust list and the public edge peer matcher with `update-cloudflare-ips.sh`, then reinstall the firewall rules when Cloudflare changes them. Caddy accepts forwarded visitor IPs only from those ranges, reduces the forwarded chain to the verified client IP, and the frontend and API trust only their named proxy peers.

Run `sudo bash install-cloudflare-docker-firewall.sh` from the installed stack directory before starting the public stack. It installs the firewall unit after `docker.service` and a website boot unit after the firewall. All six restartable website services, including Operations Server and Operations Agent, use `restart: on-failure`, so Docker does not auto-start them ahead of the firewall on reboot. An existing `agent-studio-website.service` must order itself after and require `agent-studio-cloudflare-firewall.service`. The installer adds an `ExecStartPre` drop-in that checks the subnet jump is the first `DOCKER-USER` rule before Compose may publish the edge. The script replaces its own chain and puts its jump first in `DOCKER-USER`; it allows internal bridge traffic, established connections, and Cloudflare source ranges to `172.30.83.2` on ports 80 and 443, and rejects other forwarded traffic to `172.30.83.0/24`. Re-run it after changing the Compose subnet or Cloudflare ranges. The Compose published ports bind IPv4 only; publish an A origin record and no direct AAAA origin record. Verify with `iptables -S DOCKER-USER`, a Cloudflare-proxied HTTPS request, and a direct `curl --resolve <hostname>:443:<origin-ip> https://<hostname>/` request that fails its TLS handshake or connection. The account-specific origin-pull certificate also rejects direct requests and traffic routed through another Cloudflare account.

The API keeps independent failure budgets per client, per IPv4 `/24` or IPv6 `/48` network, and per username. A client is one IPv4 address or one IPv6 `/64`. Defaults are 10 client failures, 40 network failures, and 20 username failures in 15 minutes. The client or network is denied for 15 minutes after its budget is exhausted. A client with a successful login to that account in the last 24 hours can bypass the coarse network and username budgets and has one reserved hash slot when the general pool is saturated. Other clients wait briefly after the username budget is exhausted. At most one password hash per client runs concurrently. The limits are set with `Security__LoginThrottle__ClientMaxFailures`, `NetworkMaxFailures`, `UsernameMaxFailures`, `WindowMinutes`, `ClientLockoutMinutes`, `UsernameDelaySeconds`, `RecentSuccessMinutes`, and `MaxConcurrentHashes` on the API container. Keep the Cloudflare rule active even when these limits are tuned.

If a networked login resolves to a trusted proxy or private address, the API logs an error and `/healthz` becomes unhealthy for five minutes in every networked mode; another invalid login renews the warning. Only deployments with `STUDIO_PUBLIC_CLOUDFLARE_EDGE=true` refuse that login with 503. The frontend passes API health through to the public `/healthz`, while stripping the API build tag and commit headers from that public response. The API container uses the loopback-only `/healthz/container` probe and the frontend container probes its local shell, so a private login warning does not block dependent containers. The API commit header appears only on authenticated networked API responses and is absent from anonymous public-demo API responses. For public installs, correct the edge files and verify the client address chain. Private LAN, VPN, and `Caddyfile.private` installs set the flag to `false` and retain sign-in access during diagnosis.

Login state expires on the injected clock and has separate caps for client attempts, username attempts, recent successes, and per-client delays. Each cap defaults to 8192 entries and can be set with `Security__LoginThrottle__MaxTrackedClients`, `MaxTrackedUsernames`, `MaxRecentSuccesses`, and `MaxDelayEntries` (1 to 65536). Expired entries are removed before capacity is reused. A full failure-budget table keeps its active entries. When either exact-key table is full, unknown and known usernames both use fixed-size overflow failure counters: each failed attempt checks one password at the same cost and returns the same 401, and an exhausted budget returns the same 429 without a password check, so a full table does not reveal whether an account exists. Each of the 1024 overflow client slots allows `ClientMaxFailures` password checks per `ClientLockoutMinutes`, which bounds the hash work of clients beyond the table. An overflow client that exhausts its failure budget cannot check another password until `ClientLockoutMinutes` elapses, even when the short retry delay or failure window has passed. A new client with no failures can still sign in when the exact table is full, provided its overflow bucket is clear. An exhausted username overflow budget allows one password check per client after the short delay; its failure count is shared across clients, but its retry slots are per client. Hash collisions can make an unrelated client wait for a shared lockout or delay; they cannot clear a failure budget. A full recent-success table replaces its oldest entry, so that client may face a short delay during an ongoing username attack. The recent-success reservation is in memory only: an API restart clears it, and returning clients temporarily lose the network and username budget bypass until they sign in again. Keep the Cloudflare rate limit and client failure budget active during restarts. A full delay table uses fixed-size shared delay slots so new clients can retry after the short delay; collisions can add a wait. Usernames longer than 64 characters fail without a username entry and still count against the client budget.

This stack starts an empty workspace. Add projects, runner credentials, and CLI authentication through their normal owner/operator flows before running jobs. An existing installation needs a planned workspace and project-checkout migration; [move-studio-to-server.md](./move-studio-to-server.md) performs it with a rehearsal before the agreed outage, then verify runner access and job execution.

## Backup and restore

Configure scheduled encrypted off-host backups and rehearse the restore as described in [Studio website backup and restore](./studio-backup-restore.md). Until `STUDIO_BACKUP_DESTINATION` is set, the stack runs normally and `bash backup.sh status` reports that backups are off. Keep `.env` and a copy of `STUDIO_SECRETS_KEY_FILE` in separate restricted locations; neither is in the scheduled archive. Before a planned host move or update, run `bash backup.sh` by hand as well. The scheduled archive excludes `home`; copy `home/.local/share` separately when local batch-gate state and leases must survive a move, as explained in [move-studio-to-server.md](./move-studio-to-server.md#local-state-outside-the-workspace). The secret store key remains outside the data backup and is required to open sealed secrets after restore.

For a full manual encrypted snapshot that includes `home` and edge state, stop the stack with `docker compose stop`. Generate an RSA recipient key and self-signed certificate on an offline owner machine, for example with `openssl req -x509 -newkey rsa:3072 -nodes -days 3650 -subj '/CN=studio-backup' -keyout <private-key.pem> -out <recipient-certificate.pem>`. Transfer only the certificate to the website host; keep the private key in separate owner custody outside the host and backup store. Run `bash backup-encrypted.sh "$STUDIO_DATA_DIR" "$PWD" <recipient-certificate.pem> <backup.cms>` with the output outside the live data and stack directories. It encrypts the workspace, projects, home, edge data, frontend data, origin-pull certificates, and `.env` with authenticated AES-256-GCM CMS encryption. The secret store key at `STUDIO_SECRETS_KEY_FILE` is excluded and must be preserved separately. Resume with `docker compose up -d` after the archive completes.

At least weekly, temporarily present the separately held private key to the restore host and restore the latest manual encrypted archive with `bash restore-to-scratch.sh <backup.cms> <recipient-certificate.pem> <private-key.pem> <empty-scratch-directory> "$PWD" <restore-signal.json>`. Since AGT-3379 an Owner or Operator who signs in without a second factor gets only an enrollment session, so the proof signs in the way the restored installation requires: with password and the current TOTP code. Use a dedicated restore-check Owner or Operator account with its own TOTP enrollment, so the main Owner's authenticator seed never leaves the authenticator. Set `STUDIO_RESTORE_USER_FILE`, `STUDIO_RESTORE_PASSWORD_FILE`, and `STUDIO_RESTORE_TOTP_SECRET_FILE` (the base32 TOTP secret shown at enrollment) to files kept with the decryption key, outside the archive, the stack, and the scratch directory; the script refuses them elsewhere. The script decrypts into a scratch installation, starts the private edge on loopback with random host ports, signs in to the restored API, requires a full session rather than an enrollment-only session, shuts down the scratch containers, and writes `website.restore.signin` with pass or fail, time, and archive hash to the signal file. Keep that signal outside the scratch directory. Remove the temporary key copy after the check. Delete the scratch installation only after retaining the signal; rotate or destroy its restored credentials securely. A failure or a result older than seven days is an alert. For a replacement VM, restore the original `.env` and separately held secret store key, verify UID 10001 ownership and firewall rules, then verify provider access and Studio sign-in before retiring the old VM.

Run `python3 monitor-baseline.py <access-events.jsonl> "$STUDIO_DATA_DIR/origin-pull/leaf.pem" "$STUDIO_DATA_DIR/caddy-data" <restore-signal.json>` every five minutes and send its JSON output to the owner alert channel. Normalize the access provider event export into JSONL entries with `type` (`login-failed` or `session-created`) and ISO `time`; keep the event file restricted. The monitor alerts on five failed logins in fifteen minutes, every new session, a missing or expiring origin-pull or edge TLS certificate within thirty days, and a failed, missing, or stale restore signal. Alert delivery and the weekly restore should be monitored by the host scheduler. The provider should also alert on its own login failures and new sessions so a lost event export is visible.

Enable unattended host security updates with a fixed maintenance reboot window. On Debian or Ubuntu, enable `unattended-upgrades` for the security repository, keep its automatic reboot disabled, and use a host scheduler to reboot only in the agreed weekly window after draining active work. Schedule the weekly restore outside that window and check the edge, provider login, Docker firewall, certificate, and monitor after reboot. Do not let an automatic reboot interrupt a backup or scratch restore.

## Update and stop

For an update, back up first and extract the matching release stack into a temporary directory. Copy its `compose.yaml`, all four `Caddyfile.*` files, `cloudflare-ips.caddy`, `update-cloudflare-ips.sh`, `check-edge-config.sh`, `backup-encrypted.sh`, `restore-to-scratch.sh`, `monitor-baseline.py`, `secret-key.sh`, `backup.sh`, `backup-collect.sh`, `restore.sh`, `restore-apply.sh`, `install-backup-timer.sh`, `apply-cloudflare-docker-firewall.sh`, `verify-cloudflare-docker-firewall.sh`, and `install-cloudflare-docker-firewall.sh` into the installed stack together. Retain the existing `.env`, origin-pull CA, `backup-recipients.txt`, and backup SSH files. For older installations, create the secret store key outside the data directory and set `STUDIO_SECRETS_KEY_FILE` in `.env`. Create `$STUDIO_DATA_DIR/api-tmp` (mode `0700`, the API's disk-backed `/tmp`), `frontend-data`, and `frontend-config` and give them and existing writable website directories to UID 10001 before recreating the hardened containers; also give `caddy-data` and `caddy-config` to UID 10001 and keep `origin-pull/ca.pem` readable by that user. For a public installation predating origin-pull authentication, install the account-specific CA as in Install step 3. Set `STUDIO_PUBLIC_CLOUDFLARE_EDGE=true` and `STUDIO_RESTART_POLICY=on-failure` for a public edge; use `false` and `unless-stopped` with `Caddyfile.private`. Change `STUDIO_VERSION` and all five image digest values to the published release. Verify the access provider policy and keep `STUDIO_ACCESS_AUTH_URL` and `STUDIO_ACCESS_MFA_ENFORCED=true` in `.env`. Follow the Operations upgrade steps below before starting a stack that adds Operations Server for the first time. For public installations, run `bash check-edge-config.sh <matching-release-stack-directory>`, `sudo bash install-cloudflare-docker-firewall.sh`, and `sudo bash apply-cloudflare-docker-firewall.sh`. Then run `docker compose config --quiet`, `docker compose pull && docker compose up -d`. Check `docker compose ps`, the provider access refusal without a session, sign-in, and the board. To roll back, restore the backup and previous stack files, version, and digests; reinstall the firewall rules for a public installation, then run `docker compose up -d`. To stop without removing data, run `docker compose stop`. `docker compose down` removes containers and the network but leaves the bind-mounted data directories.

### First update that adds Operations Server

An existing installation already has `.env`, so do not rerun `setup.sh`: it refuses to overwrite the owner bootstrap code. Complete these steps in the installed stack directory after copying the matching release files and before `docker compose pull` or `up`:

1. Back up the installation and retain the previous `.env` and stack files for rollback. Resolve the published `agent-operations-server:v<version>` and `agent-operations-agent:v<version>` manifest digests with `docker buildx imagetools inspect`. Add `STUDIO_OPERATIONS_SERVER_DIGEST` and `STUDIO_OPERATIONS_AGENT_DIGEST` to the existing `.env`, each as exactly 64 lowercase hex characters without `sha256:`. Keep the existing `STUDIO_BOOTSTRAP_CODE`, `STUDIO_SECRETS_KEY_FILE`, access settings, and data path. Update the API, web, and edge digests to the same release as described above.
2. Choose an absolute `STUDIO_HOST_CA_DIR` outside `STUDIO_DATA_DIR` and add it to `.env`. Set `ca_dir` in the following commands to that exact path. If a CA already exists, skip the `ssh-keygen` command and keep its key: replacing it would invalidate certificates on enrolled hosts. Store an offline copy of the private key separately from the website data backup.

   ```sh
   ca_dir='<absolute path from STUDIO_HOST_CA_DIR>'
   mkdir -p "$ca_dir"
   chmod 700 "$ca_dir"
   (umask 077; ssh-keygen -q -t ed25519 -N '' -f "$ca_dir/ca")  # new CA only
   sudo chown 10001:10001 "$ca_dir" "$ca_dir/ca" "$ca_dir/ca.pub"
   sudo chmod 700 "$ca_dir"
   sudo chmod 600 "$ca_dir/ca"
   sudo chmod 644 "$ca_dir/ca.pub"
   ```

3. Create the Studio certificate receipt directory with mode `0700` and owner UID 10001. Set `data_dir` to the exact `STUDIO_DATA_DIR` value in `.env`:

   ```sh
   data_dir='<absolute path from STUDIO_DATA_DIR>'
   sudo install -d -o 10001 -g 10001 -m 700 "$data_dir/host-certificates"
   ```

   The new `operations-principals`, `operations-agent-secret`, `operations-client-secret`, `operations-data`, and `operations-agent-data` named volumes are created by Compose; `operations-bootstrap` fills the principal and token volumes once. Preserve those volumes together during later updates and host recovery. Do not copy a token into `.env`.
4. Run `docker compose config --quiet` to catch missing variables and `bash check-edge-config.sh <matching-release-stack-directory>` to check the release baseline. For a public stack, install and apply the updated Docker firewall before Compose starts; the firewall must cover the Operations services on the website subnet and the website unit must check its rule before starting the edge. Then run `docker compose pull && docker compose up -d`. Confirm `operations-bootstrap` completed successfully, `operations-server` and `operations-agent` are running, port 5081 is bound to loopback, Studio sign-in works, and a typed host inspection produces a matching central attempt and host journal receipt.

The Compose file supplies `Operations__Url`, `Operations__ServiceTokenFile`, `Operations__Agents__local`, `HostCertificates__CaPrivateKeyFile`, `HostCertificates__StateDirectory`, and the Operations Server and Agent settings. They do not belong in `.env` for this stack. Remote host agents require the separate enrollment and private tunnel in [host access migration](operator-agent.md#host-access-migration-sm-6). Rollback uses the previous stack files and `.env` with the backup. Keep the CA and new named volumes untouched so a later retry can use the same principal identities; never use `docker compose down -v` for this rollback.

## Studio on a runner host

On a runner host, install the cgroup v2 slices before starting the website or the [orchestrator engine](../../../deploy/compose/monolith-engine/compose.yaml). The host needs systemd, Docker with its systemd cgroup driver, and at least 2 GiB RAM. From the repository checkout, run `sudo bash deploy/runner-host/apply-containment.sh`. Re-run it after a host resize or repository update; `--remove` removes the installed units, drop-ins, and derived slice properties. The script prints effective before and after properties and the required restarts. It does not restart live jobs or containers.

The script gives `studio.slice` CPU and IO weight 100 by default and a memory protection floor. It gives `agent-work.slice` CPU and IO weight 50 by default and an aggregate CPU quota, memory reclaim threshold, and hard memory limit. The weights are configurable with `--agent-cpu-weight`, `--studio-cpu-weight`, `--agent-io-weight`, and `--studio-io-weight`; the agent CPU weight must remain lower than Studio's. It calculates the work quota as all but two logical cores, with one core minimum. Studio gets up to 10 GiB of protected memory on a large host; on a smaller host the floor is a quarter of MemTotal. The work slice has the remaining memory as its hard limit and a reclaim threshold at 90% of that limit. On a 12-core, 62-GiB host these are a 1000% work CPU quota, 10-GiB Studio MemoryLow, about 46.8-GiB work MemoryHigh, and 52-GiB work MemoryMax. CPU weight favors Studio under contention; Studio has no CPU cap. MemoryLow protects memory Studio actually uses under pressure and does not allocate 10 GiB in advance.

After applying, drain coding and review work, then restart `agent-runner.service` and replace `agent-runner-review.service` through `agent-runner-deploy restart-review`. The managed Review unit refuses a direct `systemctl restart`. Their `Slice=` drop-ins move the services into `agent-work.slice`; existing delegated `worker-*` cgroups stay in their old location until those workers exit. Do not interrupt active jobs just to move them. Check placement with `systemctl show -p Slice -p ControlGroup agent-runner.service agent-runner-review.service` and inspect `/sys/fs/cgroup/agent-work.slice/`. Existing per-worker CPU and process envelopes continue to apply inside the aggregate work slice.

In `deploy/compose/monolith-networked`, use both Compose files for every website lifecycle command:

```sh
docker compose -f compose.yaml -f compose.runner-host.yaml pull
docker compose -f compose.yaml -f compose.runner-host.yaml up -d --force-recreate
docker compose -f compose.yaml -f compose.runner-host.yaml ps
```

The override places `api`, `frontend`, and `edge` under `studio.slice` through Docker's systemd cgroup driver. The API has a 1-GiB reservation; its limit is `STUDIO_API_MEMORY_LIMIT` from `compose.yaml` (default `20g`). The engine Compose file already places `orchestrator-engine` under the same slice; recreate that container after the slice is installed. Check live placement with `docker inspect --format '{{.HostConfig.CgroupParent}}' <container>` and `systemctl show studio.slice agent-work.slice -p CPUWeight -p IOWeight -p CPUQuotaPerSecUSec -p MemoryLow -p MemoryHigh -p MemoryMax`. Keep the override in update, rollback, stop, and restore commands so a recreated website container stays in the slice. After `--remove`, restart the runner services and recreate the containers to leave their current slices.
