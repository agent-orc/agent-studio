Executive summary

Five surfaces were audited independently and read-only. Each surface produced its own candidate findings. The set of candidate findings that claimed a live exploit or a real weakness was then handed to a separate verification pass whose only job was to refute each one on every available guard. What follows separates what survived that refutation (confirmed) from what was checked and set aside (verified-mitigated), and keeps the single-surface hardening notes in a final appendix.

Surfaces audited. Public demo — Studio backend (OrchestratorApi under the public-demo-readonly profile); Quality Studio (QualityStudio.Api + AgentOrchestrator.CodeQuality); public websites (ai-patterns.dev Angular 21 SSR + agent-orchestrator-website static/Caddy); runner host (Linux runner + Windows reverse-tunnel keeper); Chat & Token Economy (coding-agent-chat npm library + coding-agent-token-economy .NET/NuGet).

Adversarial verification. Eight candidate exploit findings entered adversarial refutation. Seven survived as confirmed. One — originally rated high — was reclassified to verified-mitigated because no live exploit path exists in any sanctioned deployment (its guard is a documented pre-launch invariant, not yet an enforced gate). Zero candidates collapsed into outright false-positives.

F1 · Absolute server filesystem paths leak from anonymous read endpoints

CONFIRMED Medium confidence 0.9 · information disclosure / reconnaissance

Where. backend/Shared/Models/TaskInfo.cs:30 (WatchPath), :32 (FolderPath) — no [JsonIgnore]; Features/Projects/CycleTime/TaskCycleTime.cs:43 (WatchPath in every cycle-time row); Features/Runner/RunnerEndpoints.cs:60 (orchestrator-feed emits watchPath = project.Path); serialized by TaskCrudEndpoints.cs:112/113 (/) and :115+ (/grouped); populated by JobStatsMetadataCache.cs:230,232. Anonymity gate: AccessSecurityMiddleware.cs:35 + SecurityProfiles.IsNetworked (AccessSecurityModels.cs:12).

Mechanism. Under public-demo, IsNetworked is false, so AccessSecurityMiddleware short-circuits at line 35 with no authentication — /api/* reads are anonymous — and ProjectAccessAuthorization.FilterTasks returns all tasks unfiltered when no HumanPrincipal is present. GET /api/tasks/ and /grouped therefore return raw TaskInfo objects whose serialized WatchPath and FolderPath are live absolute on-disk paths of the form runtime_root/releases/<version>.<rand>/runtime/datastore/projects/<slug>/<lane>/<key>. GET /api/projects/{p}/cycle-time and GET /api/runner/orchestrator-feed carry the same path. A public visitor learns the operator-chosen runtime_root, the release version directory, and the lane/slug layout — reconnaissance that aids path-targeting.

Survived refutation. Every guard was tried and the finding held. Anonymity is real (IsNetworked is true only for the literal networked profile); FilterTasks emits everything without a principal; the leaking endpoints are mapped unconditionally in EndpointMapping.cs; the fields are live absolute paths, not fixtures; there is no serialization guard (ConfigureHttpJsonOptions adds only a JsonStringEnumConverter, and these fields carry no [JsonIgnore] — in deliberate contrast to RemoteDispatchRejection at TaskInfo.cs:465, which does). PublicDemoExecutionLock is an execution-deny gate, not a serialization filter; the S5 build-time datastore scanner cannot catch request-time injections; no test asserts stripping. Severity is medium — disclosure, not direct compromise.

Fix. Add a public-demo response projection that strips or replaces WatchPath/FolderPath (and the orchestrator-feed watchPath and TaskCycleTime.WatchPath) before serialization, or mark them [JsonIgnore] and address tasks by an opaque stable handle. For a single-scene read-only demo the project handle suffices; the WatchPath echo (used only as the frontend's ?watchPath= link param) is unnecessary exposure.

F2 · The demo.replay exclusive-scope defense is inert in the profile the demo runs

CONFIRMED Medium confidence 0.85 · assurance gap (leans low-medium)

Where. AccessSecurityMiddleware.cs:35 (short-circuit) vs :179 (the RunnerScopes.DemoReplay check, reached only when networked); ClientIdentityMiddleware.cs:122 (replay carve-out) with Host/Program.cs:864; backend.Tests/DemoReplayScopeCompromiseTests.cs:331 (boots Security:Profile=networked); deployment profile pinned public-demo-readonly at docs/operations/demo-instanz/index.html:526.

Mechanism. Under the deployed public-demo-readonly profile, AccessSecurityMiddleware returns at line 35 before the demo.replay scope check at line 179 ever runs, and ClientIdentityMiddleware.OwnsFencedAttribution passes /api/runner/replay through with no X-Client-Id. The PublicDemoExecutionLock does not cover the ingest (the route carries no ExecutionRouteMetadata). So the ingest is reachable with no credential, gated only by DemoReplayAdmissionPolicy (pinned trace/digest/scene/kind + a valid ECDSA seal against the pinned release key) and the epoch ledger. Forgery is genuinely blocked by the seal and re-submission by the monotonic epoch cursor, so the only real effect is injecting or replaying pre-signed Simulated events onto fixture tasks, plus unbounded journal growth until the 6h reset (no app-layer rate limiting). The core defect is assurance: the entire S3 compromise suite boots under networked, so its two scope-specific tests prove properties of a mechanism that is inert in the live profile, and no test boots public-demo against the ingest.

Survived refutation. Four angles failed. The demo runs public-demo-readonly (the release manifest pins it; the replay-only-runner.md:99 "networked … is what the public demo runs" line is stale — precisely the drift the finding names). No middleware re-guards the ingest under public-demo (the full pipeline was traced: execution-lock pass, access-security short-circuit, client-identity carve-out, management-mode normal). PublicDemoExecutionProfileTests iterate only the 78 ExecutionRouteMetadata-tagged routes; the replay ingest is untagged. The admission logic is unit-tested but that is profile-independent — reachability and the two scope tests remain untested on the live profile. Direct-exploit risk is mitigated by the pinned-key seal and the epoch ledger (an external actor without the pre-signed trace cannot mint an admissible frame); the assurance/hardening gap is real and reproducible from the code.

Fix. Add a compromise/route-matrix test that boots under public-demo-readonly and asserts the ingest's actual gate there (credential-free reachability + admission-policy denials); add app-layer rate limiting on the ingest rather than relying only on the S4 edge; document that under public-demo the credential scope is not enforced and the edge + co-located replay runner is the boundary; reconcile the stale replay-only-runner.md:99 claim with the pinned deploymentProfile: public-demo-readonly.

F3 · AllowedRoots widened to C:\Projects — QS-53/R-09 recurrence, live in the working tree

CONFIRMED Medium confidence 0.8 · down-rated from High · confinement-boundary widening

Where. src/QualityStudio.Api/appsettings.json:4-7 (uncommitted working-tree edit) + RepositoryRegistry.cs:60,342,330 + ApiSecurity.cs:75-76,101 + scripts/dev-stack.mjs:139-147 + .github/workflows/build.yml (no policy).

Mechanism. git diff shows an uncommitted edit adding "../../.." to the AllowedRoots array; HEAD e31089c has only "../..". ContentRoot is src/QualityStudio.Api, so ../../.. resolves to C:\Projects. RepositoryRegistry resolves AllowedRoots relative to ContentRoot and admits any path IsWithin an allowed root that exists and holds .git — every sibling repo qualifies. Security.Mode="Local" makes ApiSecurity.Authenticate return a full-access local-development identity with CanRegisterRepositories=true and bypass the X-Client-Id mutation check, so registration needs no credential. The persisted registry already contains agent-studio → C:\Projects\agent-taskboard-devspace\agent-taskboard-stable, a sibling outside ../.. but inside ../../..; under HEAD's config ValidatePersistedEntry would throw at startup, so the widened root is load-bearing for the app to boot. A local caller (or the review data path) can register C:\Projects\agent-taskboard-devspace and read its files — including the memucho secret-rotation handoff artifacts — a path unreachable under HEAD's ../...

Survived refutation. The mechanism could not be refuted: the edit is live and load-bearing, no guard/middleware/test/unreachable-path neutralizes the review data path, and the CI recurrence-prevention gap is genuinely unimplemented. High was down-rated to Medium: the referenced dossier rates this exact class (R-09) medium; dev-stack binds the API to 127.0.0.1 and Local mode already authenticates every caller as the local operator, who has direct filesystem read of all of C:\Projects anyway — the widened root grants the only reachable principal no new capability and crosses no privilege boundary; CORS restricts cross-origin reads to http://localhost:4200; and the still-open R-01 sensor-command chain already reads any file regardless of AllowedRoots, so the widening does not amplify it. A real, reproducible boundary widening and a real CI gap — correctly Medium.

Fix. Revert the working-tree edit; keep AllowedRoots at ../.. and move machine-specific roots to environment/secret-store config, or re-parent the reviewed siblings under one intended base. Implement the tracked-config CI policy (and/or a unit test on the shipped appsettings AllowedRoots) that fails on entries resolving above the repo root, containing ../ chains, or holding absolute maintainer paths. Prefer resolving AllowedRoots relative to an explicit narrow base rather than ContentRoot.

F4 · SpendRequestsPerMinute bypass: rate-limit partition keyed on an attacker-chosen X-Client-Id

CONFIRMED Medium confidence 0.88 · practical exposure leans low (Local-only, localhost, CORS-blocked drive-by)

Where. src/QualityStudio.Api/Program.cs:88-98 (spend policy) + ApiSecurity.cs:73-76,100-101; default config RepositoryOptions.cs:27,31; async enqueue Program.cs:1062-1073; unbounded queue ReviewJobs.cs:118,125.

Mechanism. The spend fixed-window limiter partitions on Request.Headers[X-Client-Id] (fallback RemoteIp, then local). Local mode is the shipped default; Authenticate returns a fixed wildcard identity and IsMutationClientHeaderValid returns true unconditionally, so X-Client-Id is never required or validated. A caller can send each POST /api/review, /api/handover, or /api/security/attack-coverage/judgements with a fresh random X-Client-Id and obtain its own 5/min window, defeating the aggregate cap. StartReview enqueues async and returns Accepted immediately, the review Channel is unbounded, and the global limiter is a 32-permit concurrency limiter on a constant key — so neither caps review starts; MaxConcurrency=2 and the per-review token cap throttle per-run, not aggregate, spend.

Survived refutation. The raw-header partition, the Local-mode default, and the three-endpoint policy scope were all verified. The global limiter is concurrency (not rate) on a constant key; the unbounded Channel plus MaxConcurrency=2 and the 100k per-run token cap bound per-review spend, not the number of runs; CORS blocks the browser cross-origin drive-by but not the primary local-process vector or a same-origin/buggy frontend. The only spend-limiter test runs in Hosted mode, leaving the Local-mode path — where the same per-header partition becomes attacker-controllable — untested. The control-is-present-yet- ineffective logic flaw is real; practical exposure is genuinely narrowed by Local-only/localhost/CORS.

Fix. In Local mode partition on a fixed constant (or RemoteIp) and ignore any client-supplied X-Client-Id; in Hosted mode partition on the server-resolved identity.Id, never the raw header. Apply the spend policy to the other expensive endpoints (security/scan, sensors/{id}/scan, attack-coverage GET), and bound the review queue depth.

F5 · Default dependencies sensor runs npm audit / dotnet list in untrusted repos, honoring repo-controlled config

CONFIRMED Medium confidence 0.7 · exfil / SSRF / DoS · gated on tool-presence precondition

Where. src/AgentOrchestrator.CodeQuality/DependencyVulnerabilitySensor.cs:92-153 (RunAsync) + ProcessSensorCommandRunner (same file :23-61); default-on at RepositoryRegistry.cs:373-374 with Enabled=true default (:30-33) and DI registration Program.cs:49; reachable via Program.cs:281-282/957-981 (POST /api/sensors/{id}/scan) and ReviewJobs.cs:591-597 → SecurityReviewEvidence.cs:161-183.

Mechanism. On a deployment where both dotnet and npm resolve, a repo inside AllowedRoots whose tracked content includes an attacker-crafted .npmrc (registry=http://attacker) or nuget.config (malicious packageSources/auditSources) causes RunAsync to run npm audit --json in each package-lock dir and dotnet list <csproj> package --vulnerable per project. Those tools honor the repo-local config, transmitting the dependency tree to the attacker endpoint (exfil/SSRF); and because ProcessSensorCommandRunner sets no wall-clock timeout, no env allowlist, and reads stdout/stderr with no size cap, a stalling attacker endpoint hangs the request/review indefinitely and can exhaust the concurrency-limited host (MaxConcurrentRequests=32, QueueLimit=0).

Survived refutation. Default-on is verified; there is no UseRequestTimeouts/CancelAfter anywhere, and no offline/registry-pin flags, so repo-committed config is honored and a hung child is not time-bounded. Auth narrows but does not neutralize: the default appsettings.json runs Security.Mode=Local (synthetic full-access identity, no credential, RequireHttps forced off), so the default deployment is unauthenticated; even in Hosted mode the threat is untrusted repo content, which is the product's own model. The strongest real barrier is the ecosystem probe gate — a missing npm makes the sensor return Unavailable before running dotnet list, which is exactly why it is inert on the assessed host (npm absent) — but that is environmental, not a durable guard. Confidence held at 0.7 because exploitability is gated on the tool-presence precondition and, in Hosted mode, on an authenticated principal.

Fix. Run ecosystem tools offline / with a host-pinned registry and ignore repo .npmrc/nuget.config; enforce a wall-clock timeout and output-byte cap in ProcessSensorCommandRunner; scrub the child environment; do not enable network-touching sensors by default for untrusted repos; gate behind an isolated worker.

F6 · Pattern figure-SVG validator is bypassable → stored XSS on ai-patterns.dev (empirically proven)

CONFIRMED High confidence 0.9 · stored XSS · bypass reproduced in isolation

Where. scripts/lib/catalog.mjs:110 (event-handler regex) and :112 (href regex); enforced at :318-322; injected at app/src/app/pages/pattern-detail/pattern-detail.page.ts:147 + pattern-detail.page.html:82.

Mechanism. A crafted figure committed to data/patterns/<id>/article.json passes the sole content-security gate (validate-data.mjs --strict, run first in npm run check / quality.yml) and is copied byte-for-byte by build-data.mjs into app/public/data, served at /data/patterns/<id>/article.json. pattern-detail fetches it client-side and renders section.figure.svg via sanitizer.bypassSecurityTrustHtml into [innerHTML], deliberately disabling Angular sanitization. The denylist is bypassable: the event-handler rule /\son[a-z]+\s*=/ anchors only on whitespace, and the href rule /(?:xlink:)?href\s*=\s*["']/ matches only quoted values. There is no CSP anywhere, so injected handlers execute at runtime.

Survived refutation. Every angle failed. The sanitizer is explicitly bypassed; the JSON schema only requires the payload to be wrapped in <svg>…</svg>; CSP — the strongest possible mitigation — is absent at every layer (server.ts, index.html meta, angular.json autoCsp, release.yml, and any in-repo Caddy/nginx). The bypass was reproduced in Node: the control payload is blocked, all five candidate payloads pass with zero errors. Reachability and the CI gate are confirmed, and the 0-PR model removes compensating human review. A SMIL <animate onbegin begin=0s> auto-fires with no user interaction. The only mitigating factor is the write precondition (landing a data/ commit), which the documented 0-PR agent-authored, externally-derived-content model makes materially weaker than a human-reviewed repo.

Fix. Do not rely on regex denylisting for a bypassSecurityTrustHtml sink. Parse each figure SVG with a strict XML/DOM parser (jsdom is already a devDependency) and allowlist elements/attributes: reject any on* attribute regardless of separator, any non-fragment href/xlink:href (quoted or not, entity-decoded), and any element outside a known-safe SVG set. Add regression fixtures for the /-boundary, closing-quote-boundary, unquoted-href, entity-encoded-javascript, and SMIL onbegin cases. Independently, re-enable Angular sanitization (or pre-sanitize figures to static assets) and add a strict CSP without unsafe-inline/unsafe-hashes as defense in depth.

F7 · ai-patterns.dev ships with no Content-Security-Policy or security headers at the app layer

CONFIRMED Low confidence 0.8 · hardening gap (downgraded from Medium: exploitability rests on F6)

Where. app/src/index.html:1-18 (no CSP meta) and app/src/server.ts:30-48 (Express serves static + SSR with no header middleware). Verified: angular.json security = allowedHosts only (no autoCsp); no in-repo proxy or static-host header config (Caddyfile/nginx/_headers/staticwebapp.config.json/vercel.json/netlify.toml/firebase.json all absent); release.yml only tarballs the build.

Mechanism. Factually the app layer emits zero security headers and index.html has no CSP meta — a confirmed, unmitigated hardening gap. The exploit framing is what was refuted: the exfiltration chain is pure defense-in-depth and only bites if F6 is reachable (it is), and the clickjacking angle has no target because ai-patterns.dev is a read-only content library with no authentication, forms, accounts, or state-changing UI.

Survived refutation. The core factual claim cannot be refuted — every layer where a header or CSP could originate was checked and found empty. It is not mitigated (no guard exists) and not a false-positive (the headers really are missing). Severity was downgraded Medium → Low because standalone exploitability is not reproducible independent of F6.

Fix. Add a strict CSP (default-src 'self'; script-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none') plus X-Content-Type-Options: nosniff, Referrer-Policy, and HSTS, via Express middleware in server.ts or the fronting Caddy/nginx that also terminates TLS. Alternatively enable Angular's opt-in autoCsp.

M1 · public-demo-readonly does not make the instance read-only — verified-mitigated

VERIFIED-MITIGATED originally High confidence 0.6 · no live exploit path in any sanctioned deployment

Where. TaskCrudEndpoints.cs:702 (DELETE /{jobId}), :688 (DELETE orphan-folder), :709 (create), :827 (reorder), :855 (move-to-top), :864 (change-project); AccessSecurityMiddleware.cs:35; ClientIdentityMiddleware.cs:31,86; Host/EndpointMapping.cs:25,92; docs/operations/demo-instanz/index.html:978,986.

Claim. Under the profile, AccessSecurity returns at line 35 (no auth), the execution lock passes any route lacking ExecutionRouteMetadata (CRUD is not marked), ClientIdentity lets /api/clients/register through anonymously and then accepts any registered X-Client-Id, and ManagementMode passes in normal mode. So at the app layer one could mint a client id and then create/delete/reorder/retitle/change-project a task with no control stopping it.

Why it was dismissed as a live exploit. The technical core is correct and could not be refuted with any app-layer guard, middleware, or test — but the acute exploit (an anonymous internet visitor destroying the demo) is not reachable in any sanctioned deployment. S4 (read-only TLS edge + endpoint allowlist + rate limiting) and S6 (hosting/DNS) are marked "Not started" under a hard launch invariant — "the public demo does not start until S4 closes the edge" — read-only is by design an edge property (allowlist = GET + POST /api/runner/replay/events), and the only running instance is a localhost-only test stack. The caveat is that this mitigation is deployment/operational, not app-layer, and the S4 edge is not built (documented intent, not a technically-enforced gate). It is therefore a legitimate pre-launch defense-in-depth item, not a false positive.

Pre-launch action (tracked AGT-2669). Add a real app-layer default-deny read-only gate under public-demo (reject every unsafe method except the specific replay POST), and/or build the S4 edge to allow only GET plus POST /api/runner/replay/events, verified by a deploy probe-hook. Treat execution-denial (S2) and write-denial as separate properties.

False-positives: none

All eight candidates that entered adversarial verification were either confirmed (seven) or reclassified to verified-mitigated (one). No candidate was found to be factually wrong. The verification pass also confirmed several defenses as robust rather than defective — see the "verified clean" informational notes in Appendix B (the runner-host trust boundary; the public-demo deny policy, startup gates, and replay admission policy; the chat library's absence of dynamic code execution; and the token-economy supply chain).

B.1 · Public demo — Studio backend

  • Low Execution-deny coverage is opt-in per-route metadata. PublicDemoExecutionLock.cs:66-78 denies a route only if it carries ExecutionRouteMetadata; the startup inventory and count tripwire (=78) enumerate only marked routes. Service-layer admission.Demand() backstops exist for Start/Continue/Chat but not for Claim/Review/Preview/PostStep — a future unmarked route in those classes would execute in the public demo. Fix: move to default-deny for mutating methods, or add service-layer Demand() guards to those classes.
  • Info S4 read-only edge, endpoint allowlist, CSP, security headers, and rate limiting are absent (acknowledged Not-started). demo-instanz/index.html:978,986; frontend/src/index.html has no CSP meta; Program.cs:820 gates UseHsts to the networked profile; no Caddyfile/nginx in the repo.
