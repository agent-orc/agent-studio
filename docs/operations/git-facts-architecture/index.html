Git facts off the hot path

A durable read model for Git derived facts, from repository change to instant card reads, with computation near remote execution.

As of 11 October 2026Source AGT-3044Status Decision pendingPhase Decision ready

Robert's requirement is that cards load immediately and work run remotely. The recurring load is caused by deriving repository facts too often on the Windows task server, then binding those derivations to board requests or ordinary task events. This Dossier defines a repository owned snapshot boundary and a staged move to the Linux runner host. It does not change publication authority or review evidence rules; those are covered by the delivery chain, remote execution, observation, and route ownership Dossiers.

02 Recommendation

Working decision: B, then C

Publish one immutable generation per repository from a single writer. Readers use only the last published generation. Establish this boundary on the task server now, then move the producer to the Linux runner host when Phase B remote Task Server and fenced integration publication are ready. Adopt D only if cross platform measurements show a clear net gain.

Ownership and version

The fact producer owns a repository identity, a monotonically increasing generation, the observed ref set, and the effective configuration signature. A ref fingerprint contains exact object IDs for relevant refs/heads and refs/remotes; loose ref and packed-refs changes, including its mtime, are detection inputs. A filesystem timestamp alone is never the truth key. A task event may update a card's task facts but cannot invalidate commit or ref facts. A bounded periodic reconciliation detects missed watcher events. Publish by compare and swap only if the observed refs and producer fence remain current. A delayed producer cannot replace a newer generation.

Per commit facts, such as parent IDs, tree ID and diff-tree --name-only, are content addressed by repository identity and commit SHA and persisted across restarts. Per card facts join a task input signature, attributed commit set, review subject, and target ref generation. Only cards whose relevant inputs changed are rematerialized. Integration reachability is computed once per moved target ref using a bounded rev-list or commit graph traversal and merge base batch; classification is a memory join over attributed SHAs. Missing or corrupt card input produces a typed result for that card, without aborting other cards.

Placement and publication

Before remote cutover, B runs in the task server's background service. With C, a fenced runner host close to the integration repository computes and publishes a signed or authenticated generation containing repository ID, ref object IDs, config signature, producer epoch, source commit range, generation, and checksums. The Task Server verifies monotonicity and stores the generation atomically. It retains the last good generation and content addressed commit facts. The dev seat observes the Task Server; it does not derive Git facts. This follows the 5 October observer direction and the Phase B Docker Task Server plan. The remote integration Dossier owns ref mutation and authority; fact publication must follow its fenced result, not race it.

Reads and freshness

Board generations contain pre serialized slim card summaries, with detail and patches fetched by ID on demand. A request copies a generation pointer, checks an ETag covering access scope, task generation, Git generation and runtime projection inputs, then writes the immutable bytes. Matching validators return 304. The task projection also moves off the request path: TaskIndexCache.EnsureFresh can still start or wait for a filesystem scan on an expired or invalidated snapshot. Readers do not wait for either producer, and no single slot gate serializes all responses. The card can show a bounded stale or unavailable state from the snapshot; a producer error never invokes request time Git. The AGT-2703 validator contract remains, with its inputs updated for the new generation model.

Acceptance freshness binds the delivery or reviewed result SHA, attributed commit set, verification receipt and the integration containment verdict for that subject. A later target HEAD that still contains the accepted subject cannot stale the claim by itself. A force move, lost containment, changed evidence, or changed subject can. The stored claim records the ref generation used for its verdict and is reclassified on a new generation without treating an ordinary fast forward as new acceptance work. This is the working resolution for AGT-3041.

Failure and health

Health is per repository and per card: last good generation and age, current ref generation, consecutive failures, queued and active producer work, run time, Git spawns per minute, and the slowest command. Show these in the existing health area with a warning when the last good snapshot is older than two reconciliation intervals, after three consecutive failures, or when the configured spawn budget is exceeded. Proposed initial budget: at most 120 Git child processes per repository per minute during catch up, and zero in steady no change minutes; throttle producer work and warn before crossing the cap. A bad card emits an item error and does not trip repository health. A bad repository retains its last good snapshot with an explicit stale age.

Migration order

  1. Land the no Git on request guard and budgets before further cache changes. Count spawns at the common process boundary, including fallbacks and nested calls.
  2. Repair duplicate key isolation and the 94 second payload path. Keep AGT-3039 ref drift and AGT-3041 acceptance work aligned with the snapshot contract.
  3. Fold the useful AGT-2954 salvage commits into B after reviewing overlap with current develop. Its 15 reported unintegrated commits should be reconciled selectively rather than restarting the same feature or merging an old branch wholesale. Keep its snapshot vocabulary and no Git on detail rule.
  4. Add persistent per commit facts, incremental ref reachability, and generation publication. Prove B at board scale and through restart.
  5. Implement C's fenced transport and task server store after AGT-2737 authority prerequisites. Shadow one repository against B, then move fact ownership and retire task server Git derivation.
  6. Measure D on Windows and Linux using identical repositories and workloads. Adopt the fastest correct reader only if it reduces total CPU and latency without weakening the snapshot boundary.
