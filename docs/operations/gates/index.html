§1 Scope and consolidation

Three Dossiers described the same subject from different sides. The batch gate concept (AGT-W36, 11 August 2026) asked how many deliveries one suite run should cover. The remote gate target architecture (AGT-W18, 26 July 2026) asked who owns a gate execution and on which exact tree it runs. Async validation and the test staging lane (AGT-W2, 25 July 2026) asked how much validation is redundant in the first place. None of the three can be decided without the other two: batching changes the subject a remote gate claims, and the redundancy measurement is what justifies batching at all.

This Dossier is the single current record for that theme. It keeps the decisions already taken with their dates, the open choices with their current options, and the evidence that still holds. It drops dated topology snapshots, duplicated argument, and the per-source recommendation lists that the merged §9 now carries in one place. The two closed measurements the theme rests on, the 847-task pipeline time economy baseline (AGT-W28) and the reissue-convergence negative result (AGT-W29), are kept as an evidence appendix in §10 rather than as separate current Dossiers.

Boundary. This is a concept Dossier. It recommends a target and records what an operator has to choose; it changes no runtime behavior and contains no pipeline implementation. Human acceptance of a delivered card remains outside the gate contract in every option below.

§2 What a gate is, and the two planes it runs in

A gate is deterministic verification of an exact tree: build, test, lint, and the checks that have a machine-checkable verdict. It is not the model review of a diff, and it is not human acceptance. The product keeps three planes apart, and most of the confusion this Dossier resolves comes from letting them blur.

PlaneSubjectVerdict
Per-card review planeThe settled result envelope: immutable result ref, result SHA, run attempt, delivery epoch, fencing token.Model review of requirements, diff, code quality, tests authored, durable deliverables. Cheap deterministic metadata and merge preflight.
Gate planeA clean checkout of one exact SHA: either the card's own delivery, or a combined candidate assembled from several deliveries.One authoritative full-suite verdict bound to that SHA and a gate-profile digest.
AcceptanceThe integrated card.Human. Unchanged by everything below.

Two invariants hold across every option in this Dossier, because both were established by incident rather than by preference:

  • Exact subject. A gate verdict names the SHA it tested. A lane, a review narrative, a temporary branch, or a historical bookkeeping record never means gate-passed or integrated by itself. Git ancestry is stronger than bookkeeping; a record cannot manufacture integration.
  • Fail closed. Product failure, queue timeout, execution timeout, lost lease, missing snapshot, tool failure, and cleanup failure are distinct classifications. An infrastructure failure is never relabelled as a product failure, and the absence of a trustworthy result is never relabelled as a pass.

§3 Batch gate: one suite for a closed delivery wave

A batch gate is a per-project, per-repository, per-gate-profile transaction. At close time it snapshots every delivery eligible for the same full-suite profile, assembles them mechanically on one fenced temporary branch, runs the complete suite once on that exact combined candidate, and publishes only a green tip. New arrivals wait for the next batch. All pending deliveries therefore means all eligible deliveries in that closed snapshot, never an unbounded queue that can change while the suite runs.

Closed manifest and eligibility

A delivery enters the manifest only when all of these hold: its result envelope is settled and names an immutable result ref, result SHA, run attempt, delivery epoch and fencing token; per-card model review has passed that exact subject, with the build and test aspect recorded as deferred-to-batch rather than misreported as not applicable; the card is still the current generation, with no newer attempt, reissue or operator supersede; project, repository, integration branch, gate profile and platform version match the other members; and the delivery is not already owned by another batch or an active per-task gate. The manifest records every eligible key and every exclusion with a typed reason. The coordinator may not silently select an easy subset.

Members are ordered by review-subject completion time, then durable enqueue sequence, then task key as a stable tie-breaker. Order, base SHA, member subjects and gate profile form a membership digest that every later state write and every candidate ref carries.

Mechanical replay, not central conflict resolution

Each member is replayed in a disposable detached worktree onto the current batch tip using the existing conflict-free mechanical rebase rules, and every replacement SHA maps back to its original delivery SHA. A successful replay advances only the temporary batch ref; it does not make the card integrated. A member that conflicts aborts its own replay without changing the batch tip, receives the typed conflict and file list, and is ejected to the existing rebase-and-retry steer path. The coordinator never guesses which content should win. If more than a quarter of a batch, or three members in succession, conflict during construction, the candidate closes with the members already admitted and the unattempted tail moves intact to the next batch.

Green path and per-member evidence

A batch run record is persisted before execution: batch id, membership digest, base SHA, candidate SHA, gate profile and digest, host, lease fence, command list, start time and evidence location. The complete suite then runs once on a clean checkout of the candidate SHA, and the pass receipt names the same candidate SHA and profile digest. Before publication the coordinator revalidates every member generation, acquires the project publication lease, and verifies that the develop tip still equals the recorded pre-tip. Publication is a fast-forward when the tested candidate descends directly from that pre-tip; a merge topology is allowed only when the merge commit itself was prebuilt and tested as the candidate. A new, untested merge commit is never created after the suite. If develop moved, the run is marked stale-base, reconstructed on the new base and run again. That is the cost of preserving the exact-SHA claim.

Each member then needs two linked facts rather than one batch-wide narrative. The gate-passed record carries task key, run attempt, delivery epoch, original result SHA, the replacement SHA set, batch id, membership digest, base SHA, tested candidate SHA, gate profile digest, batch-run id, verdict and evidence path; missing or mismatched identity is batch-gate-evidence-missing and the card cannot be marked gate-passed. The integration record carries the integration branch, the exact remote tip, the member's integrated SHA set and evidence pointing at the same batch run and candidate; a push or ancestry verification failure is integration-unverified and the card stays out of Completed. This is the honest-completion invariant established by AGT-2543: no card reaches Completed, and no surface says gate-passed, unless its current attempt points to a successful batch run, the exact tested candidate, and its complete SHA mapping.

The existing endpoint is not a gate authority. POST /api/tasks/{id}/integration-records appends an idempotent historical classification once a card is in Human Review or later. Its five-class schema rejects in-flight lanes, never moves a card and never changes Git. A native append-only per-member batch-gate record is therefore required before lane release; the existing endpoint keeps only its integration bookkeeping role. This is open decision D3.

Red path and honest isolation bounds

A red candidate is first classified, because the three classes have nothing in common. An infrastructure red (host loss, timeout without a test verdict, registry outage, disk pressure, lease loss) attributes no member, is retried once on a healthy gate host, and pauses the batch for operator visibility on a second occurrence. A deterministic suite red (a reproduced failing test or build on the same candidate) starts ordered halving from the same base and profile. A flaky red uses the repository's existing bounded quarantine policy, preserves both runs, and is never converted into green by majority vote.

Halving splits the ordered member set, reconstructs the first half on the original base, and runs the same complete gate. A red half continues; a green half continues with the complement only under the single-cause assumption, and the green subset is preserved as evidence. At one member, that delivery is ejected to a per-task gate. Survivors are then rebuilt in original order and run once.

The log2(n) limit must not be overstated. For one reproducible, monotone offender, one failing half per level isolates it in at most ceil(log2 n) diagnostic suite runs after the initial red, plus one final survivor run. That is not a universal bound.
Failure shapeHonest boundFallback

An unresolved cohort is a visible fallback, not a batch success.

Authority, fencing, and the promotion train

Two levels of fencing apply. The batch coordinator holds a durable lease keyed by project, repository, integration branch and gate profile; lease loss cancels the suite and forbids publication, and a successor resumes only from a durable manifest whose digest and fence still match. Member attempt fences prevent stale attribution. Above both sits the project ref-mutation lease, shared with direct integration, auto-main advancement and the candidate-SHA promotion train (AGT-2594), and acquired only for final revalidation and publication so that a long suite does not block read-only preparation. The train promotes only its recorded candidate SHA and never discovers a temporary batch ref; the two publish phases cannot overlap.

A member superseded mid-batch is handled by the moment it happens: before suite start, eject the stale generation and reconstruct; while the suite runs, let it stop safely and mark its verdict unusable, because a green result for the old manifest cannot publish; after green but before publish, the mandatory final membership check fails closed; after a verified publish, the transaction is complete and the old generation's integration history is preserved, but its gate result is never transferred to a newer attempt.

The integrate-before-review contract (AGT-2528, AGT-2603) is preserved with a changed green predicate and publication unit: settled delivery, then per-card model review, then batch pending, then batch gate and verified mirror, then Human Review. A temporary replay is not the integration event; only verified membership in develop releases a member to Human Review.

The review-first amendment

Operator note, 2026-08-18. The full suite should not run per round at all. Model review and cheap deterministic checks run first on every delivery; the full suite runs only as the final gate, once a card appears done with no further round expected, and there it runs once per batch rather than once per card. This composes with the batch gate rather than replacing it: roughly half of today's suite runs are spent on rounds that die at review or on conflicts and would be eliminated outright. It is carried forward as open decision D1.

§4 Remote gate: a claimable, fenced gate step

Batching decides what a suite run covers. This section decides who owns the run. The path in production today is a direct SSH subprocess: the Studio backend chooses a SHA, derives an SSH alias from the configured execution runner, and waits for the exit code of a remote command that scans $HOME/runner-work/*/repo for a matching repository. It is fast, and it is out of band. The central control plane has no claim, lease, fence or durable gate attempt to show; the activity store is process-local and lost on restart; and once the remote command loop starts, an SSH exit can be recorded as the gate verdict instead of selecting a fallback. That is the transport boundary leaking into verdict classification.

What the replacement must make true

RequirementStatement
R1 identityRepository identity, expected result SHA, durable ref or source bundle, plan digest and pipeline-definition version are fixed before dispatch.
R2 authorityEvery execution has a lease, fence, idempotency key and explicit attempt number. A late report cannot overwrite a newer attempt.
R3 materializationThe claim names the repository and durable source. The executor fetches that source, verifies the SHA, then creates a disposable workspace. No directory guessing by glob.
R4 outcomesTest failures are product outcomes. Missing source, tool failure, timeout, lost lease and cleanup failure are typed infrastructure outcomes.
R5 visibilityQueue, claim, host, materialization, command, cleanup, retry and terminal facts are Task Server data, not backend inference.
R6 bounded scopeThe protocol accepts catalogued deterministic gate and post-step plans with bounded commands, evidence, time and resources. It does not accept arbitrary fan-out.

The central state machine is queued, claimed, materializing, running, reporting, cleaning, and then one of passed, product-failed, infra-retry, infra-failed, timed-out, cancelled. Studio derives queue age, active host, attempt count, phase, deadline, outcome and evidence availability from those durable facts. The current gate count per host becomes the sum of visible claimed, running and cleaning attempts rather than a hard-coded process-local capacity snapshot.

Materialization runs in a fixed order: the Engine resolves the authoritative result SHA and creates the immutable subject through the Task API; the Task Server admits a claim only from a host with fresh matching capabilities and a free gate slot; the host fetches the declared result ref, or the declared source bundle whose digest the subject pins, and never scans unrelated host repositories; the host verifies repository identity and object type, creates a fence-specific disposable workspace, checks that HEAD equals the expected SHA, and records tree and dirty proof; the host executes the frozen plan under per-command and overall deadlines, records bounded evidence, cleans up, and submits a fenced report; the Task Server validates the report and the Engine applies pipeline policy to the terminal outcome.

What local fallback means in the target. Another registered Agent Host eligible to claim the same immutable gate attempt. It never means silently returning to an in-process build on the Task Server or the Studio backend. Keeping that in-process path alive as a silent target fallback would preserve exactly the two-execution-model coupling this design removes.

Open migration

The migration is ordered replacement first, teardown second, and the middle step is the only new implementation card this section proposes: a gate contract, a host executor, and the central view, with the build and test gate migrated and parity proven. AGT-2262, the teardown of the SSH bridge, already exists and stays parked behind it.

Acceptance for the implementation card: the Task Server persists subject, attempt, lease, events, report, cleanup and typed retry state across restarts; the Agent Host claims only with fresh gate, repository and toolchain capabilities and materializes the declared exact SHA without directory scanning; the Engine owns no durable attempt state; product failure, queue timeout, execution timeout, lost lease, missing snapshot, tool failure and cleanup failure have distinct tested classifications; stale-fence reports and cleanup messages are rejected, and an infrastructure retry preserves the immutable subject while raising the fence; Studio reads queue, active host and phase, retry history, tested SHA and terminal evidence from Task Server facts; the migrated gate meets or improves the current remote throughput envelope and never runs in the Task Server checkout; and a bounded canary proves remote pass, product failure, host loss, Task Server restart, Engine restart, no eligible host, and cleanup failure before the bridge is disabled.

Only then does teardown remove RemoteSshHost, ResolveRemoteGateSshHost, the SSH bridge region in BuildTestGateRunner with its process-local semaphore and scripts, RemoteGateActivityStore, the backend alias-based gate-count projection, and the obsolete SSH configuration documentation in the same change. Whether the in-process compatibility path is removed or explicitly retained is a separate choice, and it must not survive by accident. The teardown threshold is open decision D9.

Status of this section. Code inspection on 26 July 2026 confirmed that the replacement does not exist, and a re-verification against develop on 24 August 2026 found the only Gate* types in the backend still belonged to the unrelated build-test gate. The design has never been approved in a sight review and has zero implementation. Nothing in §4 describes shipped behavior.

§5 Validation economy: what survives from async validation

The staging-lane proposal of 25 July 2026 started from a plausible intuition, that tests are slow and run for every card, so validation should move off the critical path. Measurement reshaped it. The test gate carried 16.6% of compute and exactly zero tokens, against token spend on the order of 2000 times the test CPU cost, so this is a throughput problem and never a money argument. Three principles from that Dossier survive unchanged and constrain everything above.

PrincipleStatusWhy it holds
No model-based test selectionExplicitly rejectedIt spends the expensive resource, tokens, to save the cheapest one, CPU. Recorded as rejected on 25 July 2026 and not reopened here.
Per-SHA gate cacheRecommended, unbuiltBind the gate result to the tested tree SHA; an identical SHA skips the run. The gate ran about 3.65 times per task and 84% of its total time was retries, much of it on barely-changed trees. Largest lever for the smallest effort, and it pays off under every option in §3 and §4.
Deterministic test scopingRecommended, unbuiltChanged files map to affected test projects through a maintained folder-to-project table, new test files always run, and a change set spanning modules falls back to the full suite. Pure diff plus lookup, zero tokens. The same shape as the existing skip-if-fresh hash rule for review units.
Staging lane and test-integration branchMeasure firstNet benefit hinges on the batch green rate. A red five-card batch can cost up to five further individual runs, which is slower than per-card testing would have been. §3 answers the same question with a closed manifest and bounded halving, so this is now the same decision, taken once (D10).

Two open quantities from that Dossier are still unmeasured and still gate the same choices: the batch green rate, meaning how often N individually review-green cards are test-green together, and the same-SHA re-test rate, meaning how often exactly the same tree is revalidated on a reissue, which is the ceiling on the cache's benefit and is expected to be high. Two upkeep questions remain attached to scoping: who keeps the folder-to-test-project map current, because a stale map yields falsely green gates, and whether the machine-wide gate lock stays machine-wide or becomes per integration branch.

§7 Recommendation

Recommended default

Run the full suite once per closed batch, as the final gate after model review, on an exact combined candidate, executed by a claimable and fenced gate step that the Task Server owns. In option terms: axis 1 is A composed with D, keeping C as the measured scale-out and B only for audited no-code classes; axis 2 is A, with capability as an admission predicate rather than an execution model.

The two axes reinforce each other. Batching without a durable attempt record would mean assembling a combined candidate and then losing its execution identity to a process-local SSH call, which is exactly the evidence gap AGT-2543 closed for single deliveries. A claimable gate step without batching would give every wave the same concurrency problem with better bookkeeping. Together they produce one fenced attempt against one exact candidate SHA, with per-member evidence that survives a restart.

Order. The per-SHA gate cache first, because it removes redundant re-validation under every other option and needs no new architecture. Deterministic scoping second, for the same reason. The claimable gate step third, because it is the prerequisite for honest batch evidence. The batch gate pilot last, starting with documentation-only deliveries, because its go or no-go depends on a batch green rate that is still unmeasured.

Non-negotiable in every variant. Per-card model review stays. The full suite is never weakened or selected by a model. Publication is never a new untested merge commit and never a force push. One shared fenced ref-mutation lease governs batch publication, direct integration, auto-main advancement and the promotion train. Infrastructure failure is never reinterpreted as product failure. Human acceptance is unchanged.

What a pilot must prove before any default changes. Full-suite runs per eligible delivered member at or below 0.40 with a mean batch size of at least 3; at least 50% fewer host-overload minutes in comparable waves; queue drain improved by at least 50% at comparable arrivals; median gate latency no worse than 15 minutes and p95 no worse than 30 minutes; batch green rate at least 80% with construction ejections at or below 10%; and zero stale-attempt passes, missing SHA mappings, untested publish SHAs or false Completed cards. The last line is a correctness floor, not a target: any violation stops the pilot. Cost is reported but is not a success metric, because §10 already established that gates are not where the money is.

Rollback. Batching is disabled per project by stopping manifest formation. An unmirrored batch is marked abandoned-by-rollback, its manifest, logs and candidate ref retained for a bounded evidence period, and each current member returns to the per-task gate with the same immutable delivery subject. Coding is not reissued merely because batching was disabled. A candidate already verified and mirrored is normal history: it is never reset or rewritten, and a later regression is addressed by a normal revert delivery. Missing per-member bookkeeping is retried from the durable batch record even after routing is disabled, so rollback cannot create incomplete completion evidence.

§10 Evidence appendix: two closed measurements

Both measurements are complete, dated and no longer current Dossiers. Their numbers are kept here because the gate argument above depends on them and would otherwise rest on assertion.

Pipeline time economy: the 847-task baseline (AGT-W28, 25 July 2026)

Aggregating the per-step ledger in pipeline-execution.json across 847 tasks that carried pipeline data, out of 1,314 task folders scanned, and 2,396 attempts, gives the baseline this theme argues against. Of 798 hours of wall time, roughly 38% was waiting with no compute, 41% was redo and 21% was first-attempt work. Of 29,808 minutes of compute, the coding step took 66.8% and carried about 98% of all tokens (1.89 billion), while the deterministic test gate took 16.6% and carried a true zero tokens. The gate ran 1,954 times across the 535 tasks that had one, about 3.65 runs per task, and 84% of its total time was retries. Most retries were the intended quality loop rather than dumb repeats: 978 adapted reissue prompts across 437 tasks, and 78% of 6,320 post-processing outcomes classified as findings-added; the clearly technical cause, 560 failed post-processing events, was almost all test-gate timeouts. Priced at a stated blended token rate the corpus was on the order of 8,400 US dollars in tokens against roughly 4 dollars of test CPU, a ratio near 2000 to 1. Two caveats travel with every figure: the on-disk attempt archive keeps at most ten previous attempts, so all retry figures are a conservative floor, and a missing field is a coverage gap rather than a zero, the single true zero being the gate's token count. The absolute numbers drift with further runs and with model pricing; the ratios do not. The consequence for this Dossier is exact: gate work buys throughput and almost no budget, so batching, remote ownership and caching must be justified by concurrency and evidence quality, never as a cost saving.

Reissue convergence: a negative result (AGT-W29, 26 July 2026)

The adjacent question was whether the reducible retry volume could be cut at the source by writing sharper reissue prompts. An observational snapshot classified first reissue prompts by a deterministic text rule and compared their later explicit pipeline attempts against a right-censor-aware acceptance endpoint: 404 mapped tasks, 202 in each group, recovered from 438 first reissue histories. Concrete finding-first prompts reached 49.85% acceptance by attempt five against 47.75% for generic prompts, a difference of 2.1 percentage points with a 95% bootstrap interval from minus 12.6 to plus 18.1, and a restricted mean of 3.594 unresolved attempts against 3.752, a difference of minus 0.159 with an interval from minus 0.530 to plus 0.194. Both intervals cross zero, and the groups are visibly unbalanced by model route and task type, which are confounders rather than adjustments. The recorded decision was to keep the production default unchanged and to test concrete findings-first structure only in a controlled arm, without adding generic length, guessed references or repeated raw logs. The result matters here as a boundary: the retry volume that §10 measured cannot be assumed away by better prompting, so the gate-side levers in §3 to §5 remain the ones with evidence behind them.
