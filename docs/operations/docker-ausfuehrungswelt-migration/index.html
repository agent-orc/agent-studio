Isolierte Ausführung: Vorbereitungsskripte, Isolation, heilender Orchestrator

Wie jedes Projekt reproduzierbar vorbereitet, jeder Coding-Agent isoliert ausgeführt, jeder Test als Bürger erster Klasse geführt und jeder Ausführungsfehler von einem Orchestrator diagnostiziert und geheilt wird. Docker ist darin eine Variante, nicht die Voraussetzung. Mit Auswirkungen je Projekt, Migration in Stufen und der Frage, was Menschen erleben, die Agent Studio installieren.

(17 Projekte), Build-Profile, Gate-Logs, runner/Dockerfile, agent-runner-01
Revision 12.09. nachmittags. Die Vormittagsfassung hieß „Docker als einzige Ausführungswelt" und setzte Docker auf jedem Host voraus. Der Operator hat das präzisiert: Das Onboarden von Projekten darf nicht komplizierter werden; das Anlegen eines Worktrees soll ein Skript machen, das sich darum kümmert, dass alles da ist; ein Docker-Image ist eine optionale Variante, die Vorbereitung beschleunigen kann; das Kernproblem sind verschiedene Versionen, also gehören schnelles npm install mit Cache und dotnet restore mit Cache in saubere Skripte; es fehlt der Orchestrator, der ein Problem gründlich anschaut, einen Folgeprompt hinzufügt und die Pipeline heilt, und der Testfehler stabilisiert; Test-Analyse wird Bürger erster Klasse, eine stabile CI-Pipeline im Werkzeug ist ein Produktfeature („CI/CD integrated"), samt Testlauf-Historie mit Laufzeiten und durchgeführten Läufen. Für die Produktversion gilt: Coding-Agents in isolierten Umgebungen reichen, Kommunikation und Heilung laufen durch Agent Studio. Zuletzt: Der Agent-Orchestrator entwickelt die passenden Skripte in Zusammenarbeit mit dem Nutzer, auch auf eigene Initiative, weil Softwareprojekte unterschiedlich sind; die Basis sind Worktrees und stabile Checkouts, die immer wieder aktuell gehalten werden müssen; für die Installation von Bibliotheken gibt es technologieabhängige, allgemeine Lösungen (npm, NuGet) mit Caches. Die Vormittagsfassung bleibt in der Git-Historie.
Kernaussage. Reproduzierbarkeit entsteht nicht durch Docker, sondern durch drei Dinge, die Docker nur bündelt: eine Vorbereitung, die mit dem Commit reist (Skript im Repo, Versionen aus Lockfiles und Tool-Manifesten, Caches nach Inhalt), eine Isolation je Lauf (Prozessbaum, Dateisystem, Netz, Geheimnisse; Container ist eine von mehreren Techniken), und ein Orchestrator, der Ausführungs- und Testfehler versteht und die Pipeline heilt, statt Karten zu eskalieren. Tests bekommen dafür Inventar, Historie und Laufzeiten als eigene Daten: die Pipeline im Werkzeug ist die CI des Projekts. Onboarding heißt dann: Repo anmelden, Vorbereitungsskript aus der Stack-Erkennung erzeugen lassen, Probelauf, fertig.

§1Entscheidung und Geltungsbereich

Stand der Entscheidungen des Operators vom 12.09.2026, in der Reihenfolge ihrer Präzisierung:

  1. Windows bleibt keine Ausführungswelt im heutigen Sinn: kein Coding-Lauf, kein Gate und kein Review-Aspekt läuft mehr als nackter Prozess mit der geerbten Umgebung des Studios.
  2. Jede Ausführung ist isoliert. Für Coding-Agents in isolierten Umgebungen gilt das als ausreichend; Docker ist eine Isolations- und Beschleunigungstechnik, nicht die Voraussetzung.
  3. Die Vorbereitung eines Worktrees ist ein Skript, das mit dem Projekt reist und sich darum kümmert, dass alles da ist: richtige Versionen, Abhängigkeiten, Caches. Der Orchestrator entwickelt dieses Skript mit dem Nutzer, auch auf eigene Initiative, weil jedes Softwareprojekt anders ist. Die Basis darunter sind Worktrees und ein stabiler, aktuell gehaltener Checkout je Projekt; die Installation von Bibliotheken löst das Produkt je Technologie allgemein (npm, NuGet, Playwright) mit Caches.
  4. Ein Orchestrator bewertet Probleme projektspezifisch, ergänzt Folgeprompts, heilt die Pipeline und stabilisiert Testfehler.
  5. Tests sind Bürger erster Klasse: Inventar, Laufzeiten, Historie der Läufe, Stabilität je Test; die Pipeline im Werkzeug ist eine stabile CI, „CI/CD integrated" ist ein Produktfeature.
  6. Für die Produktversion zählt, was Menschen erleben, die Agent Studio installieren: Sie müssen solche Probleme lösen können, und Kommunikation wie Heilung laufen durch Agent Studio.

„Ausführung" umfasst weiterhin alles, was Code eines Projekts oder ein Agenten-CLI startet (Coding-Läufe, Gates, Review-Aspekte, Orchestrator-Sessions mit CLI, Post-Steps). Nicht Gegenstand bleibt, wo Task Server und Operations-Server laufen (AGT-W49).

§2Zielbild in drei Schichten

Der Unterschied zur Vormittagsfassung in einem Satz: Dort war das Image die Quelle der Reproduzierbarkeit und der Host musste Docker mitbringen. Hier ist das Skript die Quelle, und das Image ist ein gebautes Ergebnis dieses Skripts, das man nutzen kann, wenn es da ist.

§3Vorbereitung: das Skript, das sich um alles kümmert

Heute entsteht ein Worktree aus git worktree add plus dem, was zufällig da ist: das Studio-Build-Profil, ein ensure-deps.mjs im Repo, die Node- und SDK-Version des Hosts, der Dependency-Cache des Gates. Vier Quellen, keine ist zuständig. Das Ziel: eine Quelle, die mit dem Commit reist, und darunter eine Basis, die das Produkt für alle Projekte gleich löst.

Der Worktree entsteht dann in genau einem Schritt: git worktree add, prepare, Manifest lesen. Gate und Review benutzen denselben Schritt. Kein ensure-deps-Hook im Build, kein Gate-eigener Cache, kein Unterschied zwischen „im Lauf gebaut" und „im Gate gebaut".

§4Isolation je Lauf

Isolation bedeutet: der Lauf sieht nur seinen Worktree, seine Caches und seine Geheimnisse; seine Kindprozesse enden mit ihm; Netz, CPU, Speicher und Zeit sind begrenzt; der Host erbt nichts aus dem Lauf und der Lauf nichts aus der Umgebung des Studios. Welche Technik das leistet, entscheidet das Executor-Profil, nicht das Projekt:

Auf jeder Plattform gilt dieselbe Regel für die Umgebung: der Lauf bekommt genau die Variablen, die project.yml und das Executor-Profil nennen. Die geerbte Studio-Umgebung (heute mit ELECTRON_RUN_AS_NODE aus VS Code) erreicht keinen Lauf mehr. Und auf jeder Plattform hat ein Worktree einen Lease: er gehört dem Lauf, wird nach dem Lauf vom Executor aufgeräumt, und was sich nicht aufräumen lässt, wird beiseitegelegt und dem Orchestrator gemeldet (AGT-2781).

§5Der Orchestrator als Diagnose und Heilung

Das ist das fehlende Stück. Heute endet ein Ausführungsfehler in einer Klassifikation per Signaturliste und dann in einem Retry-Budget; niemand schaut hin, bis der Operator das Log liest. Der Orchestrator bekommt drei Aufgaben, in dieser Reihenfolge:

  1. Gründlich anschauen. Er liest den Fehler mit Kontext: Vorbereitungs-Manifest, Befehl, Exit-Code, Ausgabe, Baseline-Ergebnis, Testhistorie des betroffenen Tests (§5a), Fingerprint-Treffer auf anderen Karten, letzte Änderungen an project.yml. Deterministische Prüfungen zuerst (Baseline-Vergleich, sauberer Wiederholungslauf ohne Cache, Versionsabgleich, Stabilitätswert des Tests), dann, wenn nötig, ein Modellaufruf mit dem Projektkontext. Ergebnis: eine Klasse mit Beweis. Produkt, Umgebung, Version, flaky, Konfiguration.
  2. Heilen, was ihm gehört. Umgebung: Cache verwerfen und Vorbereitung wiederholen. Version: prepare erneut mit Installation, oder Vorschlag an project.yml als Karte. Worktree: aufräumen und neu anlegen. Flaky Test: Quarantäne mit Ablauf und Stabilisierungs-Karte, deren Prompt die Historie des Tests enthält (wann rot, auf welchen Executoren, mit welcher Ausgabe). Toolchain-Ausfall: Unterbrecher öffnen, Ursachen-Karte anlegen, Betroffene warten lassen. Jede Heilung ist ein Eintrag in der Timeline mit Begründung. Was er heilen darf, legt der Operator fest (D6).
  3. Folgeprompt statt Eskalation. Ist es ein Produktfehler, ergänzt er den Prompt der Karte um den Befund (genauer Test, genaue Stelle, was der Baseline-Vergleich gezeigt hat), so wie es der Operator heute von Hand tut (AGT-2778). Ist es ein Projektproblem (fehlende Version, kaputtes Skript, instabiler Test), legt er die Karte im Projekt an und verknüpft sie. Nur wenn er nicht weiterkommt, stellt er dem Menschen eine Frage, in der Karte, mit dem, was er schon weiß.

Dazu kommt eine vierte Aufgabe mit eigener Initiative: die Skripte des Projekts entwickeln. Der Orchestrator kennt die Bausteine des Produkts und die Eigenheiten des Projekts (Manifest, Fehlerhistorie, Lockfile-Änderungen). Er schlägt dem Nutzer Änderungen am Vorbereitungsskript vor, wenn ein Lauf gezeigt hat, dass etwas fehlt, wenn ein Baustein besser geworden ist oder wenn die Vorbereitung länger dauert als das Manifest erwarten lässt. Der Nutzer entscheidet im Repo; das Skript bleibt Code, der Orchestrator ist sein Mitautor.

Der Orchestrator ist projektspezifisch, weil er project.yml, das Manifest, die Testhistorie und die Karten-Historie des Projekts als Kontext hat. Er ist derselbe Mechanismus, der in AGT-W15 als Wächter und in AGT-2765 als Intervention beschrieben ist; neu ist, dass er Vorbereitung, Isolation und Testdaten als Werkzeuge bekommt und dass seine Heilungen Produktverhalten sind, keine Rezepte im Gedächtnis des Operators.

§5aTests und CI/CD als Produktfeature

Operator, 12.09.: „Testfehler sollte der Orchestrator stabilisieren. Test-Analyse muss ein First-Class-Citizen werden. Wie viele Tests gibt es, wie lange laufen die? Wir brauchen tatsächlich eine stabile CI-Pipeline im Tool, das müssen wir als Produkt-Feature sehen. CI/CD integrated ist ein Feature. Dazu gehört Testlauf-Historie: Laufzeiten, durchgeführte Läufe."

Dauer und Kosten je Schritt, im Lauf und als Statistik je Projekt

Operator, 12.09.: „Im CI/CD-Teil und im Lauf sollte klar sein, was wie lange dauert. Die Pipeline hat Build-Schritte und Test-Schritte, darum herum erweitern wir. Für die Pipeline-Ausführung soll es eine Statistikseite pro Projekt geben, damit man sieht, wie lange was dauert und auch wie teuer es ist: IO, CPU, Tokens, und in welchen Schritten immer wieder Fehler auftreten."

Zwei Ansichten, eine Datenquelle. Im Lauf (Karte, Pipeline-Tab) steht jeder Schritt mit Start, Dauer, Ergebnis und Kosten in einer Zeile: Vorbereitung (Cache-Treffer oder Install, Sekunden), Guard, Build je Ziel, Test je Suite mit Anzahl und roten Tests, E2E, Review-Aspekte mit Modell und Tokens, Integration, Deploy. Die Seite beantwortet die vier Fragen, die heute nur mit Log-Suche zu beantworten sind: Wo geht die Zeit hin (heute: nicht in den 24 Minuten Tests, sondern in Vorbereitung ohne Cache, Baseline und Wartezeit), was kostet ein Lauf (heute: Listenpreis nur für Coding-Läufe, Rest unbekannt), welcher Schritt fällt immer wieder (heute: das Build-Gate mit 588 Fehlschlägen, davon ein großer Teil Umgebung), und lohnt sich eine Maßnahme (Image als Beschleuniger, Sharding, Quarantäne) an den Zahlen vor und nach.

Zwei Konsequenzen für den Rest des Dossiers: Der Gate-Runner wird zur Pipeline-Engine, die Stufen aus project.yml liest und jede Stufe mit Dauer und Ergebnis in die Historie schreibt. Und die Testhistorie ist eine Datenquelle des Orchestrators, nicht nur eine Ansicht: ohne sie ist „flaky" ein Bauchgefühl, mit ihr ein Wert.

§9Migration in Stufen

Grundregel bleibt: jede Stufe führt eine Fähigkeit ein, lässt die alte parallel laufen und hat ein Abschaltkriterium. Der Linux-Runner geht zuerst; die Workstation folgt, sobald Host-Manager und Installer stehen. Docker ist in keiner Stufe Voraussetzung.

  1. Vorbereitungsvertrag, Generator, Test-Inventar

    Schema für project.yml (mit Test-Suiten) und prepare, inhaltsadressierter Cache je Executor, Manifest, Validator; Generator aus der Stack-Erkennung; Anzeige „Ausführung" in den Projekt-Einstellungen mit begründetem Override; Test-Inventar aus dem ersten Lauf. Agent Studio, Quality Studio und Token Economy bekommen die ersten Definitionen als Karten in ihre Repos.

    Abschaltkriterium: Gate und Lauf der drei Piloten benutzen den Vorbereitungsschritt; kein ensure-deps, kein Gate-Cache alt; Test-Übersicht zeigt Anzahl und Laufzeit je Suite. Dauer: 1–2 Wochen.

  2. Isolation je Lauf und Pipeline-Engine auf dem Linux-Runner

    Executor-Profile mit Isolationstechnik; Sandbox-Prozess als Standard (Prozessgruppe, Nutzer, deklarierte Umgebung, Ressourcen, Worktree-Lease), Container als Option pro Projekt (Tranche C C1-Kern), Sysbox für docker-capable. Der Gate-Runner wird zur Pipeline-Engine mit Stufen aus project.yml und Testlauf-Historie je Stufe; die Baseline wird zum CI-Lauf des Integrationsbranches.

    Abschaltkriterium: je Pilotprojekt 20 Läufe ohne Umgebungsfehler; kein Lauf mehr mit geerbter Umgebung; Historie füllt sich für Karten und Integrationsbranch. Dauer: 2–3 Wochen.

  3. Orchestrator: Diagnose, Heilung, Test-Stabilisierung, Folgeprompt

    Diagnosekontrakt (AGT-W50 K1) mit Manifest, Versionsabgleich und Stabilitätswert; Heilungen im Rahmen von D6; Quarantäne mit Ablauf und Stabilisierungs-Karten; Unterbrecher (K2); Folgeprompt und Projekt-Karte; Frage an den Menschen in der Karte. Replay der Fälle WEB-19, CAC-18, AGT-2778, AGT-2779 und der QS-ReviewRunStoreTests als Beweis.

    Abschaltkriterium: vier Wochen ohne manuelle Heilung durch den Operator für die Klassen Umgebung, Version, Worktree, flaky. Dauer: 2–3 Wochen, parallel zu M2.

  4. Lokale Projekte auf den Linux-Executor, Deploy als Stufe

    WEB, QSW, MKT, AOW, AIP, FAM wechseln von lokal auf den Runner; Deploy-Keys ins Geheimnis-Volume; Startregeln und Deploy-Regeln aus project.yml; Registry-Lücken schließen.

    Abschaltkriterium: 14 Tage ohne lokalen Pickup; Deploy-Läufe der Websites in der Historie. Dauer: 1 Woche.

  5. Host-Manager und Release als Artefakt

    Host-Manager als Dienst auf agent-runner-01 und dem Task-Server-Host: Executor-Profile, CLI-Pins, Stack (Compose, wenn Docker da ist, sonst Dienste), Updates mit Restart-Kontinuität (AGT-2780), LinkSupervisor (AGT-2763). Release als Artefakt-Manifest; der Update-Service wird abgelöst.

    Abschaltkriterium: Update-Drill ohne Verlust. Dauer: 2 Wochen.

  6. Workstation: Installer, Host-Manager, Sandbox-Profil auf Windows

    Installer (AGT-W8) mit Sandbox-Profil als Standard (Entscheidung D1), Docker als erkannter Beschleuniger; Host-Manager als Windows-Dienst; Ablösung von Stable-Checkout, Update-Service, Scheduled Tasks, Start-Skripten; lokale Läufe nur noch über den Executor.

    Abschaltkriterium: Onboarding-Probe auf einem frischen Windows-Rechner in unter einer Stunde bis zur ersten grünen Karte; Operator-Workstation 14 Tage nur über den Host-Manager. Dauer: 3 Wochen.

  7. Rückbau und Beweis

    Native Ausführungspfade mit geerbter Umgebung entfernen, alten Gate-Cache und Signaturlisten löschen, Windows-Gate auf windows-host beschränken, Regressionsszenario (Restart, Cache-Gift, Versionswechsel, Modell-Entzug, Kindprozess, flaky Test) als Promotion-Gate.

    Abschaltkriterium: Guard-Test verschärft: kein Host-CLI-Start außerhalb des Executors; Szenario grün. Dauer: 1–2 Wochen.

Gesamtdauer 10 bis 13 Wochen bei laufender Fleet. Kritischer Pfad: M1 → M2 → M5 → M6. M3 läuft parallel ab M2, M4 hängt an M2, M7 an allem.
