02 · Context model

Conversation Scope, Ambient Surface, and Explicit References

The active tab can change what a question means without creating a new conversation. A task is the one surface that also owns a durable task transcript.

1. Conversation scope

Where history is persisted: project or task. Selected by navigation, a chat switcher, or pinning.

2. Ambient surface

What the operator is looking at now: board, Wiki page, Dossier, task, file, or diff. Recomputed per send.

3. Explicit references

What the operator deliberately adds: cards, pages, files, commits, or selected text. Removable before send.

Studio state

Active tab, project, task, board selection, page ref, Dossier selection, commit identity.

Typed request

Scope key, surface descriptor, explicit reference ids, and one bounded budget policy.

Backend resolver

Validates scope, resolves sources, deduplicates, caps content, records revision and omissions.

Prompt + receipt

One structured context block reaches the model. The same source ledger returns to the UI.

Unresolved is visible, not a model-generated warning.

Active-context rules

  1. Snapshot at submit. Capture scope, active surface, selection, and explicit chips once when Send is pressed. A navigation change during resolution cannot alter the in-flight turn.
  2. Follow mode derives automatically. Task detail selects the task transcript. All other project surfaces select the project transcript and add their surface as ambient input.
  3. Pinning freezes the conversation scope. A newly visited tab becomes a one-click suggestion instead of silently replacing a pinned task's automatic context. Cross-project suggestions always require an explicit switch or attach action.
  4. Explicit references are additive, not authoritative. They get priority within the budget but cannot bypass project isolation or path validation.
  5. Every stateless turn gets the bounded envelope. Do not rely on the current first-send-only navigation cache. If resumable execution returns later, context deltas may optimize cost, but receipts remain per turn.
03 · Prompt and token policy

Intent and Current Evidence within the Token Budget

The budget below is a model-independent planning envelope. It does not change model routing or correctness floors. Exact provider usage remains telemetry, while the pre-send count can be an estimate.

Recommended budget contract

4,000-token soft cap for automatic context, 6,000-token hard cap for automatic context, and up to 8,000 total tokens when the operator explicitly attaches sources. An explicit source that cannot fit is never silently dropped: include a deterministic excerpt and state the omission, or ask the operator to narrow it.

Prompt assembly order

  1. Scoped chat preamble. Role, project isolation, read-only authority, and the exact conversation scope. Do not prepend the all-project global boot prompt to a project turn.
  2. Context ledger. Stable source refs, revisions, freshness, inclusion state, and budget. This is the same ledger shown in the UI receipt.
  3. Automatic evidence. Project base, task bundle or active surface, deduplicated by canonical source id.
  4. Explicit attachments. User-selected sources receive priority after safety checks. Their content cannot silently disappear.
  5. Conversation continuity and message. Add the bounded recent transcript, then the new user message. Keep the message last and unambiguous.
Degradation must be useful

If status.md is absent, a file changed after the operator viewed it, or a task key cannot resolve, the host records that state in the receipt and the prompt. The turn may continue with the remaining evidence. Scope violations, traversal, and ambiguous repositories are blocked before model invocation.

04 · Task Chat

Boundary between Task Questions and Agent Continuation

The task detail already has an Activity composer that calls continueJob, starts or queues a CLI run, and pause-then-sends while running. Task-scoped Orchestrator Q&A stays in the right side sheet and must not reuse that mutation path.

Boundary between Orchestrator task context and task-agent Activity
Dimension Orchestrator side sheet: task-scoped Q&A Activity: existing task-agent control
Meaning Questions implicitly refer to the open task and its evidence. Text is a continuation or intervention for the task agent.
Side effect Read-only answer by default. Typed actions may be proposed separately. Starts, queues, or interrupts a CLI run through existing task APIs.
Transcript Existing task:<project>/<key> orchestrator transcript. Task CLI output, run timeline, user follow-ups, and orchestrator events.
Automatic context Metadata, prompt.md, status.md, recent run summaries/error excerpts, commits[], recent task-chat turns. The task execution runtime and its own session/context rules.
UI label Orchestrator in the right side sheet, with a compact note that questions automatically refer to the active task and do not control the task agent. Activity, with “Continue task agent” action copy when a send will run work.
Project chat relationship A separate task thread. Navigating to the task activates that context in the side sheet, but does not merge histories. Evidence remains within task detail and can be cited by the orchestrator through bounded resolvers.

Decided persistence contract

Store project and task contexts centrally on the Task Server. The server owns transcript turns, compact receipts, summary, and lifecycle visibility. Project contexts are permanent. Task contexts are hidden, not deleted, after archive. Existing .orchestrator/orchestrator-chat.jsonl files are read once as an idempotent migration source.

Decided continuity contract

Read a bounded recent window from the Task Server on every stateless turn. The central short summary is derived from durable turns. Receipts remain append-only, are linked to the user turn id, and contain source metadata and hashes rather than resolved bodies.

Actor clarity is a safety feature

The two composers can look related because both use chat. The UI must state who will answer and whether Send spends task-execution quota or changes runtime state. Color alone is not sufficient.

Operator override (2026-09-06, AGT-2725): a Dossier owns its transcript

This dossier originally scoped Wiki, Workbench, board, file, and diff surfaces as context inputs only, never new transcript owners. The operator overrode that boundary for Dossiers on 2026-09-06: opening the orchestrator side sheet on a Dossier now starts an empty session scoped to workbench:<PROJ>/<DOSSIER-KEY>, mirroring the task-scoped contract above rather than adding to the project transcript. The dossier's own descriptor and entrypoint excerpt are the entire implicit context; no board or task digest carries in. Wiki pages, board, file, and diff references remain plain context inputs, unchanged by this override.

05 · Fast reference UX

Single-Click References and Evidence Inspection

CAC-20 deliberately keeps the library path-agnostic. The app host owns the picker, source resolution, and receipt. This is the correct separation.

Add context flow

Current Tab Priority

contextAttachmentAddRequested opens a host popover with one recommended row: the current tab's stable typed reference and a short estimate of what will be included.

Known-Source Search

Sections for Tasks, Wiki and Dossiers, Files, and Commits. Task references reuse live task-key validation and microcard semantics. File and commit results must carry project identity.

Send-Time Resolution

Chips hold ids and labels only. The backend resolves content at the execution checkout, records the exact revision and truncation, and returns the receipt.

Transparency contract before and after Send
Moment Operator sees Backend truth
Before Send Automatic context chip, explicit removable chips, estimated source count and token cost, plus a single Exclude automatic context action. Only stable refs and the context budget request. No frontend-supplied repository content is trusted.
While resolving Quiet pending state. A slow source names itself instead of freezing the entire workspace. Project isolation, canonical path checks, revision capture, size caps, and deduplication.
After response A compact “Used context” row with source count, total estimate/actual input usage, and an Inspect disclosure. Append-only receipt linked to the user turn id: source ref, kind, revision/hash, freshness, included characters/tokens, status, and reason.
Failure or omission Host-rendered row: unresolved, blocked, changed since viewed, excerpted, or omitted by budget. The model is not asked to confess infrastructure failures. The request continues only when remaining context is safe and sufficient. Scope or traversal violations fail before invocation.
Vocabulary recommendation

Use Chats for the current header switcher, Context for per-message evidence chips, and Usage for the token ring. The underlying contracts already distinguish these concepts; the UI should do the same.

07 · Operator decisions

Operator Choices for Cut and Rollout

The decisions below are accepted. They keep context inspectable and preserve the existing separation between orchestrator conversation and task execution.

Decision matrix
Decision Recommended Alternative Tradeoff
Automatic context depth Compact, every turn; full sources only on explicit attach. Only explicit context. Automatic compact context delivers the operator vision with bounded repeat cost. Explicit-only is cheaper but makes “this task/page” unreliable.
Task Chat role Separate orchestrator Q&A tab. Merge with Activity composer. Separation prevents an innocent question from starting or interrupting task work. A merge saves chrome but creates side-effect ambiguity.
Transcript model Project + task only. One transcript per page, Dossier, or diff. Two durable scopes preserve continuity. Per-surface threads fragment memory and multiply switcher noise.
Default entry Project surface plus side-sheet Chat open by default. New full-screen Chat route. The side sheet keeps software and board visible and follows established design doctrine. A new route duplicates navigation and hides the project surface.
Header vocabulary Rename Contexts to Chats; reserve Context for message evidence. Keep Contexts. Renaming removes ambiguity with CAC contextAttachments and token context usage. Keeping it avoids copy change but makes receipts harder to explain.
Accepted decision record, 10 August 2026

Decision, amended 11 August 2026: Orchestrator Chat is the primary project and task conversation in the right side sheet. Conversation scope remains project or task; navigation selects the active scope unless the operator pins another context; explicit references are additive. The Task Server centrally owns managed contexts, transcripts, receipts, lifecycle visibility, and short summaries. Project contexts are permanent.
