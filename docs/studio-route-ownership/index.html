02 Alternatives

studio-bff extension

Keep the small proxy and add all forwarding, security, health, and WebSocket behavior. Its current strength is a narrow /api/v1 pass-through. Hosting 95 dev-seat operations would require importing OrchestratorApi file, Git, CLI, and launcher dependencies or inventing a second local API.

OrchestratorApi connector profile

Reuse the existing dev-seat handlers and transparent v1 proxy, but compose an explicit connector-only route table. The profile excludes task storage, scanners that act as task authority, schedulers, Runner loops, and all unclassified endpoints. This is the recommended process choice.

BFF plus native helper

Run studio-bff as the credential boundary and a second native helper for Windows-only routes. It separates concerns but creates two local lifecycles, another authenticated hop, split health, and a routing table that is harder to prove complete.

Legacy OrchestratorApi

Run the monolith unchanged and proxy only /api/v1. This leaves two task authorities, exposes broad legacy handlers, and defeats the approved topology. It is not a cutover option.

03 Recommendation

OrchestratorApi connector profile

Use a connector-specific composition root in OrchestratorApi. It is the only option that reuses the 95 local handlers without preserving local task authority. Treat the route inventory as an allowlist and fail startup when a mapped route has no inventory row.

Routes

  • Map the 95 dev-seat operations locally. Do not use a broad /api/* local fallback.
  • Forward the 268 task-server operations. During migration, legacy paths may be compatibility aliases, but their handlers and writes live in the Task Server.
  • Split three mixed contracts before cutover: task file reads with scope=code, global search across tasks and repository objects, and the project snapshot that combines authority with checkout facts.
  • Keep /api/v1/management/commands and /api/v1/management/remote-hosts/provider-auth on their current paths, but implement them in the standalone Task Server. The other four frontend-used v1 operations already exist there.

WebSocket

The connector keeps the browser path /hubs/jobs. It proxies SignalR negotiation, WebSocket upgrade, SSE fallback, and long polling to a versioned Task Server hub. The upstream handshake receives the Studio bearer; browser cookies, inbound authorization, and hop-by-hop headers do not cross the boundary. The connector preserves Sec-WebSocket-Protocol and runs a bounded full-duplex pump with cancellation in both directions.

Origin, Host, and connector session checks run before the upgrade. The negotiate POST requires CSRF. A successful reconnect supplies a durable cursor, and the Task Server replays events after that cursor before live delivery. The connector never synthesizes job events and never becomes an event store.

Security

  • Listener: bind only [::1]:5031. Reject any Host other than the configured bracketed loopback authority. Do not bind IPv4 wildcard, IPv6 wildcard, LAN, or Docker Desktop default interfaces.
  • Origin: unsafe HTTP, SignalR negotiate, and WebSocket upgrade accept only the configured Studio origin, initially http://[::1]:4011. Safe reads with no Origin still require the connector session. Any present but non-matching Origin is rejected.
  • CSRF: issue an opaque HttpOnly connector-session cookie and a readable, session-bound agentstudio-csrf cookie with SameSite=Strict, no Domain, and Path /. Unsafe methods must present the matching X-CSRF-Token. Rotate both on connector restart, upstream generation change, and explicit logout.
  • Headers: strip browser Authorization, cookies, forwarded headers, and client-selected protocol identity. Inject the scoped Studio bearer and connector-owned protocol/version headers. Forward X-Client-Id only as audit attribution.
  • Credential: native mode reads target AgentStudio/TaskServer/studio-robert-windows from Windows Credential Manager. Docker mode reads a read-only ACL-protected secret file mounted at /run/secrets/studio-task-server-token. Do not use an environment variable, browser storage, config JSON, or logs.

Health

/healthz reports connector process liveness only. /readyz is 200 only when the credential is loaded, the selected upstream answers /readyz, protocol compatibility passes, the TLS identity or pin matches, and the route table checksum equals the shipped inventory. Its body may report mode, generation, masked upstream name, protocol, and last successful probe time, but no token, secret path, or private host address.

Upstream switch

The connector holds one immutable upstream snapshot: mode, base URI, TLS pin, credential handle, protocol range, and generation. A switch first validates the candidate, verifies an exact-version restore, and requires evidence that the previous authority is drained or read-only. Only then does one atomic exchange publish the new generation. Requests already in flight finish against their captured generation; new requests use the new one. A failed validation leaves the old generation untouched. No request is retried against the other authority after a partial mutation.

Runtime

The remote Task Server remains Docker-operated as approved. For the connector, native Windows hosting is the recommended starting mode because Credential Manager, Windows CLI discovery, VS Code launch, project URL processes, and repository paths are part of the accepted dev-seat scope. Run it as a restricted Windows service, with no interactive desktop privilege except an explicitly isolated launcher broker.

A Docker Desktop connector is conforming only if it binds the published port specifically to [::1], uses the secret-file contract, mounts each allowed repository explicitly, has no Docker socket, and removes or delegates every Windows process-launch route. Docker and native modes must expose the same route checksum and security test suite.

The SHA-range LRU already uses the right invariant. Its comment says a diff between two fixed SHAs never changes. However, it lives in one process's memory, it is keyed by a local checkout path, and it never holds the full diff text.

Consistency with review and gate

The card states the review scope as the attributed commits[]. The source shows two different objects:

  • Reviewed delivery. The semantic review grades merge-base(integration ref, Result-SHA)..Result-SHA on the runner. Review code never reads commits[].
  • Attributed commits. commits[] is integration and acceptance evidence. On remote completion, LeaseEndpoints.cs:1692-1744 derives it from the delivery range and filters it through RemoteCommitAttributionGuard. The Studio's aggregate diff concatenates git show output for those SHAs.

The two usually describe the same change, but nothing guarantees it. Superseded commits, merges, a moved integration base, or the AGT-W18 final merge candidate can make them differ. A central diff service should therefore name the object it shows. It should never present an attributed-commit concatenation as "the diff the reviewer saw".

Proposed diff model

Proposal. Limits are starting values to be confirmed by measurement in card 1.

  • Key. A diff object is immutable and addressed by repositoryId, baseSha, headSha, diff options (rename detection, context lines, first-parent for merges) and a renderer version. Because commits are content-addressed, the object never needs a TTL. Retention follows task archive and result-ref retention, not LRU pressure.
  • Named views. reviewed-delivery (merge-base and Result-SHA as recorded in the review receipt), commit (one attributed SHA against its first parent), integration (pre-tip to published tip from the AGT-W18 receipt) and run-checkpoint (see below). The Studio labels the view and both SHAs.
  • Manifest and pages. Each object has a manifest listing path, status, rename source, numstat and binary flag, plus one patch per file. The manifest holds up to 5,000 files. Each per-file patch holds up to 256 KiB or 5,000 lines; beyond that the file is marked truncated, never silently. The Studio pages through files by manifest cursor and loads one file patch at a time. Binary files carry metadata only.
  • Review alignment. The reviewed-delivery manifest records whether the review prompt was truncated at 200 files or 12,000 lines. The Studio then shows which files the reviewer received in full. Complete paging remains available beyond that budget.
  • No Git on read. A read never starts Git. If an object is missing, the read answers warming and enqueues one deduplicated runner operation. Other states are ready, unavailable with a typed reason such as an unknown SHA, or too-large.
  • In-flight runs. The runner publishes a bounded run-checkpoint object at defined checkpoints: after each agent turn, before handoff, and on salvage. It covers the worktree against the run's base SHA, including untracked files within the size limit. The Studio shows the latest checkpoint with its timestamp. It does not show live worktree state, because the worktree lives on the runner host.

Relation to AGT-2954

AGT-2954, "Publish versioned Git facts outside read requests", applies the same principle to the OrchestratorApi task detail. Its run commits exist only as runner salvage refs, for example origin/agent-studio/salvage/agent-runner-01/AGT-2954/…, and are not an ancestor of develop. On those refs it adds immutable snapshots keyed by ref, config and generation signatures. It adds the states warming, ready, stale and unavailable, a per-repository Git process budget of four children, and the rule that detail reads never start Git. This proposal reuses that state vocabulary and the no-Git-on-read rule. It moves the computation from the OrchestratorApi checkout to the runner host and the storage to the Task Server. AGT-2954 stays useful as the interim for the legacy OrchestratorApi; it is not a substitute for the central plane.

13 Intervention workspace

Extension · AGT-3017 operator steer · 5 October 2026

The product direction is indirection: agents implement, the Studio observes, and the remote host integrates. Operators still intervene by hand. They make quick fixes, salvage a stuck attempt, merge a delivery the server could not push, or unblock a card. The operator said on 5 October (paraphrased from German): "I wanted indirection, but there are always interventions. Then maybe there should be a dedicated Docker container for that."

Today these interventions happen in the Windows checkout, outside the card. They do not hold the card's lease. They commit under whatever identity the checkout or tool has. Review and gate see them only if they happen to land between a base and a Result-SHA. Keeping the Windows checkout for this purpose would keep a hidden side channel next to the observer-only Studio. This section proposes to make interventions explicit, central and attributable instead. VS Code on Windows becomes only the user interface. It attaches to a container on the runner host that holds the card's branch and the agent's toolchain.

14 Alternatives

Two choices carry the others. The first is where Git facts and diffs are computed and stored (D5). The second is where hand interventions happen (D7). D1 to D4 and D6 follow from those two.

Git facts plane (D5)

A · Runner host computes, Task Server stores

The runner host owns the canonical checkout per project (ADR-0073), the run worktrees, the review material and, under D7 b, the intervention workspaces. It publishes facts and diff objects through the existing outbox and artifact contracts, and serves misses through a fenced runner operation. The Task Server keeps its no-Git boundary. Cost: a new object kind, publication at run, review and integration events, and a warming state for cold reads.

B · Task Server keeps a Git mirror

The Task Server holds a bare mirror per project and answers on demand. This gives the simplest read path and lowest latency. It breaks the recorded boundaries that the Task Server has no Git access (StudioTaskHistoryContracts.cs:46-52) and spawns no checkout processes (AGT-W49). It also brings back request-driven Git load on the authority process, and cannot see in-flight run worktrees.

C · Dedicated Git facts service

A separate service with its own mirror and store, on the runner host or beside it. Isolation is clean and the service can scale independently. It adds another process lifecycle, credential, health check and API version, and it duplicates the runner's checkout. This is the evolution path if A's runner-side load becomes measurable.

D · Keep the dev seat and sync Windows

Keep all routes local and add a scheduled fetch on Windows. Nothing new is built. It keeps 35 Git-dependent operations, local process load and a second Git reader on the workstation. Diffs depend on fetch freshness, and in-flight runs remain invisible. It contradicts the 12 and 18 September decisions and the 5 October direction.

Intervention workspace (D7)

a · Local Windows checkout, as today

Nothing to build. Interventions stay outside the card, hold no lease, commit under ad-hoc identities (four on four cards since 12 September) and are reviewed only by accident. After AGT-W18 retire-local the workstation has no publication credentials, so every hand change needs an operator merge request. Keeps four dev-seat Git routes.

b · Central intervention container per card

The card's branch, the agent's prepare script and toolchain run in a container on the runner host. The intervention holds the card's newest fence, its commits are attributed, and review and gate see them like agent commits. VS Code is the user interface. Costs five cards, host capacity on the single host, and a dependency on the host being up.

c · Persistent personal container per project

An always-warm container on the runner host with the operator's own branch. Central and fast to reach, but commits have no card, no review scope and no lease, and publication needs a separate operator merge. Long-lived disk use repeats the AGT-2999 pattern. The side channel moves to the server and remains a side channel.

d · Local Docker Desktop container as fallback

A container on the workstation with the card branch. It works when the runner host is unreachable, but under the single-host exception the Task Server is then down too. It brings Docker Desktop and a Windows-hosted execution environment back to the workstation, needs local diff routes, and does not solve Windows-only work because its containers are Linux.

Attach path (D8)

The four attach paths are compared in section 13: Dev Containers over SSH, Remote-SSH into a container sshd, VS Code Remote Tunnels, and a browser IDE through the Studio. Remote-SSH through a forward-only host account is the only one with no Docker socket, no third-party relay, full extension support and no change to the Task Server edge.

Storage

Proposal.

A Task Server table git_objects holds the key, kind, state, sizes, truncation flags and retention owner (task, project or result ref). Manifest and per-file patch bodies use the existing artifact store and its limits of 8 MiB per file and 100 MiB per result, with content hashing for deduplication. Project facts are small, versioned rows keyed by repository and ref signature: ref inventory, history pages, integration state and path index. A new version replaces the previous one; it never mutates an existing row. Retention removes objects when their owning task is purged or their result ref is collected, never by memory pressure. Intervention checkpoints are run-checkpoint objects owned by the intervention attempt.
