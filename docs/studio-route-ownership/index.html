02 Alternatives

studio-bff extension

Keep the small proxy and add all forwarding, security, health, and WebSocket behavior. Its current strength is a narrow /api/v1 pass-through. Hosting 95 dev-seat operations would require importing OrchestratorApi file, Git, CLI, and launcher dependencies or inventing a second local API.

OrchestratorApi connector profile

Reuse the existing dev-seat handlers and transparent v1 proxy, but compose an explicit connector-only route table. The profile excludes task storage, scanners that act as task authority, schedulers, Runner loops, and all unclassified endpoints. This is the recommended process choice.

BFF plus native helper

Run studio-bff as the credential boundary and a second native helper for Windows-only routes. It separates concerns but creates two local lifecycles, another authenticated hop, split health, and a routing table that is harder to prove complete.

Legacy OrchestratorApi

Run the monolith unchanged and proxy only /api/v1. This leaves two task authorities, exposes broad legacy handlers, and defeats the approved topology. It is not a cutover option.

03 Recommendation

OrchestratorApi connector profile

Use a connector-specific composition root in OrchestratorApi. It is the only option that reuses the 95 local handlers without preserving local task authority. Treat the route inventory as an allowlist and fail startup when a mapped route has no inventory row.

Routes

  • Map the 95 dev-seat operations locally. Do not use a broad /api/* local fallback.
  • Forward the 268 task-server operations. During migration, legacy paths may be compatibility aliases, but their handlers and writes live in the Task Server.
  • Split three mixed contracts before cutover: task file reads with scope=code, global search across tasks and repository objects, and the project snapshot that combines authority with checkout facts.
  • Keep /api/v1/management/commands and /api/v1/management/remote-hosts/provider-auth on their current paths, but implement them in the standalone Task Server. The other four frontend-used v1 operations already exist there.

WebSocket

The connector keeps the browser path /hubs/jobs. It proxies SignalR negotiation, WebSocket upgrade, SSE fallback, and long polling to a versioned Task Server hub. The upstream handshake receives the Studio bearer; browser cookies, inbound authorization, and hop-by-hop headers do not cross the boundary. The connector preserves Sec-WebSocket-Protocol and runs a bounded full-duplex pump with cancellation in both directions.

Origin, Host, and connector session checks run before the upgrade. The negotiate POST requires CSRF. A successful reconnect supplies a durable cursor, and the Task Server replays events after that cursor before live delivery. The connector never synthesizes job events and never becomes an event store.

Security

  • Listener: bind only [::1]:5031. Reject any Host other than the configured bracketed loopback authority. Do not bind IPv4 wildcard, IPv6 wildcard, LAN, or Docker Desktop default interfaces.
  • Origin: unsafe HTTP, SignalR negotiate, and WebSocket upgrade accept only the configured Studio origin, initially http://[::1]:4011. Safe reads with no Origin still require the connector session. Any present but non-matching Origin is rejected.
  • CSRF: issue an opaque HttpOnly connector-session cookie and a readable, session-bound agentstudio-csrf cookie with SameSite=Strict, no Domain, and Path /. Unsafe methods must present the matching X-CSRF-Token. Rotate both on connector restart, upstream generation change, and explicit logout.
  • Headers: strip browser Authorization, cookies, forwarded headers, and client-selected protocol identity. Inject the scoped Studio bearer and connector-owned protocol/version headers. Forward X-Client-Id only as audit attribution.
  • Credential: native mode reads target AgentStudio/TaskServer/studio-robert-windows from Windows Credential Manager. Docker mode reads a read-only ACL-protected secret file mounted at /run/secrets/studio-task-server-token. Do not use an environment variable, browser storage, config JSON, or logs.

Health

/healthz reports connector process liveness only. /readyz is 200 only when the credential is loaded, the selected upstream answers /readyz, protocol compatibility passes, the TLS identity or pin matches, and the route table checksum equals the shipped inventory. Its body may report mode, generation, masked upstream name, protocol, and last successful probe time, but no token, secret path, or private host address.

Upstream switch

The connector holds one immutable upstream snapshot: mode, base URI, TLS pin, credential handle, protocol range, and generation. A switch first validates the candidate, verifies an exact-version restore, and requires evidence that the previous authority is drained or read-only. Only then does one atomic exchange publish the new generation. Requests already in flight finish against their captured generation; new requests use the new one. A failed validation leaves the old generation untouched. No request is retried against the other authority after a partial mutation.

Runtime

The remote Task Server remains Docker-operated as approved. For the connector, native Windows hosting is the recommended starting mode because Credential Manager, Windows CLI discovery, VS Code launch, project URL processes, and repository paths are part of the accepted dev-seat scope. Run it as a restricted Windows service, with no interactive desktop privilege except an explicitly isolated launcher broker.

A Docker Desktop connector is conforming only if it binds the published port specifically to [::1], uses the secret-file contract, mounts each allowed repository explicitly, has no Docker socket, and removes or delegates every Windows process-launch route. Docker and native modes must expose the same route checksum and security test suite.

05 Estimate

D4b contains 264 must-add Task Server operations. Every route has an individual S, M, L, or XL estimate in routes.json. The total is 436 weighted route points. At six points per engineering day, route implementation is 73 days. Connector security, protocol negotiation, replayable live updates, contract harnesses, and cutover controls add 15 days.

D4b baseline

88 engineering days, with a planning range of 71 to 115 engineering days. The range reflects handler reuse at the low end and contract, projection, or split-route discovery at the high end. Parallel delivery changes elapsed time, not total effort.

The connector profile (AGT-2754) forwards every classified task-server route to whichever handler exists at its targetRoute; it needed no change to start reaching the new P0 handlers, with one exception. A legacy frontend call such as POST /api/tasks/{taskId}/move carries only a task id, but its P0 target route is project-scoped (/api/v1/projects/{projectId}/tasks/{taskId}/move), and the connector has no task-to-project lookup of its own. The connector now substitutes the reserved literal - for an unresolvable {projectId}, and the Task Server resolves the task by id alone when it sees that literal, rather than treating - as an unknown project.
