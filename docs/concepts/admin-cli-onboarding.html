1.Problem and motive

The pipeline depends on four coding-agent CLIs being installed, on the right version, on PATH (or reachable through a correct npm shim), and signed in. Today none of that is visible until a job tries to spawn. When a dependency is missing or broken, the failure is discovered at spawn time and surfaces only as a paused lane with a terse mode-reason string.

The worst case is the npm-shim race on Windows. npm installs Node CLIs as a Bash shim plus a .cmd launcher using an atomic-rename pattern (write .<name>-<random>, then rename to <name>). On Windows that rename fails when the target is locked, leaving orphans like .claude-2shlnT4k. The claude-code postinstall additionally swaps a small stub for the real binary; an interrupt mid-postinstall, or a racing auto-updater, can put the install back into a broken shape every few minutes. As the in-repo note puts it: "a pickup that worked at boot can fail at minute twelve through no fault of the job." Source: backend/Features/Cli/Execution/NpmShimHealer.cs (class summary, lines 5-33).

The core pain: a missing or re-broken shim silently pauses the pipeline. The operator sees tasks stop, not why, and there is no in-app place to detect, install, sign in, or repair a CLI. The fix lives entirely in a terminal and in setup docs.

We already have strong machinery underneath: a --version probe with Windows PATHEXT and shim resolution, an automated self-heal for npm orphans (claude and gemini), per-CLI auth-file descriptors, and a per-CLI path override. What is missing is a surface: a place that makes each CLI's health visible and every non-green state one click away from its remedy. That is the entire scope of this concept. It introduces no new probing substrate; it aggregates and exposes what already exists.

2.How VS Code extensions do it

VS Code extensions onboard external CLIs and binaries with a repeatable five-stage spine. We mirror it directly: each stage maps to a column or action in the proposed surface.

DETECT→ INSTALL→ AUTH→ STATUS→ FIX
VS Code onboarding patterns and the reusable lesson for our Admin area.
Stage How VS Code extensions do it Reusable lesson for the Admin surface
Detection On activate() the extension resolves the binary from a stable source (PATH lookup, a known per-platform install dir, or VS Code's own extensions.json) and runs --version to gate on a minimum. Versioned folders get deleted and recreated on every update, so hardcoded paths silently break. Never hardcode a versioned path. Resolve dynamically each probe (we already do, via ResolveExecutable), run --version, and gate on a per-CLI floor. Offer a "Set explicit path" escape so the operator can pin an absolute binary and stop depending on the fragile shim.
Install Two models: bundle per-platform binaries in the VSIX (offline, deterministic), or download the matching binary from GitHub releases on first run after a showInformationMessage("...", "Download") consent prompt. rust-analyzer and the dbt extension both prompt-then-download, with a manual CLI command as fallback. A contributes.walkthroughs checklist drives the human through setup. Prefer a guided, deterministic install over a silent server-side download. For npm CLIs, run the in-process self-heal; for a true missing install, show a copy-paste npm install -g ... command plus a docs link rather than auto-running a large download. All installs are explicit operator clicks.
Auth Built-in providers via vscode.authentication.getSession(providerId, scopes, {createIfNone:true}) show the consent dialog and an Accounts-menu badge, falling back to device-code in headless or remote contexts. Custom backends implement AuthenticationProvider and store the token in SecretStorage. We cannot drive the interactive claude/codex/gemini logins headlessly, so we show an instruction card plus a "Re-check auth" button that re-probes the credentials file. Copilot offers an inline "Set GitHub token" field (a real provider-token path we already have).
Status A persistent StatusBarItem whose text, icon, and tooltip reflect signed-in vs error, whose command is a click-to-fix action, and which uses errorBackground/warningBackground only as a last resort. A spinning icon signals in-progress. A persistent header status chip ("CLIs: 3/4") is the always-on click-to-fix entry point. It deep-links into the Setup page, pre-expanded on the worst card. Reserve red and amber for genuine blocking and degraded states.
Errors A notification carries the remedy as a button ("Install", "Update", "Sign in", "Open Settings"), not a dead-end string. The persistent chip turns to an error state with click-to-fix so recovery is reachable even after the transient toast is gone. Every non-green row carries its exact remedy button inline (Install / Repair / Sign in / Set path) plus an expandable detail. The remedy lives in a persistent row, reachable any time, not only while a toast was live.

3.Current Agent Studio state and gaps

What already exists (the substrate we reuse)

  • Detection. TestCliPath() spawns a --version probe and returns (Available, Version, Path) with a 5-second timeout; ResolveExecutable() handles Windows PATHEXT and npm-shim .cmd resolution. Source: backend/Features/Cli/Execution/CliExecutionServiceBase.cs:67-94 and :104-137.
  • Self-heal. NpmShimHealer repairs atomic-rename orphans, platform-binary rename artifacts, and stub binaries, then smoke-tests claude --version after the pass. It is the in-process C# port of tools/check-cli-shims.sh and covers the npm-shim CLIs (claude and gemini). Source: backend/Features/Cli/Execution/NpmShimHealer.cs.
  • Auth-file descriptors (historical). The former CliWorkingMemoryService enumerated per-CLI credential files: Claude ~/.claude/.credentials.json, Codex ~/.codex/auth.json, Copilot ~/.copilot/config.json (plus GitHub token), Gemini ~/.gemini/settings.json. Source: backend/Features/Cli/Execution/CliWorkingMemoryService.cs:191-227.
  • Path override. Each service exposes SetCliPath(path) and a <Cli>Cli:Path appsettings fallback. Only Copilot's is wired to an endpoint today, via /api/settings/cli and /api/settings/cli/token. Source: backend/Features/Cli/CliEndpoints.cs:20-44.
  • Routing and auto-pause. CliRouter dispatches all four services; the runner trips to manual mode with a ModeReason when a CLI cannot be started after N attempts. Source: backend/Features/Cli/Execution/CliRouter.cs, backend/Features/Runner/ProjectRunner.cs.
  • Admin host. CLI Management renders model catalogs, quota caps, and completion contracts. Source: frontend/src/app/features/cli/components/cli-admin-panel/cli-admin-panel.ts.

4.Proposed Admin "CLI Onboarding" surface

A new Setup section pinned to the top of the existing CLI admin page (above the Model catalog, Quota caps, Usage, and Working-memory sections), fed by a single new aggregation endpoint GET /api/cli/health. It is the health-panel analog of a VS Code Get-Started page: one row per CLI, a rolled-up status chip, and an inline primary remedy.

Per-CLI status table

Each row probes its fields independently so the UI can show a granular checklist and a single rolled-up chip. The mockup below shows the four CLIs in representative states.

The /api/cli/health record (per CLI). Composed from existing pieces only:
  • installed, version, resolvedPath, onPathOrShim — from TestCliPath() plus ResolveExecutable(). shim-broken is inferred when the path is unresolved on Windows and the NpmShimHealer read-only pre-scan finds orphans for that CLI.
  • auth, authDetail — a file-presence probe reusing the CliWorkingMemoryService descriptor paths; absent file means unauthenticated, and expired is inferred only from a recent run's auth error (best-effort, no billable call).
  • versionOk — compared against a per-CLI minimum floor, or null when no floor is defined yet (so working installs are never false-flagged).
  • healthy, state, nextSteps, actions — derived; state is the precedence roll-up not-installed > shim-broken > path-error > sign-in-needed > outdated > ready that drives the chip color and the primary action.

Action semantics (all explicit operator clicks, no silent installs)

  • Detect / Re-detect → GET /api/cli/health?refresh=true (re-runs TestCliPath plus the auth and shim probes).
  • Repair → POST /api/cli/{cliType}/repair; for npm CLIs (claude, gemini) invokes NpmShimHealer and returns the action log inline ("Restored claude.cmd from .claude-2shlnT4k; re-ran postinstall"). The chip flips to Ready after the healer's own post-repair --version smoke test.
  • Install → a guided card with a copy-paste npm install -g ... command and a docs link, not an auto-run server-side download.
  • Sign in → for Copilot an inline "Set GitHub token" field (the existing PUT /api/settings/cli/token); for Claude, Codex, and Gemini an instruction card to run the interactive login plus a "Re-check auth" button that re-probes the credentials file.
  • Set path → PUT /api/cli/{cliType}/path { path }, generalizing the existing Copilot-only SetCliPath() endpoint to all four services. This is the escape hatch from the fragile shim: pin an absolute binary.
Graceful degradation: if /api/cli/health returns 503 for one CLI, that card shows "Unknown — re-detect" rather than blanking the page, mirroring the existing 503-not-500 convention used for the model catalog.

Fresh-system walkthrough flow

On app load the frontend calls GET /api/cli/health. If zero CLIs are ready (or a persisted "onboarding not completed" flag is set), it shows a one-time, dismissible "Set up your coding agents" wizard, re-openable from the Setup header. It is the analog of a VS Code contributes.walkthroughs checklist whose steps auto-check via completion conditions: the human does the fix, the UI reflects truth, never a fake progress bar.

  1. Choose A checklist of the four CLIs ("Which agents do you want to use?"). Any already-ready CLI is pre-checked. Most operators pick one or two.
  2. Install → Sign in → Verify (per chosen CLI) Each sub-step auto-checks on the next health poll: install turns green when installed && versionOk, auth turns green when auth == "authenticated", verify turns green when healthy. Each item's call-to-action runs the real action (Install command card, Sign-in affordance, Re-detect).
  3. Done When every chosen CLI is green, a success state and a "You're ready to run tasks" call-to-action route back to the board, and the onboarding-completed flag is set.

5.Error surfacing

Three coordinated surfaces, never a dead-end string. This mirrors the Copilot template of a visible chip plus hover detail plus one-click recovery, and ties into the AGT-1775 visual-error concept: the blocked or error visual on a card carries the remedy button, not just a red marker.

  1. Persistent header status chip (the VS Code StatusBarItem analog). A small "CLIs: 3/4" chip: neutral when all ready, amber when an actionable-degraded CLI exists, red when a CLI the runner needs is blocking. Hover gives a per-CLI roll-up tooltip ("Codex: sign-in needed"); click navigates straight to Admin > CLI > Setup, pre-expanded on the worst card. Reserve red and amber for genuine states per VS Code status-bar guidance.
  2. Runner auto-pause lane pill (already exists, re-pointed). When a spawn fails repeatedly the runner flips to manual with a ModeReason like "auto-pickup paused: the {cli} CLI for '{slug}' could not be started after N attempts...". The concept adds a "Fix CLI" link in that tooltip that parses the cliType from the reason and deep-links to the offending card. This is the bridge from "my tasks stopped" to "here is exactly why and the fix." Source: backend/Features/Runner/ProjectRunner.cs (mode pause), surfaced via ProjectRunnerStatus.ModeReason.
  3. Per-task spawn-failure diagnostic (already written to the job's cli-output log). Surface its first line as an actionable error row in the task's activity area with a "Fix the {cli} CLI" button to the Setup card. The same root cause is then reachable from the board, the task, and the header, and every entry point lands on the one card that hosts the remedy.
Cross-reference: this section depends on and extends the AGT-1775 visual-error concept. The Setup card's non-green visual is the remedy-carrying error surface that AGT-1775 describes; the deep-links above all terminate on it.

Open questions

Auth depth.
We can cheaply detect credential-file presence (reusing the working-memory paths) but not true validity or expiry without a billable call or a PTY /usage probe. Is presence-based status (authenticated / unauthenticated / unknown, with "expired" inferred only from a recent run's auth error) good enough for v1, or do we need an explicit, costly "verify auth" button per CLI?
Interactive login.
Claude, Codex, and Gemini need a real terminal login the runner cannot drive headlessly. Is an instruction card plus "Re-check auth" acceptable, or do we want a PTY-backed interactive login pane inside the Admin area (a bigger build that reuses PtySession)?
Install action policy.
Auto-run npm install -g ... from the server (deterministic but heavy, needs npm and write permissions, can hit EACCES) versus a copy-paste command plus docs link only. The research favors the guided/manual fallback for determinism. Confirm we do not want silent server-side installs.
Version floors.
Do we have known minimum supported versions per CLI to gate outdated, or should versionOk stay null until a floor is set so we never false-flag a working install?
Header chip placement.
A brand-new global header element, or folded into the existing runner status pill cluster to avoid header crowding? Needs a design call against current header density.
Per-machine vs per-project.
CLI health is host-global, but runner auto-pause is per-project. Recommendation: a single global Setup surface with per-project pause-state shown as context, living under the existing Admin > CLI tab (reuses the host).
npm-shim auto-update race.
The healer already fixes claude and gemini reactively at spawn. Should the Setup page also offer a "pin / disable auto-update" affordance to stop the re-break loop, or is that out of scope for an onboarding surface?
