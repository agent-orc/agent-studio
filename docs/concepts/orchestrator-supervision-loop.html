1. Mission and vision

Mission, one sentence: keep the pipeline RUNNING. The watch loop is a single named, always-on control loop that reads every signal, makes a clever decision through a dedicated supervision prompt, ACTS through the existing emergency primitives and state machine, and publishes both the tick and the decision on the bus so the operator can watch it think.

Today's supervisor stack already detects well and advises loudly, but the line between detection and action is where tasks strand. HardHealthCheck advises, ChatNote reports "N advisories ... 0 cycles", and the act-capable services (MetaCycle, AutoIntervention) are default-off and event-triggered rather than time-driven. The watch loop is the missing piece: it is time-driven (default 10s), it OWNS an action verb on every non-clear tick, and it closes the "detect but do not act" gap structurally.

The "detect but do not act" gap

"Detected but did nothing" is the failure mode this concept exists to make impossible. A suspicion on any tick must resolve to exactly one of: an executed ACT, or an explicit, logged WAIT-with-reason. There is no third "noticed and moved on" outcome. The loop promotes the six existing hosted services from advise-only to act-capable without reinventing infrastructure: it is a thin decide plus act coordinator wrapped around them.

L1 / L2 / L3 layering (vocabulary already in the code)

The heartbeat comment in the supervisor code already names a "Layer 3 system review". The watch loop unifies the three layers under one prompt-driven decision step:

LayerScopeCadence todayStatus today
L1 Per-task hard checks (no-progress, error-burst, quota, tool-repeat) 10s Exists (advisory only)
L2 Per-project meta-cycle (pause, inspect, resume, queue-fix) Event-driven Exists (acts, but default-off)
L3 Workspace / system review (watches heartbeats) Periodic Exists (watches, does not act)

The watch loop unifies L1's cadence with L2 and L3's authority. It is explicitly NOT a rewrite of these layers; it wraps them. It also reframes the old supervisor-doc line "not a parallel orchestrator" into a sharper claim: the watch loop IS the orchestrator's self-supervision organ, and it is designed from day one so that MULTIPLE instances with different models can run in parallel and coordinate through the bus (see Section 6).

2. How it works today, and the gap

The supervisor is six hosted background services running periodic loops at configurable intervals. They detect and advise well; only two of them act, and those two are default-off and event-triggered. Here is the full inventory as it stands:

Service Interval Default Detects Acts?
HardHealthCheckHostedService 10s ON no-progress, error-burst, quota-critical, tool-call-repeat advise only — appends to observations.jsonl + bus, no primitives
ChatNoteHostedService 60s tick / 30min window ON advisories + meta-cycle reports + jobs reaching 4/5-review advise only — emits the one-liner, never modifies state
MetaCycleHostedService 30s OFF project-level stall / fix conditions (event-driven) acts — pause/resume projects, queue fixes
SoftReasoningHostedService 600s (CLI-driven) OFF LLM soft-reasoning over recent state advise only
AutoInterventionHostedService 30s (rate-limited) OFF high-severity advisories acts — CancelRun etc., per-project/hour limiter
ProjectObservationService read helper n/a reads ProjectRunnerStatus + advisories for the others read helper (shared by the act-capable services)

The "0 cycles" explanation

The "Supervisor: N advisories on topic/topic, 0 cycles, 0 jobs reached review" line that the operator sees comes from ChatNoteSummary.Build(). It reports observed state and takes NO action itself; the "0 cycles" phrase is produced by ChatNoteSummary.BuildCyclePhrase(). It is, by design, a mirror, not a hand. The advise-only services see the problem and write it down; the act-capable services are off and only fire on events. Nothing time-driven turns a detected problem into an action.

The gap: detection without a time-driven act step. HardHealthCheck advises every 10s, ChatNote reports "0 cycles" every minute, and the two services that can act (MetaCycle, AutoIntervention) are default-off and event-triggered. A task that strands in 3-progress is detected and described, but no always-on loop owns the decision to do something about it.

3. The supervision loop

One new hosted service: SupervisionLoopHostedService, built beside the existing six and reusing their helpers. Time-driven, act-capable, and transparent on the bus. It does not reinvent infrastructure; it is the thin decide-plus-act coordinator that the six services were missing.

Interval and cadence

The loop reads Supervisor:LoopIntervalSeconds every tick, so cadence is live-reloadable (the same re-read-each-tick pattern MetaCycleHostedService already uses, around line 97). The default is 10s, the "nothing-is-wrong heartbeat" rate. When the loop opens a longer remediation cycle (for example pause then quiescence then inspect then resume) it backs its own cadence off to Supervisor:LoopBusyIntervalSeconds (default 30s) so it does not spam while a fix is in flight, then returns to 10s. A periodic "deep tick" runs a model call every Nth tick (Supervisor:LoopDeepTickEvery, default 30 ticks, roughly 5 minutes) even when nothing looks wrong.

Tick body: the five steps

The deterministic part of the tick is cheap and runs every 10s. Only one step ever spends a model call, and even then only conditionally.

Step What it does Model?
1. READ Per project, pull ProjectRunnerStatus (TaskRunnerService.GetStatus), new advisories since cursor from observations.jsonl, task OutcomeIssue kinds from the scanner projection, LifecyclePhase (ExecutionStalled), TaskRunActivity (FailedBackoff / FailedIdle / NoActiveRun), and recent bus decision / intervention messages. no
2. TRIAGE Compute a suspicion set (see Section 4). If the set is EMPTY and the runner is healthy, emit a lightweight "tick: clear" rolled-up bus heartbeat and return. Keeps the 10s loop cheap and quiet. no
3. DECIDE Only when the suspicion set is non-empty (or on a periodic deep tick) does it spend a model call. The supervision prompt receives the suspicion set + runner state + recent decisions and returns a structured DECISION (action + target + reason + confidence). Cheap, obvious cases (a watchdog-timeout on a dead PID) resolve on a deterministic fast-path with NO model, so the loop never stalls waiting on a CLI call. conditional
4. ACT Execute the decision through existing primitives: SupervisorInterventionService.{CancelRun, PausePickup, ForceFail, Resume}, MetaCycle's ResumeWithRetry / UpdateStableThenResume, TaskStateMachine.MoveJob (park a looping task to 5-human-review), or QueueFix (a 1-preparation follow-up). Every act is rate-limited (reuse AutoIntervention's per-project/hour limiter) and idempotent (do not re-pause an already-paused project, do not re-park a parked task). This is the step today's stack skips. no
5. RECORD Append the decision to interventions.jsonl (canonical), emit a bus decision message (transparency), then write the loop heartbeat. no
Decide then act, not detect then advise. The contract change is that the loop OWNS an action verb on every non-clear tick. "Detected but did not act" becomes structurally impossible: a suspicion either resolves to an ACT or to an explicit, logged WAIT-with-reason (for example "watchdog-timeout but PID still alive and producing tokens, wait one more tick").

Heartbeat and dead-loop watchdog

The loop writes SupervisorLogPaths.HeartbeatFile every tick (the mechanism already exists, around line 171 of the hard-check service). A SEPARATE, independent watchdog (the L3 system review, or a tiny always-on timer that does not share the loop's thread or scheduler) checks whether the loop heartbeat is older than Supervisor:LoopDeadAfterSeconds (default 60s, six missed ticks). If so it:

  1. emits a HIGH-severity bus advisory topic=supervision-loop-dead;
  2. shows a red "supervision stopped" banner in the activity feed header; and
  3. attempts an in-process restart of the hosted service.

A dead supervisor is the worst silent failure, so the heartbeat-watcher is the one component that must itself be dead-simple and dependency-free. Parallel orchestrators (Section 6) also cross-watch each other's heartbeats, so a peer death is surfaced even if L3 is down.

4. Suspicion model

A SUSPICION is "a task or project reports a problem, OR strands silently." Two intake paths feed one suspicion set per tick. Each member carries a severity (High / Warn) and an age. The deterministic triage decides model-versus-fast-path: High and actionable (dead PID + watchdog-timeout, quarantined, mode-drift) takes the fast-path act; ambiguous, Warn, or multiple interacting signals are handed to the prompt for a clever call. The common case stays instant; the model is reserved for genuine judgment.

5. Transparency

Everything the loop does is on the bus, so the operator literally watches it work. The design balances "every tick and decision is visible" against "do not bury the feed at 10s times N projects."

Rolled-up clear ticks versus full decision lines

Every tick emits exactly one bus message from participant orchestrator:{project} (or supervisor:{project} for pure-safety acts), kind=heartbeat when clear and kind=decision when it acts. To avoid flooding, clear ticks are ROLLED UP into a single workspace-level line such as tick: N projects clear, M suspicions, 0 acts, and per-project clear state shows as a quiet pulsing dot in the participant graph rather than a chat line. The moment a suspicion appears or an act happens, a full decision line is emitted and never rolled up. The operator sees a steady pulse (proof the loop is alive) plus loud, legible decisions.

A sample decision line

The decision message mirrors OrchestratorChatLog to a bus decision message. It carries an artifact:log-slice ref back to the evidence line and a replyToId linking to the advisory that triggered it, so the timeline shows cause then decision then effect as a chain:

[supervision] tick #4821 . suspicion=watchdog-timeout(job ASS-1769, age 11m)
  . decided=force-fail+park->5-human-review
  . model=haiku-4.5 . confidence=0.82
  . reason="PID dead, no commit, 2nd watchdog this hour"
  . artifact=log-slice:cli-output.log#L3187 . replyTo=adv-01J9...

The decidedByModel field (gap closed by AGT-3015)

Until AGT-3015 decision messages carried no model field; only token messages did (EmitTokenUsageRichAsync includes tokens.model). EmitOrchestratorChatAsync now writes an OrchestratorDecisionPayload: decidedBy is model or rule, and decidedByModel, decidedByThinkingLevel and decidedByModelSource name the model that made the call. A decision executor opens a DecisionModelContext scope after its model call returns. OrchestratorChatLog reads that scope, so the chat line and the decision step row name the same model. Wired paths: review decision, abort review, failure intervention, and the project orchestrator's auto-mode and steer turns. Without a scope the line says rule. Two parallel orchestrators are therefore distinguishable in the feed (Section 6).

Dead-loop visibility and operator controls

  • A missed heartbeat fires the HIGH bus advisory supervision-loop-dead plus a persistent red banner "Supervision loop stopped at HH:MM, auto-restart attempted" in the activity feed header, so a stopped watch loop is itself the loudest thing on screen.
  • Each decision line carries a thumbs-up/down (fed back as a User-source advisory, never counted as a trigger per AutoIntervention's feedback guard) and an undo/override for reversible acts (resume a pause, un-park a task). This makes the loop steerable without a config edit. Text-only controls, no menu icons.

6. Parallel orchestrators with different models

Because all loop output is bus messages attributed to a participant, multiple watch loops with DIFFERENT MODELS can run and coordinate without a shared in-memory coordinator. The bus is the coordination substrate.

Participant identity (the one real schema change)

Extend the derivation from orchestrator:{project} to orchestrator:{project}:{instanceKey}, where instanceKey encodes model and role, for example orchestrator:web:haiku-fast and orchestrator:web:opus-deep. AgentMessageBusBridge.ParticipantOrchestratorFor gains an instanceKey argument. participantId has no format restriction, so the bus and the participant-graph UI render each as its own node for free (Query already filters by participantId).

Role split (the natural parallel pattern)

RoleModel / cadenceOwns
FAST Haiku, 10s Cheap deterministic + light-judgment triage. Common acts: force-fail dead PIDs, resume mode-drift, park quarantined tasks. Keeps the pipeline alive.
DEEP Opus/Sonnet, 60-120s Subscribes to the SAME bus, picks up suspicions the fast loop flagged with escalate:deep, and renders the hard calls (is this classifier-unknown actually done? is this reissue loop destroying work?). The fast loop never blocks on the deep loop.

Coordination via bus (no locks, lease-based)

  • Claim. Before acting on a target, a loop emits a claim message (participantId + jobId + intendedAction + leaseSeconds). A loop must not act on a target with a live unexpired claim from another participant: cheap optimistic mutual-exclusion, consistent with the lease-based distribution direction in the worktree/lanes concept.
  • Arbitration. Conflicting decisions are resolved by an explicit priority field on the claim (role rank: deep > fast for judgment calls; fast > deep for liveness/kill acts) with a ULID tie-break. The loser emits a deferred message ("haiku deferred park decision to opus") so the operator sees the coordination, not just the outcome.
  • Chaining. replyToId / correlationId chain every claim then decision then effect, so the timeline reads as a multi-supervisor conversation.

Peer cross-watch

Each loop watches its peers' heartbeats. If the deep loop dies, the fast loop emits peer-supervisor-dead and (configurably) absorbs the deep role at reduced confidence until it returns. The parallel set is self-healing, and "a loop that dies is a problem" holds even with the L3 watcher down.

Opt-in default. Ship single-loop (fast/Haiku) first. Parallel is opt-in via Supervisor:LoopInstances, a config list of {instanceKey, model, role} entries. The architecture is parallel-ready from day one because identity and claims are designed in, but a second model is not enabled until the single loop is trusted.

7. The dedicated supervision prompt

A named prompt slot supervisor-loop-decision.md, a sibling of prompts/runtime/supervisor-soft-reasoning.md, NOT inline (the Registry+Slots rule). Unlike the soft-reasoning prompt, which says "You are advisory. You do not fix things," this one is DECIDE-AND-ACT. The backend parses [[SUPERVISOR_DECISION]] sentinels (a mirror of the existing [[SUPERVISOR_OBSERVATION]] parser), validates action is in the allowed set and confidence is at or above threshold, applies the claim/lease check, then executes via SupervisorInterventionService / TaskStateMachine and records to interventions.jsonl + bus.

# Supervisor loop -- decision prompt

You are a supervision loop for this project. Your MISSION is one thing:
keep the pipeline RUNNING and healthy. Unlike the advisory supervisor,
you DECIDE and you ACT. Every call you make resolves to exactly one
action -- including an explicit, justified WAIT. "Detected but did
nothing" is a failure.

## Your model & role
You are `{{instance_key}}` running `{{model}}`, role=`{{role}}`
(fast=keep-alive/liveness; deep=hard-judgment). Defer judgment calls to
a higher-ranked peer if one holds a live claim.

## State this tick (tick #{{seq}})
Runner: `{{runner_status}}` . active job `{{current_job_id}}`
  (`{{current_run_state}}`, phase `{{lifecycle_phase}}`)
Suspicions (deterministic triage already ran):
```
{{suspicion_set}}   // each: kind, severity, jobId, age, evidence-line
```
Recent supervisor decisions (yours and peers'):
```
{{recent_decisions}}
```
Live peer claims:
```
{{peer_claims}}
```

## Decide
For the suspicion set as a whole, output ONE structured decision per
actionable target:
```
[[SUPERVISOR_DECISION: target=<jobId|project>;
  action=<force-fail|cancel-run|pause-pickup|resume|
          update-stable-then-resume|park-to-human-review|
          queue-fix|wait|escalate-deep>;
  reason=<one line, <200 chars>; confidence=<0..1>;
  lease=<seconds>]]
```
Rules:
- Prefer the LEAST destructive action that keeps the pipeline moving.
  Resume a stalled-but-recoverable runner before you kill a job.
- NEVER re-pick a failed run that produced uncommitted work -- park it
  to 5-human-review (reissue loops destroy work).
- A dead PID + watchdog-timeout + no commit => force-fail + park.
  A live PID still emitting tokens => wait (say so).
- Mode drift (expected auto-continuous, found paused) with no blocking
  error => resume.
- classifier-unknown / heuristic-done on otherwise-clean work =>
  escalate-deep (if you are fast) or judge it (if you are deep); do not
  silently complete.
- Respect peer claims; if a higher-ranked peer claims the target, emit
  action=wait with reason="deferred to {peer}".
- Emit action=wait with a reason rather than inventing work.
  Idle-but-healthy is a valid, good state.

End with `[[TASK_DONE]]`. No prose outside sentinels.

  3. S2 — Decision sentinel + prompt slot. Add supervisor-loop-decision.md to the runtime slot registry and a [[SUPERVISOR_DECISION]] parser mirroring the observation parser. Validate the action enum, confidence, and lease.

  7. S6 — Bake-in single loop. Enable LoopEnabled=true on dev only; run a night with acts capped (LoopActRateLimit=3, LoopSeverityThreshold=High). Compare decisions against what a human operator would have done; tune thresholds live.
  8. S7 — Parallel identity + claims. Extend ParticipantOrchestratorFor with instanceKey; add claim/lease + arbitration messages; peer heartbeat cross-watch. Still single instance running, but the wire format is parallel-ready and unit-tested.
  9. S8 — Enable deep loop (Opus) in parallel. Add a second LoopInstances entry {opus-deep, role=deep}; fast escalates judgment via escalate-deep; verify lease mutual-exclusion and deferred-message visibility on the bus.

Open questions

  • Clear-tick channel. Should the 10s clear-tick heartbeat be a real bus message (auditable, but adds volume) or a separate lightweight liveness channel the feed renders as a pulse without persisting per-tick? Leaning: persist a rolled-up workspace line per minute, pulse the rest.
  • Autonomy ceiling. Which acts may the loop perform fully autonomously vs. require a one-click operator confirm? Proposal: force-fail/park/resume autonomous at High; update-stable-then-resume and queue-fix autonomous; anything that could discard uncommitted work always parks (never deletes), matching the reissue-loop-destroys-work rule.
  • Cost. A Haiku deep-tick every 5min times N projects plus per-suspicion calls: is LoopCallsPerHour=60 the right ceiling, and should the loop degrade to deterministic-only when the budget is exhausted rather than going blind?
  • Parallel arbitration priority. Is role-rank (deep > fast for judgment, fast > deep for liveness) the right default, or should it be per-action-class configurable? Does the lease + cooldown fully prevent a pause/resume oscillation war, or do we need a global per-target action cooldown across all instances?
  • Relationship to MetaCycle. Does the watch loop SUBSUME MetaCycle (fold its pause-inspect-resume rules into the act step) or RUN ALONGSIDE it? Subsuming is cleaner long-term but risks regressing the verified ResumeWithRetry/quiescence logic; recommend wrapping, not rewriting, in S3.
  • Dead-loop watchdog placement. In-process timer (simple, but dies if the host process dies) vs. external (survives a host crash, needs a second process). For a keep-the-pipeline-running mission, does host-process death need an out-of-process guardian, and is that the existing UpdateService/:5039 or a new minimal one?
  • Self-flag false positives. A legitimately long single tool call (large build, long test run) produces no log append for >120s and would self-flag as stranded. Do we need a work-in-flight signal (CPU/child-process liveness) to distinguish a genuine stall from slow-but-working before the self-flag fires?
  • Marketing scope. How much of the internal mechanism (parallel models, lease arbitration) belongs on the public Product page vs. staying in the operator wiki? Proposal: the homepage tells the outcome story (self-supervising, always-running, transparent); the wiki holds the mechanism.
