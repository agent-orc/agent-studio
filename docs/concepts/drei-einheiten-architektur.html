Die drei Einheiten: Agent Studio, Task Server, Agent Runner

Ein Produkt, drei unabhängig deploybare Rollen. Heute laufen zwei der drei noch in einem Prozess zusammen; die Trennung ist im Gange (AGT-2192, AGT-2193). Diese Seite beschreibt, was jede Einheit heute im Code tatsächlich besitzt, was sich gerade herauslöst — und räumt mit der häufigsten Verwechslung auf: dem Doppelleben des Agent Runners.

TL;DR — die drei Einheiten in fünf Sätzen

  • Agent Studio ist die Bedienebene: Board, Wiki, Reviews, Gates, Orchestrator — Angular-Frontend plus backend/OrchestratorApi.csproj. Sie soll austauschbar sein: Studio schließen darf Arbeit nicht stoppen.
  • Task Server ist die dauerhafte Control Plane — Task-Zustand, API, Identitäten/Auth. Heute steckt er noch im selben Prozess wie Studio; AGT-2192 löst ihn als eigenständig deploybare Einheit heraus, AGT-2193 liefert dafür Login, Runner-Identitäten und TLS nach.
  • Agent Runner hat eine echte Doppelnatur — aber nicht als eine geteilte Programmbibliothek, sondern als zwei separat implementierte Code-Pfade für dieselbe Rolle: lokal eingebettet in Studios Backend (ProjectRunner, WorktreeTaskLifecycle, BuildTestGateRunner) und als eigenständiger Daemon (runner/, Deployment agent-runner-01).
  • Autonomie ist Design, nicht Zufall: der Daemon claimt, führt aus, pusht und meldet kontinuierlich ohne Studio-Attach. Ein angehängtes Terminal (PTY/Chat) ist optionale Beobachtung, nie Voraussetzung für Fortschritt.
  • Git trägt den Code, die API trägt die Wahrheit. Task-Zustand, Leases und Events laufen über den Task Server; Quelltext wandert ausschließlich über origin — die drei Einheiten teilen sich nie ein Dateisystem.

§1Agent Studio — Bedien- und Orchestrierungsebene

Agent Studio ist die menschliche Oberfläche auf das System: das Angular-Frontend (frontend/src/app) plus der heutige Backend-Monolith backend/OrchestratorApi.csproj (lokal Port 5030). Fünf Fähigkeiten tragen die tägliche Arbeit:

FähigkeitFrontendBackend
Boardfrontend/src/app/features/board backend/Features/Tasks (TaskCrudEndpoints.cs, LeaseEndpoints.cs); Live-Updates über backend/Host/Hubs/TaskHub.cs (SignalR: jobsChanged, cliOutput, runnerStatusChanged …)
Wikifrontend/src/app/concept-docs backend/Features/Docs (ConceptDocsService.cs, ProjectDocsService.cs), ergänzt um Features/Drift, Features/Companion, Features/GeneratedFiles (die *.meta.json-Sidecar-Ebene, der auch diese Seite folgt)

Wichtig für das Bild als „drei Einheiten“: heute sind Board und Wiki nicht nur Studios Oberfläche über fremde Daten — backend/OrchestratorApi.csproj ist zugleich der Prozess, der Task-Zustand hält, den lokalen Runner einbettet (ProjectRunner) und die Wiki-Dateien auf Platte verwaltet. Studio und Task Server sind heute ein Deployment. Genau diese Kopplung löst AGT-2192 (§6) auf.

Zielbild (noch nicht Ist-Zustand)

„Agent Studio is the replaceable human surface. […] Closing it must not stop work.“ — distributed-agent-studio-target-architecture.md, §1. Solange Studio und Task Server einen Prozess teilen, stimmt der zweite Satz noch nicht: ein Neustart von backend/OrchestratorApi.csproj unterbricht heute auch die Control Plane.

§2Task Server — die Control Plane

Der Task Server ist im Zielbild die immer verfügbare, dauerhafte Autorität: Nutzer und Autorisierung, Task- und Orchestrierungszustand, Leases/Fences, Events/Artefakte, Audit und Management-API (Zielarchitektur §4). Heute ist er noch nicht eigenständig — er steckt, wie in §1 beschrieben, in backend/OrchestratorApi.csproj. AGT-2192 löst ihn als eigenes Deployment heraus, AGT-2193 sichert diese Einheit netzwerkfähig ab.

Die Grenze ist nicht nur Diagrammabsicht — sie ist als Test hart verdrahtet. task-server.Tests/ArchitectureBoundaryTests.cs prüft, dass task-server/TaskServer.csproj weder frontend noch OrchestratorApi.csproj noch AgentRunner.csproj noch CodingAgentRunner referenziert, und durchsucht jede Quelldatei unter task-server/ darauf, dass sie weder System.Diagnostics.Process noch den String "AgentRunner" noch "Angular" enthält. Der Task Server kann also strukturell keine Prozesse starten, keine Worktrees anfassen und keine UI-Zustände kennen.

Deployment-Form laut docs/operations/setup/task-server.md (auf demselben Branch): eigener systemd-Unit (deploy/systemd/agent-task-server.service), Standard-Listener http://127.0.0.1:5071 (der heutige Monolith läuft lokal auf 5030), GET /healthz + GET /readyz, Modi Normal/Draining/ ReadOnly/Maintenance über PUT /api/v1/management/mode, Protokoll-Versionierung per X-Task-Protocol-Version-Header (HTTP 426 bei Mismatch), und Backup/Restore über SQLite-Backup + SHA-256-Integritätsprüfung.

Ohne AGT-2193 bewusst noch nicht netzwerkfähig

Der Runbook-Text auf dem Extraktions-Branch ist explizit: „Do not expose this initial service beyond loopback or an SSH-only private tunnel until AGT-2193 supplies authentication and TLS.“ Die Extraktion (AGT-2192) trennt den Prozess; die Absicherung (AGT-2193) macht ihn erst netzwerkfähig.

Was AGT-2193 nachliefert

Verifiziert am Commit ce541586 „feat(AGT-2193): task-server security — human login, runner identities, tls“ auf Branch task/task-server-human-auth-runner-service-identities-tls, laut Commit-Message ein aus einem verlorenen Salvage-Branch geretteter Squash (Nachwirkung des Remote-Runner-Ausfalls vom 11.07.). Ebenfalls noch nicht gemergt.

  • Human Login: Nutzer mit Rollen owner / operator / viewer, Auth-Profile local (kein Login nötig) vs. networked (Login + Bootstrap-Flow für den ersten Owner) — backend/Features/Security/AccessSecurityEndpoints.cs, AccessSecurityStore.cs, PasswordSecretHasher.cs; frontend components/auth-gate + services/auth.service.ts.
  • Runner-Service-Identities: ein Runner bekommt nie ein Menschen-Passwort. Sein Credential kommt ausschließlich über RUNNER_AUTH_TOKEN_FILE oder RUNNER_AUTH_TOKEN — die Kommandozeilen-Option --auth-token wirft absichtlich einen Fehler, damit kein Token in der Shell-History landet (runner/RunnerOptions.cs). Autorisierung serverseitig über backend/Features/Security/RunnerLeaseAuthorization.cs.
  • TLS: RunnerOptions verlangt für jede nicht-loopback RUNNER_SERVER_URL zwingend https und ein gesetztes Auth-Token — ein Runner verweigert den Start gegen eine unverschlüsselte, nicht-lokale Server-Adresse.

Zusammen sind AGT-2192 und AGT-2193 das Remote-Ready-Ziel: eine zentrale, TLS-gesicherte Task-Server-URL, gegen die jeder Studio-Client und jeder Runner-Host spricht — statt des heutigen Eins-Prozess-Zustands mit Tunnel/LAN-Notlösungen.

§3Agent Runner — die Doppelnatur

Der Agent Runner ist keine einzelne Sache, sondern eine Rolle, die zweimal gebaut ist: einmal eingebettet in Studios Backend für lokale Ausführung, einmal als eigenständiger Daemon für pull-basierte Remote-Ausführung. Empfohlene Sprechweise, um beide Seiten sauber zu benennen: Runner Core (die Rolle/das Verhalten, library-förmig) und Runner Daemon (die deploybare Einheit). Der genaue Code-Befund dazu steht in §5.

(a) Runner Core — die eingebettete Rolle

Für lokale Ausführung (der Fall, in dem das Studio-Backend selbst claimt und ausführt) lebt dieselbe konzeptionelle Verantwortung direkt in backend/Features/Runner und backend/Features/Pipeline:

VerantwortungLokal, eingebettet (AgentStudio.*)Remote, Daemon (AgentRunner)
Git-Workspace / Worktree backend/Features/Runner/WorktreeTaskLifecycle.cs (Branch task/<id>) runner/GitWorkspace.cs (Branch runner/<runner-id>/<task-key>)
CLI-Hosting backend/Features/Cli/Execution/* (CliExecutionServiceBase.cs, BuiltInCliBehaviors.cs, ClaudeOneShot.cs, CodexOneShot.cs) runner/CarWorkerExecution.cs + runner/CliSelection.cs
Pickup / Lebenszyklus backend/Features/Runner/ProjectRunner.cs runner/RemoteTaskRunner.cs + runner/RemoteRunnerDaemon.cs
Build/Test-Gate backend/Features/Pipeline/BuildTestGateRunner.cs — läuft ausschließlich zentral im Backend, als Pipeline-Post-Step, unabhängig davon, ob der Coding-Run lokal oder remote lief. Der Daemon führt selbst kein Gate aus.

Was die beiden Seiten wirklich teilen, ist nicht Quellcode, sondern der Datenvertrag: „Remote pickup ownership lives in the project record (executionRunner plus remoteExecutionEnabled). The remote claim endpoint and local ProjectRunner consult the same record“ (docs/system/domains/runner.md). Beide Pfade münden außerdem in denselben zentralen Pipeline-Post-Steps (Gate, Review-Grade, Aspect-Findings) — ein Remote-Run liefert nur Evidenz per API an, das Urteil fällt immer im Backend.

(b) Runner Daemon — die deploybare Einheit

Der Daemon ist ein abhängigkeitsfreier .NET-Konsolenprozess (runner/AgentRunner.csproj), heute als agent-runner-01 auf einem Linux-Host (Hetzner) deployt. Er besitzt keinen Task-Zustand — alles, was er über den Zustand einer Aufgabe weiß, kommt aus der jeweils letzten API-Antwort.

  • Pull-basiert: RemoteRunnerDaemon.RunAsync ruft in einer Schleife POST /api/runner/claim, solange freie Slots da sind (HostMaxParallelism, Standard 2); ohne Claim wartet er PollSeconds und fragt erneut.
  • Nur ausgehende Verbindungen, keine offenen Ports: der Testhost ist heute nur per SSH-Tunnel oder LAN-Adresse erreichbar (docs/operations/setup/linux-runner-host.md); eine zentrale, TLS-gesicherte URL (§2) ist das Zielbild, keine offene Inbound-Regel.
  • Runs on any host with Git and the agent CLIs: the default provider (RUNNER_CLI_TYPE) and provider-specific executable paths are configurable; CodingAgentRunner owns protocol and headless flags.

Autonomie ist Design

Aus dem Klassenkommentar von runner/RemoteTaskRunner.cs: „acquire the fenced lease, start heartbeating, prepare the git working tree, spawn the agent CLI […], ship its output to the server, upload the results/ evidence, post a fenced runner completion […], and always release the lease.“ Dieser gesamte Zyklus läuft ohne jedes Studio-Attach. Teardown ist fail-closed: GitWorkspace prüft bei jeder Beendigungsart den Status, committet Änderungen notfalls als wip(runner): salvage before teardown und pusht sie nach runner/<runner-id>/<task-key>, bevor der Worktree entfernt wird (docs/system/domains/runner.md). Ein angehängtes Terminal (PTY/Chat, Frontend-Features session-events / visible-cli-task) beobachtet diesen Ablauf nur — es setzt ihn nie voraus.

§4Diagramm: drei Einheiten, drei Kommunikationsrichtungen

Studio und Task Server sprechen heute noch im selben Prozess miteinander (der Pfeil existiert schon als API-Vertrag, aber ohne Netzwerkgrenze dazwischen). Der Runner spricht den Task Server ausschließlich pull — er nimmt nie eine eingehende Verbindung an. Quelltext nimmt einen dritten Weg: ausschließlich über git origin, nie über die Task-API.

§5Häufiges Missverständnis

„Runner = nur Library“ vs. „Runner läuft überall“

Beide Sätze sind wahr — aber sie beschreiben zwei verschiedene Packagings derselben Rolle, nicht einen Widerspruch. Wer sagt „der Runner ist nur eine Bibliothek“, meint Runner Core: die Verantwortung (Git-Workspace, CLI-Hosting, Pickup-Lebenszyklus), wie sie library-förmig in Studios Backend eingebettet ist und dort für ProjectRunner-getriebene lokale Ausführung sorgt. Wer sagt „der Runner läuft überall“, meint Runner Daemon: die eigenständig deploybare Einheit (runner/AgentRunner.csproj), die auf jedem Host mit .NET, git und einer Agent-CLI installiert werden kann — heute agent-runner-01, morgen jeder weitere Linux- oder Windows-Host.

Verifizierte Präzisierung, die beim Debuggen zählt: „Library“ heißt hier nicht eine einzige kompilierte Assembly, die beide Seiten referenzieren. Es gibt heute keine ProjectReference zwischen runner/AgentRunner.csproj und backend/OrchestratorApi.csproj, und die Namespaces laufen auseinander (AgentRunner vs. AgentStudio.Runner / AgentStudio.Pipeline / AgentStudio.Cli). GitWorkspace.cs existiert nur im Daemon, WorktreeTaskLifecycle.cs nur im Backend — zwei unabhängig gepflegte Implementierungen derselben Aufgabe, verbunden über einen gemeinsamen Datenvertrag (§3), nicht über gemeinsamen Code. Ein Fix in runner/GitWorkspace.cs repariert also nicht automatisch den analogen Pfad in WorktreeTaskLifecycle.cs, und umgekehrt.

Empfohlene Sprechweise: Runner Core für die Rolle/Library-Seite, Runner Daemon für die deploybare Prozess-Einheit. Wenn eine Änderung „den Runner“ betrifft, zuerst klären: Core-Verhalten (beide Implementierungen prüfen) oder Daemon-Deployment (nur runner/ und der Host)?
