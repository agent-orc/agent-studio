02 Cut of cards

A dispatcher can only order what it is given. Three cuts cause most of the overlap.

Waves from one source

Playthroughs, review-finding sweeps and the scout create many cards for one area at once. On 17 November three playthroughs created 57 cards in one minute with no dependency, and 33 of them formed one overlap cluster. Rules:

  • A source that emits more than 5 cards writes a wave id and, per finding, the cited paths it already knows. The playthrough cards cite files with line numbers in their cause field. The cards land in Backlog with creationSource and wave id.
  • The live dispatcher plans the wave as a whole before any card enters Ready: packages (Packer only), chains for dense clusters, and interleaving so that sparse cards fill parallel slots while chains run.
  • Source prompts gain one instruction: group findings that share a cause file into one card, and say which findings must land before which.

Cards that are too large

IN-13 (AGT-3921) changed 66 files, of which 29 are code files, and merged develop six times. The finding text gave no warning. Over the 55 wave cards with source text, real code files correlate at 0.10 with the forecast size and at 0.04 with the number of cited files (both printed by replay.py). Measured on the finding text itself, which the wave file does not keep, they correlate at 0.08 with the number of acceptance criteria and at 0.12 with the word count. Size must therefore come from a size prior per source kind, the median real code files of earlier delivered cards from that kind of source. On this wave that is 17 for playthrough product gaps and 5 for review findings. Rules:

  • A card whose forecast spans more than 3 modules, or whose source prior exceeds 25 code files, runs exclusive or gets a split proposal before the start.
  • When a delivery's real change exceeds 40 code files, the ledger records it and the size prior is updated. The dispatcher never recuts a card that has started.
  • Packages respect the prior. In the first replay draft the Packer bundled IN-13 with two other incident cards because their forecasts looked small, which would have produced a card of about 90 code files. The size prior rule prevents this.

Collection cards of small fixes

DP-18 (AGT-3908) collected three small deployment fixes and touched 26 code files with 23 partner cards. RV-20 to RV-22 (AGT-3943 to AGT-3945) collected 6 to 7 review findings each, touching 5 to 15 code files with 2 to 3 partners. Spread is harmless when the modules are cold and harmful when one of them is hot. Rule: a collection card that touches a hot module is split by module, and the hot part is chained behind the cluster. A collection card in cold modules stays whole, because one review is cheaper than seven.

04 Slices

Twelve slices, listed in delivery order. A slice that changes the same area as an earlier one depends on it, directly or through a chain, so no two slices of one area run at the same time. Every such edge is a dependsOn entry in workbench.json, which promotion turns into an enforced card dependency. Backend slices register services through one AddDispatch extension created by DS-1, not by new lines in Program.cs, the hottest file of the wave. Every slice that registers there therefore depends on DS-1.

Cards outside this Dossier

PT-13 to PT-20 of the persona team addendum are not delivered. They can only become dependencies after promotion, and dependsOn names slices of this Dossier only. So no slice waits for them, and none needs them. DS-5 always delivers its own allow list and log under the names and fields of the addendum. When PT-15 or PT-18 land, those cards take the dispatcher's data over.

The remaining risk is that DS-5 and a PT card edit the same files at the same time. The platform prevents this through the scope rule, not through prose:

  • DS-5 depends on DS-4 and through it on DS-0. When DS-5 can start, the scope rule runs on both claim paths and compares with every in-flight card.
  • The DS-5 prompt names the directories it changes: backend/Features/Personas/, backend/Policies/personas/ and backend/Features/Dispatch/. The PT-13 prompt names backend/Policies/personas/, so the two cannot run together.
  • Every PT-13 to PT-20 prompt, and every DS prompt, names docs/persona-team/index.html. Their scopes share docs/persona-team, so any DS slice and any PT addendum card are serialized while both are in flight. This also covers DS-8 against PT-19 and PT-20, the persona pages.

This separation is coarse. It holds back more pairs than necessary, which the owner's rule of efficiency before lead time accepts. DS-6 replaces it with forecast files.
