Concept Dossier · Agent Studio

Git facts off the request path

A durable fact store with one writer per repository, invalidated by ref and configuration generations, so that the board and every card read published facts and never start Git.

As of 13 October 2026, code at 9e2526be5Source AGT-3044Status Decision pendingPhase Decision readyRevision 2, replaces the 11 October draft 4c9cb6d88

Robert's requirement of 11 October is short. Cards must load instantly, work must run remotely, and the Git performance problem must not come back. Six incidents since July had the same shape. A Git or filesystem fact was computed on demand, on the Windows task server host, as a side effect of a read or of a task event, by spawning the git CLI at roughly 70 to 100 ms per process. Each incident got a local fix such as a debounce, a TTL or a bounded origin read. The next growth step reopened it: 120, then 180, then 235 live cards, plus 2,088 archived cards.

This revision answers the concept review of the first draft. It inventories every request path that still spawns Git or walks history, at the current commit, with a code location for each claim. It names the durable fact store and its writers. It defines invalidation by ref and configuration generation, the cold-start and crash-recovery story, and a sliced migration plan with measurable targets. The headline target is card list and card detail under 200 ms at the current board size, with zero Git processes per read.

01 Request paths today

The 11 October hotfixes and the integrated AGT-2954 work already moved the board's own reads onto a snapshot. When a card opens, the Studio still fires several Git-backed requests, and each one spawns processes on the request thread. One of them walks the whole workspace history. Background producer and storage

GitStateIndexService is the only writer of the board's Git snapshot (SetSnapshot, TaskListGitProjectionCache.cs:197-206). It is triggered by task watcher events (GitStateIndexService.cs:328-338), a FileSystemWatcher on HEAD, packed-refs, config and refs/ (:275-326), a 45 s sweep (:364-411) and explicit RequestRefresh (:222). The defaults are a 400 ms debounce, 2 concurrent repositories and a 90 s run deadline (:699-718). appsettings.json overrides none of them. Each run starts with one git config --includes --show-origin --null --list (:477, GitConfigSignature.cs:14-36). It skips the rest only when its captured input is unchanged (:481-484). A task event therefore still costs at least one Git process per repository.

Fault isolation is partial. One failing card is marked unavailable. If the first min(3, n) cards all fail, the whole run is failed, and MarkFailed keeps the previous snapshot (TaskListGitProjectionCache.cs:386-394, GitStateIndexService.cs:541-561). The snapshot is a ConcurrentDictionary. Nothing is persisted, so every restart starts empty and readers report warming until the first full run completes (TaskListGitProjectionCache.cs:285-287).

The runner already publishes a Git fact. DurableGitFactsPayload carries repository, base SHA, result SHA and immutable result ref (runner/DurableHandoffPayloads.cs:28-34). It is emitted at result handoff (runner/RemoteTaskRunner.cs:627-637) and posted as runner.git-facts (runner/TaskServerClient.cs:1885-1906). The Task Server stores it as a generic event row (task-server/TaskServerStore.cs:2426-2433), and no code reads it back. The structured copy lives in result_handoffs (:3944-3967) in the SQLite database task-server.db (:126).

Spawn boundary and telemetry

Most Git processes pass through GitService.RunGitProcess (GitService.cs:8259-8274), which records GitProcessTelemetry. Several spawn sites do not: TaskFileHistoryService.RunGit (TaskFileHistoryService.cs:585-604), GitService.RollbackGitArgs (GitService.cs:6661), RemoteReviewPlanBuilder.Git (RemoteReviewPlanBuilder.cs:399), CommitCandidateGate.cs:628, PublishActionService.cs:338-392 and WorkspaceArtifactPushWorker.cs:211. Request scopes exist only for tasks/list, tasks/grouped, tasks/detail, tasks/detail/git, tasks/git/* and tasks/provenance. The /commits*, /commit*, /runs/* and /result-history routes are not measured at all. No guard stops a request from starting Git. The only rule is a comment (GitStateIndexService.cs:32). The admin endpoint GET /api/admin/git-telemetry warns above a grouped p95 of 1 s or 20 spawns per minute (GitTelemetryAdminEndpoints.cs:15-20). It is rendered inside the prompt admin panel (prompt-admin-panel.component.html:199), not in a health area.

02 Alternatives

Each alternative is judged against six criteria. Does any read start Git? Does the board survive a restart instantly? Does it survive a crash? What does it cost on Windows? How much work is it? Does it wait for the remote Task Server (AGT-2737)?

A · Harden on-demand reads and caches

Batch the provenance merge-base calls, cache log --all --grep by HEAD, memoize result history per workspace HEAD, add telemetry scopes. Every path in the table stays, and only its constant shrinks. A cache miss, a restart or a new route still spawns on the request thread. This is the pattern of every fix since July, and each one held only until the next growth step. Useful as a hotfix, never as the architecture.

B · Single-writer fact store on the task server

Extend the existing indexer into the only writer of a persistent store. The store holds ref generations, content-addressed commit facts, reachability, per-card facts and result versions. Readers read only the store. This works today, without AGT-2737, and fixes cold start and crash recovery. It still computes on the task server host, on Windows while Stable runs there, though only for deltas.

C · Facts computed on the runner host, published as data

The Linux runner host owns the canonical checkout (ADR-0073) and runs the integration that moves refs. A fenced producer there computes the same facts and publishes generations to the Task Server's SQLite store, extending runner.git-facts. Spawns are cheap, the facts sit next to the ref writer, and a sleeping workstation cannot block a read. It needs the Phase B Task Server, a fenced transport and a shadow period. This is the target, and it matches AGT-3017 D5.

D · In-process Git library

LibGit2Sharp, or gitoxide behind a small sidecar, removes process start-up for rev-parse, merge-base, diff-tree and config. It does not decide ownership, invalidation or placement, and it brings native binaries and semantic gaps: conditional includes, worktrees, commit-graph and reftable. It is a possible accelerator inside B or C, chosen by measurement.

03 Recommendation

Working decision: guardrails, then B with the target schema, then C

First make every Git spawn on a read request a test failure. Then build option B on the current backend with exactly the schema the Task Server will own, so that the move to option C relocates the writer, not the model. Evaluate D only as a reader inside the producer, after measurement. No read path keeps a fallback to request-time Git.

The fact store

One SQLite schema, the Git fact store, has two placements. In B it is a file git-facts.db in the backend state directory. The backend already uses SQLite in ProjectChatIndex.cs. In C the same tables live in task-server.db, next to result_handoffs and the artifact store (task-server/TaskServerStore.cs:3499-4140). That placement inherits the Task Server's fence, transaction (InWriteTransactionAsync) and backup model. Diff bodies are not part of this schema. They follow the AGT-3017 diff-object contract (D1), keyed the same way.

Writers

Each table has exactly one writer. Request handlers write none of them.

  • Fact producer, one per repository. In B, this is GitStateIndexService, extended. In C, it is a fenced producer on the runner host beside the canonical checkout. It holds a lease per repository with a monotonically increasing producer_epoch. A publish whose epoch is lower than the stored one is rejected. This is the single-writer write gate of the fencing model.
  • Platform result writer. Result versions are recorded when the platform writes status.md. ResultVersionStore already snapshots the prior document into results/history/ whenever a producer replaces it (ResultVersionStore.cs:9-15), and it becomes the writer of result_versions. A one-time background backfill imports legacy workspace history once, so TaskFileHistoryService.GetWorkspaceResultHistory leaves the request path.
  • Runner final-result handoff. Base SHA, result SHA and result ref stay in result_handoffs. The producer reads them as the input signature of a card. It does not re-derive them from log --all --grep.

Invalidation by ref and configuration generation

A generation identifies the exact Git input of every published fact. It is (repo_id, ref fingerprint, config_generation, settings version), and it moves only when one of those moves.

  • Ref fingerprint without spawning. ReadOnlyGitRefFingerprint already hashes loose ref files, symbolic refs and packed-refs size and mtime without starting Git (ReadOnlyGitRefFingerprint.cs:6-105). The watcher and the sweep call it first. The packed-refs mtime and the file watcher are detection inputs only. The stored truth is the object ID of each ref, read in one for-each-ref after a fingerprint change. A reftable repository falls back to that one call per sweep.
  • Configuration generation from the watcher. config, config.worktree and included files are already watched (GitStateIndexService.cs:309-325). Only a change in them runs git config --list and advances config_generation. This removes the spawn that every task event causes today.
  • Task events invalidate no Git fact. A task event can change a card's input signature: a new attributed commit, a new review subject or a delivery epoch. Then only that card is rematerialized, as a join over stored commit facts and reachability. A new SHA costs one batched read for that SHA. An unchanged signature costs nothing.
  • Reachability per ref move, not per card. On a fast-forward of a target ref from old to new, one rev-list old..new appends the newly reachable commits. A non-fast-forward move recomputes that ref's set once. Classification of all cards is then an in-memory join. With core.commitGraph and fetch.writeCommitGraph enabled, the full recompute stays bounded on the current history.
  • Superseded work is discarded. A run that finishes after its input generation was superseded is not published; it reruns. The current code already does this (GitStateIndexService.cs:518-527).

Cold start and crash recovery

The store makes a restart a non-event for readers.

  1. Start. The backend opens the store and loads the last published generation of each repository. Readers serve it at once with state restored, and its age is shown. No Git runs before the first read is served.
  2. Confirm. The producer computes the ref fingerprint and the configuration signature from files. If both equal the stored generation, the generation becomes ready with zero Git processes. If they differ, the producer runs a normal delta run, and readers keep the restored generation until the new one is published.
  3. First ever start or a deleted store. This is the only path that computes from scratch. It is bounded by the spawn budget. Readers answer warming per card, never by waiting, and never by falling back to Git.
  4. Crash during a run. A generation is published in one SQLite transaction in WAL mode: the facts, the card rows and the generation pointer. A crash before commit leaves the previous generation intact. Commit facts are idempotent upserts by SHA, so partial work is reused on the next run.
  5. Stale or duplicate producer. After a restart, a failover or a second runner, the new producer takes the lease with a higher epoch. A late publish from the old one fails the epoch check and is discarded.
  6. Corruption. On start, PRAGMA quick_check runs. If it fails, the file is moved aside, a typed health event is raised and the first-start path runs. The Task Server placement in C is also covered by its backup and restore (FullBackupService.cs).

The task index needs the same treatment, or the board still blocks on a cold scan (R1). Persist the last published slim board summaries per project with their index generation. On start, serve them as restored while the background scan runs. EnsureFresh must never run Refresh on a request thread. A request reads the current snapshot and, at most, signals the background refresher.

Reads

Every read route in R1 to R7 reads the store or the task index, and nothing else.

  • Provenance (R4). A projection of card_git_facts: branch presence and containment per attributed commit, read from git_reachability.
  • Commit lists and files (R5). From card_git_facts and git_commit_facts.
  • Default diff (R5). Served from a SHA-keyed diff object that the producer writes at publication. Its key follows AGT-3017 D1. Until the object exists, the response is warming and the producer is asked to compute it with priority.
  • Result history (R6). One indexed query over result_versions.
  • Run views (R7). Read the run's captured SHA range from commit facts.

Each response carries the generation and its age, and responds to If-None-Match. The board keeps the AGT-2703 ETag contract. The board signature already includes the Git generation (BoardReadSignatureSource.cs:98-128), so a new generation changes the ETag. The single-flight memo in BoardReadConcurrencyGate stays.

Mutations and review planning

Mutations may need a fact that is newer than the published generation. One example is the containment check before a card enters Completed (R9). The handler then asks the producer for "a generation at least as new as the current ref fingerprint" and waits at most 2 s. If the producer has not answered by then, the move returns 409 integration-check-pending and the Studio retries. The handler never spawns Git itself, so the spawn budget and the single writer hold. Review planning triggered by a project-settings write (R10) is queued to the existing ReviewInfrastructureRetryScheduler background service instead of running per attempt inside the request. The scoped-review delta uses the common spawn boundary.

Acceptance freshness

The AGT-3041 fix is in HEAD. DeliveryLanePolicy.IsAcceptedDeliveryStale no longer compares TargetRefFingerprint; the comment at DeliveryLanePolicy.cs:32 calls the target HEAD "a cache key for the Git reachability calculation, not part of the accepted delivery". The snapshot model keeps that rule. A claim binds the result SHA, the delivery epoch and the containment verdict. It records the generation at which containment was proven. A new generation can stale the claim only if containment of the accepted SHA is lost, which means a non-fast-forward move removed it from git_reachability. An ordinary push to the target never stales it.

Fault isolation, budgets and health

  • Card scope. A failure in one card, such as a duplicate key, a corrupt sidecar or a missing object, writes a typed error into that card's row and leaves the others alone. The current repository-wide abort after min(3, n) failures becomes a repository health state that keeps the last good generation serving.
  • Repository scope. A failing repository keeps serving its last good generation with an explicit age. Other repositories are unaffected; each has its own producer queue.
  • Spawn budget. Zero Git processes per minute while no input moves. At most 120 per repository per minute during catch-up. The producer throttles above that and raises a warning at 80 percent. The existing 4-slot GitProcessBudget stays as the concurrency bound.
  • Health area. fact_producer_health is shown in the Studio health area, not only in the prompt admin panel. It alarms when the last good generation is older than two sweep intervals, after three consecutive failures, or when the spawn budget is exceeded.

AGT-2954

The brief reports AGT-2954 in Human Review with 15 unintegrated commits. At 9e2526be5, the latest AGT-2954 salvage ref (fe9f04210, 5 October) is an ancestor of HEAD and of origin/develop. The 15 commits that are not ancestors come from the five early runs of 26 and 27 September. Ten of them are patch-identical to commits already in HEAD. The other five are alternative versions of the same first commit, each touching the same 18 files, and later runs superseded them. AGT-2954 delivered the versioned in-memory snapshot, the input signatures and GitConfigScope. It did not deliver persistence. The recommendation is to close it as integrated and fold nothing further from its salvage refs.

04 Migration plan

The slices are ordered so that each one is measurable on its own, and so that the first one stops later slices from regressing. Latency is server-side handler time, as measured by TaskOperationTimingFilter, at p95 over a 30-switch replay. That is the method of the task switch Dossier.
