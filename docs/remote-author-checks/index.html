Dossier

Remote author checks

A coding session on the crowded server can send a named build or test to KORI, wait without a model call, and receive feedback on the exact unfinished source it submitted.

Source card AGT-4428Evidence date 28 November 2026Phase Decision ready

Kurzfassung · Alternatives · Recommendation · Evidence · Open decisions · Implementation · Pilot operation

Kurzfassung

Eine Coding-Sitzung bleibt auf dem Server. Für einen Lösungsbuild kann sie ihren aktuellen Arbeitsstand an den Task-Server übergeben. KORI führt den Build bei freier Kapazität in einem frischen Arbeitscontainer aus. Die Sitzung blockiert bis zum Ergebnis, ohne das Modell zum Warten aufzurufen. Sie erhält den Namen der Prüfung, den Ausgang, die ersten Fehler und einen Verweis auf das vollständige Protokoll auf der Karte.

  • Arbeitsstand. Ein befristetes Git-Bundle enthält die ausgewählten Änderungen, auch vor dem ersten Commit. Der Host erhält Zugriff auf genau dieses Paket. Für die Pilotphase empfehle ich keinen Push zum Git-Anbieter.
  • Kapazität. Eine eigene Prüfart verwendet die vorhandene Vergabe mit Lease und Fence. Reviews und Gates haben Vorrang. Ein Pilotplatz auf KORI, eine offene Anfrage je Karte, höchstens zwei neue Ausführungen je Karte und Stunde und vier insgesamt pro Pilotstunde begrenzen die Belastung.
  • Auswahl. Der Agent wählt die benannte Prüfung. Kurze Builds eines Projekts und einzelne Testdateien bleiben standardmäßig lokal. Eine gemessene Laufzeit und die aktuelle Auslastung entscheiden später mit, ob sich die Verlagerung eines Lösungsbuilds oder einer Testsuite lohnt.
  • Vertrauen. Das Ergebnis dient der laufenden Sitzung. Das Review prüft die spätere Lieferung eigenständig. Ein Gate prüft weiterhin seinen eigenen Integrationsstand.
  • Messung. Die 12,0 Befehlsstunden der Review-Hosts zeigen, dass KORI solche Arbeit ausführt. Wie viel Serverlast sich einsparen lässt, ermitteln wir mit einem vergleichbaren lokalen Lauf und einem Lauf auf KORI. Für drei Lösungsbuilds sind zusammen 40,6 Minuten Laufzeit belegt. Für die gesamte Nacht lässt sich aus den vorhandenen Daten keine belastbare Aussage zur CPU-Ersparnis ableiten.

Ich empfehle, zunächst einen Lösungsbuild von genau einer Sitzung auf KORI nachzuweisen und die Funktion außerhalb dieses Piloten ausgeschaltet zu lassen. Wenn später ganze Coding-Versuche auf geeigneten Hosts in frischen Containern laufen, entfällt die feste Route Server–KORI. Der gleiche Prüfbefehl kann dann lokal im Versuch laufen oder eine schwere Prüfung an einen anderen geeigneten Host abgeben. Der Task-Server und der öffentliche Webserver behalten ihre Sonderrolle.

Recommendation

Use AGT-4381 as the front door and AGT-4382 for blocking wait behavior. Begin with one opted-in Agent Studio coding session on agent-runner-01, one named solution build, and one KORI check slot. Reuse the post-work claim and bounded execution mechanics and extract only the applicable project-plan and materialization helpers from review. Keep the check receipt advisory.

Snapshot and custody

The platform runner captures tracked working-tree contents, additions named by the session, deletions and executable bits in a temporary index. Include staged changes as they exist in the working tree at capture time. Exclude ignored outputs, credentials, machine-local files and undeclared untracked files. Reject a capture with unresolved conflicts, changing inputs, unsupported submodule or LFS changes, or an unavailable prerequisite. Return the captured tree digest and what was excluded so the author knows which state the check covered. Capture under the active coding lease, recheck it on registration and commit to the artifact store before making the check claimable. Keep the snapshot SHA separate from the delivery SHA. The coding index, branch and worktree stay intact.

Start with a 64 MiB compressed input ceiling, a 256 MiB materialized delta ceiling and a 10-minute pre-claim artifact-registration expiry. These are pilot bounds to verify. Use actual expanded bytes and object quotas during import. Verify repository ID, prerequisite, artifact hash, snapshot SHA and tree digest in an isolated import before any preparation. A host may use a provisioned read-only base already authorized for that project. Give the worker process only the materialized snapshot and the approved dependency sources. Assign the check capability to one existing KORI host registration through server-side policy. The host adapter authenticates to the Task Server outside the container. Existing review enrollment alone does not grant access to author snapshots. The host adapter redeems a short-lived read grant tied to the live check lease and project. Keep provider homes, task and repository credentials, writable shared caches, other attempts and the container socket outside the workload. A checkout of unfinished code can execute build hooks, so package cache sharing is limited to verified inputs and egress to approved dependency sources.

Drop the runner's temporary local Git ref after upload acknowledgement or on the next sweep after interruption. The bundle uses a private import namespace on the receiver. Delete the bundle and that namespace on terminal cleanup, with a one-hour hard ceiling from admission and a retrying sweeper for crash recovery. A trusted base cache can survive. If a remote-ref option is selected later, fence creation and deletion, purge by exact expected SHA after terminal receipt or expiry, and track orphan refs. Short-lived refs do not guarantee deletion of Git objects from the provider. Keep the card log under normal artifact retention with card access checks.

Admission and authority

The Task Server authenticates the submitting attempt and checks project policy. Allocate one child check ID with its own lease ID, executor identity, authority epoch and fence. The active parent fence remains necessary for renewing, reading inputs and committing a child receipt. Cancel on parent settlement, replacement or cancellation. On lost authority, stop the process tree and release admission. Refuse stale reports and never rerun automatically after an ambiguous loss in the pilot. A caller reconnects by check ID. A soft wait interruption does not start another run. After ambiguous lease loss, even an explicit retry of the same key waits for confirmed process cleanup or the workload's enforced hard deadline.

Admit a host only when its project grant, author-check capability, pinned toolchain, disk and host budget are current and it has a free slot. Keep one KORI slot, with an initial envelope of up to four cores and 8 GiB subject to the real host grant. Charge it against the physical KORI host across its role adapters. A queued eligible review or gate gets first claim on spare capacity. Include active and queued SSH-bridge gates via the gate coordinator while the bridge is in use. If those facts or the physical host budget are stale or unknown, remote check admission stays closed. An admitted check runs within its bounded grant. Further claims wait when protected work arrives. Keep a protected gate/review reserve so a newly arriving protected item can start; no preemption in the pilot.

Within checks, serve the oldest eligible request first. Reserve quota atomically with enqueue after deduplication. Allow one queued or running check per card, two new check IDs per card and four across the pilot project in a rolling hour, counting canceled and failed submissions once admitted. Cache reads and same-ID reconnects spend no execution quota. Rate-limit submissions and staged uploads separately; one staged upload per live attempt. If the queue has no grant within 90 seconds, return unavailable and explain the cause. Never launch a second copy as fallback. A forced remote call ends with the result or an explicit infrastructure status. In automatic mode, a human or agent can knowingly start local after remote unavailability.

Local and remote routing

The agent chooses the check by intent. Keep one-project incremental builds and single-file tests local by default, and allow an explicit mode override on eligible checks within policy. Class filters are useful for expensive setup or known slow classes. On the pilot, an explicit remote mode is the only trigger. Later, automatic routing applies to named solution builds and broad suites when destination admission is open and estimated local p50 is at least two minutes and greater than measured remote p90 including transfer, queue and setup by at least 30 seconds. Use recent samples for the same check, toolchain and load band. With insufficient samples, use local and collect timings. Never infer consent to upload arbitrary shell commands.

Trust and placement

The check receipt carries its advisory purpose, parent attempt, exact source and plan identity. It cannot change the card lane, grade, approve, integrate, satisfy review verification, populate review verification reuse, or alter a gate. Keep verification provenance and caches for those authorities separate. Review performs its own verification on the delivered subject under its established principal and evidence rules. Gate policy independently decides verification for the integration subject.

In the target architecture, any eligible host can pull any work kind against one host budget. The Task Server and public web server retain their installation roles and reserved capacity. The author-check API, plan, snapshot identity, advisory receipt, deduplication and model-free wait still apply. Local execution inside the coding container is the usual shortcut when it already has suitable capacity. Cross-host checks still help with a heavy suite, hardware unavailable on the current host, or contention. The fixed server-to-KORI route, manual reserve split and role-specific long-lived pilot infrastructure can retire as host-wide grants and fresh containers cover every attempt. Warm images and read-only dependency caches can outlive an attempt without keeping work containers alive.

Installation and measurement windows

  • Server, 28 November. The operator placement page reports 14 active coding slots on the 12-core server alongside the Task Server. CPU was at 100% in the observation, with median Linux load 143 over the preceding twelve hours. A solution build reported at one to two minutes in isolation reached 21 minutes under contention. Load includes runnable and uninterruptibly waiting tasks. It cannot be converted to cores or subtracted as a utilization percentage.
  • KORI, 28 November. The 24-core, 49 GB VM ran three review containers and an SSH-bridge gate container. The 3% CPU at 11:50 UTC is a snapshot. The 16% average spans eight days. Neither gives a spare-capacity time series for the review night. The operator's 27 November night tally reports 909 build, test and lint invocations in 105 review rounds over roughly eleven hours. Their cumulative command wall time is 12.0 hours, or 6.9 minutes per round and 1.09 concurrent command equivalents across the interval. CPU consumption and burst concurrency may be very different, since commands can overlap and use multiple cores.
  • Coding traces. AGT-4375's baseline from 27 November at 21:52 UTC through 28 November at 09:12 UTC includes 127 starts on 58 coding cards and 19,774 model responses. The strict eleven-hour cut ends at 08:52 UTC. Its 5,516 wait-only responses for the wider baseline are a measure of model activity. AGT-4383 links all 127 starts to Codex records and measures output and replayed context. Those published aggregates have no total build/test wall time, host CPU accounting, transferable-state sizes or remote queue trace.

Offload estimate

Coding-side timing extract. I linked the 127 starts to the retained Codex turns with AGT-4375 response signatures and AGT-4383's matching method. In the strict eleven-hour window, I counted 106 literal shell calls with one recognized, unfiltered dotnet build targeting an explicit solution. The same scan found 26 project builds and one project test. Three matched solution-build outputs from three cards had a single MSBuild Time Elapsed line, totaling 40.6 minutes, with the longest at 17.7 minutes. Those three are examples of local build wall time that could move if their snapshots and plans were eligible. I excluded shell polling gaps, compound cases with multiple matching commands, calls that hid commands in scripts or variables, and other tooling. The extract has no defensible test-time total and cannot establish how many invocations used an identical tree or how much CPU they used.

A planning scenario uses one eligible check on each of 58 coding cards as its offered volume. At 25% and 50% take-up, rounded to 15 and 29 distinct accepted checks, the 6.9-minute review-round proxy implies about 1.7 or 3.3 hours of KORI command wall time across eleven hours. A 21-minute crowded build moved to a six-to-seven-minute execution could save the author about 12.5 to 15 minutes after up to 90 seconds in queue, before transfer and cold setup. A one-to-two-minute local build with the same remote execution time would add delay. One slot can supply at most eleven wall-clock hours in that window and four new checks per hour imply a separate ceiling of 44 submissions. Gate/review priority and actual arrival bursts can reduce either scenario. Review command time is an imperfect proxy for a named build or test, and a card can request zero or several different checks.

For the server, every accepted remote run replaces a local command only if the author would otherwise run it locally. The directional effect is fewer runnable build and test processes during those checks, with less contention on the Task Server. At an assumed six local minutes per replaced check, the 15- and 29-check scenarios displace 1.5 and 2.9 hours of local command wall time. If their average instead matched the three timed solution builds at 13.5 minutes, the figures would be 3.4 and 6.5 hours. Three retained timings are too few to use as a fleet average. As a separate sensitivity example, if 29 checks each avoid six minutes locally while consuming two CPU cores on average, the displaced demand is 5.8 core-hours. Across eleven hours that is 0.53 cores, or 4.4% of the server's 12-core capacity on average. Both the six minutes and two cores are assumptions. Saturation may keep CPU near 100% while queueing improves. Moving a local process that mostly waits removes much less CPU demand. No numerical prediction for load 143, throughput, lead-time distribution or token savings from offload follows from these figures. Blocking wait saves polling calls even when execution stays local.

For transfer, sample a warm delta of 5 MiB and a log of 1 MiB per request. At 29 requests that is 174 MiB of logical payload, or about 348 MiB across both upload and download legs if the caller also downloads each full log. At 100 Mbit/s effective on each leg, moving the input twice has a serialization floor of 0.84 seconds per check. At the 64 MiB cap the floor is about 10.7 seconds. Those examples exclude hashing, materialization, dependency traffic and request latency. Time in queue ranges from immediate admission to the 90-second deadline for an accepted request. A KORI reserve can make the wait end as unavailable. The sources cannot establish the bundle distribution, cold-start latency, queue percentiles or per-card cost.

Verify one worker execution for duplicate calls, a live viewer-accessible card log, zero model calls during the block, no extra local build and no review/gate mutation. In the next pilot window, report counts of replaced local runs, deduplicated calls, refusals and timeouts. How should the unfinished source reach the execution host?

Implementation

The manifest enforces the order below. The first slice crosses the runner, Task Server and host boundaries to prove one complete build. Once it is delivered, command-plan changes and execution lifecycle hardening can run independently in their respective areas. Routing waits for both. The fleet migration remains in Dynamic placement.

  1. pilot. One coding session, one solution build, one KORI container, one card receipt.
  2. plan. Named suite support, exact class filters and compact diagnostics in the command and plan layer. Depends on pilot.
  3. authority. Durable limits, result reuse, revocation and admission across KORI adapters in the Task Server and host. Depends on pilot.
  4. routing. Measure the pilot and use those measurements for opt-in automatic routing. Depends on plan and authority.
