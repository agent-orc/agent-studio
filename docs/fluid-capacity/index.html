Concept Dossier · AGT-3019 · 6 October 2026

Fluid capacity

A host spends one live resource budget across coding, review, gates and post-processing. The operator sees whether work is flowing relative to that budget. A bounded orchestrator check explains and can adjust the allocation.

Problem

The operator's 04:00 UTC measurement on 6 October found 84% CPU idle and load15 of 3.4 on a 12-core, 62 GB runner host. Twenty-one review-passed Agent Studio cards waited for integration; ten Ready cards depended on them while eight coding slots were free. Two serial gates lasted 54 and 34 minutes with DOTNET_PROCESSOR_COUNT=2. At 34 to 54 minutes each, 21 sequential gates imply roughly 12 to 19 hours before overlap or reuse; the observed estimate was 12 to 15 hours. The processor hint is read at backend start, and restarting aborts the active gate.

Idle CPU is not evidence that more coding slots would help. Here the constraining lane is integration. The host needs a joint budget and a visible reason when waiting work cannot consume it.

Mechanism

Extend the existing RuntimeCapacitySettingsService host record with versioned role ceilings, operator bounds and the last applied allocation. Its current maxParallelism, targetLoadPercent and rampStrategy remain the host policy. The existing runtime-capacity-editor remains the operator editor for that host policy and extends to show desired and applied grants. The same service publishes one host allocation version. Agent-host reports measured occupancy and applies the allocation to local role controllers. Host identity follows the physical execution host: post-processing joins this budget only when it actually runs there; a backend on another machine has its own host row.

Allocation

Unit. Grant CPU in half-core units per physical host. The role grant is a quota ceiling, not an entitlement or a promised speedup. Active leases, gate slots and cgroup occupancy reserve grants before new admission. A 12-core host begins with a 2-core host and system reserve, so no more than 10 cores are granted across active roles. An operator profile may lower that amount. The existing slot ceiling still bounds coding; one slot does not equal one core. A gate slot additionally declares its requested cores and obtains one host grant before dispatch.

Inputs and cadence. HostTelemetrySampler continues at 30 seconds. Each 60 seconds, or on a queue, completion or band transition, the host controller evaluates a two-minute CPU average, load1 per core, memory available and swap activity, iowait, steal, cgroup throttled share, active grants, lane queue depth and oldest eligible wait. Load15 is a trend and display context; it cannot delay a fresh response. Missing or stale telemetry blocks raises, never revokes running grants. A single versioned allocation is calculated from the same host record with compare-and-swap; project settings cannot mint CPU.

Routine control. Keep the decided AIMD admission policy. If pressure is below target and eligible work waits, add at most one half-core grant per lane per minute, weighted by oldest wait and queue depth, after a two-minute raise cooldown. If pressure crosses target or throttling and gate duration rise together, multiply the future admission ceiling by 0.7 and hold raises for five minutes. Allocate minimum forward progress to coding and integration when both have eligible demand; promote the oldest eligible integration item before enlarging a fresh review batch. Never admit more half-core requests than the remaining host grant. Model actions can change weights and ceilings within this envelope, with a TTL and reason. No counter of repeated findings escalates authority on its own.

Safety. Pause new heavy admissions when available memory falls below the larger of 4 GB or 15% of RAM, or when swap-in/out shows sustained pressure. Iowait or steal above the existing finding thresholds prevents CPU-driven raises. Cgroup CPU, I/O and optional measured memory envelopes from the decided resource-governance policy are hard ceilings. DOTNET_PROCESSOR_COUNT and tool thread hints merely improve efficiency. Lowered grants affect only future dispatches; running gates and suites retain their original admission and finish. Agent-host may raise a unit's runtime quota to serve a new grant, then reduce it after older work drains, subject to the operator-owned profile ceiling. Every apply acknowledgement names host, version, role and fence.

Measured idle case. Within two telemetry windows, the host reads roughly 16% actual CPU against an 80% target, confirms 21 integration waits and emits under-used: serial integration. It gives the next eligible gate a larger processor hint from live headroom, initially 4 and up to 6 cores if subsequent samples remain healthy. The running 2-core gate is not restarted. If W70's parallel candidate lane exists, newly prepared candidates may claim additional gate grants within minutes; until then the global serial merge lock remains the structural limit, and the UI says so. A higher hint is measured against gate wall time and process-tree CPU before keeping it; no proportional speedup is assumed.

Saturated case. If three reviews and a promotion gate saturate the host, the next review admission is refused and post-processing yields its next slot. Fresh coding claims pause above the target, while any existing coding, reviews and the promotion gate continue under their admitted envelopes. The promotion gate keeps its grant and fenced publication priority. The controller reports which active role consumes the grant, which new work was held, and whether cgroup throttling rather than CPU alone explains the pressure. It resumes admissions after pressure falls; it does not cancel a review to make room.

Load band

Every host has exactly one visible band: under-used when the two-minute CPU average is at least 20 percentage points below its target for three samples and eligible or blocked work is waiting over two minutes; over-loaded when CPU is over target plus 10 points for three samples, or memory/swap or cgroup pressure is acute; otherwise in band. Idle with no demand reads in band · no work waiting. An under-used finding joins telemetry to lane queues and admission verdicts, so it can distinguish dependency-gated, serial integration, provider quota, CPU hold and paused. The finding records first seen, last seen and the reason; it clears after work flows or demand disappears. Where several reasons apply, show the oldest blocked queue first and all reason counts on expansion.

Promote HostCapacityPolicy verdicts from DEBUG to structured, rate-limited operator events with host, lane, reason, target, actual and affected wait count. Show the latest verdict in host detail and its history. The status bar gives fleet state and count; Execution Hosts gives one row per host; the Ops view shows the explanation, role grants, held admissions, step reports and history. Fleet state is over-loaded if any host is over-loaded, otherwise under-used if any is under-used, otherwise in band. Fleet actual and target are core-weighted values, accompanied by counts so an average cannot hide a hot host.

Capacity check

Register capacity-check as a host-scoped StepKind.Orchestrator run every 30 minutes and once on a band change or a queue that grows for five minutes while the host idles. Coalesce events for ten minutes. Allow at most 48 scheduled and 12 event calls per host per UTC day, one call at a time, and a hard 180,000 input / 90,000 output token daily contingent. A skipped occurrence still writes a step outcome and a deterministic short info. The 60-call cap is a spending limit, not an escalation counter. Host allocation and load-band computation keep running every minute without a model.

The bounded evidence pack is a versioned, at-most 3,000-input-token summary of two-minute and 30-minute telemetry aggregates, role occupancy and throttling, lane depth and oldest wait, recent admission verdict counts, last ten allocation changes and their outcomes, plus source timestamps and omissions. It contains no raw logs, CLI sessions, unbounded paths or automatic log excerpts. This follows the AGT-3010 redo card's artefact boundary; the capacity step needs narrower aggregates than its general 32 KiB pack. If one project's queue is the subject, include only that project's identifiers and settings; a host-wide check uses host totals.

The model and thinking level resolve through OrchestratorSettingsResolver and PipelineStepConfigResolver: existing environment override first, then a project step override, project orchestrator setting, workspace default and platform default. The caller layers the environment value over the resolvers and records the winning source. A host-wide report uses the owning workspace default, or platform default for a shared host with no unique owner. A project override governs only project-scoped actions, never the whole host. Recommended default is gpt-5.6-sol at high, subject to the repository model-routing floor and live availability. The operator can see the resolved value and source at #/workspace/settings/orchestrator and the project pipeline step setting.

The Watcher supplies the precedent for interval scheduling, a token/call contingent and RecordUsage; capacity remains a separate pipeline orchestrator step because Watcher model settings come from restart-only appsettings and its case queue is a different subject.

The response schema has report (maximum 600 characters), assessment, evidence references and up to three typed actions. Allowed actions are set-role-share with bounded grant and TTL, reorder-integration for eligible queued items without changing in-flight train order, pause-intake with a maximum 15-minute TTL, and open-defect-card through the Task API with an idempotent fingerprint. Every action passes host safety, memory, admission, profile, project ordering and fence validation; a rejected action is recorded with its reason. The model chooses when a safe action is useful. Guard rails report facts and enforce floors; they do not rewrite the model's assessment or escalate after a count of warnings.

Every scheduled, event, failed and budget-skipped occurrence uses the AGT-3015 pipeline step record, keyed by host, trigger and execution id: step kind, model and thinking level, input and output tokens, calculated cost or unknown price, bounded input summary and evidence digest, report text, proposed and applied actions, rejected reasons, status, timestamps and correlation/fence. The host history is a projection of those records, not a second cost ledger. No-call skips have zero usage; attempted calls with missing usage retain unknown fields rather than becoming zero. A deterministic fallback says why no model ran and preserves the last safe allocation; it never retries past the contingent or issues model actions on an unparseable response.

Cost estimate, 6 October 2026. At the recommended default's published standard API rates of $4 per million input and $20 per million output tokens, 48 scheduled calls at 3,000 input and 1,500 output tokens cost $2.02 per host-day: 48 × ($0.012 + $0.030). At the 60-call daily cap, the same per-call usage costs $2.52 per host-day. Output includes reasoning tokens. These are uncached API-equivalent estimates; the actual step record uses the selected model's price and measured tokens, which may differ by CLI billing and overrides.

Alternatives

A · Tune restart-only values

Raise the gate's processor count and review slots in env files. It may shorten the next gate, but a restart aborts the current one, and fixed values become wrong as queues and contention change.

B · Live host allocation

Extend the central host capacity record, admit from measured headroom and adopt each role's next dispatch live. Keep cgroups as the hard boundary and add a bounded model decision step. This is recommended.

C · Model controls every admission

Ask an LLM for each claim or gate. It adds cost and outage dependence to a safety-critical fast path, and cannot supply the cgroup enforcement the existing decision requires.

Recommendation

Adopt B in bounded slices

Start with the gate's processor count chosen from live headroom at each new dispatch and an under-used finding with its blocker. Keep the one-gate lock in slice 1: raising its count cannot bypass today's global serial integration lock, and a safe cross-process counting gate is a separate, testable change. Follow with one versioned host allocator, live role adoption, the full load-band view and a periodic orchestrator step. The first slice helps the next gate without a backend restart and makes the current bottleneck visible even before W70 exists.
