# Integration lane measurement, AGT-3070

The Task Server appends typed `integration-lane-events.jsonl` records to each delivery folder. The 24-hour lane projection and the 7-day or 30-day gate projection share `GET /api/gate-economics`. The endpoint reads per-delivery gate receipt headers and durable batch execution facts for gate time, wait and rung; it reads typed lane events for arrival, lock, gate and publication times. Per-delivery queue wait is machine gate wait plus merge-lock wait. The final successful attempt of a published batch has its `durationMs` divided by its recorded gate-run member count to express minutes per merge. A missing historical field is unknown.

Both integration paths write lane events. A coordinator delivery uses the coordinator's sequence. Its events run enqueued, dequeued, merge-lock acquired, gate requested, gate token waiting or acquired, gate finished, publication lock acquired, and published or ejected. The runner tags its events with that sequence through an async delivery scope. Before enqueueing a background push it persists `publication-queued` with the exact approved SHA and captures the sequence in `IntegrationPushRequest.DeliverySequence`. The worker passes the sequence explicitly; the restart backstop recovers it only from the matching approved SHA. An unrelated later delivery never supplies it. Gate-environment replays allocate a new sequence, retain review-subject completion time, and scope dequeue, merge, gate and terminal events without changing retry decisions. An event outside any delivery, such as a local merge, is not recorded and never borrows an earlier sequence. A batch-deferred delivery uses its durable batch enqueue sequence. Its events run enqueued at settlement, dequeued when its batch starts, ejected `Conflict` on a replay conflict, and gate requested and finished for every batch or isolation run it is part of. They continue with publication lock (the ref-mutation lease), then published, or requeued when the batch is abandoned, or ejected `Superseded`. A batch member handed to the per-task fallback records the fallback gate, then `handed-off`. The coordinator continues it under its own sequence. Arrivals count each delivery once, by project, card and review completion time, so a hand-off is not a second arrival. Only the emergency fallback, which never entered the batch queue, records no batch events; its coordinator events still cover enqueue to publication.

Counting rules: a receipt is placed in the window by its own `recordedAtUtc` token, else by the gate's `originalCompletedAtUtc`. Only a legacy receipt with neither token falls back to its file time, so a clone or checkout cannot pull dated receipts into the window. Gated merges count green per-card receipts plus the members of a batch run that was published. Gate minutes per merge use only those integrated receipts and the final successful attempt of a published batch, amortized across its released members. Exact and disjoint reuse each divide integrated members on that rung by all gated merges; a red attempt cannot depress the rate. Gate runs (green, red, cancelled) and full-suite share still count each batch attempt, so red-isolation reruns add gate outcomes and costs but never merges. A receipt whose gate never ran (`failureKind=MissingSource`) records `gateRung=none`; it counts as unknown for rung, full-suite share and minutes and is excluded from gate outcome counts. New batch facts store the actual gate-run member keys, excluding ejected or deferred manifest members. Legacy facts use only durable member releases matching that run; unavailable membership leaves amortized minutes unknown. Out-of-window receipt headers are rejected before scanning the legacy selection audit. The 30-second cache stores unredacted evidence for its visible project set and applies holding-project authorization separately for every response. A scoped account sees only its member projects, and the all-projects row aggregates exactly those projects.
