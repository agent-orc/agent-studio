AGT-2994 · Concept Dossier · Integration lane

Integration lane throughput

Only the publication of a merge must be serial per project. Preparing the next deliveries, gating them and running agent rounds can run in parallel, bounded by cores. A speculative merge train with ordered publication doubles one busy project's modelled merge rate on the 12-core host. Gating the train tip while the queue is deep roughly quadruples it.

Problem

On the night of 28 to 29 September 2026 a delivery reported at 16:35 was integrated at 03:51, a lag of 11 hours 16 minutes. The lane spent 42 minutes per merge in the Windows gate. A Quality Studio merge waited 55 minutes behind an Agent Studio gate. An agent round for AGT-2373 waited 44 minutes for a coding slot. Every one of these waits sits in front of one serial section. That section is wider than the card assumes: it spans all projects in the process, not one project.

The serial section today is fetch → sync → merge → gate → rollback, held under one process-wide semaphore. Only the push happens outside it, on a separate queue. The next delivery cannot even be fetched until the previous gate has finished. Because every merge moves develop, the reuse rule that would skip the suite for an unchanged tip can succeed for at most the first delivery in a queue. Every later delivery runs the full suite by construction.

Alternatives

Each alternative keeps the existing merge invariants: merge first, then mechanical merge, then guarded rebase; ambiguous attribution fails closed as AgentRoundRequired; a red gate never reaches develop. Throughput figures use the model in Throughput model.

A · Split the global locks only

Replace the process-wide merge semaphore with one lock per project, and the machine gate lock with a small core-bounded slot pool. Each project remains a serial fetch, merge and gate loop.

Removes the cross-project wait, such as the 55-minute Quality Studio case. One busy project still lands at most 60/45 per hour (1.20 with a 10 percent red rate). The 11-hour backlog shape is unchanged. Small change. Necessary, but not sufficient.

B · Prepare-ahead without speculation

A: plus fetching, verifying and warming the next N deliveries while the current gate runs. The gate still runs on the real tip after the previous merge.

Saves only the preparation minutes, about 3 of 45 (assumption). Gates stay serial per project because each depends on the landed tip. Reuse still fails for every queued delivery because develop moves between review and merge.

C · Speculative merge train with ordered publication

A and B, plus candidates chained on the predicted tip: C1 = tip + D1, C2 = C1 + D2. Up to k candidates gate in parallel. Publication is strictly in chain order and fast-forwards develop to the exact gated candidate. A red Ci is abandoned, and every later candidate in the chain is rebuilt without Di.

Modelled 2.34 merges per hour for one busy project with two slots. A candidate's own green gate stays valid at publication, so no delivery is re-gated because its predecessor landed. Costs a durable train manifest and cancelled-gate waste after a red candidate.

D · Batch Gate for a closed wave

The archived AGT-W36 concept: close a manifest of all eligible deliveries, replay them onto one temporary branch, run one suite, publish the green tip, and bisect on red.

Highest throughput per suite at high load, but it adds a whole coordinator with its own manifest lifecycle, waits for a wave to close, and bisects a large batch on every red. At low load it adds latency compared with C.

E · Make the gate shorter

Stop the full OrchestratorApi.Tests project from running for every backend change. Today DotNetWorkPackagePlanner.PlanSlice returns the whole project whenever referenced production code changes.

This is the largest single lever per merge, but it changes verification policy, needs its own evidence of test-impact accuracy, and is independent of lane shape. It is out of scope here and noted as a follow-up in D7.

Recommendation

Recommended default

Adopt C, the speculative merge train, on top of A's lock split. While a project's queue is deep, allow C to gate only the train tip. This backlog mode borrows D's mechanism without D's separate coordinator. Publication is the only serial step per project. Gate slots come from one core-bounded token pool shared by all projects. Agent rounds leave the train immediately and re-enter at the tail after review.

Lane rules

  1. Intake. A passed review writes its settlement record, as today, and appends the delivery to a durable per-project queue. The review report request returns without waiting for the merge. Order is review-subject completion time, then a durable enqueue sequence. This is today's QueuedDeliveryComparer, made persistent.
  2. Prepare-ahead. A per-project worker prepares the next N = 4 queued deliveries. It fetches the delivery ref, verifies the fenced SHA, computes changed paths, and materialises a disposable worktree with dependency caches. Preparation holds no gate token and no publication lock. At most two preparations run per host at once.
  3. Candidate chain. Candidate Ci is built as Ci-1 + Di. C0 is the current develop tip. The existing merge order is reused unchanged. Candidates are disposable refs with ordered parents and a delivery attribution map. A conflict or ambiguous attribution ejects Di before any gate starts.
  4. Gate slots. Each candidate gates as an exact subject on a token from one host-wide pool. A token is 3 cores, and the test runner's thread count is capped to match. The pool size is max(1, floor((cores − reserved) / 3)). On the 12-core host with 6 coding and 6 review slots, reserved is 6 and the pool is 2 tokens. Review-run suites and integration gates draw from the same pool, as they already share the machine lock today. A project with no running gate is served first. No project holds more than 2 tokens.
  5. Ordered publication. Under the project ref-mutation lease (AGT-W18 D7), the publisher checks three things: develop still equals the candidate's predecessor, the candidate has a green receipt, and the candidate is next in chain order. It then fast-forwards and pushes. This step is serial per project and takes seconds to minutes. A candidate whose own gate passed is published without another gate. Its base equals the landed predecessor by construction, so "moved since the review" no longer triggers a second suite.
  6. Order rule. Merges land in chain order, which is intake order. A later delivery never lands before an earlier eligible one, because its candidate contains the earlier delivery. A delivery ejected for a conflict, an agent round or a red gate forfeits its position. It re-enters at the tail when its next review passes. There is no expedite path in the first slice.
  7. Agent rounds. AgentRoundRequired and Conflict eject the delivery at candidate construction. Later candidates are chained without it, and the recovery round waits for a coding slot outside the lane. The existing budget of one automatic round is kept.
  8. Backlog mode. When at least 4 prepared deliveries are waiting, a project gates only every third candidate. A green tip publishes the chain up to it, so each delivery in the batch lands as an ancestor of a gated commit. On red, the batch is bisected on free tokens, and the members that are not implicated keep their position.

Composition with adopted decisions. The train is the scheduling layer of the AGT-W18 remote integration target. Each candidate is an IntegrationSubject whose expected base is its predecessor, and each publication uses the single D7 publisher. Build the scheduler as a portable component. Before cutover, it drives the current MergeIntoDevelopRunner path; after cutover, it drives the remote integration executor. Under W18 D14 the lock split is bounded transitional work; the train itself is target work.

Throughput model

The model counts merges per hour for one busy project. The host is the 12-core host with 6 coding and 6 review slots, and the gate token pool derived above (2 tokens). The only observed input is the 42-minute gate. Every other parameter is an assumption stated here, and card 1 replaces each one with a measurement.

Failure modes

Speculation only ever touches disposable candidate refs, so "rollback of a queued merge" means discarding refs and cancelling gates, never resetting develop. Today a red gate hard-resets the shared integration worktree to the captured tip. The train removes that reset from the normal path.

Open decisions

Each decision names a recommended working option. Promoted cards implement the recommendation unless a recorded operator decision selects another option. No operator decision is recorded yet.

D1 · Lane shape

  • A: split the locks only
  • B: prepare-ahead without speculation
  • C: speculative train with ordered publication
  • D: Batch Gate coordinator

Recommended: C, including A's lock split. It is the only option that makes both gate parallelism and gate reuse work within one project. Its backlog mode keeps D's gain without a second coordinator.

D2 · Gate slot bound

  • Fixed slot count per project
  • Core-bounded token pool shared by all projects and by review suites
  • Unbounded, relying on the load throttle

Recommended: the token pool. 3 cores per token, with the test runner capped to match. Pool size max(1, floor((cores − reserved)/3)), which is 2 on the 12-core host. At most 2 tokens per project, and a project with no running gate is served first. Fixed per-project slots oversubscribe with several projects; unbounded gates repeat the load-22 night.

D3 · Prepare-ahead depth

  • N = 1
  • N = 4
  • The whole queue

Recommended: N = 4, at most two preparations per host at once. That is enough to feed two tokens and a batch of three, while bounding disk and fetch work. Preparing the whole queue wastes work on deliveries that later get superseded.

D4 · Landing order and re-entry

  • FIFO by review completion; an ejected delivery re-enters at the tail
  • An ejected delivery keeps a reserved position
  • Priority classes or operator expedite

Recommended: FIFO with tail re-entry. A reserved position would force the whole chain behind it to be rebuilt when the delivery returns, which recreates the blocking the card wants removed. Expedite stays out of the first slice.

D5 · Backlog mode

  • Off: gate every candidate
  • Automatic: gate every third candidate when 4 or more prepared deliveries wait
  • Always batch

Recommended: automatic, off below the threshold. The develop tip is always a gated object, and each intermediate commit is an ancestor of a green tip. It is the only modelled option that is stable at the assumed wave demand. The Ops view shows when it is active.

D6 · Placement

  • Rework the current Studio-side coordinator only
  • Build the scheduler only inside the future remote integration executor
  • A portable scheduler used by both

Recommended: the portable scheduler. It delivers throughput before the AGT-W18 cutover without adding workstation-only logic, which D14 forbids. The lock split (card 2) is the bounded transitional part.

D7 · Shorter gate

  • Keep the full test project for backend changes
  • Open a separate test-impact concept

Recommended: a separate concept after card 1's data. It changes verification policy and needs its own accuracy evidence. This Dossier does not depend on it.

Implementation

Five independently reviewable slices, one workbench.json implementationTasks entry each. Card 1 comes first, because it replaces the model's assumptions with measurements. Cards 2 to 5 depend on it and on each other in number order. Decision content above remains unchanged when slices append their status here.

  1. Measure the integration lane and show it in the Ops view. Lane events and projections for delivery-to-integration lag per project, publication-lock wait, gate token wait, gate duration, queue depth and ejections. The acceptance bar is a before baseline covering at least one full wave.
  2. Per-project lanes and a core-bounded gate token pool. Remove the process-wide merge semaphore for remote deliveries. Replace the single machine gate slot with a token pool shared with review suites. Move the lane out of the review report request into a durable hosted worker.
  3. Prepare-ahead and a speculative train with ordered publication. Prepare N = 4 deliveries, chain the candidates, gate on up to 2 tokens, publish in order, and accept the train receipt without a second gate.
  4. Eject and re-enter. Conflicts, AgentRoundRequired and red candidates leave the train and dependents are rebuilt. Re-entry happens at the tail after review. The round-budget documentation drift is fixed.
  5. Backlog mode. Gate the train tip at depth 4 or more, with bisect isolation.
