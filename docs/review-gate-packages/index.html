Concept dossier · AGT-3400

Review and gate on packages

Most batches are pairs because the planner closes as soon as it can see two cards, and at the current arrival rate it rarely sees more. This Dossier decides the package for each check. The gate package becomes the post-merge window that D1 already decided. The review package becomes the cards of one Dossier wave, but only for the review aspects that gain from shared context. Build, tests and requirement fit stay per card.

00 Summary

Why so few batches form. The look-ahead planner sets its target size to the number of cards it can see right now, waiting or due inside the look-ahead window. With two cards waiting and nothing due, the target is two, so it closes the pair at once as "target size reached". The 15-minute deadline never comes into play. A single card on an idle gate host skips the wait and goes straight to the per-card fallback. At about 2.6 gated merges per day, a second card arrives within 15 minutes about 5 % of the time. No deadline setting turns that into batches of four without hours of waiting. Deliveries that do not batch take the per-card fallback: a full suite on the card's SHA, then a second full suite in the integration lane, because the integration gate does not reuse the fallback verdict.

Package for the gate. The gate package is the post-merge window (T3) that D1 already decided. Cards merge after T1 and T2, and the window tests what merged together. In this design batch size no longer costs lead time, so small packages stop being a problem. The pre-merge batch gate stays as the fallback mode, with settings changes only.

Package for review. The review splits into two tiers. A card check runs per card and per round: build, affected tests (T1), deterministic checks and the requirement-fit aspect. A package review runs once per Dossier wave: code quality, documentation impact, tests and evidence, grade, plus a new cross-card consistency check against the Dossier. Every member keeps its own verdict and lane state, and a passing member never waits for a failing one. Cards without a Dossier stay on today's per-card review.

Where the hours are. On the measured figures, D1 saves about 31 to 42 runner-hours a week and 33 to 66 minutes of lead time per card. The 3.4 review hours per card come mostly from Remote Review running its aspects one after another. Running them in parallel saves more wall time than packaging, at no token cost. Packaging saves tokens and catches cross-card inconsistencies, which no step checks today.

First step. Activate D1 for Agent Studio. Replay T1 on recent review plans. Install the post-merge timers on the runner host, which needs a host-specific drop-in because the unit templates name a user that does not exist there. Size the window with the batch settings, then switch testing.mode to post-merge. This takes the full suite out of every card's path. Most of the code exists, the fallback to pre-merge is automatic, and rollback is one setting.

02 Why few batches form

A card enters the batch queue when its Remote Review passes while it is in Auto Review. Its ready time is the review completion (V1ReviewPlaneEndpoints.cs:1446-1450). Every 30 seconds the pilot groups waiting cards by project, repository, branch, gate profile and platform version. It builds a snapshot and asks the pure planner BatchGateLookAheadPlanner.Plan for one of four decisions: idle, wait, close or per-task. Each decision is appended to plans/<project>.jsonl.

Why the count fell to none

Three explanations fit "1, 5, 3, 3, 1 per day, then none". The census script separates them on the Studio host.

  • Fewer arrivals. 18 gated merges in the last 7 days is below the 13 to 29 October rate (C2).
  • A new instance folder. The folder name hashes the content root and the task repository path (BatchGateStorageRoot.cs:11-15). A moved installation therefore writes to a fresh, empty batch-gates folder. Counting only the old folder shows "none" even if batches continued. The census must run on every instance folder that has a batch-gates directory.
  • No reviews completing. Since 31 October, the review runner on agent-runner-01 logged 11,193 "could not reach the task server" lines. Without completed reviews nothing enters the queue.

Why pairs do not pay at the measured green rate

The planner's own cost model is ExpectedRunsPerCard = (1 + (1 − P(all green)) · (⌈log2 n⌉ + 1)) / n. With the historical per-card green rate after review of 57.9 % (docs/operations/gates/d10-measurement.md) and independent outcomes, it gives:

RouteFull suites per card, green path and isolationPlus fallback of ejected members
Per-card fallback1 on the card SHA, plus 1 in the integration lane when green: 1 + 0.579 = 1.58none
Batch of 21.16+ 0.42 → about 1.58
Batch of 31.14+ 0.42 → about 1.56
Batch of 40.92+ 0.42 → about 1.34

A pair costs about as many full suites per card as the per-card route and adds a wait. Only batches of four save a fifth of the suite runs. The observed 4.3 full-suite runs per merge is far above either model. The rest comes from attempts that went red and did not merge in the window, infrastructure retries, full-suite reviews of non-deferred cards (C7) and promotion runs. Slice S2 attributes the 77 runs.

03 The right package

A good package saves something that each member would otherwise pay separately, without making any member wait longer than that saving is worth. Gate and review save different things. The gate saves suite runs, a cost that depends on the size of the tree, not on what the cards mean. The review saves reading: instructions, the Dossier, its decisions and the shared code around the change.

Two review tiers

Formation. A package holds the members of one Dossier whose card check passed within 60 minutes of the first. It is capped at four members and at the Remote Review material budget of 200 files and 12,000 lines (RemoteReviewWorkspace.cs:21-22). It never waits for cards still being coded, and a lone member is reviewed as a package of one. The subject is a stacked candidate: members applied in dependency order on the current integration tip, with each member's commits kept separate so every hunk has an owner.

04 Failed packages

Gate before merge (today, and the fallback mode)

A red candidate is classified first. An infrastructure red gets one retry on the same SHA. A red base pauses the batch as integration-branch-red without halving. A flaky red follows quarantine. A deterministic red starts ordered halving: ⌈log2 n⌉ probes per cycle, within a total budget of min(6, 2·⌈log2 n⌉), then a green survivor run publishes (BatchGateIsolation.cs:29-85; BatchGatePilotService.cs:1247-1289, 1552-1630). Ejected or unresolved members take the per-card fallback (:1358-1359).

SizeFull suites, one offender, worst caseWall time at 33 to 43 min per suite
21 candidate + 1 probe + 1 survivor + 1 fallback for the offender = 41.7 to 2.2 h before the survivor merges
31 + 2 + 1 + 1 = 52.2 to 2.9 h (the fallback runs in parallel only if a slot is free)
41 + 2 + 1 + 1 = 52.2 to 2.9 h

Every member waits for the isolation, so a red member costs its partners hours.

Gate after merge (D1 T3 window)

A red window costs no member any waiting. Merges continue outside the failing area (D2 A). Attribution runs in three cheap steps. First, it intersects each suspect merge's paths with the failing tests' project map. Second, it reruns only the failing tests at the merge points; a failed-class rerun took 7.3 s against 93 min for the suite (AGT-W77 P3). Third, it bisects only when more than one suspect remains. Then one repair card per failure fingerprint reverts the merge when that is clean, and fixes forward otherwise. The cost is seconds to minutes of targeted test runs and one repair card. It is not hours of full suites.

Review package

A review package does not fail as a whole. Each member gets its own verdict and its own engine decision through the existing TransitionDecisionPolicy, within its own round budget (AGT-W65 D18).

  • A passing member proceeds to T2 and merge at once. It never waits for a failing member.
  • A failing member returns to 2-ready with its findings, as today. In the next round it runs its card check, then a scoped package review of its own delta. If another package of the same Dossier is forming within 60 minutes, it joins that one instead.
  • A cross-card finding goes to the later member in dependency order. It names the earlier member as related but does not block it.
  • An ejection invalidates the package verdict of members that share files with the ejected one, which then get a scoped re-review (section 03).

Cost compared with today. A failing member costs one more round, as it does now. Its second round is cheaper than today's, because the package-tier aspects rerun on the member's delta, not on the whole card. Passing members pay nothing more.

07 Alternatives

Gate package

G-A · Tune the pre-merge batch

Use overlap: adjacent, the threshold planner with closeSize: 4 and a 60-minute deadline, and fix C1 to C6 in code. At 2.6 arrivals a day, batches of four cost hours of waiting. Pairs save no suite runs at a 57.9 % green rate (section 02). Develop stays green by construction.

G-B · Post-merge window as the gate package (recommended)

Activate D1 T-B. Cards merge after T1 and T2, and the T3 window, sized by maximumSize and lookAheadMinutes, tests what landed together. Waiting no longer depends on package size. The pre-merge batch stays as the automatic fallback.

G-C · Dossier wave as gate package

Gate a wave's members together before merge. Members finish hours apart, and test failures do not cluster by Dossier. This takes the worst of both: long waits, plus isolation when one member is red.

Review package

R-A · Per card and round (today)

Every aspect, every round, every card, run serially. No package risk. The context is paid per card, and nobody checks cross-card consistency.

R-B · Card check per card, package review per Dossier wave (recommended)

Build, T1, deterministic checks and requirement fit stay per card. Code quality, documentation impact, tests and evidence, grade and cross-card consistency run once per wave package. Every member keeps its own verdict. Cards without a Dossier stay on R-A.

R-C · Whole review per package

All aspects, requirement fit included, run on the package. This saves the most tokens, but a member's own criteria get blurred and the miss risk is highest.

R-D · Batch candidate or time window as review subject

Review the combined batch candidate or what arrived in a time window. Formation is circular for the candidate, there is no shared context in a window, and the makeup is random.

Review execution

X-A · Serial aspects (today)

Simple and predictable on load. Wall time is the sum of all aspect calls.

X-B · Parallel aspects within one attempt, cap 4 (recommended)

The local path already does this. Wall time becomes the longest aspect. Tool commands keep running first, and checkpoints are kept per aspect.

08 Recommendation

Recommended default

G-B, R-B and X-B, in the order S1, S2, S3, S4, S5. The gate works on packages by testing after merge: the T3 window is the package. The review works on packages for the aspects that read shared context, with one package per Dossier wave, while per-card facts stay per card. Run aspects in parallel within every review. Keep the pre-merge batch gate as the fallback mode with overlap: adjacent, and change its planner code only if a project stays pre-merge for 30 days after S1.

The most important reason. The largest measured cost is the full suite in every card's path: 77 runs a week, two per non-batched card. D1 removes it. That is decided, built and reversible by one setting. Bigger pre-merge batches cannot reach the same saving at today's arrival rate.

First step

S1: activate D1 for Agent Studio.

  1. Replay T1 on the last 20 Agent Studio review plans.
  2. Install the window and nightly post-merge timers on agent-runner-01 with a drop-in for the host's user and paths, and run them in dry-run for one day.
  3. Set maximumSize: 6 and lookAheadMinutes: 30. In post-merge mode these values size the window (PostMergeRunEndpoints.cs:31-37).
  4. Switch testing.mode to post-merge.

Why this step has the least risk: the automatic fallback returns the project to pre-merge after two hours of red develop or an escalated repair (PostMergeModeService.cs:9-39), and rollback is one setting. It gives the largest gain: 31 to 42 runner-hours a week and 33 to 66 minutes of lead time per card.
