Orchestrator improvement scout

Scope

The operator asked on 6 October for an orchestrator step that keeps reporting what is going poorly and proposes improvements. This scout is a named periodic StepKind.Orchestrator profile. AGT-3018 supplies DecisionGroundsV1, action vocabulary, authority checks and the artefact boundary. AGT-3019 supplies capacity measurements and its own admission decisions. AGT-3015 supplies one costed occurrence record. The scout consumes their outputs after delivery; it neither allocates host resources nor decides card transitions.

The Watcher already owns detector cases, bounded evidence packs, model analysis, contingent and proposals. Grow its analysis stage to include the scout. Its five-minute sweep checks whether a daily or weekly scout occurrence is due and coalesces duplicate triggers. There is one scheduler and one proposal family. The weekly loop-discovery run shows the review pattern: candidate proposals are written for human judgment. The scout does not register a second loop inventory or add a ledger.

Step contract

A due occurrence is keyed by workspace, profile, window end and policy version. Grounds contain the window, scope, counts with denominators, trends, freshness, coverage, detector fingerprints, up to 20 evidence references, prior proposal outcomes, candidate Dossier homes and omissions. The model receives at most 8,000 metered input tokens and never receives raw logs, CLI sessions, arbitrary filesystem paths or an unbounded timeline. Drill-down links authorize a separate read of the source artefact. If a required denominator or source ref is missing, the finding states the gap and confidence drops; it does not label the period clean.

The response has at most five findings and five proposals per occurrence. Each finding names signal id, measured value/window, confidence, competing explanations and cited fact ids. Each proposal is a typed prepare(dossier-revision) or ask(operator-question) under AGT-3018. A validator checks source refs, Dossier key, current revision, decision state and idempotency before publication. A stale revision or invalid output produces a failed receipt and a bounded retry on the next due pass. No failed model call is counted as zero cost; unavailable usage stays unknown.

Model and thinking level resolve through OrchestratorSettingsResolver and PipelineStepConfigResolver: existing environment override first, then project step override, project orchestrator setting, owning workspace default and platform default for project-scoped findings; host-wide findings use the owning workspace or platform default, never an arbitrary project. Persist the winning source, prompt/policy versions, aggregate digest, model response, action validation result, Dossier revision ids, token categories, price basis and outcome links in the AGT-3015 occurrence. The current run content and evidence live there; Dossiers link to it instead of copying prompts. No new cost ledger is created.

Improvement Dossiers

Every improvement Dossier has a stable project-scoped Dossier key, ordinary workbench.json identity and promotion path, plus kind: improvement and origin: orchestrator-scout in the proposed descriptor extension. The source of truth remains the repository Dossier. Catalogue, board links and search may filter by kind and show a quiet “Improvement” badge. Existing product Dossiers retain their own pattern; a scout revision on one is attributed by origin at revision level, not by changing the whole Dossier's kind.

Begin with four themes: delivery integrity (fencing, stale completion, integration correctness), review quality (requirement fit, evidence, repeat rounds), capacity and economics (wait, utilization, quota, spend), and credentials and operations (effective credential source, false alarms, repeated intervention). A finding goes to the Dossier that owns its proposed fix first, such as AGT-3019's capacity Dossier or AGT-3021/3022's delivery integrity Dossier. An improvement theme Dossier is created only when no active owner fits. This is a target of roughly four to six active themes per project, not a hard quota. Split when two subtopics have different decision owners or implementation paths and at least three independent findings each; close after 90 days without an open proposal, with all decisions settled and card outcomes linked. Closed Dossiers stay searchable and may reopen on material new evidence.

Each update is an append-only dated section with revisionId, scoutRunId, actor “Orchestrator scout”, source digest, finding/proposal ids, evidence links, old/new section and decision ids, and a one-line change summary. The API owns atomic writes and version checks. It never silently replaces decided prose or a recorded option. A contradiction to a decided recommendation becomes a new open decision that links the earlier receipt. A changed recommendation in an undecided section is explicitly summarized and versioned. A duplicate run id and finding fingerprint returns the existing revision.

Update visibility

Each operator has a cursor per Dossier over monotonically increasing revision ids. A revision is unread for that operator when its id exceeds the cursor. The API projects a section-level diff: counts and labels for new findings, new or reopened decisions, changed recommendation, and new card draft. It does not compute text diffs in the list. Opening a successfully loaded Dossier or its revision summary advances only that operator's cursor through the displayed revision; a separate “Mark seen” action does the same. Merely rendering a list, an error page or another operator's visit does not clear the marker. Later revisions remain unread. Cursor state is application-owned, not written into workbench.json.

The central and project Dossier lists show a filtered count and one-line summaries, and Nordstern links into the same updated subset. A linked Dossier on the board shows a quiet “Updated” badge on its Dossier chip; the Dossier header shows the revision count and change categories. The board badge describes the linked document's unread revision, not a historical card outcome. Counts equal visible children under filters. History and settled outcomes are quiet, following the design hard rules.

Cadence and economics

The Watcher remains on its five-minute sweep. The scout gets one scheduled daily pass per workspace over 14 days and one weekly pass over 90 days. A material detector case can bring the daily pass forward once, with a six-hour coalescing window; this consumes the day's call rather than adding another. The weekly pass groups themes and checks outcomes. There is a maximum of 10 scout model calls, 110,000 total tokens and five published proposals per workspace-week, inside the Watcher's existing 100-call, one-million-token and 40-proposal weekly contingent. A daily run may use at most 8,000 input and 3,000 output tokens. Exhaustion writes a no-call receipt and leaves detector cases for the next window. Capacity step budgets stay separate.

Planning estimate as of 7 October 2026. The recommended initial model is gpt-5.6-sol at high reasoning, subject to the AGT-3018 correctness floor and availability. Official OpenAI Docs list standard uncached API rates of $4 per million input and $20 per million output tokens. Eight expected calls per week at 6,000 input and 2,000 output tokens cost $0.51 per workspace-week: 8 × (6,000 × $4 + 2,000 × $20) / 1,000,000 = $0.512. At the 10-call maximum with 8,000 input and 3,000 output tokens, the envelope is $0.92 per workspace-week. Reasoning output is included in metered output. This is an API-equivalent estimate, not a CLI invoice; configured model, caching, provider billing and actual usage can change it. The AGT-3015 receipt shows measured cost or unknown price, never an assumed zero.

Proposal lifecycle

A proposal records proposalId, issue fingerprint, problem, evidence artefact links, time/cost/quality effect estimate with basis, confidence, home Dossier key and section, suggested action, source run, creation time, state and decision history. Suggested actions are: open a decision in the Dossier by default; draft a bounded implementation card in that Dossier; propose a setting or rule change for operator review; or ask a question. The effect estimate distinguishes measured baseline from forecast. Unknown benefit stays unknown.

Before publication, compare the normalized issue fingerprint and target scope with open cards, active Watcher proposals and earlier Dossier proposals. If one owner exists, append new evidence there and link it; do not raise a second proposal. A rejection stores its evidence digest and rationale. It remains suppressed until a later run shows material new evidence, such as a new failure cohort, changed severity or a different effective source, then a new proposal links to the rejection. Deferral records a review date and stays visible in history without repeated daily alerts.

The scout may observe, prepare a bounded Dossier revision, open an undecided question, and draft a card inside the Dossier through an allowlisted A1 application API. It may not move or cancel running work, change a setting, waive a gate, rewrite decided content, or promote a card. Those are operator decisions or stronger AGT-3018 classes. “Accept open card” is one operator action that invokes the existing promote-concept path and Task API, creates one preparation-lane card, and stores the Dossier key, proposal id and scout run id as provenance. Accepting a question records the operator's choice in the ordinary Dossier decision path. Every mutation is idempotent and auditable.

Alternatives

A · Watcher analysis profile

One detector and analysis stack, one contingent and proposal store, with a named periodic step receipt. Recommended because the Watcher already correlates cases and drafts proposals.

B · Sibling periodic service

A separate scheduler and analyzer would duplicate Watcher cases, proposal deduplication and budget enforcement. Reject.

C · Capacity-step extension

Cheap to trigger, but AGT-3019 owns host allocation and has a 30-minute resource cadence. Its narrow pack cannot carry review and delivery patterns. Reject.

For publication, compare themed improvement Dossiers with a Dossier per finding and one global perpetual Dossier. Themed homes keep decisions and cards coherent; one-per-finding floods the list, while one global Dossier blurs ownership. Prefer the existing product Dossier when it already owns the fix.

Recommendation

Implement the scout as a named, budgeted Watcher analysis profile that publishes append-only, attributed proposals into keyed Dossiers. Make unread revisions visible per operator and require the existing Dossier decision and promotion path for cards and rule changes.

Start with a shadow delivery-integrity finding and a complete AGT-3015 occurrence. Then add the Dossier write API, proposal lifecycle, visibility and remaining aggregate catalogue. Four-week shadow review should compare precision, duplicate rate, missed calibration incidents, operator attention and priced cost before enabling automatic Dossier publication by default. This rollout does not grant the scout authority over live runs.
