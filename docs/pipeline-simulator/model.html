The first three loops feed each other. A long wait at the gate lets more merges land, so a conflict becomes more likely. Every sync round adds another review and another wait. A card that waits past the threshold is reviewed again. The simulator has to show this compounding, because it is what turns a 60-minute card into a 7-round card.

The engine does not carry its own copy of these rules. Batch formation, batch start, isolation and red-test triage are already pure policies in orchestration-decisions/ (BatchFormationPolicy, BatchGateStartPolicy, BisectVerdictPolicy, RedTestTriagePolicy since RT-2). DispatchPlanPolicy (AGT-3993) exists there with no caller yet. The engine calls them with simulated facts. Two rules are pure but sit elsewhere: the window close rule in runner/PostMergeRunPlan.cs and the stale-verdict check in the review plane. SIM-2 moves each into the library before the engine uses it. This keeps the AGENTS.md rule that transition rules live only in the decision library, and it means a simulated strategy is the real strategy. A preset that has no policy yet, such as "fast as intended" with quarantine scope, is marked in the strategy picker as a model of a design, not of shipped code.

A parameter set is dated and versioned. A what-if run names the set it started from, and the owner's changes are a named layer on top, for example "two more review slots". A nightly refresh creates a new set and never changes an old one, so a saved comparison stays reproducible.

06 Check against reality

Two replays check two different things.

  • Trace replay takes the recorded day as it was: arrivals, durations of every run, which merge conflicted. Only queueing and the rules are simulated. If its waits and publication times differ from the recording, a rule or a slot count is wrong in the model.
  • Model replay keeps the recorded arrivals and slot counts but draws durations, conflicts and defects from the parameter set, over 200 seeded runs. If its distribution misses the recording, a parameter is wrong.

Each replay reports, per hour and for the day: cards per hour, median and p95 wait at the gate, lead time, rounds per card, the number of sync rounds, tokens and USD split into first pass and rework, and quota points used. The first replay days are 17 November (the wave), 18 November (the rework day of the 40 % finding) and 23 November (fast as built). A replay fits when throughput is within 15 %, median gate wait within 25 % and USD within 20 % of the recording. The p95 is shown but not gated, because one stuck card moves it. The nightly fit is shown next to the parameter set. A set that does not fit is marked as such and is never silently used.

08 Cost

The simulation uses no model tokens. The engine is plain code over recorded facts and the decision library's pure policies. A replay reads records. Dispatcher strategies are model-free in the decision path (docs/dispatcher-personas/). The wave model in this Dossier ran 4 strategies with 200 seeded runs each, a total of 45,600 card journeys, in about 2.5 seconds of processor time in Python on one core. An engine in .NET will be at least as fast, so a what-if run can be repeated after every slider move.

Three things would use tokens, and none is proposed as part of the simulator:

  • A narrated explanation of a run written by a model ("why did the gate fill at 14:00"). The headline statement and the bottleneck reading are computed, not written by a model. A narration can be added later as a persona action on the persona budget (decision PS-D10).
  • Replaying a persona that has a model step, such as the line guardian's bounded classification call or the Packer's recut. A replay uses that step's recorded output and never calls the model again.
  • Building the simulator. At the starting values each implementation card costs about one point of the weekly Claude window (a first run of 9 to 19 USD plus reviews and rounds, at about 18 USD a point).
